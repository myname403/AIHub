### 已确认的真实缺陷 / 违规
1. `ChatAppService`（application 层）引用 `com.aihub.ai.infra.ai.agent.PlanningAgent.NAME`
   → 违反 ArchUnit 规则「application 不得依赖 infra」；只因 `static final String` 常量被编译期内联，

   不满足传递性，策略 >2 条时可能抛 `Comparison method violates its general contract`。
3. `QuotaService.currentUsed` 按 appId 累加（`upsertConsume` 传 appId）但查询未带 appId 条件 → 跨应用混算。
4. `ChatAppService.reportUsage` 的 tokenIn/tokenOut/modelCode 全传 null → M1 DoD「每次调用落 Token 与耗时」未达成，
   用量看板无数据可用。

### M2 消息与引用落库（含修掉一个更严重的会话隔离 bug）

  即流式下**也会**写回记忆 —— 所以流式结束后再落引用是安全的。

### M5 配额多维度
- 新增跨服务共享常量 `QuotaDimensions`（request/token/doc/task）——放契约模块，
  避免两端各写一份字面量导致扣减口径漂移。
- `QuotaService.consume(QuotaConsumeRequest)`：**两阶段**——先全维度试算，全部通过才累加；
  任一维度超限则整体拒绝且**不产生任何扣减**（否则会留下「request 扣了、token 没扣」的脏用量）。
  单维度 `checkAndConsume` 改为委托它，逻辑只留一份。
- AI 侧接入：对话按 `request` 扣（前置）+ `token` 扣（事后补扣，因为用量只有拿到响应才知道）；
  Agent 任务按 `task` 扣；文档入库按 `doc` 扣。全部**失败降级放行**——能力不因统计故障而不可用。
- V5 迁移补齐 4 个维度的演示策略 + 用量表 `(tenant_id, dimension, period_key)` 索引。

### M5 TraceId 全链路
- `TraceContext`（common，ThreadLocal + **同步写 SLF4J MDC**）：`ensure()` 惰性生成、
  `wrap(Runnable)` 跨线程传递并在结束后**还原**（不污染线程池里复用的线程）。
- 三个服务的日志 pattern 加 `%X{traceId:--}`，业务代码零侵入。
- 链路完整性：
  - 网关新增 `TraceIdGlobalFilter`（`HIGHEST_PRECEDENCE`，早于鉴权过滤器，
    这样 401 响应也能带上 traceId）；
  - `R.build()` 统一出口自动填 `traceId` 字段（含异常响应），无需各工厂方法手工传；
  - `FeignTenantConfig` 透传 `X-Trace-Id`，AI → 平台调用串成一条链路；
  - 跨线程显式传递：SSE 线程池、NDJSON `StreamingResponseBody`、WebSocket 任务、入库存档线程池。
- `TraceContextTest`（12 用例）。**注意**：`wrap` 必须在父线程调用（它此刻捕获链路 ID），
  测试写在 worker 内部会导致捕获到 worker 自己的值——这个坑踩过一次。

### Micrometer 指标
- `infra/metrics/AiMetrics implements domain/spi/MetricsRecorder`。
- **又踩了一次 ArchUnit**：`KnowledgeAppService`（application）直接 import `infra.metrics.AiMetrics`
  → `applicationShouldNotDependOnInfraOrWeb` 失败。解法：在 domain 建 `MetricsRecorder` 端口，

  （这是第二次因埋点破坏分层，端口反转是标准解。）

  `ingest.latency` / `quota.rejected`；**标签只放低基数枚举**，绝不放 tenantId/userId/conversationId。

### API Key 认证（网关校验 + 本地缓存）
- `ApiKeyCodec`（common）：`ak_` + 48 位 hex（24 字节 SecureRandom）；存储哈希用
  **HMAC-SHA256 而非 bcrypt** —— 鉴权在每请求热路径，bcrypt 的刻意慢会拖垮吞吐；
  而 Key 本身是 192+ bit 随机值，不存在弱口令爆破风险。
- 平台侧 `ApiKeyService`：签发（数量上限）/ 校验（status + expireAt 双重判断，
  失败统一返回 empty 避免探测）/ 吊销（**带 tenantId 校验**，否则可用别人的 keyId 越权吊销）。
- 网关侧 `ApiKeyVerifier`（WebClient 调 `/internal/apikey/verify`，超时 2s，**fail-closed**）
  + `ApiKeyCache`（Caffeine AsyncCache，TTL 60s，**失败结果不缓存**，缓存键用 hashCode 避免明文驻留堆）。
- `AuthGlobalFilter` 重写为双通道：`X-API-Key` 优先于 `Authorization: Bearer`；
  API Key 通道**只注入租户、不注入 userId**（它代表系统调用，无用户身份）。

### 本轮踩到的两个命名/框架坑（值得记）
1. **Jackson 会把 `isDefault()` 映射成 JSON 属性 `default`**（boolean getter 的 `is` 前缀规则）。
   我用 `record ModelInfo(..., boolean isDefault, ...)` 时前端拿到的是 `default` 字段，对不上。
   统一改名为 `defaultModel`，请求 DTO 也改成 `Boolean defaultModel`（Lombok 生成 `getDefaultModel()`）。
2. **MyBatis-Plus `update(entity, wrapper)` 默认忽略 null 字段**（`FieldStrategy.NOT_NULL`）。
   编辑模型时前端传 `apiKey: null` 表示「保持原值」，正是靠这个默认行为才没把密钥抹掉。
   这是隐式契约，已在 `DbModelAdminRepository.updateModel` 加注释 + `DbModelAdminRepositoryTest`
   用「断言 patch 里 apiKeyEnc 为 null」把它钉住。
