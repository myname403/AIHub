## 项目差距审查（文档承诺 vs 代码落地）
对 README + docs/01~07 的里程碑 DoD 与 M0~M5 任务清单，逐条比对实际 Java / DDL / 前端代码，输出差距清单。

**完成度估算**：M0 9/10、M1 5/7、M2 5/8、M3 2/6（最差）、M4 5/9、M5 2/6（最差）

### 已确认的真实缺陷 / 违规
1. `ChatAppService`（application 层）引用 `com.aihub.ai.infra.ai.agent.PlanningAgent.NAME`
   → 违反 ArchUnit 规则「application 不得依赖 infra」；只因 `static final String` 常量被编译期内联，
   字节码无类引用才逃过检测。修复：在 domain 建 `AgentNames.PLANNING` 常量。
2. `QuotaService.checkAndConsume` 的比较器 `(a,b) -> "day".equals(a.getPeriod()) ? -1 : 1`
   不满足传递性，策略 >2 条时可能抛 `Comparison method violates its general contract`。
3. `QuotaService.currentUsed` 按 appId 累加（`upsertConsume` 传 appId）但查询未带 appId 条件 → 跨应用混算。
4. `ChatAppService.reportUsage` 的 tokenIn/tokenOut/modelCode 全传 null → M1 DoD「每次调用落 Token 与耗时」未达成，
   用量看板无数据可用。

### 文档有、代码无
- M1：无审计 Advisor、无 `StreamAroundAdvisor`（文档 R9 风险明确要求双路径）；Advisor 链只有 MessageChatMemoryAdvisor。
- M2：无 `ai_message_reference` 表 → 引用不落库，刷新页面引用丢失；`ai_ingest_task` 表存在但入库是同步串行的
  （无异步 / 进度 / 重试）；无跨租户自动化测试用例（只有 ArchUnit 4 条，0 业务单测）。
- M3：`spring-ai-starter-mcp-client` 依赖已引入但**零集成代码**（全仓无 ToolCallback / McpSyncClient 引用）；
  `ai_tool` / `ai_mcp_server` 表无对应实现；工具只有 TimeTools 一个，无调用审计 `ai_tool_call_log`。
- M4：`ai_agent_task` / `ai_agent_step` 表无写入 → 无 checkpoint / 恢复；「停止」只是前端 `uni.request.abort()`，
  服务端循环不感知（M4 DoD「后续步骤真正取消」未达成）；三重预算只有 maxSubTasks，缺 maxToken / maxTimeout。
- M5：配额只有 request 维度（缺 token / document / task）；无 Micrometer 指标、无 TraceId 全链路、无 API Key、
  无用量查询接口与看板页面。

### M5 配额多维度
- 新增跨服务共享常量 `QuotaDimensions`（request/token/doc/task）——放契约模块，
  避免两端各写一份字面量导致扣减口径漂移。
- `QuotaService.consume(QuotaConsumeRequest)`：**两阶段**——先全维度试算，全部通过才累加；
  任一维度超限则整体拒绝且**不产生任何扣减**（否则会留下「request 扣了、token 没扣」的脏用量）。
  单维度 `checkAndConsume` 改为委托它，逻辑只留一份。

  Agent 任务按 `task` 扣；文档入库按 `doc` 扣。全部**失败降级放行**——能力不因统计故障而不可用。
- V5 迁移补齐 4 个维度的演示策略 + 用量表 `(tenant_id, dimension, period_key)` 索引。

### M5 TraceId 全链路
- `TraceContext`（common，ThreadLocal + **同步写 SLF4J MDC**）：`ensure()` 惰性生成、
  `wrap(Runnable)` 跨线程传递并在结束后**还原**（不污染线程池里复用的线程）。
- 三个服务的日志 pattern 加 `%X{traceId:--}`，业务代码零侵入。
- 链路完整性：
  - 网关新增 `TraceIdGlobalFilter`（`HIGHEST_PRECEDENCE`，早于鉴权过滤器，
    这样 401 响应也能带上 traceId）；
  - `R.build()` 统一出口自动填 `traceId` 字段（含异常响应），无需各工厂方法手工传；
  - `FeignTenantConfig` 透传 `X-Trace-Id`，AI → 平台调用串成一条链路；
  - 跨线程显式传递：SSE 线程池、NDJSON `StreamingResponseBody`、WebSocket 任务、入库存档线程池。
- `TraceContextTest`（12 用例）。**注意**：`wrap` 必须在父线程调用（它此刻捕获链路 ID），
  测试写在 worker 内部会导致捕获到 worker 自己的值——这个坑踩过一次。

### API Key 认证（网关校验 + 本地缓存）
- `ApiKeyCodec`（common）：`ak_` + 48 位 hex（24 字节 SecureRandom）；存储哈希用
  **HMAC-SHA256 而非 bcrypt** —— 鉴权在每请求热路径，bcrypt 的刻意慢会拖垮吞吐；
  而 Key 本身是 192+ bit 随机值，不存在弱口令爆破风险。
- 平台侧 `ApiKeyService`：签发（数量上限）/ 校验（status + expireAt 双重判断，
  失败统一返回 empty 避免探测）/ 吊销（**带 tenantId 校验**，否则可用别人的 keyId 越权吊销）。
- 网关侧 `ApiKeyVerifier`（WebClient 调 `/internal/apikey/verify`，超时 2s，**fail-closed**）
  + `ApiKeyCache`（Caffeine AsyncCache，TTL 60s，**失败结果不缓存**，缓存键用 hashCode 避免明文驻留堆）。
- `AuthGlobalFilter` 重写为双通道：`X-API-Key` 优先于 `Authorization: Bearer`；
  API Key 通道**只注入租户、不注入 userId**（它代表系统调用，无用户身份）。

### 本轮踩到的两个命名/框架坑（值得记）
1. **Jackson 会把 `isDefault()` 映射成 JSON 属性 `default`**（boolean getter 的 `is` 前缀规则）。
   我用 `record ModelInfo(..., boolean isDefault, ...)` 时前端拿到的是 `default` 字段，对不上。
   统一改名为 `defaultModel`，请求 DTO 也改成 `Boolean defaultModel`（Lombok 生成 `getDefaultModel()`）。
2. **MyBatis-Plus `update(entity, wrapper)` 默认忽略 null 字段**（`FieldStrategy.NOT_NULL`）。
   编辑模型时前端传 `apiKey: null` 表示「保持原值」，正是靠这个默认行为才没把密钥抹掉。
   这是隐式契约，已在 `DbModelAdminRepository.updateModel` 加注释 + `DbModelAdminRepositoryTest`
   用「断言 patch 里 apiKeyEnc 为 null」把它钉住。

## 第四轮：MCP Server 三模块（ADR-3）

### 交付
按 `docs/04-技术选型与版本矩阵.md` 的 ADR-3，把 AIHub 自身能力开放为 MCP Server：

| 模块 | 作用 |
| --- | --- |
| `aihub-mcp-service` | 工具的纯业务实现（`@Tool`），**协议无关**、可单测 |
| `aihub-mcp-sse` | SSE 传输（在线），`Protocol=SSE` + webmvc starter |
| `aihub-mcp-stdio` | stdio 传输（本地），无 web，打成 `aihub-mcp-stdio.jar` |

对外 4 个工具：`aihub_list_applications` / `aihub_list_knowledge_bases` /
`aihub_search_knowledge(kbId,query,topK)` / `aihub_ask(message,appId,scene)`。

### 关键决策
- **`aihub-mcp-service` 刻意不依赖 `aihub-common`**：后者带 `spring-boot-starter-web`，
  会把 servlet 容器拖进 stdio 这个 CLI 进程。代价是自写 `ApiEnvelope<T>` 镜像服务端 `R<T>`
  （反正是公开 HTTP 契约，像 SDK 一样自带客户端类型反而更稳）。
- **`@Tool` 注解在 `spring-ai-model`**，不在任何 mcp 包里（`unzip -l` + `javap` 实证），
  所以工具模块不需要引传输层依赖。

### 实证确认的框架契约（全部来自 javap + spring-configuration-metadata.json，不是猜的）
- 配置前缀统一 `spring.ai.mcp.server`；`protocol` 默认 `sse`（`SSE`/`STREAMABLE`/`STATELESS`）
- **`spring.ai.mcp.server.stdio: true` 就是 stdio 传输的开关**
  （`McpServerStdioDisabledCondition.StdioDisabledCondition` 判定 stdio 缺失或 false 时走 web 那套装配）
- 工具来源：`ToolCallbackConverterAutoConfiguration` 收集容器里的 `ToolCallbackProvider`，
  合并后调 `.distinct()` 去重 → 我们那个 Bean 就是「对外暴露能力」的开关
- `type` 默认 `sync`（`syncTools` bean 的 `@ConditionalOnProperty` matchIfMissing=true）
- `request-timeout` 默认仅 **20s**，小于我们调上游的 60s → 两处都设 70s（MCP > HTTP）

### 端到端验证（都真跑过，不是只编译）
- **stdio**：手工灌 JSON-RPC（`initialize` → `notifications/initialized` → `tools/list`），
  stdout 只有 2 行纯 JSON，返回正好 4 个工具；日志落 `%TEMP%/aihub-mcp-stdio/`。
- **SSE**：`GET /sse` 返回 `event:endpoint` + sessionId，POST `initialize` / `tools/list` 均 200，
  流里回来 4 个工具；启动日志 `Registered tools: 4`。

### 本轮踩的坑（4 个都已修，写进 README 3.8）
1. **stdio 下 stdout 就是 JSON-RPC 通道**。Spring Boot banner + 默认 ConsoleAppender 都往
   stdout 写，插一条就让客户端解析失败（"一连上就崩"且报错无指向性）。
   → `spring.main.banner-mode: off` + 专用 `logback-spring.xml` 把 console 改到 **System.err**
   （`target=System.err`）并落文件。
2. **stdio 必须显式开开关** `spring.ai.mcp.server.stdio: true`，否则安静地起 Tomcat 等 HTTP。
3. **关掉用不到的注解扫描器** `spring.ai.mcp.server.annotation-scanner.enabled: false`。
   不关的话 starter 里第三方 `mcp-annotations-0.8.0.jar`
   （`org.springaicommunity.mcp.provider.tool.SyncMcpToolProvider`）会扫 `@McpTool`，
   扫不到就 WARN `No tool methods found ...`，纯噪音还容易被误读成"工具没注册上"。
   关掉后启动 WARN 从 4 条降到 1 条（剩下那条是我们自己"未配 API Key"的合理提示）。
4. **手工测 stdio 必须保持 stdin 打开并留间隔**：一次性灌完立刻 EOF，进程会在处理第二个请求前

### 本轮踩的坑（5 个，全部修复）
1. **record 不能有实例字段**：`record Session(...)` 里写 `volatile long lastUsedAt` 直接编译失败
   （"字段声明必须为静态"），改静态内部类
2. **finally 里读 try/catch 赋值的局部变量**：javac 以确定性赋值分析拒绝（catch 块自身可能
   先抛异常、变量尚未赋值就进 finally）。收尾逻辑挪到 try-catch 之后
3. **Chrome 对相对 --user-data-dir 视为无效**：回落默认配置目录并拒绝开调试端口
   （"DevTools remote debugging requires a non-default data directory"），
   `ChromeLauncher` 必须 `toAbsolutePath()`
4. **页面标注"幽灵引用"（E2E 揪出来的真 bug）**：元素隐藏后旧 data-testid 残留 →
   同一 ref 挂两个元素 → click 的 querySelector 命中**隐藏旧元素** → rect 全零 →
   鼠标点 (0,0)；遮挡校验的 `t.contains(w)`（祖先包含也算命中）把空点误判为 hit →
   **静默无效果**。三处修复：标注脚本开头清掉自己上轮的 eN 引用（只清自己的命名空间，
   不碰页面自带 data-testid）；click/type 定位取"第一个可见匹配"；遮挡校验删掉 t.contains(w)
5. **URL 白名单前缀混淆**：`startsWith("https://example.com")` 会放行
   `https://example.com.evil.io`。修复：前缀相等，或紧随字符是 / ? # : 才算命中
   （测试用例补了裸域与同源带端口应放行）
