# 08 · 系统设计与场景题

> 设计题没有标准答案，评分看的是：**你能不能把需求拆清楚、把瓶颈点出来、把权衡讲明白**。
> 所有设计题都按这个四步答：**需求与量级 → 接口与数据模型 → 核心流程 → 瓶颈与权衡**。

## 一、开放题：设计一个多租户 AI 能力中台

**（这题基本是照着你的项目问，务必能画能讲）**

### 1. 需求澄清（先问，不要上来就画）

- 规模：多少租户？QPS？单租户最大上下文？
- 隔离等级：共享表还是独立库？有无合规要求（数据不出境）？
- 模型：用哪家？要不要支持多供应商、主备？
- SLA：首 token 延迟？可用性目标？

### 2. 核心架构（四层）

```
接入层：网关（鉴权 / 限流 / 路由 / 防伪造头 / TraceId 起点）
   ↓
平台层：租户 / 配额 / 审计 / API Key / 用量统计
   ↓
AI 层（内聚）：模型网关 / RAG / 工具 / Agent / 记忆
   ↓
基础设施：MySQL（两库）/ Redis Stack（向量）/ Nacos / 对象存储
```

**关键决策"AI 能力内聚"的理由**：见 [02](02-架构设计题.md) Q1
（规避分布式事务、流式跨服务传递、Agent 跨服务编排三难题）。

### 3. 三个必须回答的难点

| 难点 | 方案 |
| --- | --- |
| **多租户隔离** | 四道防线（见 [05](05-数据层与多租户.md)）；框架级兜底用拦截器 |
| **计量与限流** | 四维配额 + `ON DUPLICATE KEY UPDATE` 原子累加；并发改进走 Redis Lua |
| **成本失控** | 三重预算（Agent）+ 记忆窗口 + 元素/分片上限 + 指标告警 |

### 4. 演进

- 一期：单机 + 本地文件 + 内存取消标志（**你现在的状态**）；
- 二期：对象存储（MinIO）+ Redis 取消标志 + 消息队列削峰；
- 三期：向量库独立（Milvus/PGVector）+ 检索服务拆分 + 多区域部署。

## 二、配额系统（你做得最深的一块，会被连环追问）

### 2.1 现状实现

- 四个维度：`request` / `token` / `doc` / `task`；
- 周期：`day` 等（策略排序时 `day` 优先）；
- 存储：`ai_quota_usage` + 唯一键 `uk_usage(tenant_id, app_id, dimension, period_key)`；
- 扣减：`INSERT ... ON DUPLICATE KEY UPDATE used_value = used_value + #{amount}`；
- 流程：AI 侧拦截 → Feign 调平台 `/internal/quota/check` 与 `/consume`。

### 2.2 ★ 连环追问与答法

**Q：并发下会不会超扣？**
> 会。两阶段试算 + 非事务，并发请求可能同时通过试算。

**Q：为什么设计成两阶段？**
> 因为要"**要么全扣，要么全不扣**"——一次调用可能同时消耗 token 和 request 两个维度。
> 如果逐个扣，可能出现"扣了 token 但 request 超限"的部分扣减，导致脏数据。
> 所以先对所有维度试算，全过才统一扣减。

**Q：怎么改进成强一致？**（四种方案，讲两种就够）

| 方案 | 做法 | 权衡 |
| --- | --- | --- |
| **Redis + Lua**（推荐） | 把"读已用 → 判断 → 累加"写进一个 Lua 脚本，Redis 单线程执行保证原子 | 快；但要处理 Redis 与 DB 的**持久化同步**（异步落库，Redis 挂了可能丢少量计数） |
| **预扣 + 确认/释放** | 调用前预扣，成功确认，失败/超时释放（TCC 思路） | 一致性强；但要处理**悬挂**（释放先到、确认后到）和**空回滚** |
| 悲观锁 `FOR UPDATE` | 锁住配额行 | 简单；但**热点行竞争**（同租户同维度串行），性能差 |
| **分段配额** | 把额度切成 N 段（如 10 个 slot），随机/哈希选一段扣 | 降低热点；但某段耗尽会**误拒**（需要合并判断） |

**我倾向的方案**：Redis Lua 原子扣减 + 异步落库 + 定期对账（DB 为准修正 Redis）。
理由：配额允许极小误差，但**不能成为性能瓶颈**。

**Q：配额校验失败要不要 fail-open？**
> **分场景**：
> - **鉴权（API Key）必须 fail-closed**——平台服务不可用就拒绝，宁可不可用也不能放行未授权的调用；
> - **配额可以 fail-open**——平台服务抖动时放行并记日志，业务可用性优先。
>
> 我项目里就是这么区分的：网关 API Key 校验异常 → 拒绝；AI 侧配额调用异常 → catch 放行。

## 三、幂等设计

**场景**：网络重试、用户双击、MQ 重复消费。

**方案**（按推荐度）：
1. **唯一键去重**：用业务唯一键（如 `uk(tenant_id, doc_id)`）做唯一索引，
   重复插入直接失败——**最可靠，我项目里 `ai_ingest_task` 的 `uk(tenant+doc)` 就是这个作用**；
2. **Token 机制**：先申请 token → 携带 token 提交 → 服务端用 Redis `SETNX` 保证只用一次；
3. **状态机**：`status` 字段 + 乐观锁 `UPDATE ... WHERE status = 1`（影响行数判断）；
4. **分布式锁**：慎用（性能差、有死锁风险），只在必要时。

**追问**：*"重试一定安全吗？"* → 只有**幂等操作**才能安全重试。
写操作要通过唯一键或幂等号保证。我的入库重试就是靠唯一键 + 状态判断实现的。

## 四、异步任务系统（入库）

**需求**：上传文档 → 解析 → 分片 → 向量化 → 落库，耗时长，不能阻塞请求。

**我的实现**：
- 提交即落 `ai_document` + `ai_ingest_task`（返回 taskId），
  **原始文件先落盘**（本地或 MinIO）；
- 提交到**独立线程池**（4 线程 daemon，与请求线程隔离）；
- 进度四阶段：10（解析）/ 30（分片）/ 50（落库）/ 70（向量化）；
- 失败重试：**最多 2 次**，指数退避 `min(200 << (attempt-1), 2000)` ms；
- 成功后才删除暂存文件（失败时文件还在 → **可重试**）；
- 前端轮询 `GET /kb/ingest/{taskId}`，也提供 `/retry`。

**★ "为什么原始文件必须落持久化存储"**（很好的设计点）：
> 早期方案是内存暂存，服务重启后文件丢失，任务无法重试。
> 落盘后重启仍能重试。多实例时本地盘不共享，所以又抽象出 `IngestFileStore` SPI，
> 实现 MinIO 版本，`aihub.storage.type` 一个开关切换，**业务代码零改动**。

**追问**：*"多实例下重试打到别的节点怎么办？"*
→ 就是上面这个 MinIO 方案。另外任务表要带 `tenant_id`，重试接口要校验租户。

**追问**：*"为什么不用 MQ？"*
→ 一期不想引入中间件。**但 MQ 才是正确解**：削峰、持久化、重试、广播，
现在是自己用线程池 + 重试 + 进度表"手搓"了一个简化版任务队列。

## 五、限流方案对比

| 维度 | 单机限流 | 分布式限流 |
| --- | --- | --- |
| 实现 | Guava `RateLimiter`（令牌桶）、Sentinel 本地 | Redis + Lua（令牌桶/滑动窗口）、Sentinel 集群流控、网关层限流 |
| 优点 | 零依赖、性能好 | **全局准确** |
| 缺点 | 实例数变化时不准（总量 = 单机阈值 × N） | 依赖 Redis（可用性 + 网络开销） |

**选型建议**：
- **网关层限流**（我项目用 Sentinel `gw-flow`）——挡在外面，最划算；
- 需要精确全局配额时：Redis Lua；
- 允许近似时：单机限流更简单（**总量按实例数折算**）。

**追问**：*"被限流的请求怎么处理？"*
→ 快速失败（返回 429 + `Retry-After`）、排队等待（漏桶，适合秒杀）、
预热（Warm Up，冷系统慢慢放量）、降级（返回兜底内容）。

## 六、一致性：outbox 与分布式事务

**★ 你有真实素材（虽然是反面素材）**：

`ai_event_outbox` 表**建了但没有代码写它**。
`PlatformClient.reportUsage` 的注释说"AI 侧失败时落 outbox 异步补偿"，
但实际失败只 `log.warn` 吞掉了。

**如果被问到"跨服务一致性怎么做"，标准答案**：

1. **避免分布式事务**（最优）：把需要事务的能力内聚到一个服务（我这 AI 内聚就是这个思路）；
2. **Outbox + MQ**（最终一致，推荐）：
   本地事务里同时写业务表和 outbox 表 → 独立投递线程读 outbox 发 MQ → 成功后标记。
   **保证"业务发生则消息一定发出"**；
3. **Saga**：每个步骤配补偿动作，失败时反向补偿（适合长事务）；
4. **TCC**：Try/Confirm/Cancel 三阶段（强一致，但侵入大）；
5. **最大努力通知 + 对账**（兜底）：失败重试 + 定时对账修复差异。

**追问**：*"为什么不用 2PC/XA？"*
→ 性能差（锁持有到全局提交）、协调者单点、且很多中间件根本不支持。**生产基本不用。**

## 七、可观测体系（三支柱）

| 支柱 | 我的实现 |
| --- | --- |
| **指标 Metrics** | Micrometer → `/actuator/prometheus` → Prometheus + Grafana 仪表板（10 面板）。**标签只放低基数枚举** |
| **日志 Logging** | MDC 注入 TraceId，格式 `[traceId] [thread] logger - msg`；跨线程用 `TraceContext.wrap` |
| **链路 Tracing** | 自研轻量 TraceId：网关生成 → Feign 透传 → MDC → 响应头 + 响应体 `traceId`。**没上 SkyWalking/Zipkin**（一期用不着） |

**追问**：*"为什么不用 SkyWalking？"*
→ 自研 TraceId 已经能解决 90% 的排查问题（grep 一个 id 串起三个服务），
引入 APM 有 agent 开销和运维成本。等链路复杂度上升（异步、MQ、多语言）再上。

**追问**：*"指标标签为什么不能放 userId？"*
→ **基数爆炸**。Prometheus 每个标签组合是一条独立时间序列，
10 万用户 × 10 个指标 = 100 万条序列，内存和查询都会崩。
userId 这类高基数信息应该放**日志**，用 TraceId 关联。

## 八、安全设计

| 威胁 | 我的防线 |
| --- | --- |
| **越权（水平/垂直）** | 四道租户防线；更新删除带 tenantId 作为 WHERE 条件，影响 0 行视为越权 |
| **SSRF**（浏览器 Agent 高危） | URL 前缀白名单；只放行 http/https（拒绝 `file://`、`javascript:`）；独立临时 user-data-dir |
| **密钥泄露** | 模型 Key AES-GCM 加密落库（响应只有 `hasApiKey` 布尔）；开放 API Key 只存 HMAC-SHA256，明文仅签发时出现一次 |
| **时序攻击** | 令牌比较用 `MessageDigest.isEqual`（**常量时间比较**，不能用 `String.equals`——它会在第一个不同字节处提前返回，可被测时推断） |
| **重放/伪造头** | 网关**先 remove 再 set** 租户头 |
| **提示词注入** | 输入隔离 + 最小权限 + 白名单（**无法根治**，只能降低爆炸半径） |

**追问**：*"AES-GCM 的 IV 怎么处理？"*
→ 每次加密生成 **12 字节随机 IV**，密文格式 `base64(iv || ciphertext)`（IV 不需要保密，但不能复用）。
GCM 自带 128 位认证标签，能检测篡改。
**★ 已知缺口**：没有版本号/keyId 字段，**轮换 data-key 后旧密文解不开**——
生产要加 keyId 前缀支持平滑轮换。

## 九、其它常见设计题（速查）

| 题目 | 关键思路 |
| --- | --- |
| **短链系统** | 发号器（雪花/号段）→ Base62 → 301/302（302 便于统计，301 减轻服务器压力）+ 缓存 |
| **延迟队列** | Redis ZSet（score=执行时间，轮询/定时捞取）、RabbitMQ 死信/插件、时间轮（Netty `HashedWheelTimer`） |
| **分布式 ID** | 雪花（趋势递增、含时间，但**时钟回拨**问题）、号段（Segment，DB 取一段本地发）、Redis INCR、UUID（无序，索引碎片） |
| **分布式锁** | Redis `SET key val NX PX ttl`（**必须带过期** + Lua 解锁校验 value）；Redisson 看门狗续期；**锁的粒度要小、要可重入、要考虑业务超时** |
| **秒杀** | 层层削减：CDN 静态化 → 网关限流 → 库存预热到 Redis + Lua 原子扣减 → MQ 异步下单 → 防重复下单（唯一键）；**核心是"把请求挡在 DB 之前"** |
| **幂等 + 重试** | 唯一键 / 幂等号 / 状态机 + 指数退避 + 最大次数 + 死信 |
