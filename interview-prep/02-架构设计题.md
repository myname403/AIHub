# 02 · 架构设计题

> 架构题的评分点从来不是"你记住了多少名词"，而是 **你能不能说清楚"为什么不那样做"**。
> 这一篇每一题都配了「替代方案 + 为什么不选」，这是拉开差距的地方。

---

## Q1 你的微服务为什么这么拆？AI 能力为什么内聚成一个服务？

**面试官真正想听**：你是不是照着教程拆的，还是真的想过边界。

### 我的答法

三个服务：网关（8080）、平台服务（8081）、AI 服务（8082）。
AI 服务内部包含对话、RAG、工具、Agent 四块能力——**这是刻意内聚的**。

原因是有三个难题会在"拆细"时被放大：

1. **分布式事务**：一次对话调用要"扣配额 + 写消息 + 检索 + 调模型"。
   如果对话、知识库、Agent 各是一个服务，一次业务动作就要跨 3 个服务写数据，
   要么上 Seata（重），要么做最终一致（复杂）。
2. **流式响应跨服务传递**：SSE / NDJSON 是长连接流，跨服务传递意味着要么透传字节流
   （丢失背压与错误语义），要么在中间做二次流式（延迟叠加、连接管理复杂）。
3. **Agent 跨服务编排**：Agent 的一个子任务可能要"检索知识库 + 生成表格 + 调工具"，
   拆开后每个子任务都是一次跨服务调用，编排逻辑和事务边界会非常难看。

**所以服务间只留三类调用**：租户校验、配额扣减、审计上报。
这三类有个共同点——**都是无事务的幂等动作**，失败了可以降级（代码里 AI 侧配额调用异常一律 catch 放行）。

### 追问预警

- **"那 AI 服务会不会太臃肿？"**
  会。我的边界是：**只要是需要事务一致、需要流式、需要被 Agent 编排的能力，就内聚**。
  如果将来检索量爆炸，我会把"向量检索"单独拆——因为它符合"读多写少、无事务、可独立扩容"。
  现在的 `KnowledgeRetriever` 是 domain 的 SPI 接口，拆出去只要换实现类，业务代码不动。
- **"为什么不用 MQ 解耦？"**
  一期没引入是刻意控制组件数量。但设计上留了口子：`ai_event_outbox` 表已经建了，
  审计/用量上报这类最终一致场景可以走 outbox + MQ。
  **注意**：如果你被追问"outbox 实现了吗"——**诚实回答没有**，表建了但代码只做了 `log.warn` 降级。
  这是我在文档里主动标出来的"未完成项"（见 `12-自测清单`的照妖镜）。

## Q2 你的分层为什么是 `web → application → domain ← infra`？和传统三层有什么区别？

### 我的答法

传统三层（Controller / Service / Dao）的问题是**依赖是单向向下的，但业务核心被压在 Service 里**，
Service 会同时依赖 MyBatis、Redis、Spring AI、HTTP 客户端——业务和技术细节焊死。

我用依赖倒置把方向拧了一下：

| 层 | 职责 | 允许依赖 |
| --- | --- | --- |
| `web` | Controller、拦截器、流式 Sink 实现 | application、domain |
| `application` | 用例编排（ChatAppService、KnowledgeAppService） | domain |
| `domain` | 业务模型 + **SPI 端口接口** | 无（零框架） |
| `infra` | Spring AI 适配、MyBatis 仓储、Redis、安全 | domain（实现其接口） |

关键差别：**domain 定义接口，infra 去实现**。
比如 domain 定义 `IngestFileStore`（入库文件存储端口），
infra 提供 `LocalIngestFileStore` 和 `MinioIngestFileStore` 两套实现，
靠 `aihub.storage.type` 一个配置切换，**业务代码零改动**——这就是后来加 MinIO 时一行业务代码都没改的原因。

### 已经落地的 SPI 端口（可以报名字，很有说服力）

`ModelGateway`（模型调用）、`KnowledgeIndexer`/`KnowledgeRetriever`（向量读写）、
`StreamSink`（流式输出）、`ChatExecutor`、`ChatMemoryStore`、`AgentRegistry`、
`MetricsRecorder`、`IngestFileStore`、`BrowserDriver`/`BrowserSessionManager`、`ArtifactStore`。

### 追问预警

- **"domain 零框架依赖，怎么做到的？值不值？"**
  代价是要写接口 + 实现类 + 一层转换（DO ↔ 领域对象），代码量大概多 20%。
  收益是：框架升级的影响面被锁死在 infra。
  我验证过这一点——Spring AI 1.1 → 2.0 的迁移，按 ADR 只需要改 `infra.ai` 适配层，
  domain 和 application 不用动。
- **"为什么不用完整的 DDD（聚合根、值对象、领域事件）？"**
  这个项目**没有复杂的领域不变量**——没有"订单必须满足 X 才能流转"这种强约束，
  引入聚合根只会增加样板代码。我借鉴的是 DDD 的**依赖方向和端口思想**，不是全套战术模式。
  这是我认为最划算的取舍。

## Q3 ArchUnit 是怎么用的？真能拦住违规吗？

### 我的答法

4 条规则，写在 `ArchitectureTest` 里，随 `mvn test` 跑：

1. `domain` 不得依赖 `application`/`web`/`infra`，也不得出现
   `org.springframework.ai..`、`com.baomidou..`、`org.springframework.data.redis..` 的包；
2. `application` 不得依赖 `infra` / `web`；
3. `web` 不得依赖 Spring AI 与 `infra`；
4. `infra.ai` 不得依赖 `infra.persistence` / `infra.security`。

它**真的拦住过**：我在写 MinIO 那次，试图在 application 层直接引配置类，构建直接失败。

### ★ 这里有个真实的坑，讲出来很加分

**`static final String` 常量会被编译期内联**，字节码里根本没有对常量所属类的符号引用，
所以我曾经在 application 层引用 `PlanningAgent.NAME`，ArchUnit **检测不到**——违规悄悄溜过去了。

解法是在 domain 建一个 `AgentNames` 常量类。

> 讲这个坑的价值：证明你不是"配了 ArchUnit 就觉得万事大吉"，
> 而是**理解它的检测原理（字节码静态分析）和盲区**。

### 追问预警

- **"规则能 100% 覆盖吗？"** 不能。目前只约束了 `infra.ai → infra.persistence/security`
  这一个方向，其它 infra 包之间没有卡口。这是已知缺口。
- **"为什么不用 Checkstyle/SpotBugs 一起？"** 可以做，但我认为 ArchUnit 的投入产出比最高——
  它管的是**架构腐化**，而架构腐化是唯一"不可逆"的技术债。

## Q4 项目里的循环依赖怎么解决的？

**场景**：`PlanningAgent` 需要 `AgentRegistry` 来派发子任务，
而 `AgentRegistry` 要收集所有 `Agent` 实现（包括 PlanningAgent 自己）——**典型的循环依赖**。

### 三种解法（我用了其中两种，都能讲）

1. **`@Lazy` 注入**（用在 `AgentRegistryImpl`）：
   构造器注入 `@Lazy List<Agent>`，Spring 注入代理对象，真正调用时才解析。
   `PlanningAgent` 一侧也用 `@Lazy AgentRegistry` 打破环。
2. **`ObjectProvider<T>` 延迟获取**（用在可选依赖）：
   例如 `ChatClientFactory` 回退时用 `ObjectProvider<ChatModel>`；
   MCP 工具用 `ObjectProvider<ToolCallbackProvider>.orderedStream()`——**缺席即降级**，
   没配 MCP 时不会启动失败。
3. Setter 注入（项目里也有，但我不推荐，会让依赖关系变隐晦）。

### 追问预警

- **"为什么不用 `@Lazy` 一把梭？"**
  `@Lazy` 是**掩盖**循环依赖，不是消除。它让启动能过，但环还在。
  真正的解法是重构：把 `AgentRegistry` 的"注册"和"查找"拆开，
  让 PlanningAgent 只依赖查找接口。这个我知道，但一期为了控制改动范围用了 `@Lazy`。
  **承认这一点，比装作没问题更可信。**

## Q5 如果让你重做，架构上你会改什么？

**这道题几乎必问，答不出 = 没有反思能力。**

我的答案（挑 2-3 个讲）：

1. **多租户隔离不该靠"人工记得写 tenant_id"**。
   这条我已经动手补了：实现了 MP 的 `TenantLineInnerInterceptor` 兜底
   （ai-service `TenantSqlGuardConfig` / platform `MybatisPlusConfig`，含白名单 +
   "无租户上下文即跳过"），但**默认关闭**。
   理由是**验证边界**：它改的是每一条 SQL，而单测是 mock 的、覆盖不到真实 SQL 改写。
   我会把「起 MySQL 跑通全部数据访问链路」作为开启前置条件——**没验证过的全局改动不当默认值**。
2. **配额扣减应该放到 Redis 用 Lua 原子化**。
   现在是 `INSERT ... ON DUPLICATE KEY UPDATE` 的两阶段试算 + 统一 upsert，**非事务**，
   并发下有超扣窗口。改成 Lua 脚本一次做完"读-判断-累加"，或者做预扣 + 释放。
3. **outbox 已经实现掉了**（原先是"表建了没写、失败只 `log.warn`"）。
   现在是 `domain/spi/EventOutbox` 端口 + `DbEventOutbox` 落库 + `EventOutboxDispatcher`
   守护线程重投（30s/批 50/重试 3 次后放弃）。**踩到的关键点**：
   后台线程没有请求上下文，而 Feign 只在租户非空时写 `X-Tenant-Id`、
   平台侧又强制要求该头 —— 不补上下文的重投会 100% 失败（已加用例钉住）。
4. **还应该引入 MQ** 削峰入库任务。现在入库是本地 4 线程的固定池，多实例部署时各节点各自为战；
   outbox 的投递通道也可以由守护线程平滑换成 MQ（表结构不用动）。

## Q6 从单机到多实例部署，你要改什么？

**这道题考察你对"有状态"的敏感度。**

| 有状态点 | 现在的做法 | 多实例要改什么 |
| --- | --- | --- |
| 入库原始文件 | 本地磁盘 | 切 MinIO（`aihub.storage.type=minio`，已实现，业务零改动） |
| 会话记忆 | MySQL（`ai_message.conv_key`） | 已无状态 ✅ |
| ChatClient 缓存 | 本地 `ConcurrentHashMap` | 各实例各缓存一份，TTL 60s，无正确性问题（只是缓存命中率下降） |
| Agent 取消标志 | `InMemoryAgentCancelRegistry`（内存 Set） | ✗ **必须改成 Redis**，否则取消请求打到另一个实例不生效 |
| SSE 会话 | 无状态（每次请求重建） | ✅ |
| 浏览器会话 | 本机 Chrome 进程 | ✗ 只能在特定节点跑，需要路由亲和或独立部署 |
| 本地限流（Caffeine） | 网关本地缓存 API Key | 各实例各缓存，回源量 ×N，可接受 |

**答这道题时点出"Agent 取消标志是内存 Set"这个细节，会显得你真的做过。**

## Q7 你怎么保证"设计文档写的"和"代码实现的"是一致的？

**（这是一道陷阱题，但你可以主动讲——因为你有真实案例）**

我的做法：写文档前先读代码，发现不一致就**以代码为准并标出来**。
这个项目里我实际发现并记录了 10 处不一致，举三个：

1. 设计文档说"租户条件由 MP 拦截器兜底"——**代码里没有这个拦截器**；
2. `spring.ai.vectorstore.redis.initialize-schema: false` 这个配置**完全无效**——
   `VectorStoreConfig` 里硬编码了 `.initializeSchema(true)`，配置从未被读取；
3. `ai_event_outbox` 表建了，但**全仓库搜不到任何写它的 Java 代码**。

> 主动暴露不一致 = 诚实 + 有代码审查习惯。但**只说你已经修掉或明确记为 TODO 的**，
> 不要暴露一堆"我知道有坑但一直没管"的问题。

## Q8 高频短问答（30 秒一把梭）

| 问题 | 答法 |
| --- | --- |
| 为什么选 Spring AI 而不是 LangChain4j？ | 团队栈是 Spring，Spring AI 与 Boot 的依赖注入、自动装配、Actuator 天然一体；且 Advisor 链的模型与 Servlet Filter 同构，学习成本低。**代价**：Spring AI 版本迭代快，1.1 → 2.0 有 breaking change，所以我把所有 Spring AI 调用收敛在 `infra.ai`。 |
| 为什么用 Redis Stack 而不是专用向量库？ | 一期规模小（万级分片），Redis 本来就要用，少一个组件。Redis Stack 支持元数据过滤（`tenant_id`/`kb_id`），正好满足租户隔离。**切换成本**被锁在 `VectorStore` 一个实现类里，超百万分片再换 PGVector/Milvus。 |
| 为什么向量模型默认指向本地 Ollama？ | 这是**开发环境的默认配置**（`embeddinggemma`，localhost:11434），避免每个开发者都要申请云端 embedding key。生产换 OpenAI/通义的 embedding 只需改配置。**注意**：这意味着没装 Ollama 时 RAG 不可用，程序会自动降级（不装 Redis 时同理）。 |
| 服务间用 Feign 还是 MQ？ | 强一致读（租户校验、配额预检）用 Feign；最终一致写（用量上报、审计）**应该用 MQ**——目前没引，是待改进项。 |
| 为什么不用 gRPC？ | 内部调用语义简单、QPS 不高，HTTP + JSON 的可调试性收益更大。真到性能瓶颈再说。 |
