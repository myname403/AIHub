# 07 · 全栈前端题

> 全栈岗看两件事：**你能不能把后端能力"对接地"暴露给前端**，
> 以及**你知不知道前端的限制**（尤其小程序）。流式渲染你做了三种实现，这是硬通货。

---

## 一、Vue 3

### 1.1 响应式原理（必考）

- **Vue 2**：`Object.defineProperty` 劫持属性的 getter/setter。
  **缺陷**：无法检测**新增/删除属性**（要 `$set`）、**数组索引和 length 变化**（要重写数组方法）。
- **Vue 3**：`Proxy` 代理整个对象。
  优势：能拦截新增/删除/数组索引/`in`/`deleteProperty`；**惰性递归**（访问到才转换子对象，性能好）。

**追问**：*`ref` 和 `reactive` 区别？*
→ `reactive` 用于对象（返回 Proxy）；`ref` 用于基本类型（包一层 `{value}` 并对 value 做响应式），
但**也能包对象**（内部会自动 `reactive`）。**`reactive` 解构会丢失响应式**（要用 `toRefs`）。

### 1.2 其它高频

| 考点 | 要点 |
| --- | --- |
| `computed` vs `watch` | computed 有**缓存**、必须同步、有返回值；watch 无缓存、可做异步、监听变化做副作用。`watchEffect` 自动收集依赖 |
| `v-if` vs `v-show` | `v-if` 是**真实销毁/重建**（切换开销大）；`v-show` 是 `display:none`（首次渲染开销大）。频繁切换用 `v-show` |
| `key` 的作用 | diff 时**识别节点身份**。用 index 做 key 在**列表插入/删除**时会导致错误的复用（状态错位） |
| `nextTick` | Vue 的更新是**异步批量**的（`nextTick` 合并同一 tick 的修改），`nextTick` 回调在 DOM 更新后执行 |
| 组件通信 | props/emit、provide/inject、Pinia、事件总线（mitt）、模板 ref / `defineExpose` |
| `keep-alive` | 缓存组件实例（`activated`/`deactivated` 生命周期），用于 Tab 切换保留状态 |
| diff 算法 | 双端对比 + 最长递增子序列（减少节点移动） |

### 1.3 `<script setup>` 组合式 API 的好处

逻辑可以按**功能聚合**（而不是被 data/methods/computed 切碎），
且**逻辑可以抽成 composable 复用**（`useXxx`）。

## 二、Vite 与工程化

### 2.1 Vite 为什么快？

- **开发环境**：利用浏览器原生 **ESM**，请求到哪个模块才编译哪个（**按需编译**），
  不需要像 Webpack 那样先打包整个 bundle；
- **预构建**：用 **esbuild**（Go 写的）把第三方依赖预打包成 ESM，
  esbuild 比 Babel/TSC 快 10~100 倍；
- **HMR**：只替换变更模块，不刷新页面。

**生产环境**仍用 Rollup 打包（tree-shaking 更好）。

### 2.2 你项目的 Vite 配置

- 端口 8849（管理后台），hash 路由；
- **代理**（这是真实改写点）：

```ts
proxy: {
  "/auth": { target: "http://localhost:8080", changeOrigin: true },
  "/api":  { target: "http://localhost:8080", changeOrigin: true }
}
```

- 输出按类型分目录（`static/js/[name]-[hash].js`），`chunkSizeWarningLimit: 4000`。

**追问**：*"生产环境怎么解决跨域？"*
→ 开发用 Vite 代理（**纯前端方案，只解决开发期**），生产用 **Nginx 反向代理**或后端 CORS。
**★ 这里有个真实的坑你可以主动讲**：我的 `Dockerfile` 是
`node:20-alpine` 构建 → `nginx:stable-alpine` 托管 `dist`，
**早期只 COPY 了 dist，没有 nginx 配置**，容器里 `/api`、`/auth` 没有反向代理——
页面能打开但所有接口 404。现在已经补上了：

- `deploy/nginx/default.conf.template`（含 SPA 回退、gzip、/api 与 /auth 反代、静态资源缓存），
  在 Dockerfile 里 COPY 到 `/etc/nginx/templates/`，由官方镜像启动时的 **envsubst**
  注入 `${BACKEND_URL}`（默认 `http://host.docker.internal:8080`，即宿主机网关）；
- 同时 `rm` 掉镜像自带的 `default.conf`，避免两个 server 块抢 80 端口默认虚拟主机。

> 这个坑的价值在于：**它只在"部署形态"下暴露**，本地 `pnpm dev` 一切正常。
> 讲出来能说明你不只会在开发环境跑起来。

## 三、网络层（你改写过的地方，值得讲）

### 3.1 axios 封装做了三件事

1. **响应解包**：适配后端统一响应体 `R{code,message,data}`
   → `code === 0` 时**直接返回 `body.data`**（调用方不必层层 `.data.data`）；
2. **401 处理**：`code === 10002` → 清 token + 跳登录；
3. **token 无感刷新**：
   - 用 `isRefreshing` 标志 + `requests[]` 队列；
   - 第一个 401 到达时发起刷新，后续请求**挂起进队列**，刷新成功后统一重放；
   - 白名单（`/login`、`/refresh-token`）不拦截。

**追问**：*"为什么需要队列？"*
→ 因为刷新是异步的，期间可能有多个并发请求同时 401，
如果不挂起，每个都会触发一次刷新（重复请求 + token 竞态）。

### 3.2 请求头里为什么没有租户头？

**这是很好的问题**——因为租户头**不该由前端加**。
后端网关从 JWT 解析出 `X-Tenant-Id` 并注入，且**强制剥离客户端伪造的同名头**。
前端只在登录 body 里传一次 `tenantCode`，此后全程只带 `Authorization`。

> 讲这个能证明你理解**安全边界在哪一侧**：前端传的任何东西都是不可信的。

## 四、流式渲染（★ 全栈岗最强卖点）

### 4.1 为什么不用 EventSource？

**EventSource（SSE）无法携带自定义 Header**（不能带 `Authorization`），
只能靠 cookie 或 URL 参数——不安全也不优雅。
所以 H5 侧我用的是 **`fetch` + `ReadableStream` 手动解析 NDJSON**：

```js
const reader = res.body.getReader()          // 逐块读
// → 解码 → 累积 buffer → 按 \n 切行 → 每行 JSON.parse
```

### 4.2 小程序侧：为什么是 chunked？

**微信小程序不支持 SSE，也没有 `TextDecoder`**。
`uni.request` 的 `enableChunked: true` + `onChunkReceived` 回调可以拿到分块数据。

### 4.3 ★ 半包处理（高频考点，你写过）

网络分块**不保证按行边界切分**——一块可能是"前半行"，也可能是"三行半"。
标准做法：

```js
buffer += text
const lines = buffer.split('\n')
buffer = lines.pop() || ''      // ★ 最后一段可能是半包，留到下一块
lines.forEach(line => handle(JSON.parse(line)))
```

**为什么必须留 buffer**：直接按块 parse 会 `JSON.parse` 失败。

### 4.4 ★ 小程序手写 UTF-8 解码

`onChunkReceived` 返回的是 `ArrayBuffer`，而小程序**没有 `TextDecoder`**，
所以要手写 UTF-8 → 字符串（含 4 字节字符的处理 `String.fromCodePoint`）。

**为什么不能简单 `String.fromCharCode`**：它只处理 UTF-16 码元（<= 0xFFFF），
**emoji 等 4 字节字符会乱码**。

### 4.5 三种通道与前端的对应关系

| 后端通道 | 前端实现 | 适用 |
| --- | --- | --- |
| SSE（`/api/ai/chat/sse`） | 管理后台暂未接入（无 EventSource） | H5，简单流式 |
| **NDJSON**（`/api/ai/chat/ndjson`） | H5：`fetch`+Reader；小程序：`enableChunked` | **双端通用**，我用得最多 |
| WebSocket（`/ws/ai?token=`） | Agent 长任务，双向（可发取消） | 需要服务端主动推/客户端反向控制 |

**★ 为什么小程序要禁 gzip**（后端配合）：
小程序 `enableChunked` 依赖**增量到达**，一旦被压缩或代理缓冲，
数据会被攒成一整块，**收不到增量**。所以后端显式设置：

```
Content-Encoding: identity
X-Accel-Buffering: no
Cache-Control: no-cache, no-transform
```

> 这三行响应头是前后端**联调才能发现**的细节，讲出来非常有说服力。

### 4.6 事件帧协议

```
{"i":序号,"e":"msg.start|token|rag.sources|agent.step|artifact|msg.end|error","ts":..,"data":{..}}
```

前端按 `e` 分发：`token` 追加文本、`rag.sources` 渲染引用、
`agent.step` 渲染 `[agent.type] content`、`artifact` 展示产物链接。

### 5.2 小程序的硬限制（必知）

1. **不支持 SSE**（→ 必须 chunked）；
2. **无 `TextDecoder`**（→ 手写 UTF-8 解码）；
3. **主包 2MB 限制**（→ 管理端页面要放**分包**）；
4. **无 DOM/BOM**（→ 不能用 `window`、`document`，也不能用大部分 Web 组件库）；
5. 不支持 `v-html`（→ Markdown 渲染要用 Towxml 之类的方案）。

**rpx**：750rpx = 屏幕宽度，自动适配（设计稿按 750px 出图）。

### 5.3 你项目的前端技术事实（诚实版）

- Vue 3.5.42 + Vite 5.4.21 + `@dcloudio` alpha 版；
- **没有引入 uview / uni-ui**，只用内置组件 + 手写 rpx 样式（控制包体积）；
- 8 个页面：`chat`、`login`、`register`、`kb`、`admin/{index,usage,model,app}`；
- token 存 `uni.setStorageSync`（不是 cookie，因为小程序没有可靠的 cookie 机制）。

### ★ 动态路由与权限（值得细讲）

后端返回菜单树 `MenuNode{menuType: "M"|"C"|"F"}`，前端递归转成路由，
**`F`（按钮）不进路由**，而是作为权限点：

```ts
const children = (menu.children ?? []).filter((c: any) => c?.menuType !== "F")
```

配合 `v-perms` 指令（比对后端返回的 `permissions` 数组）控制按钮显隐。

**追问**：*"前端权限够安全吗？"* → **不够**。前端权限只是**体验优化**（隐藏按钮），
**真正的鉴权必须在后端每个接口做**。前端隐藏了按钮，用户直接 curl 依然能打。

### 已知简化（主动说明）

**业务接口没有下沉到 `api/` 层**，而是直接在 `.vue` 里裸调：

```ts
overview.value = await http.request("get", "/api/platform/usage/overview", { params: { days } })
```

这是**我做项目时的简化**，不是规范做法。
如果重做，我会按领域拆分 `api/usage.ts`、`api/model.ts` 等，并加上 TS 返回类型。

## 七、前端安全与性能

| 考点 | 要点 |
| --- | --- |
| **XSS** | 永远不要 `v-html` 渲染用户输入；富文本要做白名单过滤（DOMPurify）。CSP 是最后一道防线 |
| **CSRF** | 我们**不用 cookie 存 token**（用 `Authorization` 头），所以**天然免疫 CSRF**——这是 JWT + Header 方案的一个真实优势 |
| token 存储 | localStorage 有 XSS 风险；httpOnly cookie 有 CSRF 风险。**没有完美方案**，我们选了 localStorage + 短期有效期（7200s）+ 刷新机制 |
| 首屏优化 | 路由懒加载、组件异步、`manualChunks` 拆 vendor（我项目**没配**，是改进点）、CDN、Gzip/Brotli |
| 长列表 | 虚拟滚动（我项目没做，数据量小） |

## 八、前后端联调事实（可能被问）

| 问题 | 答案 |
| --- | --- |
| 管理后台怎么连后端？ | 开发：Vite 代理 `/auth`、`/api` → `localhost:8080`。生产：Nginx 反代（`deploy/nginx/default.conf.template` + Dockerfile envsubst 注入 `BACKEND_URL`） |
| 小程序怎么连？ | **不走代理，直连** `config.js` 里的 baseUrl，依赖后端 CORS；真机调试要改成局域网 IP |
| 租户头谁加？ | **前端不加**，网关从 JWT 解析后注入，并剥离客户端伪造的同名头 |
| TraceId 前端处理了吗？ | **没处理**（后端有响应头 `X-Trace-Id`，前端没读）。这是改进点：可以在 axios 响应拦截器里取出来，错误提示时带上，方便用户报障 |
