## 一、MySQL 索引

### 1.1 为什么是 B+ 树？

| 候选 | 为什么不选 |
| --- | --- |
| 哈希索引 | 只支持等值，**不支持范围查询和排序**；哈希冲突退化 |
| 二叉搜索树 | 树太高（每个节点最多 2 叉），磁盘 IO 次数多 |
| B 树 | 非叶子节点也存数据，导致**单页能放的关键字少** → 树更高 |
| **B+ 树** ✅ | **非叶子只存关键字（不存数据）**，单页能放上千个 key，树高只有 3~4 层（千万级数据 3 次 IO）；且**叶子节点用链表相连**，范围查询只要顺着链表扫 |

**InnoDB 的关键事实**：
- 主键是**聚簇索引**（叶子存整行）；二级索引叶子存**主键值**（所以要回表）；
- 页大小默认 16KB；三层 B+ 树能存约 **2000 万**行（按主键 BIGINT 8B + 指针 6B 估算）。

### 1.2 你项目的索引设计原则（★ 很好讲）

**所有业务表的索引都以 `tenant_id` 打头**：

```
ai_document        idx_tenant_kb (tenant_id, kb_id)
ai_document_chunk  idx_tenant_kb / idx_doc
ai_model_route     idx_tenant_scene (tenant_id, scene)
ai_agent_task      idx_tenant (tenant_id, ...)
ai_tool_call_log   idx_tenant_time / idx_tenant_tool
ai_message         idx_tenant_convkey (tenant_id, conv_key)
ai_message_reference idx_tenant_conv
sys_user           uk_tenant_username (tenant_id, username)   ← 唯一键跨租户
```

**为什么**：因为**所有查询都强制带租户条件**，把 tenant_id 放索引第一列，
既满足了最左前缀，又天然把单租户的数据聚在一起。

这就是"**索引设计跟着查询模式走**"，比背八股有说服力。

### 1.3 索引失效的 7 种场景（必背）

1. 违反**最左前缀**（复合索引跳过第一列）
2. 索引列上做**函数/计算/隐式类型转换**（`where date(create_time)=...`；字符串列传了数字）
3. `like '%xxx'` 前缀模糊
4. `or` 连接非索引列
5. `!=` / `not in` / `is not null`（通常走全表，优化器判断）
6. 范围查询**之后**的列失效（`a=1 and b>2 and c=3` 里 c 用不上索引）
7. **回表代价过高**时优化器直接选全表（比如要查 30% 以上的行）

**追问**：*"怎么判断 SQL 走没走索引？"* → `EXPLAIN`，看 `type`（至少到 `range`，最好 `ref`/`const`）、
`key`（实际用的索引）、`rows`（预估扫描行数）、`Extra`（`Using index` = 覆盖索引，
`Using filesort` = 需要排序，`Using temporary` = 用了临时表，都该优化）。

## 二、事务与 MVCC

### 2.1 隔离级别

| 级别 | 脏读 | 不可重复读 | 幻读 |
| --- | --- | --- | --- |
| 读未提交 | ✗ | ✗ | ✗ |
| 读已提交（RC） | ✓ | ✗ | ✗ |
| **可重复读（RR，MySQL 默认）** | ✓ | ✓ | ✓（靠 next-key lock 基本解决） |
| 串行化 | ✓ | ✓ | ✓ |

### 2.2 MVCC 怎么实现的？

三个组件：
1. **隐藏列**：`DB_TRX_ID`（最后修改的事务 ID）、`DB_ROLL_PTR`（指向 undo log 的回滚指针）；
2. **Undo Log 版本链**：每次修改把旧值写入 undo log，用 `DB_ROLL_PTR` 串成链表；
3. **Read View**：事务快照读时生成，包含「当前活跃事务列表」，
   通过比较 `DB_TRX_ID` 决定**这一行对当前事务可见的版本**是哪个。

**关键差别**：
- **RR**：Read View 在**第一次快照读时生成，之后复用**（所以可重复读）；
- **RC**：**每条语句**都重新生成 Read View（所以能读到别人已提交的）。

### 2.3 当前读 vs 快照读

- **快照读**：普通 `SELECT`，走 MVCC，**不加锁**；
- **当前读**：`SELECT ... FOR UPDATE` / `LOCK IN SHARE MODE` / `UPDATE` / `DELETE`，
  读最新版本并**加锁**。

**幻读怎么解决**：
RR 下，快照读靠 MVCC（看不到新插入的行）；
当前读靠 **next-key lock（行锁 + 间隙锁）**，锁住索引记录及其前面的间隙，阻止插入。

### 2.4 锁

| 锁 | 说明 |
| --- | --- |
| 记录锁（Record Lock） | 锁单条索引记录 |
| 间隙锁（Gap Lock） | 锁两条记录之间的**间隙**（防止插入，只在 RR 下有效） |
| 临键锁（Next-Key Lock） | 记录锁 + 间隙锁，**左开右闭**，InnoDB 默认行锁算法 |
| 意向锁 | 表级锁，用于快速判断表内是否有行锁 |

**★ 重要**：行锁是**加在索引上**的。
**如果 UPDATE 的 WHERE 条件没走索引，会锁全表所有行**（退化成表锁级别的影响）。

**死锁排查**：`SHOW ENGINE INNODB STATUS` 看 `LATEST DETECTED DEADLOCK`；
常见原因是**加锁顺序不一致**——统一按主键/id 排序后再更新即可避免。

## 三、项目里的关键 SQL

### 3.1 配额的原子累加（★ 必考题）

```sql
INSERT INTO ai_quota_usage (id, tenant_id, app_id, dimension, period_key, used_value, ...)
VALUES (?, ?, ?, ?, ?, ?, ...)
ON DUPLICATE KEY UPDATE used_value = used_value + #{amount}
```

**要点**：
- 依赖唯一键 `uk_usage (tenant_id, app_id, dimension, period_key)`；
- **`ON DUPLICATE KEY UPDATE` 是原子的**——数据库保证"存在则累加，不存在则插入"不可分割，
  不需要先 `SELECT` 再 `UPDATE`（那样有竞态）；
- 主键用 MyBatis-Plus 的 `IdWorker.getId()`（雪花算法）。

**追问链**：
- *"为什么不用 `UPDATE ... SET used = used + 1 WHERE ...`？"*
  → 因为首月/首日没有记录，`UPDATE` 影响 0 行，要先判断再插入，多一次往返且有竞态。
- *"那并发下会不会超扣？"* → **会**。
  因为整个 `consume()` 是"**先试算所有维度 → 再统一 upsert**"的两阶段，且**没有事务**。
  两个请求同时通过试算，都会执行累加，可能超过限额。
- *"怎么改？"* → 见 [08-系统设计与场景题](08-系统设计与场景题.md) 的配额专题
  （Redis Lua 原子化 / 预扣释放 / 悲观锁 / 分段配额）。

> **主动承认"会超扣"是加分不是减分**——能说出边界和改进方案的人，比说"我用了分布式锁（其实没用）"的人可信。

### 3.2 两库为什么不能 JOIN

`aihub_platform`（租户、配额、审计、API Key）和 `aihub_ai`（应用、模型、知识库、Agent）**两个独立库**。

**原因**：
1. 两个库**可能部署在不同实例**，跨库 JOIN 会变成跨实例，无法执行；
2. 业务边界清晰：平台库是"租户维度"，AI 库是"应用维度"，分开后可以独立扩容；
3. 强制约束：跨库 JOIN 一旦出现，两个服务的边界就焊死了。

**代价**：需要冗余字段 + 应用层组装（例如用量看板要"按模型聚合"，
模型名在 AI 库、用量在平台库，只能在应用层拼）。

## 四、MyBatis-Plus

### 4.1 用法

`BaseMapper<T>` + `Wrappers.lambdaQuery()` 类型安全的条件构造；
复杂查询用 `@Select` 原生 SQL（如 `AiMessageMapper.selectHistoryByKey`、
`selectLastIdByRole`）；手工 upsert 用 `@Insert`。逻辑删除字段 `deleted`（1/0）。

版本 **3.5.7**。

### 4.2 ★ 一个必须知道的隐式契约（面试可以主动讲）

**MP 的 `update(entity, wrapper)` 默认忽略 null 字段**（`FieldStrategy.NOT_NULL`）。

我把它当成了**特性**而不是坑：后台编辑模型时，**API Key 留空表示"保持原值"**——
因为前端不传 key，实体里该字段是 null，MP 就不会更新它。

但这是**隐式契约**，改动时很容易破坏，所以我用单测钉住了它：
`DbModelAdminRepositoryTest.updateWithoutApiKeyLeavesCipherUntouched`。

> 讲"我用单测锁住隐式行为"，体现工程素养。

### 4.3 追问

- *"#{} 和 ${} 的区别？"* → `#{}` 是**预编译占位符**（防 SQL 注入）；
  `${}` 是**字符串拼接**（有注入风险，只能用于动态表名/列名且必须白名单校验）。
- *"一级缓存和二级缓存？"* → 一级是 `SqlSession` 级别（默认开）；
  二级是 `namespace` 级别（跨 SqlSession，需要配置）。
  **分布式环境一般关掉二级缓存**（容易脏读），改用 Redis。

## 五、Flyway

- 平台库 V1、V4–V10（**缺 V2/V3**，历史原因，不影响——Flyway 只要求版本号递增不重复）；
  AI 库 V1–V9。
- 脚本**幂等**：`CREATE TABLE IF NOT EXISTS`，种子数据用 `ON DUPLICATE KEY UPDATE`。
- **铁律：已上线的迁移脚本绝不修改**（改了会导致其它环境 checksum 校验失败）。
  要改就写新版本。
- AI 库 V9 做过一次字段类型变更：`ai_message.conversation_id` 从 `BIGINT` 改成 `VARCHAR(64)`
  （因为会话 ID 改成了字符串形态）。

**追问**：*"大表加字段怎么办？"* → MySQL 8.0 支持 **INSTANT DDL**（秒级，只改元数据）；
不支持的用 `pt-online-schema-change` 或 gh-ost（建影子表 + 触发器同步 + 重命名）。

## 六、Redis

### 6.1 用在哪

| 场景 | 实现 |
| --- | --- |
| **向量检索** | Redis Stack（**必须 Stack，普通 Redis 没有向量能力**）。`RedisVectorStore` + `JedisPooled`，元数据字段 `tenant_id` / `kb_id` / `doc_id` 声明为 **tag 类型**（可做过滤） |
| API Key 缓存（网关） | **Caffeine `AsyncCache`**，`expireAfterWrite(60s)` + `maximumSize(10000)` |

**注意**：会话记忆**不在 Redis**，在 MySQL（`ai_message.conv_key`）。
不装 Redis 时对话和 Agent 仍可用，**只有 RAG 不可用**（程序自动降级）。

### 6.2 向量检索的关键点

- 检索表达式：`tenant_id == 'x' && kb_id == 'y'`（**在向量检索里做租户过滤，不是召回后再过滤**）；
  topK 默认 4，相似度阈值 0.6；
- 索引算法一般是 **HNSW**（快，近似）或 **FLAT**（暴力，精确）。
  维度建索引后**不可修改**——这是 Redis Stack/大部分向量库的硬约束，扩容要重建索引。
- **★ 出口还有一道 `TenantGuard`**：即使向量库过滤被绕过，
  `RedisKnowledgeRetriever` 会逐条比对 `meta.get("tenant_id")`，不匹配就跳过并打 warn。

### 6.3 缓存三兄弟（必考）

| 问题 | 现象 | 解法 |
| --- | --- | --- |
| **缓存穿透** | 查一个**一定不存在**的 key，每次都打到 DB | 布隆过滤器 / 缓存空值（短 TTL） |
| **缓存击穿** | **热点 key 过期**瞬间大量请求打到 DB | 互斥锁重建 / 逻辑过期（不设 TTL，值里存过期时间） |
| **缓存雪崩** | **大量 key 同时过期** | TTL 加随机抖动 / 多级缓存 / 熔断降级 |

**一致性**：一般用 **Cache Aside**（读：命中返回，未命中查 DB 回写；写：**先更新 DB，再删缓存**）。
为什么是删不是更新？——更新缓存可能因为并发写导致脏数据，删除则让下次读重新加载。

## 七、多租户（招牌题，务必讲透）

### 7.1 四道防线（对应代码位置）

| # | 防线 | 实现 |
| --- | --- | --- |
| 1 | **源头只认 JWT** | 租户 ID **只能**从 JWT / API Key 解析，绝不接受前端传参 |
| 2 | **网关防伪造** | `AuthGlobalFilter` **先 remove 再 set** `X-Tenant-Id` / `X-User-Id` |
| 3 | **检索/查询强制过滤** | 所有 SQL 手写 `.eq(Xxx::getTenantId, ...)`；向量检索带 `tenant_id` 过滤表达式 |
| 4 | **出口校验** | `TenantGuard`：向量检索结果逐条比对 `tenant_id`，不匹配跳过并告警 |

### 7.2 更新/删除的防越权写法（★ 很实用）

**把 tenantId 作为 WHERE 条件本身**，而不是"先查出来再判断"：

```java
int rows = mapper.update(entity,
    Wrappers.lambdaUpdate(Xxx.class)
            .eq(Xxx::getId, id)
            .eq(Xxx::getTenantId, tenantId));   // ★ 租户条件是 WHERE 的一部分
if (rows == 0) throw new BizException(NOT_FOUND_OR_FORBIDDEN);
```

**影响行数为 0 即视为越权或不存在**——一次 IO 完成"鉴权 + 修改"，且**天然防住了 TOCTOU 竞态**
（先查后改的写法，查和改之间数据可能已被换掉）。

### 7.3 ★ 这道题的正确答法：承认缺口 + 说清"我做到哪一步"

> **框架级兜底现在有了，但默认关闭——这是我要主动交代的。**
>
> 项目里已实现 `TenantLineInnerInterceptor` 兜底（ai-service `TenantSqlGuardConfig`、
> platform `MybatisPlusConfig`），带表白名单与"**无租户上下文即跳过**"的安全语义：
> 登录、异步入库线程、内部接口这些没有上下文的链路行为不变。
> **但它是默认关的**（`aihub.tenant.sql-guard.enabled=false`）。
>
> **为什么默认关**：它改的是每一条 SQL，而本项目自动化测试以 Mockito 单测为主、
> Mapper 是 mock 的，**覆盖不到真实 SQL 的解析与改写**。没有在真实 MySQL 上回归过，
> 我不把它设成默认行为——**宁可它先不生效，也不能拿一个没验证过的全局改动当基线**。
>
> 开启路径我写在了配置注释里：起 MySQL → 跑通「登录 → 对话 → 知识库 → Agent →
> 看板 → 管理端 CRUD」→ 日志无 SQL 异常 → 再考虑开启。

**这道题的加分点**（比"我上了拦截器"强得多）：
- 你知道**约定 ≠ 强制**：手写 `.eq(tenantId)` 是约定，拦截器/构建卡口才是强制；
- 你知道**验证边界**：单测 mock 覆盖不到真实 SQL，所以默认值必须保守；
- 你还留了后续动作：跨租户端到端回归测试（用两个租户的数据跑同一批 Repository 用例，
  交叉验证取不到对方数据）——这是设计文档里明确要求、目前仍缺的一项。

> 大多数候选人会说"我们所有查询都加了租户条件"——那是约定；
> 能说出"约定不可靠，我需要框架级卡口，而且我知道它验证到了哪一步"，
> 这是工程师而不是背答案的人的思维。

### 7.4 多租户三种方案对比（可能会被问）

| 方案 | 隔离性 | 成本 | 适用 |
| --- | --- | --- | --- |
| **共享库共享表 + tenant_id**（我用的） | 低 | 最低 | SaaS 中小客户，租户数多、数据量小 |
| 共享库独立 schema | 中 | 中 | 中等客户 |
| 独立库 | 高 | 高 | 大客户、有合规要求 |

我选第一种的原因：租户数量可能很多（几十上百），单租户数据量小，
共享表 + tenant_id 的运维成本最低。**代价是隔离性弱，所以才需要四道防线。**

## 八、分库分表（没做，但要能讲）

**为什么没做**：当前数据量远未到瓶颈（单表百万级以内），过早分片会带来
分布式事务、跨片查询、全局 ID、扩容迁移四大难题。

**如果做**（能说出这套就够了）：
- **分片键**：`tenant_id`（租户是所有查询的前缀，天然适合）；
- **全局 ID**：雪花算法（项目里已经在用 `IdWorker.getId()`）/ 号段模式 / Redis INCR；
- **中间件**：ShardingSphere-JDBC（客户端，轻量）或 Proxy（独立部署）；
- **扩容**：一致性哈希 或 预分片（如 1024 个逻辑片，前期物理上放一起，迁移时整体搬）；
- **跨片查询**：避免 JOIN，用应用层组装 / 广播表（字典表）/ 绑定表（同分片键的父子表）。
