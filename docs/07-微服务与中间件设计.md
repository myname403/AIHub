# 07 · 微服务拆分与中间件设计

> 本文记录「模块化单体 → 微服务」的拆分决策、服务边界、Nacos 与 Sentinel 的用法。
> 与 03 号架构文档配合使用：03 定义**服务内部**的分层，本文定义**服务之间**的边界。

---

## 1. 拆分决策

### 1.1 核心原则：**AI 能力内聚为一个服务**

拆分的最大风险不在"拆"，而在"拆错地方"。以下三件事一旦跨服务，复杂度会急剧上升：

| 高危跨场景 | 为什么危险 |
| --- | --- |
| 知识库入库（文档 → 分片 → 向量） | 跨服务的多写一致性，需要分布式事务 |
| 流式输出（SSE / Chunked / WebSocket） | 流式响应跨服务传递，连接与背压管理复杂 |
| Agent 长任务（多步执行、可中断） | 跨服务编排状态、中断信号传播困难 |

**决策**：这三者全部放在 `aihub-ai-service` 内部完成，**不拆**。服务之间只保留简单、无事务的调用。

### 1.2 服务清单

| 服务 | 职责 | 独享数据表 |
| --- | --- | --- |
| **`aihub-gateway`** | 统一入口、路由、鉴权、Sentinel 限流、跨域 | 无（无状态） |
| **`aihub-platform-service`** | 登录认证、租户、用户、角色、API Key、配额策略与扣减、审计日志、用量统计 | `sys_*`、`ai_quota_policy`、`ai_quota_usage`、`ai_usage_record`、`ai_audit_log` |
| **`aihub-ai-service`** ★ | 模型网关、应用（助手）配置、知识库与 RAG、工具与 MCP、Agent 内核、会话与记忆、产物 | `ai_app*`、`ai_model*`、`ai_knowledge_base`、`ai_document*`、`ai_tool*`、`ai_mcp_*`、`ai_agent*`、`ai_conversation`、`ai_message*`、`ai_artifact`、`ai_prompt_*`、`ai_event_outbox` |
| `aihub-mcp-sse` / `aihub-mcp-stdio` | 对外提供 MCP 服务（可并入 AI 服务部署，也可独立） | 复用 AI 服务数据 |

### 1.3 服务内部仍保持分层

微服务**不替代**分层解耦，而是叠加在它之上。每个服务内部依然是：

```
web → application → domain ← infra
```

`aihub-ai-service` 内部保留 `domain / application / infra-ai / infra-persistence / infra-security / web` 的包（模块）划分，ArchUnit 依赖卡口继续生效，只是作用域从"整个工程"变为"该服务内"。

## 2. 跨服务交互规则

**只允许以下三类跨服务调用**，新增任何调用都必须符合其一：

| # | 调用 | 方式 | 事务性 |
| --- | --- | --- | --- |
| 1 | gateway → platform：校验 Token / API Key，解析 `tenantId` | OpenFeign | 无 |
| 2 | ai → platform：校验租户状态、扣减配额 | OpenFeign（幂等 + 失败降级） | 无（最终一致） |
| 3 | ai → platform：上报审计与用量 | **异步**（outbox 表 + 定时投递或 MQ） | 无 |

**禁止项**
- 禁止跨服务 JOIN 或跨库查询
- 禁止 AI 服务直接读写 `sys_*` 表（必须走 platform 接口）
- 禁止在跨服务调用中传播流式响应

**降级策略**：platform 不可用时，AI 服务按"本地配额快照"放行并记录待补扣，避免认证/配额故障导致整个 AI 能力不可用。

## 3. Nacos 用法

### 3.1 双重角色

| 角色 | 用途 | 是否启用 |
| --- | --- | --- |
| **配置中心** | 基础设施配置的集中管理与**热更新** | ✅ 启用 |
| **注册中心** | 服务注册与发现（配合 OpenFeign） | ✅ 启用 |

### 3.2 ★ 配置归属：什么放 Nacos，什么放 MySQL

这是最容易搞混的地方，必须遵守：

| 配置类型 | 存放位置 | 理由 |
| --- | --- | --- |
| 模型 `base_url`、超时、最大 Token | **Nacos** | 基础设施级，需热更新，无租户差异 |
| 限流阈值、熔断规则 | **Nacos** | 运维级，需热更新 |
| 功能开关（如是否启用 MCP） | **Nacos** | 运维级 |
| MCP Server 地址与启动参数 | **Nacos** | 基础设施级 |
| 线程池、连接池参数 | **Nacos** | 基础设施级 |
| 应用（助手）配置、系统提示词 | **MySQL** | 需版本、审计、多租户隔离 |
| 知识库、文档、分片配置 | **MySQL** | 同上 |
| 提示词模板与版本 | **MySQL** | 同上 |
| 模型密钥 | **MySQL**（加密存储） | 租户隔离 + 加密，不放配置中心明文 |
| 配额策略 | **MySQL** | 业务规则，需审计 |

> 一句话：**运维/基础设施配置 → Nacos；业务/租户配置 → MySQL。**

### 3.3 热更新实现方式

- 配置类加 `@RefreshScope`，或监听 `NacosConfigManager` 的配置变更事件
- 典型热更新场景：改模型地址 → 无需重启；调限流阈值 → 立即生效；开关 MCP → 立即生效
- **注意**：密钥类配置变更需要重建 `ChatModel` Bean，需配合 `ChatClientFactory` 的缓存失效机制

### 3.4 命名空间规划

| 命名空间 | 用途 |
| --- | --- |
| `public`（或 `aihub-dev`） | 开发环境 |
| `aihub-prod` | 生产环境 |
| 分组 `DEFAULT_GROUP` | 按服务名划分 dataId，如 `aihub-ai-service.yaml` |

## 4. Sentinel 用法

| 层面 | 位置 | 规则 |
| --- | --- | --- |
| **网关层** | `aihub-gateway` | 按 API Key / 租户 / 路径做 QPS 限流；突发流量削峰 |
| **服务层** | `aihub-ai-service` | 对**模型调用**单独埋点限流与熔断（防止模型超时拖垮线程池） |
| **工具层** | 工具调用 | 单工具并发数与超时熔断 |

**与配额体系的分工**

| 机制 | 作用 | 时间维度 |
| --- | --- | --- |
| **Sentinel** | 瞬时流量保护、熔断降级 | 秒级 |
| **配额（Quota）** | 周期总量控制、计费依据 | 日 / 月 |

两者互补，都要有。

## 7. 本地环境（docker-compose）

一键拉起：MySQL 8 + Redis Stack + Nacos 3.0.3 + Sentinel Dashboard 1.8.9。

**健康检查要点**
- Redis Stack：断言 `MODULE LIST` 含 `search`（否则向量能力缺失）
- Nacos：等待 `/nacos/v1/console/health` 或端口存活
- Nacos 3.x 需要设置认证相关环境变量（`NACOS_AUTH_TOKEN` 等）

## 8. 引入微服务后的新增风险

| # | 风险 | 缓解 |
| --- | --- | --- |
| MR1 | Nacos 版本与 Boot 不匹配 | 严格锁定 SCA 2025.0.0.0；禁止引入 2025.1.x |
| MR2 | 配置散落两处（Nacos / MySQL）造成混乱 | 严格执行第 3.2 节的归属规则，并在文档中固化 |
| MR3 | platform 不可用导致 AI 服务不可用 | AI 服务对配额/认证做本地快照降级 + 待补扣队列 |
| MR4 | 跨服务调用未传 `tenantId` | 统一 Feign 拦截器自动透传租户上下文，服务端强制校验 |
| MR5 | 流式响应误走跨服务 | 架构卡口：流式接口只允许在 gateway → ai-service 的**直连**链路上，禁止二次转发 |
| MR6 | Sentinel 规则丢失 | 规则持久化到 Nacos（DataSource 配置） |
