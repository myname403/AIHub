## 1. 索引——为什么查询快/慢

### 1.1 B+ 树一图流（必须理解到"能画出来"）

```
                    [ 10 | 30 | 60 ]            ← 根节点（非叶：只存键+指针）
                   /      |       \
          [3|7]      [10|22]      [60|88]       ← 中间层
          /  \        /  \          /  \
      [1,3][7,9][10,15][22,30][60,71][88,99]    ← 叶子层：存数据 + 兄弟指针（链表）
                                                 → 范围查询顺着链表扫
```

三个推论：① 树高 3 层可撑千万级数据（每次查询 = 3~4 次磁盘 IO）；② **叶子链表**使范围查询/排序极快；③ 为什么用 B+ 树不用哈希/二叉树——哈希不支持范围查询、二叉树太深 IO 多。

### 1.2 项目里的索引实战

```sql
-- V1 迁移脚本的真实索引设计
UNIQUE KEY uk_code (code)                        -- 租户码：唯一约束 = 幂等保障
UNIQUE KEY uk_tenant_username (tenant_id, username)  -- 复合唯一：租户内用户名不重
KEY idx_tenant (tenant_id)                       -- 所有业务表第一索引位
UNIQUE KEY uk_usage (tenant_id, app_id, dimension, period_key)  -- 配额计数器唯一键

-- 最左前缀原则：索引 (a, b, c) 能命中 a / a,b / a,b,c，命中不了 b,c
-- 所以 AIHub 的"租户隔离查询永远先 tenant_id"不只是安全，还正好吃到索引
```

**索引失效场景**（每条都在生产环境咬过人）：对索引列用函数/运算（`DATE(create_time)`）、隐式类型转换（varchar 列用数字查）、前导模糊 `LIKE '%x'`、`OR` 两侧有无索引列。

### 1.3 聚簇索引与回表

InnoDB 主键索引的**叶子存整行数据**（聚簇）；二级索引叶子存**主键值**——查 `SELECT name FROM user WHERE username='x'` 若 username 有索引且 name 也在索引里 = **覆盖索引**（不回表，最快）；否则拿主键回聚簇索引再查一次 = **回表**。

实践：高频查询把需要的列加进索引（`INDEX(tenant_id, create_time, model_code)`）实现覆盖——但索引不是越多越好（写入变慢+占空间）。

## 2. 事务——ACID 与隔离级别

### 2.1 隔离级别与现象

| 隔离级别 | 脏读 | 不可重复读 | 幻读 | InnoDB 默认 |
|---|---|---|---|---|
| READ UNCOMMITTED | 有 | 有 | 有 | |
| READ COMMITTED | 无 | 有 | 有 | |
| **REPEATABLE READ** | 无 | 无 | InnoDB 基本无 | ★ 默认 |
| SERIALIZABLE | 无 | 无 | 无 | 性能差不用 |

InnoDB 的 RR 靠 **MVCC**（多版本并发控制：每行带隐藏版本号，读的是快照）+ **间隙锁**防幻读——读不加锁、读写不冲突，这就是"读多写少系统选 InnoDB"的原因。

### 2.2 项目里的两个事务案例

```java
// 案例 1：注册（@Transactional 写 5 张表）——原子性
// 租户/用户/角色/角色菜单/用户角色，任何一步失败全部回滚
@Transactional(rollbackFor = Exception.class)   // ★ rollbackFor 显式声明：
public AuthRegisterRespVO register(...) { }     //   默认只回滚 RuntimeException，受检异常不回滚是坑

// 案例 2：配额两阶段扣减——一致性
// 第一阶段试算所有维度 → 第二阶段统一 upsert；任一维度超限整体拒绝
// 不追求严格事务（跨服务），用"先试算后累加"把脏数据窗口压到最小
```

**事务失效的经典场景**（每个都真实发生过）：方法非 public、同类内部调用（不走代理）、异常被 catch 吞了、rollbackFor 没写且抛的是受检异常。

## 3. 锁——从 `ON DUPLICATE KEY UPDATE` 说起

```sql
-- AIHub 配额扣减的核心 SQL（AiQuotaUsageMapper.upsertConsume）
insert into ai_quota_usage (id, tenant_id, app_id, dimension, period_key, used_value)
values (#{id}, #{tenantId}, #{appId}, #{dimension}, #{periodKey}, #{amount})
on duplicate key update used_value = used_value + #{amount}
-- ↑ 命中唯一键就"原子累加"——一条 SQL 完成，天然并发安全
```

**为什么这比"先查再改"安全**：先 `SELECT used` 再 `UPDATE used = 新值` 之间，另一个请求可能也读了旧值（丢失更新）。四种修复对比：

| 方案 | 原理 | 代价 |
|---|---|---|
| `ON DUPLICATE KEY UPDATE` 原子累加 | DB 行锁内完成 | ★ 项目方案，最简 |
| `UPDATE ... WHERE used + ? <= limit`（条件更新） | 影响行数=0 即超限 | 更严格，但试算逻辑分开 |
| `SELECT ... FOR UPDATE` 悲观锁 | 显式行锁 | 持锁时间长，易死锁 |
| 分布式锁（Redis） | 跨服务互斥 | 引入新组件（见 14 篇） |

**死锁认识**：两个事务互相等对方的锁。规则：按相同顺序访问资源、事务尽量短。排查：`SHOW ENGINE INNODB STATUS` 里的 LATEST DETECTED DEADLOCK。

## 4. SQL 优化——EXPLAIN 是唯一真理

```sql
EXPLAIN SELECT * FROM ai_usage_record
WHERE tenant_id = 1001 AND create_time >= '2026-10-01';
-- 重点看四列：
-- type:  至少 range（ref/const 更好）；ALL = 全表扫描，必须优化
-- key:   实际用到的索引（NULL = 没用上）
-- rows:  预估扫描行数（越少越好）
-- Extra: "Using index"=覆盖索引佳；"Using filesort/temporary"=要优化
```

优化三板斧：**先看 EXPLAIN** → 加/调索引 → 改写 SQL（避免 SELECT *、深分页用 `WHERE id > ?` 游标方式、大表 JOIN 前先过滤）。

## 5. 分库分表——AIHub 双库是它的第一课

```
垂直分库：按业务拆 —— AIHub 已经做了（platform 库 / ai 库）
垂直分表：按冷热拆 —— 如把大字段(content mediumtext)拆出主表
水平分表：按行拆 —— 单表超千万行后按 tenant_id / 时间哈希拆
```

水平分表带来的四个新问题（这就是"能不拆就不拆"的原因）：
1. **跨分片查询**：需要聚合层或异构索引（ES）；
2. **分布式 ID**：不能用自增——AIHub 用雪花 ID（IdWorker）已提前规避；
3. **事务跨库**：跨库 JOIN/事务失效——AIHub 的"服务间只走接口"架构天然规避；
4. **扩容迁移**：一致性哈希/基因法。

**AIHub 的设计前瞻**：双库分治 + 雪花 ID + 禁止跨库 JOIN + 服务间接口化——这四条正好是水平分表的前置条件，将来 ai_usage_record 按月分表只需改分片路由。

## 6. 面试视角速记

| 高频问题 | 一句话回答 |
|---|---|
| B+ 树为什么不用红黑树/哈希？ | 矮胖树 IO 少 + 叶子链表支持范围查询 |
| 聚簇 vs 非聚簇？ | 主键叶子存整行；二级索引叶子存主键（回表） |
| RR 怎么解决幻读？ | MVCC 快照读 + 间隙锁当前读 |
| 事务失效场景？ | 非 public、自调用、异常被吞、rollbackFor 缺失 |
| 分库分表何时做？ | 单表 > 千万行或单库写瓶颈；先索引优化/读写分离/归档 |
