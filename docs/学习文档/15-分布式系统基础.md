# 15 · 分布式系统基础 —— CAP、幂等、分布式事务、一致性

> 锚点：AIHub 已经在无感知中做了三件分布式的事——配额扣减的**幂等**（requestId）、
> 用量上报失败的**降级与补偿**（outbox）、Feign 跨服务调用的**最终一致**。本篇把这些
> "朴素实践"升级成理论体系，你会发现自己早就在用分布式系统的经典方案。

---

## 1. CAP 与 BASE——分布式系统的"物理定律"

```
CAP 三选二（网络分区 P 无法避免，实际是 CP 与 AP 之争）：
C 一致性：所有节点同一时刻看到相同数据
A 可用性：每个请求都有响应（哪怕数据旧）
P 分区容忍：网络断开时系统还能运转

CP：ZooKeeper/etcd —— 分区时拒绝服务保一致（选主、配置类）
AP：Nacos/Eureka  —— 分区时返回旧数据保可用（注册发现类）
```

**AIHub 的选择就是教科书**：Nacos 用 AP（注册中心要可用，实例列表短暂旧一点无妨）；
扣配额本质要 CP（不能多扣）但用"数据库行锁 + 幂等"在 AP 系统里实现了关键路径的 C——
**分布式设计的艺术就是：在正确的位置做正确的取舍**。

BASE 是 CAP 的工程化落地：Basically Available（基本可用）+ Soft state（软状态/中间态）+
Eventually consistent（最终一致）——AIHub 的"用量上报失败落 outbox 稍后补偿"就是典型的最终一致。

## 2. 幂等——AIHub 已经给你打了样

**定义**：同一操作执行 N 次与执行 1 次效果相同。分布式下重试无处不在（Feign 重试、MQ 重消费、用户双击），**没有幂等就没有可靠性**。

AIHub 的三种幂等实现（对照源码）：

```java
// ① 唯一键幂等：sys_user 的 uk_tenant_username (tenant_id, username)
//    重复插入直接违反唯一键——数据库层兜底
//    SysUserService.create 里先 selectCount 再 insert 只是给友好提示，唯一键才是真防线

// ② upsert 幂等：配额计数器（uk_usage 唯一键）
INSERT ... ON DUPLICATE KEY UPDATE used_value = used_value + #{amount}
//    注意：累加类天然不幂等！所以扣减入口有 requestId——AI 侧生成的 UUID，
//    平台侧按 requestId 去重（M5 设计，完整实现可拓展）

// ③ 状态机幂等：入库任务 status 流转 0待处理→1处理中→2完成/3失败
//    "处理中"的任务再触发只会被忽略——用状态本身做防重入
```

**幂等手段选择表**：

| 手段 | 适用 | 例子 |
|---|---|---|
| 唯一约束 | 创建类 | 用户名/订单号/Key 签发 |
| 去重表（requestId） | 扣减/转账类 | 配额扣减 |
| 状态机 | 流程类 | 入库任务、订单流转 |
| 乐观锁版本号 | 更新类 | `UPDATE ... WHERE version = ?` |
| 天然幂等 | 查询/删除/覆盖写 | GET、DELETE by id、SET |

## 3. 分布式事务——从"2PC 理论"到"AIHub 的务实选择"

### 3.1 理论谱系（知道即可，别背实现细节）

```
2PC/XA：强一致，准备-提交两阶段，同步阻塞 → 性能差，数据库层支持
TCC：   Try(预留)-Confirm(确认)-Cancel(取消)，业务层手写三个接口 → 侵入大
Saga：  长事务拆成多个本地事务 + 补偿操作，失败了逐个反向补偿 → 最常用
本地消息表/outbox：业务与消息同库写入，后台扫表发 MQ → 最简单可靠（AIHub 预演过）
```

### 3.2 AIHub 的务实答案（对照源码）

```
场景：对话要同时完成"AI 生成（本地）"+"扣配额（远程平台服务）"+"用量上报（远程）"
分布式的标准难题：AI 成功了但扣配额失败怎么办？

AIHub 的取舍（有意的架构决策，见 docs/07 MR3）：
① 扣配额失败 → 抛异常拒绝对话（强一致的关键闸门，失败必须拦住）
② 上报用量失败 → 只记日志降级放行（宁可账面少扣，不能让用户对话失败）
③ token 补扣失败 → 记日志（下轮 checkQuota 自然兜住）
④ outbox 表 → 补偿机制的地基（M5 预留）

面试表述："我们没有引入 Seata 这类分布式事务框架——因为跨服务操作被设计成
'可补偿的弱一致'：关键路径（配额闸门）同步强校验，统计路径（上报）允许最终一致，
配合降级放行与 outbox 补偿。分布式事务选型的第一原则是：先问能不能不用事务。"
```

## 4. 一致性哈希与负载均衡——"请求打到哪"的学问

```
轮询/随机：最简单，但不考虑机器差异与数据位置
一致性哈希：环形哈希空间，节点增减只影响相邻区段——缓存类系统标配
```

AIHub 的负载均衡由 Spring Cloud LoadBalancer 默认轮询处理（Nacos 提供实例列表）；
`lb://aihub-ai-service` 背后就是它。sticky session（会话粘滞）在 AIHub 不需要——
JWT 无状态，任何实例都能处理任何请求，这正是无状态设计的好处。

**限流算法顺带一讲**（Sentinel 的内部）：固定窗口（临界突刺）、滑动窗口（Sentinel 默认）、
令牌桶（允许突发，Sentinel 匀速排队）、漏桶（恒定速率）。

## 5. 分布式"生存指南"清单

```
□ 所有跨服务写操作问一句：重试安全吗（幂等）？
□ 所有远程调用问一句：失败怎么办（降级/补偿/放弃）？
□ 超时必须显式设置（Feign/MQ 消费/锁过期），默认值经常是坑
□ 关键状态变更落库（状态机），别只放内存
□ TraceId 贯穿（AIHub 已做），否则排障是盲人摸象
□ 监控先行：没有指标的分布式系统 = 没有仪表盘开车
```

## 6. 面试视角速记

| 高频问题 | 一句话回答 |
|---|---|
| CAP 怎么理解？ | 分区不可避免，C/A 二选一；注册中心 AP、配置/锁 CP |
| 分布式事务方案对比？ | 2PC 强一致慢；TCC 侵入大；Saga/outbox 最终一致最常用 |
| 什么是幂等？怎么实现？ | 多次执行同一次效果；唯一键/去重表/状态机/版本号 |
| 为什么选 Nacos 不是 ZooKeeper？ | 注册发现要 AP 可用性；ZK 的 CP 在分区时不可用 |
| 限流算法有哪些？ | 固定/滑动窗口、令牌桶、漏桶；Sentinel 滑动窗口 |
