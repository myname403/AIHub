# 14 · 中间件全家桶 —— 消息队列、分布式锁、任务调度、Elasticsearch

> 锚点：AIHub 用了 Nacos + Redis + MySQL + Sentinel——但你迟早会遇到"需要一个 MQ"的
> 时刻（比如配额扣减失败重试）。本篇讲清楚：这些中间件解决什么问题、AIHub **为什么现在
> 不用它们**、什么时候该引入。

---

## 1. 消息队列（MQ）——异步、削峰、解耦

### 1.1 三大价值一图流

```
同步（现在）：AI 服务 ──阻塞等待──> 平台服务扣配额    平台挂 → 对话也挂（有降级，但账可能丢）
异步（MQ 后）：AI 服务 ──发消息即返回──> [MQ] ──> 消费者慢慢扣   平台挂了消息留着，恢复再消费

异步：主流程不等非核心流程（用量上报发 MQ，接口立刻返回）
削峰：瞬时 1 万次调用先进 MQ，消费者按自己的节奏扣减
解耦：AI 服务不认识平台服务，只认识"quota.consume 这个事件"
```

### 1.2 选型速查

| | RocketMQ | Kafka | RabbitMQ |
|---|---|---|---|
| 出身 | 阿里，电商场景 | LinkedIn，日志流 | Pivotal，通用 |
| 强项 | 事务消息/延迟消息 | 超高吞吐/流式 | 灵活路由/低延迟 |
| Java 生态 | ★★★（Spring 集成好） | ★★★（大数据标配） | ★★ |
| 适合 | 业务消息/订单 | 日志/埋点/流计算 | 中小规模/异构系统 |

**AIHub 场景代入**：`用量上报`和`配额扣减失败补偿`最适合 MQ——现在用 try-catch 降级 + outbox 表（ai_event_outbox）兜底，本质就是"手写了一个简陋 MQ"；量上来后引入 RocketMQ，outbox 模式可以直接换成事务消息。

### 1.3 必懂的三个问题（面试高频）

```text
① 消息丢失：生产者没发出去 / MQ 挂了没落盘 / 消费者没处理完就 ack
   → 三端都要防：发送确认 + 持久化 + 手动 ack
② 重复消费：网络重试必然导致 at-least-once
   → 消费端幂等（AIHub 的 requestId 去重就是预演）
③ 顺序消费：同一订单的消息必须有序
   → 按 key 分区（同 key 进同一队列）
```

## 2. 分布式锁——单机锁管不了多实例

### 2.1 为什么需要

AIHub 单实例部署时，`ON DUPLICATE KEY UPDATE` 的数据库行锁够用。**一旦部署两个实例**（生产必然），两个实例同时处理同一租户的扣减——数据库行锁依然兜底（同库）。但**跨资源**的互斥（如"同一个租户同时只允许一个入库任务在跑"）就需要分布式锁。

### 2.2 Redis 分布式锁最小实现（与 AIHub 的 Redis 天然配套）

```java
// 加锁：SET NX PX = "不存在才设置 + 过期时间" 必须原子（一条命令）
Boolean ok = redis.opsForValue().setIfAbsent("lock:ingest:" + kbId, uuid, Duration.ofSeconds(30));
if (Boolean.TRUE.equals(ok)) {
    try { /* 干活 */ }
    finally {
        // 释放：只能释放自己的锁（比对 uuid），用 Lua 保证"比对+删除"原子
        String script = "if redis.call('get',KEYS[1])==ARGV[1] then return redis.call('del',KEYS[1]) end";
        redis.execute(new DefaultRedisScript<>(script), List.of(key), uuid);
    }
}
```

三个必懂的坑：**忘了设过期时间**（实例挂了锁永不释放）；**释放了别人的锁**（A 超时后 B 拿到锁，A 回来把 B 的删了——所以值放 uuid 比对）；**业务没干完锁过期**（看门狗续期，Redisson 自带）。

**直接用 Redisson**：生产别手写，`RLock lock = redisson.getLock(key); lock.lock(); ... lock.unlock();` 自带看门狗续期与可重入。

## 3. 任务调度——单机定时器到分布式调度

### 3.1 谱系

```
@Scheduled（Spring 自带）  AIHub kb.vue 的轮询在其对面的服务端对应物
   ↓ 问题：多实例会重复执行 / 不能动态改 cron / 没有失败重试与告警
XXL-JOB（大众点评开源）      调度中心 + 执行器架构：Web 界面管任务、分片广播、失败重试
PowerJob / Quartz           同类替代
```

**AIHub 的候选定时任务**（现在没有定时任务，但你拓展时可以练手）：配额周期切换清理、outbox 补偿重发、api_event_outbox 扫描、文档嵌入重试、用法数据日报。

## 4. Elasticsearch——倒排索引与全文检索

### 4.1 与 AIHub 向量检索的关系（很多人混）

```
RAG 检索的两种流派：
向量检索（AIHub 现用）：语义相似——"退货政策"能召回"售后规则"（理解意图）
关键词检索（ES 擅长）：  字面匹配——"退货"精确命中含"退货"的分词
生产级 RAG 常用混合检索：两者各召回 topK → 合并重排（AIHub 的"重排与阈值过滤"预留了位置）
```

ES 核心：**倒排索引**（词 → 文档列表，正排的反向）。分词器（IK 中文分词）决定检索质量；`match`（分词匹配）vs `term`（精确值）是新手第一坑。

## 5. 中间件引入决策表（何时用什么）

| 信号 | 引入 | AIHub 对应 |
|---|---|---|
| 接口里有"发完就该异步做"的步骤 | MQ | 用量上报/审计（现 try-catch 降级） |
| 某流程失败需要重试补偿 | MQ（重试队列）/ outbox | ai_event_outbox 已预演 |
| 多实例互斥/限流协调 | 分布式锁（Redisson） | 单实例暂不需要 |
| 定时任务跨实例重复执行 | XXL-JOB | 暂无定时任务 |
| 全文/语义搜索需求升级 | ES 混合检索 | Redis 向量检索已覆盖 |

## 6. 面试视角速记

| 高频问题 | 一句话回答 |
|---|---|
| MQ 怎么保证不丢消息？ | 生产确认 + 持久化 + 消费手动 ack，三端各管一段 |
| 重复消费怎么办？ | 消费端幂等：唯一键/状态机/去重表 |
| Redis 分布式锁怎么实现？ | SET NX PX + 唯一值 + Lua 释放；生产用 Redisson |
| Redis 为什么快？ | 内存 + 单线程无锁竞争 + IO 多路复用 + 高效结构 |
| ES 为什么快？ | 倒排索引 + 分片并行 |
