# 03 · 架构设计说明书

> 本文是项目最重要的设计文档。所有模块划分、依赖方向、扩展点以本文为准。

---

## 1. 架构原则

| # | 原则 | 说明 |
| --- | --- | --- |
| P1 | **依赖倒置** | 能力接口定义在 `domain`，实现放在 `infra-*`。业务代码只认识接口 |
| P2 | **单向依赖** | 表现层 → 编排层 → 领域层 ← 基础设施层。禁止反向与横向依赖 |
| P3 | **配置驱动** | 模型、知识库、工具、Agent 策略、提示词全部配置化，改配置不改代码 |
| P4 | **租户优先** | 任何数据访问路径都必须携带租户上下文，且由框架强制而非人工约定 |
| P5 | **流式一等公民** | 所有 AI 交互天然按流式设计，非流式只是流式的特例 |
| P6 | **可替换** | 模型 / 向量库 / 工具 / 记忆 / Agent 策略 五处必须可替换 |
| P7 | **可观测内建** | 指标、日志、链路、审计在架构层内建，而非事后补 |

## 2. 分层视图

```
┌──────────────────────────────────────────────────────────┐
│ 表现层  aihub-web                                          │
│ Controller · 鉴权 · 三种 StreamSink(SSE/Chunked/WebSocket) │
└───────────────────────────┬──────────────────────────────┘
                            ↓ 依赖
┌──────────────────────────────────────────────────────────┐
│ 编排层  aihub-application                                  │
│ 用例编排 · 事务边界 · 事件发布 · 配额校验 · DTO 转换        │
└───────────────────────────┬──────────────────────────────┘
                            ↓ 依赖
┌──────────────────────────────────────────────────────────┐
│ 领域层  aihub-domain                                       │
│ 实体 · 值对象 · 全部 SPI 接口 · 领域事件   （零框架依赖）   │
└───────────────────────────▲──────────────────────────────┘
                            │ implements
┌───────────────────────────┴──────────────────────────────┐
│ 基础设施层                                                 │
│ infra-ai（Spring AI 适配）· infra-persistence · infra-security │
└──────────────────────────────────────────────────────────┘
```

**关键点**：`domain` 不依赖任何框架（Spring AI / MyBatis / Redisson 都不依赖），它是纯业务语义的载体。框架适配全部下沉到 `infra-*`。

## 3. 模块划分

| 模块 | 职责 | 关键内容 |
| --- | --- | --- |
| `aihub-parent` | 父 POM，BOM 与版本锁定 | Spring AI BOM、Spring Boot BOM |
| `aihub-common` | 通用支撑 | 统一响应体、错误码、工具类、常量。**不依赖任何业务模块** |
| `aihub-domain` | ★领域层 | 实体、值对象、**全部 SPI 接口**、领域事件 |
| `aihub-application` | 编排层 | 用例服务、事务、事件发布、配额校验、DTO 转换 |
| `aihub-infra-ai` | AI 能力适配 | 模型网关、ChatClient 工厂、Advisor 链、ETL、工具注册、Agent 内核、记忆 |
| `aihub-infra-persistence` | 持久化 | MySQL（MyBatis-Plus）、Redis、文件存储、Flyway 迁移 |
| `aihub-infra-security` | 安全 | 认证、租户解析、权限、脱敏、护栏 |
| `aihub-mcp-service` | MCP 工具实现 | 工具的**业务实现**（对齐课程拆法） |
| `aihub-mcp-sse` | MCP Server（SSE） | 以 SSE 对外提供在线 MCP 服务 |
| `aihub-mcp-stdio` | MCP Server（stdio） | 打包 jar，通过 `java -jar` 进程调用 |
| `aihub-web` | 表现层 | Controller、鉴权拦截器、三种 StreamSink |
| `aihub-bootstrap` | 启动模块 | **唯一** `@SpringBootApplication`，只做装配 |

> MCP 三模块拆法直接照搬课程第三章的工程结构：`service`（业务实现）/ `sse`（在线服务）/ `stdio`（进程服务）。好处是同一套工具可以同时以两种协议对外提供。

### 4.2 ArchUnit 规则（违反即构建失败）

```java
// 1) domain 保持纯净：不得依赖任何框架与上层
noClasses().that().resideInAPackage("..aihub.domain..")
    .should().dependOnClassesThat().resideInAnyPackage(
        "..aihub.application..", "..aihub.web..", "..aihub.infra..",
        "org.springframework.ai..", "com.baomidou..", "org.redisson..")
    .check(classes);

// 2) application 不得依赖 infra 与 web（只认接口）
noClasses().that().resideInAPackage("..aihub.application..")
    .should().dependOnClassesThat().resideInAnyPackage("..aihub.infra..", "..aihub.web..")
    .check(classes);

// 3) web 不得直接触碰 Spring AI 与持久化类型
noClasses().that().resideInAPackage("..aihub.web..")
    .should().dependOnClassesThat().resideInAnyPackage(
        "org.springframework.ai..", "..aihub.infra.ai..", "..aihub.infra.persistence..")
    .check(classes);

// 4) infra 各模块之间禁止横向依赖
noClasses().that().resideInAPackage("..aihub.infra.ai..")
    .should().dependOnClassesThat().resideInAPackage("..aihub.infra.persistence..")
    .check(classes);
```

**收益**：这四条规则把"分层解耦"从口头约定变成**构建期强制**，是本项目架构不腐化的根本保障。

## 5. 核心 SPI（扩展点清单）

所有接口定义在 `aihub-domain`，实现在 `aihub-infra-*`。

### 5.1 模型网关

```java
public interface ModelGateway {
    /** 按场景解析出可用的 ChatModel（含主备降级） */
    ChatModel resolve(ChatScene scene, ModelRoute route);
}

public interface ChatModelResolver {
    boolean supports(String provider);          // openai / volcengine / dashscope / ollama
    ChatModel build(ModelConfig config);
}

public interface ModelSelectionStrategy {
    /** 场景选模：聊天 / 检索 / 嵌入 / Agent规划 可走不同模型 */
    ModelRoute select(TenantId tenantId, AppId appId, ChatScene scene);
}
```
**替换方式**：新增供应商 = 新增一个 `ChatModelResolver` 实现 + 一条 DB 配置，业务代码零改动。

### 5.2 ChatClient 装配

```java
public interface ChatClientFactory {
    /** 纯函数：应用配置 -> ChatClient，结果可缓存 */
    ChatClient create(ChatClientSpec spec);
}

public record ChatClientSpec(
    TenantId tenantId, AppId appId, String systemPrompt,
    ModelRoute route, List<AdvisorFactory> advisors,
    List<ToolCallback> tools, MemoryPolicy memory) {}

public interface AdvisorFactory {
    boolean enabled(ChatClientSpec spec);
    Advisor create(ChatClientSpec spec);
}
```
**注意**：旁路型 Advisor 必须同时实现 `StreamAroundAdvisor`，否则流式场景不生效（见风险 R9）。

### 5.3 检索与向量

### 5.5 Agent 内核（★ 对齐课程 MyManus）

```java
public interface AgentStrategy {
    String code();                                   // react | plan_execute | multi_agent
    AgentResult execute(AgentTask task, AgentContext ctx, StreamSink sink);
}

public interface AgentRegistry {                     // 对应课程 AgentFactory
    Agent lookup(String agentName);
    void register(Agent agent);
}

/** 端上系统状态上下文（课程原文概念） */
public interface AgentContext {
    void put(String key, Object value);
    <T> T get(String key, Class<T> type);
    String snapshot();                               // 供下一轮 Observation 使用
}

/** ReAct 循环：思考 -> 行动 -> 观察，直到 done 或预算耗尽 */
public interface ReActLoop {
    ReActResult run(ReActSpec spec, AgentContext ctx, StreamSink sink);
}

public interface SubTaskChain {
    List<SubTask> decompose(String goal);            // 任务拆解
    void complete(SubTaskId id, String result);      // 结果拼接
}
```

**课程原文的四条约束必须落地**：
1. Thinking 与 Action 来自**同一条 AssistantMessage**（`thinking` 作为固定参数随 ToolCall 一起返回）；
2. Observation **独占一条 UserMessage**，并与最新 `AgentContext` 快照组合触发下一轮；
3. 全程维护**端上系统状态上下文**；
4. 用**固定的 `done` Action** 终止循环并收集最终结果。

## 6. 关键时序

### 6.1 一次流式对话

```
1 前端 → web: POST /api/chat/stream (携带 Token / API Key)
2 web: 鉴权 → 解析 tenantId → 写入 TenantContext（线程/反应式上下文）
3 web → application: ChatCommand
4 application: 配额校验 → 加载应用配置 → 构造 ChatClientSpec
5 application: ChatClientFactory.create(spec)  ← 缓存命中则复用
6 application → infra-ai: 执行 Advisor 链
   记忆Advisor → RAG Advisor（检索并注入上下文）→ 安全护栏 → 审计Advisor
7 infra-ai → 模型: 流式调用
8 逐 token → StreamSink → SSE / Chunked / WebSocket → 前端
9 结束前: 落库消息 + Token 用量 + 审计日志 + 指标上报
```

### 6.2 RAG 入库

```
上传文件 → 落临时存储 → 创建 IngestTask(异步)
→ 文档解析（Tika/PDFBox）→ 文本清洗
→ 分片（策略可配：段落 / 固定字数 / 重叠窗口）
→ 批量 Embedding（走模型网关的 embed 场景）
→ VectorStoreProvider 写入 Redis（metadata 必带 tenant_id / kb_id / doc_id）
→ 回写分片状态与任务状态；失败可重试
```

### 6.3 RAG 检索

```
用户问题 → 查询重写（可选）
→ 意图路由（可选，缩小知识库范围）
→ 向量召回（topK * N）
→ 元数据过滤（强制 tenant_id + kb_id）
→ TenantGuard 逐条校验
→ 重排（可选）→ 相似度阈值过滤
→ 返回命中分片 + 来源引用
```

### 6.4 Agent 执行

```
任务下达 → AgentRegistry 查找入口 Agent（对齐课程 AgentFactory）
→ PlanningAgent 拆解为子任务链
→ 逐个 SubTask 交由专用 Agent（Browser / Table / Chart / HtmlDoc / ...）
→ 每个 Agent 内部走 ReActLoop：
     思考(Thinking) → 行动(ToolCall) → 观察(Observation) → … → done
→ 每步 emit agent.step 事件（WebSocket 推送）
→ 产物经 ArtifactStore 落盘并 emit artifact 事件
→ 结果拼接 → 返回；任一预算超限即终止并返回已得结果
```

### 6.5 MCP 集成

**作为 Client**：配置外部 MCP Server（stdio 走 `npx` 拉起，或 SSE 直连）→ 拉取工具列表 → 转为 `ToolCallback` → 经 `ToolRegistry` 注册 → 挂到 `ChatClient`。

**作为 Server**：`aihub-mcp-service` 定义工具业务 → `aihub-mcp-sse` 以 SSE 暴露 → `aihub-mcp-stdio` 打 jar 供进程调用。

> **课程已踩坑**：外部 SSE 型 MCP 服务必须用**配置类代码方式**集成，仅配 url 不生效；stdio 必须指定 **UTF-8** 编码，否则中文参数乱码。

## 7. 流式三通道设计

### 7.1 统一事件帧

```json
{ "i": 12, "e": "token", "ts": 1757400000000, "data": { "content": "你好" } }
```

| 事件 | 含义 |
| --- | --- |
| `msg.start` | 消息开始，携带 messageId |
| `token` | 增量文本 |
| `tool.start` / `tool.end` | 工具调用开始 / 结束（含名称与参数摘要） |
| `rag.sources` | 检索到的引用来源 |
| `agent.step` | Agent 步骤（思考 / 行动 / 观察） |
| `artifact` | 产物生成完成（含预览地址） |
| `msg.end` | 结束，携带 Token 用量 |
| `error` | 错误（含错误码） |
| `ping` | 心跳保活 |

### 7.2 三种传输

| 通道 | 适用端 | 实现要点 |
| --- | --- | --- |
| **SSE** | H5 | `text/event-stream`；前端用 `fetch + ReadableStream` 解析（**不用 EventSource**，它不能带自定义 Header 且只支持 GET） |
| **NDJSON Chunked** | 微信小程序 | `application/x-ndjson`；`uni.request({ enableChunked: true, responseType: 'arraybuffer' })` + `onChunkReceived`，客户端维护 buffer 按 `\n` 切分处理半包 |
| **WebSocket** | Agent 长任务 | 双向通信，支持中断；对齐课程 MyManus 的做法 |

**服务端硬性要求**（小程序场景尤其关键）：
- `Content-Encoding: identity`（**禁止 gzip**，否则分块被压缩后无法按行切分）
- `X-Accel-Buffering: no`、`Cache-Control: no-transform`
- Nginx 需 `proxy_buffering off`

## 8. 多租户隔离设计

### 8.1 总体策略

**逻辑隔离**：所有业务表带 `tenant_id`，所有查询强制带上租户条件。

### 8.2 四道防线（★ 最高危项）

| # | 防线 | 说明 |
| --- | --- | --- |
| 1 | **入口收敛** | 业务代码禁止注入 `VectorStore`，唯一入口是 `KnowledgeRetriever` |
| 2 | **强制注入** | Provider 内部对每次检索**强制 AND 注入 `tenant_id`** 过滤条件，调用方无法绕过 |
| 3 | **出口校验** | 返回后 `TenantGuard` 逐条校验 metadata 中的租户，不匹配即丢弃并告警 |
| 4 | **来源可信** | `tenantId` 只从 JWT / API Key 解析，**绝不接受前端传参**；MyBatis 拦截器兜底补全查询条件 |

必须有**跨租户自动化测试**（A 租户检索不得命中 B 租户数据）作为回归保障。

### 8.3 向量索引的租户方案

Redis（RediSearch）约束：向量 `DIM` 建索引后不可改；混合过滤过严会召回不足；向量常驻内存。

- **默认**：共享索引 + `tenant_id` 作为 **TAG 字段强制过滤**
- **大租户**：可选独立索引（每个租户一个 index），由 `VectorStoreProvider` 透明切换

### 8.4 零停机重建索引

索引名带版本号 `v{n}` + 使用 Redis 索引别名（`FT.ALIASADD` / `FT.ALIASUPDATE`）。
更换 Embedding 模型流程：**建 v2 → 双写 → 回灌历史数据 → 切别名 → 删除 v1**。

## 9. 部署视图

> 已升级为微服务形态：**AI 能力内聚为单个服务**，避免知识入库 / 流式输出 / Agent 长任务跨服务。
> 服务边界、Nacos 与 Sentinel 用法详见 **07-微服务与中间件设计.md**。

```
                         ┌────────────────────────┐
    H5  ────────────────▶│  aihub-gateway  :8080  │  Sentinel 限流 + 鉴权 + 路由
    微信小程序 ─────────▶└───────┬────────┬───────┘
    (uniapp 多端)                │        │
                    ┌────────────▼───┐ ┌──▼──────────────────────┐
                    │ platform       │ │ ai-service       :8082  │
                    │ service  :8081 │ │ 模型网关/RAG/工具/MCP    │
                    │ 租户/登录/配额  │ │ Agent/会话/产物  （内聚） │
                    └────────┬───────┘ └────────┬────────────────┘
                             │                  │
              ┌──────────────▼──────────────────▼─────────────────┐
              │ Nacos :8848   MySQL :3306   Redis Stack :6379      │
              │ Sentinel Dashboard :8858    本地文件 / OSS（产物）   │
              └────────────────────────────────────────────────────┘
                                  │
                                  ├──▶ 外部大模型 API（火山方舟 / 通义 / OpenAI / Ollama）
                                  └──▶ 外部 MCP Server（stdio 子进程 或 SSE）
```

- 本地 `docker compose` 一键拉起：MySQL 8 + Redis Stack + Nacos + Sentinel Dashboard
- 无状态设计：会话与记忆外置到 Redis / MySQL，两个服务均可水平扩展
- 流式接口只在 `gateway → ai-service` 直连链路上，**禁止二次转发**
