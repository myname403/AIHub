## 0. 全局蓝图：谁在跑、跑在哪、怎么连

先给一张全景 ASCII 图，把"容器里的中间件"与"宿主机上的 Java 服务"分开画——这是理解本文一切配置的基础：

```text
┌─────────────────────────── 浏览器 / 手机 ───────────────────────────┐
│   管理端 aihub-admin-ui (dev 端口 8849)     用户端 aihub-app (H5)     │
│   开发期把 /auth /api 代理到 → 8080          baseUrl 直连 8080         │
└──────────────────────────────────┬──────────────────────────────────┘
                                   │ HTTP
                        ┌──────────▼──────────┐
                        │  aihub-gateway :8080 │  ← 宿主机 Java 进程
                        └──────┬────────┬──────┘
              lb://aihub-      │        │      lb://aihub-
              platform-service │        │      ai-service
              ┌────────────────▼──┐  ┌──▼─────────────────┐
              │ platform :8081     │  │ ai-service :8082   │  ← 宿主机 Java 进程
              │ (认证/RBAC/配额/租户)│  │ (知识库/RAG/Agent)  │
              └──┬───────┬────┬───┘  └──┬───────┬─────────┘
                 │ JDBC  │    │         │ JDBC  │ Redis 协议
┌────────────────▼───────┼────▼─────────▼───────┼─────────────────────┐
│  Docker Compose 基础设施 │                      │                     │
│  ┌──────────────┐ ┌────▼──────────┐ ┌─────────▼──────────────────┐  │
│  │ mysql :3307   │ │ nacos :8848   │ │ redis-stack :6379          │  │
│  │ (3306→3307)   │ │ 9848/9849 gRPC│ │ 含 Redis Query Engine 模块  │  │
│  └──────────────┘ └───────────────┘ └────────────────────────────┘  │
│  ┌──────────────┐ ┌───────────────┐ ┌────────────────────────────┐  │
│  │sentinel:8858 │ │prometheus:9090│ │ grafana :3000              │  │
│  └──────────────┘ └───────────────┘ └────────────────────────────┘  │
└──────────────────────────────────────────────────────────────────────┘
```

一个刻意的设计决策：**Java 服务全部跑在宿主机，Docker 只承载基础设施**。这样做的理由：

- 本地开发改代码后重启快（IDE 直接跑 main 或 `java -jar`），不用每次构建镜像；
- 断点调试、日志文件（`aihub/logs/` 下的 `gateway.log`/`platform.log`/`ai.log`）都留在本机，排查方便；
- 代价是 Prometheus 抓取目标不能写 compose 服务名，必须写 `host.docker.internal`（见第 6 节）。

对应的部署形态：`aihub/start-services.bat` 用三个最小化窗口拉起 gateway/platform/ai 三个 jar；`aihub-admin-ui` 有生产用 `aihub-admin-ui/Dockerfile`（构建产物由 nginx 托管，模板见 `aihub-admin-ui/deploy/nginx/default.conf.template`）。

## 1. docker-compose 全景

来源文件：`aihub/docker-compose.yml`（version: "3.8"）。文件头注释明确了版本对齐红线：

> Spring Boot 3.5.x → Spring Cloud 2025.0.x → Spring Cloud Alibaba 2025.0.0.0；Nacos 3.0.3 / Sentinel 1.8.9。

### 1.2 启动顺序：为什么 compose 里几乎不写 depends_on

六个服务之间只有一条真实依赖：grafana 依赖 prometheus（仅保证启动顺序，数据源本身靠 provisioning 自动装配）。其余服务互相**不写 depends_on**，这是有意的：

- MySQL/Redis/Nacos 各自带健康检查，Java 服务不通过 compose 拉起，自然不需要 `depends_on: condition: service_healthy`；
- 真正的启动顺序约束转移到了**操作手册**里（第 7 节）：先 `docker compose up -d` → 等 `docker compose ps` 全部 healthy → 再跑 `start-services.bat`。这是"脚本化顺序"替代"编排声明顺序"的取舍——本地开发场景更直观、可控。

### 1.3 逐个说清"为什么是这个配置"

**MySQL 为什么映射 3307 而不是 3306？**
本机很可能已装了原生 MySQL 占着 3306（Windows 上极常见）。compose 用 `3307:3306` 避开宿主机端口冲突，所以两个服务的 JDBC URL 默认端口都是 3307：

```yaml
# aihub/aihub-platform-service/src/main/resources/application.yml #8
url: jdbc:mysql://${MYSQL_HOST:127.0.0.1}:${MYSQL_PORT:3307}/${MYSQL_DB:aihub_platform}...
# aihub/aihub-ai-service/src/main/resources/application.yml #14
url: jdbc:mysql://${MYSQL_HOST:127.0.0.1}:${MYSQL_PORT:3307}/${MYSQL_DB_AI:aihub_ai}...
```

全部走环境变量占位符（`MYSQL_HOST/PORT/DB/USER/PASSWORD`），本地默认值直接可用，生产用环境变量覆盖，符合"默认能跑、上线改配"的原则。

**Redis 为什么必须是 redis-stack？**
普通 Redis 没有向量检索能力。compose 第 36 行注释写得直白："★ 必须是 redis-stack：普通 Redis 没有向量检索能力"，而且健康检查不是 ping 端口，而是 `redis-cli MODULE LIST | grep -q search`——**断言 Redis Query Engine（search）模块真的在**。缺了模块容器就不算 healthy，下游 RAG 功能直接失去意义，这个健康检查设计把"能启动"升级成"能力可用"。

**Nacos 为什么暴露三个端口？**
Nacos 2.x 起客户端长连接走 gRPC：`9848 = 8848 + 1000`（客户端偏移）、`9849 = 9848 + 1`（服务端间同步）。服务注册、配置拉取走的是 gRPC 长连接而不是 HTTP，只开 8848 会导致"控制台能打开、服务注册不上"这种经典故障。

**Sentinel 控制台为什么换镜像源 + 加账号密码？**
compose 第 79 行注释：bladex 原镜像拉取不到，走 `docker.1ms.run` 镜像代理；旧镜像默认账号 sentinel/sentinel，此处显式设置 `AUTH_USERNAME/AUTH_PASSWORD` 固定下来。Sentinel 控制台本身**不持久化规则**（重启即丢），所以规则真正存在 Nacos 里，控制台只是观察台——见 6.3 节。

**Prometheus 的 extra_hosts 是关键一笔：**

```yaml
# aihub/docker-compose.yml #105-107
extra_hosts:
  # Java 服务跑宿主机，Prometheus 用 host.docker.internal 抓取（Linux 也生效）
  - "host.docker.internal:host-gateway"
```

容器内默认无法访问宿主机端口，`host-gateway` 把 `host.docker.internal` 解析到宿主机网桥，抓取目标才能写成 `host.docker.internal:8080/8081/8082/8090`（来源：`aihub/monitoring/prometheus.yml`）。

### 1.4 compose 与 Java 服务之间的连接关系表

| Java 服务 | 连接的中间件 | 连接配置位置 |
|---|---|---|
| aihub-gateway (8080) | Nacos（注册+配置+Sentinel 规则源）、Sentinel 控制台 | `aihub/aihub-gateway/src/main/resources/application.yml` #10-63 |
| aihub-platform-service (8081) | MySQL `aihub_platform`、Nacos、Sentinel | `aihub/aihub-platform-service/src/main/resources/application.yml` #7-50 |

## 2. Nacos 3.0.3 鉴权专题（本项目真实踩坑）

这是本项目近期真实踩过并修复的问题（背景事实清单第 1 条）。**现象、根因、修复三段完整还原**，所有配置都来自当前仓库文件。

### 2.1 为什么默认开鉴权

先回答"是什么"：`NACOS_AUTH_ENABLE: "true"`（`aihub/docker-compose.yml` #69）让 Nacos 对**所有接口**启用鉴权——包括服务注册（gRPC）、配置拉取、以及 OpenAPI。没有合法身份的客户端请求一律 403。

再回答"为什么"：Nacos 2.x/3.x 历史上多次出现"未授权访问漏洞"通报（未开鉴权的 Nacos 可被任意读取配置、注册恶意服务），3.x 更是把鉴权相关变量变成了**显式必配项**。AIHub 作为多租户 AI 平台，配置中心里存着模型 API Key 等敏感配置（`ai_model.api_key_enc` 落库前已加密，但 Nacos 里还有 `spring.ai.openai.api-key` 这类明文键），裸奔不可接受，所以本地开发环境就按生产姿势开鉴权。

### 2.2 开了鉴权之后，客户端为什么 403

故障链条是这样的（每一步都是当时真实发生的）：

1. compose 打开 `NACOS_AUTH_ENABLE=true` 后启动，客户端（Spring Cloud Alibaba Nacos Discovery/Config）开始连 8848/9848；
2. 客户端带着用户名/密码去登录换取 accessToken——但 **Nacos 3.x 不再提供默认账号密码**（2.x 时代默认 nacos/nacos，3.x 出于安全取消了），控制台首次访问也强制要求初始化管理员；
3. 于是登录接口直接返回 403，客户端注册/拉配置全部失败，服务启动报 Nacos 相关异常，日志里表现为一堆 403/连接失败；
4. 反过来，如果把客户端的账号密码配上但**管理员从未初始化**，结果一样是 403——因为账号根本不存在。

一句话总结根因：**开鉴权 = 服务端要验票，3.x 既不默认发账号，也不允许匿名初始化，必须先用运维通道把管理员建出来，再让客户端持有同一套账号密码。**

### 2.3 初始化管理员：那条真实的 curl

修复第一步，进入容器调用 Nacos v3 的管理员初始化接口（**仅当管理员不存在时可调用一次**）：

```bash
# 来源：aihub/docker-compose.yml #67（compose 内注释即官方操作指引）
docker exec aihub-nacos curl -s -X POST 'http://127.0.0.1:8848/nacos/v3/auth/user/admin' -d 'password=Nacos@aihub123'
```

三个细节必须讲清楚：

- **为什么 curl 在容器里执行**：8848 虽映射到了宿主机，但在容器内 `127.0.0.1:8848` 一定可达，不受宿主机防火墙/端口占用影响，是最稳的执行环境；
- **`/nacos/v3/auth/user/admin` 是 3.x 专属接口**：POST 一个 `password`，创建内置管理员 `nacos`。接口有幂等保护——管理员已存在时再调用会失败，这是刻意的（防止攻击者重置管理员密码）；
- **密码 `Nacos@aihub123` 不是随便定的**：它就是随后所有客户端配置里写的密码，两边必须一字不差（compose 注释原话："凭据需与 aihub-common.yml 的 spring.cloud.nacos 账号一致"）。

验证初始化成功的方式：浏览器开 `http://127.0.0.1:8848/nacos`，用 `nacos / Nacos@aihub123` 能登录控制台，即管理员通道打通。

### 2.4 客户端账号密码配置：四个文件，一个约定

管理员建好后，所有需要连 Nacos 的客户端都要配上用户名密码。本项目三个 Java 服务 + Sentinel 规则数据源共四处，写法完全一致：

```yaml
# aihub/aihub-platform-service/src/main/resources/application.yml #17-29
cloud:
  nacos:
    # 本地开发默认账号（Nacos 3.x 开启了鉴权）。生产环境用环境变量覆盖，不要提交真实密码
    username: ${NACOS_USERNAME:nacos}
    password: ${NACOS_PASSWORD:Nacos@aihub123}
    discovery:
      server-addr: ${NACOS_ADDR:127.0.0.1:8848}
      namespace: ${NACOS_NAMESPACE:public}
      group: ${NACOS_GROUP:DEFAULT_GROUP}
    config:
      server-addr: ${NACOS_ADDR:127.0.0.1:8848}
      namespace: ${NACOS_NAMESPACE:public}
      group: ${NACOS_GROUP:DEFAULT_GROUP}
      file-extension: yaml
```

其余三处（用户名/密码键位相同，不再重复贴全文）：

| 位置 | 键路径 | 作用 |
|---|---|---|
| `aihub/aihub-ai-service/src/main/resources/application.yml` #28-40 | `spring.cloud.nacos.username/password` | ai 服务注册与配置 |
| `aihub/aihub-gateway/src/main/resources/application.yml` #10-22 | `spring.cloud.nacos.username/password` | 网关注册与配置 |
| `aihub/aihub-platform-service/src/main/resources/application.yml` #36-45（ai 服务 #48-57 同理） | `spring.cloud.sentinel.datasource.flow.nacos.username/password` | **Sentinel 规则源也在 Nacos 里**，拉规则同样要过鉴权，必须单独再配一份账号密码 |

注意最后一行这个最容易漏的坑：很多人以为"配了 `spring.cloud.nacos` 就全通了"，但 Sentinel 的 Nacos 数据源（`spring.cloud.sentinel.datasource.*.nacos.*`）是独立的客户端配置，账号密码要**再写一遍**。本项目三个服务的规则 data-id 分别是 `aihub-gateway-flow-rules`、`aihub-platform-service-flow-rules`、`aihub-ai-service-flow-rules`（+ `aihub-ai-service-degrade-rules`），样例文件在 `aihub/docs/nacos/` 目录。

### 2.5 版本升级 breaking changes 的教训

把这次踩坑沉淀成通用教训（面试可直接引用）：

1. **中间件大版本升级 = 协议级变更，不只是镜像 tag 变了**。Nacos 2.x→3.x 同时动了三件事：默认账号取消、鉴权变量必配（`NACOS_AUTH_TOKEN`/`NACOS_AUTH_IDENTITY_KEY`/`NACOS_AUTH_IDENTITY_VALUE`，见 compose #63-65）、OpenAPI 从 `/nacos/v1`、`/nacos/v2` 演进到 `/nacos/v3`。任何一件事没对齐都是启动失败；
2. **"服务端升级"要和"客户端配置"成对出现**。开鉴权那一刻起，所有客户端（包括你以为不算客户端的 Sentinel 数据源）都要补身份，漏一处 403 一处；
3. **初始化动作要写进部署脚本/注释里**。管理员初始化是一次性动作，最怕"换台机器重新 compose up 后忘了做"。本项目把它写在 compose 的环境变量注释里（#66-68），谁拉起环境谁就能看到；
4. **健康检查要能区分"进程活着"和"功能可用"**。Nacos 的健康检查用的是 `curl index.html`（控制台可访问），配合客户端注册成功才能算环境就绪。

## 3. MySQL 初始化与库表划分

### 3.1 init.sql 的执行时机（只此一次）

来源：`aihub/docker/mysql/init.sql`，全文只有两行 DDL：

```sql
-- 容器首次启动时执行：创建两个服务的独立库（服务间禁止跨库 JOIN）
CREATE DATABASE IF NOT EXISTS aihub_platform DEFAULT CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;
CREATE DATABASE IF NOT EXISTS aihub_ai       DEFAULT CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;
```

执行时机规则（MySQL 官方镜像的约定，必须理解否则会踩坑）：

- 挂载在 `/docker-entrypoint-initdb.d/` 下的脚本**只在数据目录为空时执行一次**，即首次 `docker compose up` 建卷的那一刻；
- 之后重启容器、甚至 `docker compose down`（只要不删 `mysql-data` 卷）都不会再执行——想重放初始化必须 `docker compose down -v` 删卷；
- 所以它只适合放"建库级"语句。**所有建表/种子数据都不在这里**，而是由 Flyway 在 Java 服务首次启动时执行（下一节），职责边界：init.sql 管库，Flyway 管表和数据。

### 3.2 双库划分：每个微服务独占一个 schema

| 库 | 归属服务 | JDBC 配置 |
|---|---|---|
| `aihub_platform` | aihub-platform-service (8081) | `aihub/aihub-platform-service/src/main/resources/application.yml` #8 |
| `aihub_ai` | aihub-ai-service (8082) | `aihub/aihub-ai-service/src/main/resources/application.yml` #14 |

## 4. Flyway 版本化迁移

两个服务的配置完全一致：

```yaml
# aihub/aihub-platform-service/src/main/resources/application.yml #12-15
flyway:
  enabled: true
  baseline-on-migrate: true
  locations: classpath:db/migration
```

### 4.1 机制四件事：checksum / baseline / 顺序 / 为什么不能改历史

1. **执行时机**：服务启动时，Flyway 连上各自的库，比对 `flyway_schema_history` 表与 classpath 下 `db/migration/V*.sql`，把没执行过的版本按号升序依次执行，全部成功后应用才继续启动；
2. **checksum 防篡改**：每个已执行脚本的 checksum 记录在 `flyway_schema_history`。若你回头修改了已执行的 V1，启动时 checksum 对不上，Flyway 直接报错拒绝启动——**这不是麻烦，是保护**：生产库里表结构已经按旧 V1 建好了，你改的脚本不会重放，"代码里的 V1"和"库里的表结构"从此对不上，一切诡异问题由此而生。正确做法永远是**追加新版本号**（V10、V11……）；
3. **baseline-on-migrate 的意义**：首次对**已存在表结构**的库启用 Flyway 时（比如库是手工建的、或从旧项目迁来），不加 baseline 会因"非空 schema 没有 baseline"拒绝执行。`baseline-on-migrate: true` 会自动打一个 baseline 标记，从那之后的 V* 才开始生效。本项目两个库都是"空库 + 全量 V1 起步"，此开关属于保险丝；
4. **版本号可以不连续**：platform 库就没有 V2、V3（规划中的迁移拆分后未落盘），Flyway 只要求"已应用的版本不缺、不重、checksum 不变"，V1→V4 跳号完全合法。

### 4.3 案例A：V10__fix_admin_seed_password.sql——BCrypt 哈希与注释不符

文件：`aihub/aihub-platform-service/src/main/resources/db/migration/V10__fix_admin_seed_password.sql`（全文 10 行）

**现象**：按一切文档/注释的指引，用 `admin / admin123` 登录，必然报"用户名或密码错误"。

**根因**：V1 里种子的哈希贴错了。看 V1 的两段代码（`aihub/aihub-platform-service/src/main/resources/db/migration/V1__init_platform.sql`）：

```sql
#118 行注释：-- 初始化演示租户与用户（密码： admin123）
#123 行数据：
INSERT INTO sys_user (id, tenant_id, username, password_hash, nickname, status)
VALUES (1, 1001, 'admin', '$2a$10$N.zmdr9k7uOCQb376NoUnuTJ8iAt6Z5EHsM8lE9lBOsl7iKTVKIUi', '管理员', 1)
    ON DUPLICATE KEY UPDATE nickname = VALUES(nickname);
```

注释说 admin123，但这一串 BCrypt 哈希实际对应的是 `123456`（生成脚本贴错哈希）。**BCrypt 是单向哈希、无法反解**——这既是事故难发现的原因（谁也没法"看一眼哈希"发现问题），也决定了验证思路（对拍，见下）。此处这个哈希值正是 BCrypt 的经典示例串，各路教程里常用来演示 `123456` 的加密结果，被复制粘贴时带进来了。

**为什么修 V10 而不是改 V1**：V1 已经在（所有）库里执行过，改动它 = checksum 变化 = Flyway 拒绝启动（4.1 节第 2 条）。V10 文件头注释写得明明白白：

```sql
-- 处理：不动 V1（Flyway 校验已应用脚本的 checksum，改历史脚本会导致启动失败），
--       用本增量迁移把 admin 的哈希更新为 admin123 的正确 BCrypt 值。
UPDATE sys_user
SET password_hash = '$2a$10$4a6Yl4qwbtuOs8vD5j0yZ.lgnSSeh1jKyROA116dG366EUc7Bf5gG'
WHERE id = 1 AND username = 'admin';
```

**对拍验证法（BCrypt 事故的标准验证手段）**：无法反解哈希，就用"同算法对拍"——写个最小程序，用同一个 BCrypt 实现分别 `encode("admin123")` 与 `matches("admin123", 旧哈希)`、`matches("123456", 旧哈希)`，两个布尔值一对照，旧哈希对应哪个密码水落石出；再对新哈希做同样验证。仓库里留有这次对拍的现场：`.tmpcheck/BcryptCheck.java`（及其编译产物 `.class`）。平台侧登录校验用的是 Spring Security 的 `BCryptPasswordEncoder.matches`，与此对拍实现同族，结论等价。

**教训**：
1. 种子数据的**注释不是契约，行为才是**——密码类种子必须在 CI 或本地做一次"真能登录"的冒烟验证；
2. 生成脚本与 SQL 文件之间的人工复制粘贴是事故高发环节，能脚本化就不要手贴；
3. 出了错也不许改历史迁移，修复必须是**新版本增量迁移**，这就是版本化迁移体系的自愈方式。

### 4.4 案例B：V10__kb_add_create_time.sql——DO 有字段、表没列

文件：`aihub/aihub-ai-service/src/main/resources/db/migration/V10__kb_add_create_time.sql`（引入于修复提交 `43a7333`，当前工作区状态见 4.2 红框说明；内容 7 行）

**现象**：知识库相关接口（知识库列表 `GET /api/ai/kb`、新建知识库）全部 500，日志报 MySQL `Unknown column 'create_time' in 'field list'`。

**根因**：DO 与 DDL 不一致，两边各自都"对"：

- **表侧**：V1 建 `ai_knowledge_base` 时遗漏了 `create_time` 列（对照 `aihub/aihub-ai-service/src/main/resources/db/migration/V1__init_ai.sql` #58-69，该表只有 id/tenant_id/name/embedding_model_id/vector_dim/index_name/status/deleted）；
- **DO 侧**：`aihub/aihub-ai-service/src/main/java/com/aihub/ai/infra/persistence/dataobject/AiKnowledgeBaseDO.java` #32 声明了 `private LocalDateTime createTime;`；
- **写入侧**：`aihub/aihub-ai-service/src/main/java/com/aihub/ai/infra/persistence/DbKnowledgeBaseRepository.java` 的 `create()`（#24 起）显式给 DO 的 createTime 赋值后 insert——MyBatis-Plus 会把 DO 全字段映射成 INSERT 列清单，表里没有 `create_time` 列，SQL 直接报 Unknown column。

于是出现一个隐蔽现象：**SELECT（`select *`）时列少无所谓，一旦 INSERT/显式 SELECT 就炸**，而且只炸知识库这一个实体，其他表都有 create_time，问题不易第一眼定位。

**修复**（V10 原文，与 43a7333 提交内容一致）：

```sql
-- 修复 ai_knowledge_base 表缺失 create_time 列的问题。
-- 背景：V1 建表时遗漏 create_time，而 AiKnowledgeBaseDO 含 createTime 字段
--       （DbKnowledgeBaseRepository.create() 还会显式写入），导致知识库列表
--       （GET /api/ai/kb）与新建知识库接口全部因
--       "Unknown column 'create_time' in 'field list'" 报 500。
ALTER TABLE ai_knowledge_base
    ADD COLUMN create_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP AFTER deleted;
```

仍是增量迁移思路：不动 V1，用 ALTER 补列，`DEFAULT CURRENT_TIMESTAMP` 与其他表的结构约定对齐，存量行自动填当前时间。

**同源案例（platform 库的同款问题）**：`aihub/aihub-platform-service/src/main/resources/db/migration/V8__fix_user_role_addtime.sql` 是一模一样的剧本——`sys_user_role` 在 V1 建表没建 create_time，本期启用该表后 DO 的 createTime 让查询报同样的 Unknown column，V8 补列。同一个坑在两个库里各踩了一次，说明这不是运气问题而是**流程缺口**。

**教训（这一节是面试的黄金素材）**：
1. **DO 与 DDL 的一致性要有机械保证**：靠人眼 review 迟必漏。可落地的手段：集成测试连真实 MySQL 跑一遍全表 CRUD（本项目自动化以 Mockito 单测为主、覆盖不到真实 SQL，两个迁移注释里都自我检讨过这一点）；或引入 DO↔DDL 比对的架构测试；
2. **建表脚手架要模板化**：所有表统一带 create_time/update_time/deleted/tenant_id，新表从模板复制而不是手敲列清单；
3. **修复一律走增量迁移**，同时警惕 `select *` 给人的假安全感（本案例中"列表页能打开"与"新建必炸"并存，正是查询写法差异造成的错觉）。

### 4.5 常见误用与排障速查

- **误用一**：改了已执行的 V 脚本想"反正本地库，重跑就行" → checksum 报错。正确做法：还原脚本；确要重置环境用 `docker compose down -v` 删卷重来；
- **误用二**：把种子数据写进 `aihub/docker/mysql/init.sql` → 只有首次建卷执行，服务端 Flyway 不认识它，两套来源必漂移。init.sql 只放建库语句；
- **排障**：服务启动卡在 SQL 异常，先看 `flyway_schema_history` 表的 success 字段与 checksum，再比对 classpath 下的脚本；
- **排障**：`Unknown column 'xxx' in 'field list'` 十有八九是 DO 有字段表没列（或迁移没跑到），先 `SHOW CREATE TABLE` 对齐 DO。

## 5. Redis 三重角色（缓存 / 验证码 / 向量检索——含"真实边界"）

本节标题呼应任务清单，但**以代码事实为准**，把"理想中的三重角色"与"代码里的真实状态"都讲透——这本身就是好素材：知道哪些能力做了、哪些留了口子，比背概念更有价值。

### 5.1 角色一：Redis Stack 向量检索（已落地，RAG 的地基）

**为什么需要它**：RAG 要把问题与文档分片都变成向量，再按相似度找 topK。向量之间的相似度检索需要专门的索引结构（Redis Stack 的 Redis Query Engine 提供 HNSW/FLAT 向量索引），普通 Redis 只是个 KV 存储，算不了向量相似度——这就是 compose 坚持用 redis-stack-server 镜像、健康检查断言 search 模块的原因（1.3 节）。

**装配核心**（`aihub/aihub-ai-service/src/main/java/com/aihub/ai/config/VectorStoreConfig.java`）：

```java
#58-84 行（节选）：
@Bean
public VectorStore vectorStore(EmbeddingModel embeddingModel, ...) {
    return RedisVectorStore.builder(new redis.clients.jedis.JedisPooled(uri), embeddingModel)
            .indexName(indexName)      // 默认 spring-ai-index，见下
            .prefix(prefix)            // 默认 embedding:
            .metadataFields(
                    RedisVectorStore.MetadataField.tag("tenant_id"),
                    RedisVectorStore.MetadataField.tag("kb_id"),
                    RedisVectorStore.MetadataField.tag("doc_id"))
            .initializeSchema(initializeSchema)
            .build();
}
```

四个要点：

1. **indexName**：向量索引名，配置键 `spring.ai.vectorstore.redis.index-name`（`aihub/aihub-ai-service/src/main/resources/application.yml` #78-80，默认 `spring-ai-index`，前缀 `embedding:`，`initialize-schema: false`）。业务侧另有更细的索引名约定——`ai_knowledge_base.index_name` 列注释"Redis 索引名(带 v{n} 版本)"（`V1__init_ai.sql` #64），代码里建库时按租户生成：`"aihub:kb:" + tenantId`（`aihub/aihub-ai-service/src/main/java/com/aihub/ai/application/KnowledgeAppService.java` #116）。索引名带版本号是为了**零停机重建索引**（换嵌入模型/改维度时建 v2 新索引、切别名、弃 v1）；
2. **vectorDim（维度强校验）**：`ai_knowledge_base.vector_dim` 与 `ai_model.vector_dim` 两列都带"强校验"注释（`V1__init_ai.sql` #39/#63），DO 注释进一步写明"vector_dim 必须与所选 Embedding 模型维度一致（强校验，建索引后不可改）"（`AiKnowledgeBaseDO.java` #13）。管理端请求里的默认值 1536（`aihub/aihub-ai-service/src/main/java/com/aihub/ai/web/KnowledgeController.java` #113，注释"须与模型一致（如 1536 / 1024）"）。**为什么必须一致**：Redis 向量索引建索引时就固定了向量维度（HNSW 索引的 DIM 参数），写入维度不符的向量直接报错；而且不同模型的嵌入空间互不兼容——1536 维的问题向量去和 768 维的文档向量算余弦相似度，数学上无意义。本项目当前嵌入模型是本机 Ollama 的 `embeddinggemma`（768 维，`VectorStoreConfig.java` #28-29 注释），显式装配是为了避免 Spring AI 默认装配去连 api.openai.com 导致离线时**无限阻塞**（种子的"绑定过知识库的应用 9001 所有对话卡死在思考中"——这也是一次真实修复）；
3. **tenant_id/kb_id/doc_id 建成 TAG 字段**：检索时以 TAG 过滤强制限定租户与库，这是租户隔离在向量层的防线（`VectorStoreConfig.java` #21 注释："租户隔离防线之二"）——没有它，A 租户的对话可能检索到 B 租户的文档分片；
4. **一次真实的"静默失效"修复**：`VectorStoreConfig.java` #66-69 注释记录——早期版本 `initializeSchema` 参数被硬编码为 true，配置文件里写 `initialize-schema: false` 完全不生效（"配置项存在但形同虚设"）。修复后配置真正被读取。教训：加了配置项必须让配置真的流到使用点，否则排查时会被"我明明配了"误导半天。

**常见误用**：本地起了普通 redis 而不是 redis-stack（比如用 systemd 里的 redis-server），服务能连上、健康检查过了（如果健康检查只写 ping），一到向量检索就报 unknown command——所以健康检查要断言模块，别断言端口。

### 5.2 角色二：验证码缓存——真实状态是 Caffeine，不是 Redis

计划背景里曾把验证码归给 Redis，但代码事实是**本地缓存**。`aihub/aihub-platform-service/src/main/java/com/aihub/platform/auth/service/CaptchaService.java`：

```java
#22-23 行注释：
 * 为什么存 Caffeine 本地缓存而不是 Redis：验证码是短命数据且单机部署够用，
 * 不引入跨服务依赖；多实例部署时需换 Redis（学习取舍点，见学习文档 07）。
#38-42 行实现：
private final Cache<String, String> captchaCache = Caffeine.newBuilder()
        .expireAfterWrite(Duration.ofMinutes(2))
        .maximumSize(10_000)
        .build();
```

工作流（类注释 #16-20）：前端 `GET /auth/captcha` → 后端生成图片 + 唯一 ID，答案存缓存 2 分钟 → 提交时带 id+答案 → 比对（`verify` 用 `remove` 取出，**一次性、防重放**，#68）。同类取舍也出现在 `PermissionService.java`（#37/#96：菜单权限缓存单机 Caffeine，生产可换 Redis）。

**为什么这是合理设计而不是偷懒**：验证码是秒级生命周期的短命数据，引入 Redis 等于为一个 2 分钟 TTL 的 KV 加一个网络往返与一个故障依赖；单机部署下 Caffeine 进程内读写快几个数量级。**什么时候必须换 Redis**：多实例负载均衡——验证码生成在实例 A、校验请求落到实例 B，本地缓存就查无此码了。这是一个教科书级的"按部署形态选缓存"案例。

### 5.3 角色三：缓存加速与兜底预留（API Key 缓存同样是 Caffeine）

网关侧的 API Key 校验结果缓存也是本地 Caffeine（`aihub/aihub-gateway/src/main/java/com/aihub/gateway/apikey/ApiKeyCache.java`）：AsyncCache、TTL 60 秒、上限 1 万条（配置在 `aihub/aihub-gateway/src/main/resources/application.yml` #86-90）。类注释 #17-31 讲透了两个设计点：

- 60 秒是"延迟"与"Key 吊销及时性"的平衡——Key 被禁用后最多再放行 60 秒；
- **不缓存失败结果**：否则平台服务抖动时，"校验失败"会在 60 秒内被放大成全量请求误拒（负缓存放大故障）。

另外两处 Redis 的"预留位"（写在注释/配置里但当前未启用）：

- 配额计数：`AiQuotaUsageMapper.java` #16 注释"生产高并发场景可替换为 Redis 计数 + 定时回写"——当前用量累加走数据库；
- 多租户 SQL 兜底开关（`aihub.tenant.sql-guard.enabled`，默认 false，`application.yml` #70-78）：与 Redis 无关但同属"预留位"，文档与配置的对应关系要看注释而不是想当然。

**本节小结（面试可背的版本）**：AIHub 里 Redis 的**生产性角色只有一个——Redis Stack 承担 RAG 向量检索**（JedisPooled + RedisVectorStore，indexName/prefix/TAG 元数据/维度强校验）；验证码与权限缓存用 Caffeine（单机够用、少一个依赖），API Key 校验缓存用 Caffeine（60s TTL 平衡延迟与吊销）；Redis 计数、多实例缓存共享都是注释中写明的演进方向。**技术选型不是堆名词，是按数据生命周期与部署形态做匹配。**

## 8. 本章面试三问与参考回答

**Q1：你们的数据库迁移为什么选 Flyway？如果上线后发现某个已执行的迁移脚本写错了怎么办？**

参考回答：选 Flyway 因为它是"SQL 即真相"——迁移文件就是普通 SQL，进 git、可 review、数据库结构与代码同版本演进；服务启动时自动比对 `flyway_schema_history` 增量执行，多环境不会漂。发现写错**绝不改历史脚本**：Flyway 记录了每个脚本的 checksum，改历史必然启动失败，这保护的是"代码里的结构"与"库里的结构"永远一致。正确做法是追加一个新版本迁移做修正。我们项目就有两个真实案例：一个是种子管理员密码的 BCrypt 哈希贴错（注释写 admin123 实际对应 123456，BCrypt 无法反解、用同算法对拍程序验证后，V10 增量 UPDATE 修正哈希）；另一个是建表漏列（ai_knowledge_base 漏 create_time 而 DO 有该字段，INSERT 必炸 Unknown column，V10 用 ALTER ADD COLUMN 补齐）。两个修复都遵守"只追加、不回改"，所以任何环境的库都能安全升级。

**Q2：为什么本地 Redis 用的是 redis-stack-server 而不是普通 Redis？索引名和维度为什么要在知识库表里存一份？**

参考回答：因为 RAG 需要向量检索，Redis Stack 自带的 Redis Query Engine 提供 HNSW/FLAT 向量索引，普通 Redis 只是 KV 存储算不了相似度。我们连健康检查都不是 ping，而是 `redis-cli MODULE LIST` 断言 search 模块存在——把"容器活着"升级为"能力可用"。indexName 记在 `ai_knowledge_base.index_name`、且约定带 v{n} 版本号，是为了零停机重建：换嵌入模型或改维度时建新版本索引、双写切换、弃旧的；vectorDim 存两处（知识库表与模型表）是因为**维度必须与嵌入模型一致且建索引后不可改**——Redis 索引建的时候就固定了 DIM 参数，维度不符写入直接报错，不同模型的嵌入空间也不可比较。我们还在向量元数据里把 tenant_id/kb_id 建成 TAG 字段做检索过滤，把租户隔离延伸到向量层。另外有个真实教训：VectorStoreConfig 早期把 initializeSchema 硬编码 true，配置写 false 不生效，这种"配置静默失效"比报错更可怕，排查时人会先怀疑自己配错。

**Q3：为什么验证码、菜单权限、API Key 校验这些缓存你都没用 Redis，反而用 Caffeine？什么时候才必须换 Redis？**

参考回答：判断标准是**数据生命周期 + 部署形态**。验证码是 2 分钟生命周期的短命数据，单机部署下进程内缓存读写快几个数量级，为一个短命 KV 引入网络往返和故障依赖不值；API Key 校验在网关主链路上，Caffeine 异步缓存 60 秒 TTL 平衡了延迟与吊销及时性，而且我们刻意不缓存校验失败的结果，避免平台服务抖动被负缓存放大成全量误拒。**必须换 Redis 的信号只有一个：多实例部署**——验证码生成在实例 A、校验落到实例 B 时本地缓存就失效了，权限与 Key 缓存的跨实例一致性也一样。所以代码注释里都写明了这个演进点。这本质是容量规划问题：单机够用就不过度设计，但把"什么时候必须换"想清楚并写进代码，比无脑上 Redis 更体现工程判断。
