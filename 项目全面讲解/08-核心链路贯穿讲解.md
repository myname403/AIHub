**为什么所有请求都过网关**：把"TraceId、鉴权、租户头注入、限流、CORS"五件事收敛在一处做一次，下游服务就只需信任内网流量（边界统一鉴权模式），业务代码彻底不碰令牌解析。

### 1.2 逐跳讲解

**第 1 跳：验证码（防暴力破解的第一道闸）**
`AuthController#captcha（AuthController.java:47）` 调 `CaptchaService#generate（CaptchaService.java:49）`：用 Hutool 生成 4 位线段干扰验证码，**答案存 Caffeine 本地缓存（TTL 2 分钟、上限 1 万条）**，只把 `{id, imageBase64}` 给前端。
- 为什么存 Caffeine 而不是 Redis：验证码是短命数据，当前单机部署够用，不引入跨服务依赖；注释中明确指出多实例部署时需换 Redis（`CaptchaService.java:22-23` 类注释），这是教学级的"够用即可 + 演进路径"取舍。
- 为什么校验后立即删除：`CaptchaService#verify（CaptchaService.java:61-70）` 用 `captchaCache.asMap().remove(captchaId)` 原子地"取出即删除"，同一个验证码不能反复尝试（防重放）。失败与成功都删除。
- `aihub.auth.captcha-enabled=false` 可整体放行，供自动化测试使用（生产默认开启）。

**第 2 跳：网关白名单**
`AuthGlobalFilter#isPublicPath（AuthGlobalFilter.java:170-172）` 只放行 `/auth/` 与 `/actuator/health`。**为什么白名单极小**：每多一行白名单就多一分"绕过鉴权"的风险面；健康检查放行是因为探活不能要求凭证。

**第 3 跳：登录主流程（AuthService#login，AuthService.java:87-121）**
按 ⓪~⑥ 六步执行，顺序本身就是设计：
1. ⓪ 验证码放最前——验证码不对就不查库，**既省资源，也不泄露"账号是否存在"的信息**；
2. ① `AuthService#resolveTenantId（AuthService.java:225-240）`：`SELECT ... WHERE code = ? last("limit 1")` 把租户码换算成租户 ID，顺带校验租户 status；
3. ② `SysUserMapper#selectByTenantAndUsername`：SQL 自带 `tenant_id = ?` 条件——**同名用户在不同租户互不干扰，天然防跨租户撞库**；
4. ③ `passwordEncoder.matches(明文, 库里哈希)`：BCrypt 慢哈希，单次比对约百毫秒级，穷举成本极高；
5. ④ 状态校验 `status != 1` 拒绝停用账号，null 也按停用处理（fail-safe：不确定时按最严处理）；
6. ⑤ `JwtTokenProvider#generate（JwtTokenProvider.java:66-75）` 签发令牌；
7. ⑥ 组装 `AuthLoginRespVO` 返回。

**防枚举细节**：用户不存在与密码错误返回**同一句**"用户名或密码错误"（`AuthService.java:98-104` 两处 throw）。如果分别提示，攻击者可批量探测哪些用户名有效。

**第 4 跳：JWT 里到底放了什么（链路二的源头）**
`JwtTokenProvider#generate（JwtTokenProvider.java:66-75）`：

| Claim | 值 | 作用 |
|---|---|---|
| `sub` | username | 便于日志排查"这条日志是谁产生的" |
| `tenantId` | 租户 ID | **租户上下文的唯一可信来源**（常量 `CLAIM_TENANT`，JwtTokenProvider.java:37） |
| `userId` | 用户 ID | 审计"是谁在操作" |
| `iat` / `exp` | 签发/过期时间 | 默认 7200 秒（配置 `aihub.security.jwt-expire-seconds:7200`） |

- **为什么是无状态 JWT 而不是 Session**：服务端不存会话，网关和任何服务都能本地验签，微服务横向扩容零成本；代价是"签发后无法主动作废"——过期即失效，密钥泄露只能换密钥。
- **为什么 tenantId 放 claims 而不是让前端传**：JWT 有 HS256 签名，篡改即验签失败；前端传参谁都能伪造。**租户身份的可信度完全由"签名"背书**。

**第 5 跳：后续请求的网关校验与租户头透传（两条全局过滤器）**
执行顺序由 `getOrder()` 决定：
1. `TraceIdGlobalFilter#filter（TraceIdGlobalFilter.java:35-52）`，`getOrder()` 返回 `Integer.MIN_VALUE`（TraceIdGlobalFilter.java:57）：沿用或生成 `X-Trace-Id`，写入下游请求头**并回写响应头**（前端 Network 面板直接可见）。它是第一个——保证 401 响应里也带 traceId，而 401 恰恰多是客户端配置错误、最需要排障信息。
2. `AuthGlobalFilter#filter（AuthGlobalFilter.java:83-103）`，`getOrder()` 返回 `-100`（AuthGlobalFilter.java:208）：
   - `resolveToken（AuthGlobalFilter.java:175-181）` 从 `Authorization: Bearer ` 前缀后截令牌；
   - `authenticateByJwt（AuthGlobalFilter.java:132-167）` 用**与签发端同一把密钥** `aihub.security.jwt-secret`（网关 `application.yml:78-80`）验签解析，取 `tenantId/userId`；
   - `headers.remove(...)` 再 `headers.set(...)`（AuthGlobalFilter.java:159-162）：**强制剥离客户端伪造的 X-Tenant-Id / X-User-Id 再注入可信值**。不剥离的话，攻击者自带一个假租户头就能冒充别的租户——因为下游 `TenantResolveInterceptor` 信任这个头。
   - 令牌无效/过期走 `unauthorized（AuthGlobalFilter.java:187-200）`：WebFlux 环境没有 common 的 `GlobalExceptionHandler` 可用，只能手写响应体 `{"code":10002,"message":"...","traceId":"..."}`，格式与 `R` 保持一致，前端一套逻辑兼容两处。

**为什么要"网关验一次、下游不再验"**：验签是 CPU 操作，重复做三遍是浪费；更重要的是**边界统一**——下游 `TenantResolveInterceptor#preHandle（TenantResolveInterceptor.java:42-56）` 直接信任网关注入的头，业务代码永远不需要接触令牌。前提是网络边界可靠（内网服务不对外暴露端口）。

### 1.3 本链路面试三连

**Q1：为什么 JWT 能做到"无状态"，它和 Session 的本质区别是什么？本项目为无状态付出了什么代价？**
参考回答：Session 的状态（登录态）存在服务端，请求只需带一个不透明 ID，服务端查存储还原身份——横向扩容时要么粘性会话要么共享存储。JWT 把状态本身（claims）+ 签名一起发给客户端，服务端只持有验签密钥，验签即可信，天然适合多实例。代价有三个：①无法主动作废（本项目靠 2 小时短过期兜底，敏感操作要求重新认证）；②令牌一旦泄露在有效期内可用（所以传输必须 HTTPS、前端存储要防 XSS）；③payload 是 Base64 可解码的，**只能放非敏感字段**——本项目只放 tenantId/userId/username，绝不放密码或手机号。

**Q2：BCrypt 为什么比 MD5+盐安全？`matches()` 内部在做什么？**
参考回答：BCrypt 三重优势——①自带随机盐并**把盐编进哈希结果**（`$2a$10$盐$哈希`），无需单独存盐列；②"慢"：cost factor 指数级控制计算轮数（默认 10 轮约几十毫秒），穷举成本比 MD5 高几个数量级，且硬件升级可通过调 cost 追涨；③抗 GPU 并行优化（内存依赖）。`matches(明文, 库里哈希)` 从哈希串里解析出盐和 cost，用同参数重算一遍再常量时间比较。本项目 `AuthService#login（AuthService.java:103）` 直接 `passwordEncoder.matches`，注册侧 `AuthService#register` 用 `encode()` 落库，永不存明文。踩过的真实坑：种子数据哈希与注释不符，因为 BCrypt **无法反解**，只能用对拍验证法（同一密码 encode 后 matches）确认——教训是种子数据也要有自动化验证。

**Q3：验证码为什么放最前校验？如果不放最前会有什么问题？**
参考回答：`AuthService#login（AuthService.java:90-92）` 把 `captchaService.verify` 放在第 0 步。①资源保护：验证码都不对就不值得花费一次数据库查询 + 一次 BCrypt 慢哈希（BCrypt 是故意设计成"贵"的，攻击者可借它反刷 CPU）；②信息泄露：如果先查用户再验验证码，攻击者可通过响应时间/错误类型差异推断账号是否存在（时序侧信道）；③防重放：verify 用 `asMap().remove` 一次性消费，同一个验证码第二次必失败。

### 2.2 四级传递逐跳讲解

**第 1 级：token claims（源头，不可伪造）**
`JwtTokenProvider#generate（JwtTokenProvider.java:66-75）` 把 tenantId 写进 claims。设计原则在 `TenantContext` 类注释中写得斩钉截铁（TenantContext.java:17-18）：**租户 ID 只允许从 JWT / API Key 解析后写入，绝不接受前端传参**。

**第 2 级：HTTP 请求头（网关是唯一写入者）**
`AuthGlobalFilter#authenticateByJwt（AuthGlobalFilter.java:157-164）` 先 `remove` 后 `set` 写入 `X-Tenant-Id`/`X-User-Id`（常量定义于 `TenantContext.HEADER_TENANT/HEADER_USER`，TenantContext.java:26-29）。API Key 通道 `authenticateByApiKey（AuthGlobalFilter.java:106-129）` 走 `ApiKeyCache#verify（ApiKeyCache.java:67）` → `ApiKeyVerifier#verify（ApiKeyVerifier.java:56）` 回调平台服务反查租户，同样剥头再注入——API Key 不带用户身份，所以只注入租户头、显式清空用户头。

**第 3 级：ThreadLocal（请求内传递，免参数穿透）**
`TenantResolveInterceptor#preHandle（TenantResolveInterceptor.java:42-56）` 读头后调 `TenantContext#set（TenantContext.java:42-45）`：
- **为什么用 ThreadLocal**：Spring MVC 一个请求一个工作线程，Controller→Service→Mapper 调用再深也能 `TenantContext.getTenantId()` 直取，避免每个方法都带 tenantId 参数（参数穿透是代码坏味道）。
- **fail-fast**：租户头缺失直接抛 `BizException(TENANT_MISMATCH)`（TenantResolveInterceptor.java:49-51），绝不让"无主请求"进业务层。
- **防串台**：`afterCompletion（TenantResolveInterceptor.java:63-66）` 调 `TenantContext#clear（TenantContext.java:82-85）`——Tomcat 线程池复用线程，不清就会把 A 租户的 ID 带进 B 租户的请求，这是 ThreadLocal 最经典的线上事故。

**第 4 级：查询条件（行级隔离的两道防线）**
- **第一道（人工约定）**：所有 Repository 手写 tenant_id 条件。如 `KnowledgeController#list（KnowledgeController.java:43-46）` 每个接口都 `TenantContext.requireTenantId()` 传入 Service；`KnowledgeAppService#requireKb（KnowledgeAppService.java:332-336）` 用 `kbRepository.exists(tenantId, kbId)` 先验证归属再操作。
- **第二道（框架兜底，默认关）**：`MybatisPlusConfig#mybatisPlusInterceptor（MybatisPlusConfig.java:48-62）` 注册 `TenantLineInnerInterceptor` + 内部类 `PlatformTenantLineHandler`：
  - `getTenantId()（MybatisPlusConfig.java:105-108）` 返回 `TenantContext.getTenantId()`；
  - `ignoreTable()（MybatisPlusConfig.java:111-117）` 排除全局表 `sys_tenant`、`sys_menu`、`sys_role_menu`（菜单是平台全局定义的）与无租户上下文的场景；
  - 开关 `aihub.tenant.sql-guard.enabled` 默认 false。**为什么默认关**（MybatisPlusConfig.java:77-90 类注释讲得很透）：它改写每一条 SQL，而模块单测是 Mockito 级别、覆盖不到真实 SQL 改写，必须"先在真实库回归、再开"，漏写条件不再等于越权。

**向量世界的租户隔离（容易忽略的第三战场）**
向量库不在 SQL 里，隔离要单独做：
- 写入侧：`RedisKnowledgeIndexer#index（RedisKnowledgeIndexer.java:28-43）` 把 `tenant_id/kb_id/doc_id` 写进每条向量的 metadata——**这是租户隔离的数据源头，缺失该元数据的向量在检索侧会被丢弃**；
- 检索侧双防线：`RedisKnowledgeRetriever#retrieve（RedisKnowledgeRetriever.java:36-75）` ①强制拼 `filterExpression("tenant_id == '<id>' && kb_id == '<id>'")`（RedisKnowledgeRetriever.java:40-49）调用方无法绕过；②出口逐条校验 metadata 的 TenantGuard（RedisKnowledgeRetriever.java:59-64），不匹配即丢弃并 `log.warn` 告警。

**跨服务透传**：ai 服务通过 Feign 调平台服务扣配额时，`aihub-api` 的 `FeignTenantConfig`（aihub-api/src/main/java/com/aihub/api/config/FeignTenantConfig.java:34）自动把 `X-Tenant-Id`/`X-User-Id` 加到 Feign 请求头，租户上下文不断链。

### 2.3 本链路面试三连

**Q1：多租户隔离有哪三种方案？本项目为什么选共享表行级隔离？**
参考回答：①独立库：隔离最彻底、备份/迁移按租户走，但连接数与运维成本随租户数线性涨，小租户严重浪费；②独立 Schema：折中，但跨租户统计与升级（每个 schema 都要跑迁移）麻烦；③共享表 + tenant_id 行级隔离：成本最低、一张表服务所有租户、跨租户运营报表好做，代价是**隔离靠代码纪律**，一条 SQL 漏写 WHERE 就是事故。本项目是 SaaS 教学平台，租户数量多、单租户数据量小，行级隔离 + 双防线（手写条件 + MyBatis-Plus 租户插件兜底）+ 向量侧 metadata 过滤与 TenantGuard，性价比最高。

**Q2：ThreadLocal 存租户 ID 有什么坑？本项目怎么防的？**
参考回答：三大坑——①**线程复用串台**：Tomcat 线程池复用，不清理则下个请求读到上个租户的 ID，本项目在 `TenantResolveInterceptor#afterCompletion` 强制 `TenantContext#clear()`；②**异步丢上下文**：ThreadLocal 不跨线程，本项目入库线程用 `TraceContext.wrap(...)` 同思路处理（TraceContext.java:99-113 的快照-还原模式），知识库入库与流式对话都这么包；③**内存泄漏**：key 是弱引用、value 不是，线程池长存导致 value 无法回收——及时 remove 同时解决②③。防御思路上还有一招：`requireTenantId()`（TenantContext.java:53-61）把"取不到"升级为抛异常，宁可失败不静默。

**Q3：MyBatis-Plus 租户插件能 100% 防越权吗？本项目为什么默认关闭？**
参考回答：不能。它只拦截走 MyBatis-Plus SQL 注入器的语句，原生 SQL、`IgnoreStrategy` 误用、动态表名都可能绕过；它也不是身份校验，tenantId 的值仍来自 `TenantContext`——源头错了插件无能为力。默认关闭的原因是工程化的诚实：改写每一条 SQL 属于全局高影响变更，而项目自动化测试是 Mockito 单测，Mapper 被 mock、覆盖不到真实 SQL 解析改写，没有证据就敢全量开启是把测试环境当生产。落地路径写在 `MybatisPlusConfig` 注释里：真实 MySQL 环境回归全链路后再开。这体现"框架兜底 + 人工纪律"的双层观：兜底没验证前，纪律就是唯一防线。

### 3.2 逐跳讲解

**跳 1：建库（vectorDim 与 indexName 的伏笔）**
`KnowledgeController#create（KnowledgeController.java:37-41）` → `KnowledgeAppService#createKb（KnowledgeAppService.java:115-118）`：索引名固定 `aihub:kb:<tenantId>`。**为什么索引按租户划分**：物理上先隔一层，检索时再叠加 metadata 过滤，纵深防御。`vectorDim` 默认 1536（KnowledgeController.java:113），**必须与 Embedding 模型输出维度一致**，否则向量写不进或检索全空——这是建库时就锁定的契约。

**跳 2：上传即返回（异步化是本链路最重要的一跳）**
`KnowledgeController#upload（KnowledgeController.java:59-75）` → `KnowledgeAppService#submitIngest（KnowledgeAppService.java:137-156）`：
- 类型白名单 `SUPPORTED = {txt,md,markdown,pdf,docx}`（KnowledgeAppService.java:84）；
- `checkDocQuota（KnowledgeAppService.java:167-181）`：Feign 调 `PlatformClient#consume` 扣 DOC 维度配额，**平台不可用时降级放行**（catch 后仅 log.warn）——能力不因统计故障而不可用；
- 落文档记录、建入库任务、**原始文件落盘暂存**（`ingestFileStore.save`，服务重启后仍可重试——注释明说早先用进程内 Map 重启即丢）；
- `ingestExecutor.submit(TraceContext.wrap(() -> runWithRetry(...)))`（KnowledgeAppService.java:152-153）：4 线程池异步执行，`TraceContext.wrap`（TraceContext.java:99-113）把请求链路 ID 快照带到工作线程。
- **为什么异步**：解析 + 向量化对大文件是分钟级操作，同步会占满 Tomcat 请求线程；改为提交即返回 taskId，前端轮询 `KnowledgeController#ingestProgress（KnowledgeController.java:78-84）`。

**跳 3：解析与切片（execute 四阶段，KnowledgeAppService.java:256-287）**
进度埋点按 10%→30%→50%→70% 推进，每段用 `timed()` 计时上报指标，瓶颈可见：
- **解析**：`parseText（KnowledgeAppService.java:87-99）` switch 分发——pdf 走 PDFBox（`parsePdf`，101-105 行）、docx 走 POI（`parseDocx`，107-113 行）、其余按 UTF-8 纯文本。
- **切片**：`TextChunker#split（TextChunker.java:20-61）`，参数 `aihub.rag.chunk-size:500`、`chunk-overlap:100`：
  - 优先按段落（空行）切——语义边界完整；
  - 超长段落用 `slidingWindow（TextChunker.java:74-85）` 滑动窗口二次切分（步长 = size - overlap）；
  - 相邻分片保留 overlap 字符重叠（TextChunker.java:44-51 刷缓冲时截尾部回填）——**防止关键句恰好被切断，两个半句各自检索都命不中**。类注释点名：按段落 + 重叠的检索效果明显优于固定字数硬切。

**跳 4：Embedding 与向量入库**
`RedisKnowledgeIndexer#index（RedisKnowledgeIndexer.java:28-43）`：把每个 Chunk 包成 Spring AI `Document(content, metadata)`，metadata 强制写 `tenant_id/kb_id/doc_id`，然后 `vectorStore.add(documents)` 一行完成**Embedding + 写入**——Embedding 由 Spring AI 的 EmbeddingModel 在 VectorStore 内部自动调用，业务代码无感。向量最终落在 Redis Stack（RediSearch HNSW 索引，`VectorStoreConfig` 装配）。

**跳 5：检索（topK + 相似度阈值 + 双重租户防线）**
`KnowledgeAppService#search（KnowledgeAppService.java:319-324）`（默认 topK=5、threshold=0.5）→ `RedisKnowledgeRetriever#retrieve（RedisKnowledgeRetriever.java:36-75）`：
- `SearchRequest.builder().query(...).topK(...).similarityThreshold(...).filterExpression("tenant_id == '..' && kb_id == '..'")`（RedisKnowledgeRetriever.java:45-50）——问题文本先被 Embedding 成向量，再到向量库里做余弦相似度 TopK，过滤表达式在引擎内部生效，**调用方拿不到不带租户过滤的结果**；
- 出口 TenantGuard 逐条再校验 metadata（RedisKnowledgeRetriever.java:59-64），跨租户向量直接丢弃并告警。
- 检索调试台独立成接口 `POST /api/ai/kb/search`（KnowledgeController.java:102-106），能直接看命中分片与相似度——调 RAG 先调它，肉眼确认"检索对不对"再谈"生成好不好"。

**跳 6：拼 Prompt（受限上下文 + 防幻觉约束 + 引用编号）**
对话时 `SpringAiChatExecutor#stream（SpringAiChatExecutor.java:114-175）` 先走 `augment（SpringAiChatExecutor.java:181-222）`：
1. `appRepository.knowledgeBaseIds(tenantId, appId)` 查应用绑定的知识库（绑定动作在 `KnowledgeController#bind`，KnowledgeController.java:95-99）；
2. `retrieveWithTimeout（SpringAiChatExecutor.java:239-253）` **3 秒超时保护**——检索前要先调嵌入模型把问题向量化，未配嵌入模型时 Spring AI 默认连 api.openai.com 会无限阻塞，曾导致绑定知识库的应用全部卡死（类注释里的真实事故）；超时/失败一律返回空列表，降级为普通对话；
3. 命中分片拼成 `[1] 内容 [2] 内容…`，并套上防幻觉外壳（SpringAiChatExecutor.java:213-217）："请仅依据下方知识库内容回答……不足以回答请明确说明，禁止编造。回答末尾以 [n] 标注引用来源。"
4. 发 `rag.sources` 事件（SpringAiChatExecutor.java:210）给前端渲染引用角标；回答结束后 `referenceStore.save`（SpringAiChatExecutor.java:156）把引用与消息落库，供 `ChatController#references` 溯源。

**为什么 RAG 叫"开卷考试"**：模型权重里没有你的私有文档，先检索再把资料塞进上下文，等于把闭卷题改成开卷题；防幻觉约束则明确"资料里没有就直说"，禁止模型脑补。

### 3.3 本链路面试三连

**Q1：chunk-size 和 chunk-overlap 分别影响什么？怎么权衡？**
参考回答：chunk 太大——单个分片混入多个主题，Embedding 向量"语义稀释"，检索命中但内容嘈杂，还挤占上下文窗口；chunk 太小——语义片段支离破碎，"哪句话都只说一半"，检索到的内容不足以支撑回答。overlap 是缓冲带：关键句横跨两个分片边界时，重叠区保证至少一个分片包含完整语句。本项目 500 字 + 100 重叠（20%），是中文文档的常见起点；代码层面 `TextChunker#split` 还做了两层保护：overlap 上限为 size/2（TextChunker.java:26），超长段落滑动窗口步长为 size-overlap（TextChunker.java:76）。调参方法论：用检索调试台（`/api/ai/kb/search`）看真实命中质量再调，不看数据调参都是玄学。

**Q2：向量检索的"相似度"是怎么算的？为什么 vectorDim 必须和模型一致？**
参考回答：文本经 Embedding 模型映射为固定长度浮点向量，语义相近的文本向量夹角小；Redis Stack（RediSearch）用 HNSW 近似最近邻索引高效找 TopK，Spring AI 的 `similaritySearch` 返回 score（余弦相似度归一化到 0~1），`similarityThreshold` 过滤低质量命中。vectorDim 是索引建库时锁定的向量维度——Embedding 模型输出 1536 维就必须建 1536 维索引：写入维度不符直接报错，维度"恰好能写"但模型不同则两套语义空间完全不可比，检索结果是垃圾。所以本项目在 `createKb` 时就让用户声明 vectorDim 并与索引绑定，换 Embedding 模型 = 重建全部向量。

**Q3：RAG 检索失败了要不要让对话也失败？本项目怎么处理的，为什么？**
参考回答：不要。RAG 是增强能力，不是对话的前提。本项目 `SpringAiChatExecutor#retrieveWithTimeout（239-253 行）` 用 `CompletableFuture.get(3, SECONDS)` 硬超时，超时/异常返回空列表，`augment` 检索不到就返回 `Augmented.plain(原始问题)`（206-208 行、218-221 行），对话照常进行。背景是一次真实事故：未配置嵌入模型时 Spring AI 默认连 api.openai.com，网络不通导致所有绑定知识库的应用永远"思考中"——**可选能力绝不能拖死主链路**。同样的降级哲学贯穿全项目：配额校验失败放行（`ChatAppService#checkQuota`）、用量上报失败转发件箱（`ChatAppService#reportUsage`）。

```text
    │<──event: error{code,message}───────────│  →sink.close()                     │
    │ (120s 无事件) emitter 超时自动 complete  │                                    │
```

### 4.2 逐跳讲解

**跳 1：三种通道一个编排（入口设计）**
`ChatController` 类注释（ChatController.java:37-56）给出选型结论：
- **SSE**（`POST /chat/sse`）：HTTP 长连接单向推送，浏览器原生支持，H5 首选；
- **NDJSON**（`POST /chat/ndjson`）：微信小程序 request API 不支持 SSE，只能 `enableChunked` 分块接收、每行一个 JSON 自行切分；
- **同步**（`POST /chat`）：一次性全文，调试用。
三通道共享 `ChatAppService` 编排，差异只封装在 `StreamSink` 实现（`StreamSink.java:11-17` 只有两个方法 `emit/close`）——**依赖倒置**：编排层不知道自己在跟谁说话。

**跳 2：SseEmitter 生命周期与线程模型（本链路最值得学的一跳）**
`ChatController#chatSse（ChatController.java:103-118）`：
1. `new SseEmitter(120_000L)`：120 秒无事件则容器自动 complete（超时兜底，防止连接悬挂）；
2. **把流式任务丢进自建 32 线程池** `streamExecutor`（ChatController.java:81-85），**容器线程立即返回 emitter**——模型生成一句话要几秒到几十秒，不能占着 Tomcat 请求线程干等；这也意味着后续所有 emit 都发生在工作线程，必须 `TraceContext.wrap` 带链路 ID（ThreadLocal 不跨线程）；
3. 任务里 `new SseStreamSink(emitter)` 后调 `chatAppService.chatStream(turn, sink)`，异常时 `sink.emit(StreamEvent.error(9999,"50000","服务异常"))` 再 `sink.close()`。

**SseEmitter 三种结束方式**：①正常 `SseStreamSink#close（SseStreamSink.java:54-64）` 调 `emitter.complete()`；②发送失败（客户端断开）在 `emit（SseStreamSink.java:38-51）` 里捕获 IOException/IllegalStateException 置 `closed=true`，**后续事件静默丢弃不再尝试**（写已断开的连接只会持续抛异常）；③120 秒超时容器强制 complete。

**volatile 的正确性意义**（SseStreamSink.java:31 类注释）：`closed` 被流任务线程与可能的超时线程并发读写，volatile 保证写入立即对其他线程可见——否则可能一直读到缓存旧值 false，往已关闭连接写数据。

**跳 3：流式编排（异常语义与同步路径不同）**
`ChatAppService#chatStream（ChatAppService.java:93-113）`：
- 配额检查走 `checkQuotaOrEmit（ChatAppService.java:215-226）`：**复用同步版 `checkQuota（ChatAppService.java:122-142）` 的判定逻辑，只把"抛异常"翻译成"发 error 事件"**——因为流式连接建立后 HTTP 响应头已发出，再抛异常前端根本收不到，必须用事件帧表达失败；"超限判定"保持一份逻辑，避免两处漂移；
- Agent 场景先 `consumeAgentTaskOrEmit` 扣 task 配额再 `runAgent`；
- 普通对话 `chatExecutor.stream(turn, sink)` 后上报用量、补扣 token；
- 最外层 catch 只记日志不上抛（ChatAppService.java:109-112）：向上抛只会断开连接，错误早已通过事件帧送达。

**跳 4：事件帧协议（StreamEvent 统一信封）**
`StreamEvent`（StreamEvent.java:22）是 Java record：`{ "i":12, "e":"token", "ts":..., "data":{...} }`。事件类型常量（StreamEvent.java:24-34）：`msg.start → [rag.sources] → token×N → [tool.start/tool.end]×N → [agent.step]×N → msg.end`，出错发 `error`，空闲发 `ping`。**index 序号从 0 递增**，前端用它排序/去重/判断丢帧。`SpringAiChatExecutor#stream（SpringAiChatExecutor.java:114-175）` 里 `int[] index = {0}` 用单元素数组在 lambda 中做可变计数；`Flux.doOnNext` 对每个到达的 token 增量拼全文 + emit，`blockLast()` 阻塞等流结束——"响应式数据源 + 阻塞消费"的混合用法，因为服务是 MVC（Servlet 线程模型），在自建线程池里阻塞是安全的（类注释 SpringAiChatExecutor.java:36-38）。

**跳 5：NDJSON 与 SSE 的差异（小程序通道）**
`ChatController#chatNdjson（ChatController.java:122-148）`：返回 `StreamingResponseBody` 直接手写 `OutputStream`；`NdjsonStreamSink#emit（NdjsonStreamSink.java:31-42）` 每事件一行 JSON + `\n` 后 `flush()`。**四个硬性响应头**（ChatController.java:141-147）：
- `Content-Type: application/x-ndjson;charset=UTF-8`；
- `Content-Encoding: identity`——**禁 gzip**：小程序 chunk 接收拿到的是压缩字节流还得自己解压，且 gzip 会攒缓冲破坏"逐 token"体验；
- `X-Accel-Buffering: no`——禁 Nginx 缓冲（否则中间层攒够 buffer 才转发，流式变"一顿一顿"）；
- `Cache-Control: no-cache, no-transform`——禁代理转换。
断连处理同 SSE：`emit` 捕获 IOException 置 closed； finally 里 `TraceContext.clear()`（ChatController.java:136-138）。

**跳 6：前端接收差异**
- H5：**必须用 `fetch + ReadableStream` 手工解析**，不能用 `EventSource`——EventSource 只支持 GET 且无法带 `Authorization` 自定义头（SseStreamSink.java:22-23 类注释明确说明），而本项目鉴权必须带头；
- 小程序：`uni.request({enableChunked:true})` 的 `onChunkReceived` 回调，按 `\n` 切分并处理半包（一行 JSON 可能跨两次 chunk 到达，需缓存不完整行）。

### 4.3 本链路面试三连

**Q1：为什么选 SSE 不选 WebSocket？什么情况下必须换 WebSocket？**
参考回答：对话场景是"一次请求、服务器单向推送 N 个增量"，SSE 恰好匹配：①纯 HTTP，网关/代理/负载均衡零改造；②浏览器自动重连与 last-event-id 内建；③协议开销小，无需心跳握手协议。WebSocket 是全双工，适合聊天室、协同编辑这类双向高频场景，但要处理连接升级、网关支持、心跳保活、状态管理一堆复杂度。本项目其实留了 WebSocket 通道给 Agent 场景（`web/ws/AgentWebSocketHandler`），因为 Agent 长任务可能需要客户端主动发"取消"指令——**需要双向才上 WS，单向推送一律 SSE**。微信小程序不支持 SSE 则用 NDJSON Chunked 兜底，这就是"一个编排、三个 Sink"架构的由来。

**Q2：SSE 连接中断时服务端怎么知道？会不会往死连接里一直写？**
参考回答：TCP 断开是"下次写才发现"——服务端不会立刻收到通知。本项目的处理是三层：①`SseStreamSink#emit` 每次写都可能抛 IOException/IllegalStateException，捕获后置 `volatile closed=true`（SseStreamSink.java:46-50）；②`emit` 入口先查 closed 直接 return（SseStreamSink.java:39-41），后续事件零成本丢弃，不会反复尝试写死连接；③兜底 `SseEmitter(120_000)` 超时自动 complete，即使任务卡住连接也会被容器回收。业务侧无需感知断连：编排继续跑完（用量照记），只是事件发不出去——这比"断连即取消"简单且语义正确（用户关页面不代表不想要这次回答的账务）。

**Q3：流式接口为什么不能把异常直接抛出去？怎么把"失败"告诉前端？**
参考回答：HTTP 响应头（200 + text/event-stream）在连接建立时已发出，此时再抛异常，Spring 已无法改写状态码，客户端只看到连接断开，无法区分"正常结束"与"服务崩溃"。所以流式协议必须把错误设计成**一种事件帧**：`StreamEvent.error(index, code, message)`（StreamEvent.java:44-46）。工程上还有个巧妙复用：`ChatAppService#checkQuotaOrEmit（215-226 行）` 不重写配额判定，而是复用同步版 `checkQuota` 后 catch `BizException` 转成 error 事件——**判定逻辑只有一份，"异常→事件"只是一层翻译**，同步与流式两条路径永不漂移。

### 5.3 逐跳讲解

**跳 1：工具从哪里来（装配期）**
`ChatClientFactory#buildToolCallbacks（ChatClientFactory.java:211-234）` 是工具的"点名册"：
- 内置工具：`new TimeTools()` + 注入的 `KnowledgeTools`（+可选 `BrowserTools`）经 `MethodToolCallbackProvider` 反射收集 `@Tool` 方法（TimeTools.java:17/22、KnowledgeTools.java:30 各自的 @Tool 描述）；
- 外部工具：`externalToolProviders.orderedStream()`——**MCP Client starter 自动装配的 `ToolCallbackProvider`**，接了几个 MCP Server 就多几组工具；未接 MCP 时流为空，自然降级为"仅内置工具"（ChatClientFactory.java:225-229）；
- 每个工具统一套 `AuditedToolCallback` 包装，source 标记 `local`/`mcp`。
**为什么工厂 + 缓存**（ChatClientFactory.java:47-49 注释）：每个 `(租户, 应用, 场景, 模型)` 组合的模型/提示词/工具不同，不能全局共享一个 ChatClient；每次装配又太贵，所以按 key 缓存 + TTL 过期（`create`，ChatClientFactory.java:134-150，双重检查锁）。

**跳 2：Agent 循环（运行期，模型是决策者）**
模型收到工具清单（名称 + 描述 + 参数 Schema）后自主判断：
1. **意图与选工具**：模型返回 tool_call（如 `searchKnowledge{"query":"…"}"`）——**工具描述是模型选工具的唯一依据**，所以 `@Tool(description=...)` 要写得像说明书（AiHubTools 类注释 30-33 行强调这一点）；
2. **执行**：Spring AI 框架执行 `ToolCallback#call` → `AuditedToolCallback#call（AuditedToolCallback.java:58-77）` 计时、委托、finally 落审计（`record`，AuditedToolCallback.java:79-94，写 `ai_tool_call_log` + Micrometer 指标；审计失败只 warn 不中断调用）；
3. **回填**：工具结果作为 tool 消息拼回上下文，模型带着结果继续生成；
4. **循环**：模型可连续多次 tool_call 直到认为可以回答。
租户安全在工具内部收口：`KnowledgeTools#searchKnowledge（KnowledgeTools.java:31-56）` **不接收任何租户参数**，从 `AiCallContext` 取 tenantId/appId，检索入口仍是带双防线的 `KnowledgeRetriever`（KnowledgeTools.java:20-22 注释：工具方法不接收租户参数，全部从调用上下文解析）。

**跳 3：Agent 规划链（scene=agent 的多步循环）**
`ChatAppService#runAgent（ChatAppService.java:233-240）`：从 `AgentRegistryImpl#lookup（AgentRegistryImpl.java:36）` 按名取 `PlanningAgent`。`PlanningAgent#execute（PlanningAgent.java:83-116）`：
- 建任务记录（`taskRepository.create`）→ `run（PlanningAgent.java:118-167）`：
  - `decompose（PlanningAgent.java:182-217）`：用 `BaseAgent#llm（BaseAgent.java:48-67）` 把用户目标拆解成 JSON 子任务链 `[{"agent":"chart","task":"…"}]`；`extractJsonArray（PlanningAgent.java:219-229）` 截取 `[...]` 防模型废话；解析失败退化为单个 html 子任务（PlanningAgent.java:213-215）；
  - 循环执行每个子任务：每步前查 `cancelRegistry.isCanceled`（用户点"停止"立即生效）、查预算（`AgentBudgetExceededException`）、`registry.lookup` 找执行 Agent（Table/Chart/Html）、`emit(agent.step)` 广播 + `appendStep` 落库（**事件给前端时间线，落库给审计回放**，PlanningAgent.java:170-174）；
- `BaseAgent#llm（BaseAgent.java:48-67）` 调用前后各 `checkBudget（BaseAgent.java:69-81）` 一次——超时/Token 超限抛 `AgentBudgetExceededException`；这是模板方法模式：骨架在基类，子类只实现 execute（BaseAgent.java:15-21 类注释）；
- finally 保证任务终态落库（PlanningAgent.java:101-114，连 Error 兜底的 NPE 防御注释都值得读）。

**为什么 Agent 要三重预算（步数/Token/耗时）**：LLM 决策不受程序员控制，可能"想"出无限循环；没有预算上限，一次 Agent 调用可能烧掉整个租户的 token 预算。预算触顶返回 `AgentResult.BUDGET_EXCEEDED`，对应业务码 `AGENT_BUDGET_EXCEEDED(20005)`。

**跳 4：MCP 对外暴露（三件套分工）**
- **mcp-service（纯库）**：`AiHubTools` 四个 `@Tool`（`AiHubTools#listApplications` 59 行、`#listKnowledgeBases` 88 行、`#searchKnowledge` 115 行、`#ask` 153 行）。三个刻意设计（类注释 18-42 行）：①全部返回 String——纯文本最不会错；②错误转文字不抛异常——抛出去变 JSON-RPC error 模型会直接放弃，"鉴权未通过，请检查 API Key"能让它继续推理；③描述像说明书。`AiHubMcpConfiguration#aiHubToolCallbackProvider（AiHubMcpConfiguration.java:56-60）` 把 `@Tool` 方法注册为 `ToolCallbackProvider`——MCP Server 自动装配据此生成 tools/list。
- **mcp-sse（远程传输）**：`McpChannelAuthFilter#doFilterInternal（McpChannelAuthFilter.java:44-61）` 只拦配置的保护路径，令牌校验用 `MessageDigest.isEqual` **常量时间比较**（`matchesToken`，74-82 行）防时序攻击。用 Servlet Filter 而非拦截器是因为 `/mcp/**` 端点由 Spring AI MCP 框架注册、不走自家 Controller（类注释 26-31 行）。
- **mcp-stdio（本地进程传输）**：同一套 `AiHubMcpConfiguration` 装配（AiHubMcpConfiguration.java:14-19 类注释：一套工具、SSE 与 stdio 两种协议复用，这就是 ADR-3 的"工具与传输分离"）。

**跳 5：MCP 工具回调 AIHub 的鉴权回路**
`HttpAiHubApi#configure（HttpAiHubApi.java:60-73）` 给 RestClient 统一挂 `X-API-Key` 头。请求过网关走 `AuthGlobalFilter#authenticateByApiKey（AuthGlobalFilter.java:106-129）`：`ApiKeyCache#verify（ApiKeyCache.java:67，本地缓存 TTL 60s，见网关 application.yml:82-90）` → `ApiKeyVerifier#verify（ApiKeyVerifier.java:56）` 回调平台服务反查租户 → 注入 `X-Tenant-Id`。**为什么 MCP 用 API Key 而不是 JWT**（HttpAiHubApi.java:23-25 注释）：MCP Server 不代表某个终端用户，用固定 Key 标识"哪个租户在通过 MCP 使用 AIHub"最贴切。错误处理 `exchange（HttpAiHubApi.java:148-162）` 把 401/403/404/429 翻译成中文——模型看到"401"只会瞎猜，看到"API Key 无效或已停用"才知道怎么办。

### 5.4 本链路面试三连

**Q1：Function Calling 的完整循环是什么？模型"调用"工具时实际发生了什么？**
参考回答：模型并不能真的执行代码。流程是：①装配期把工具清单（名称/描述/参数 JSON Schema）随请求发给模型；②模型判断需要外部信息时，返回一个结构化的 tool_call（工具名 + JSON 参数）——这只是一段**文本**；③**真正执行方是应用侧框架**（本项目是 Spring AI），它按名称找到对应 `ToolCallback` 执行 Java 方法（本项目包装了 `AuditedToolCallback` 做审计）；④执行结果作为 tool 角色消息拼回对话历史，再次请求模型；⑤模型基于结果继续生成，或再次 tool_call，循环直到给出最终回答。安全要点：工具执行在服务端、参数来自模型但入口校验在代码——本项目 `KnowledgeTools#searchKnowledge` 不接收租户参数、从 `AiCallContext` 取，租户边界不依赖模型"自觉"。

**Q2：怎么防止 Agent 无限循环烧钱？**
参考回答：多层防御。①**三重预算**：`AgentBudget` 限制最大子任务数 / 最大 Token / 最大耗时，`BaseAgent#checkBudget（BaseAgent.java:69-81）` 在每次 LLM 调用前后校验，触顶抛 `AgentBudgetExceededException`，`PlanningAgent#run` 循环里也每步检查（PlanningAgent.java:138-145）；②**成本前置**：Agent 场景先扣 task 维度配额（`ChatAppService#consumeAgentTaskOrEmit`，197-208 行），平台明确拒绝（allowed=false）直接终止；③**取消机制**：`AgentCancelRegistry` 每步检查用户"停止"信号；④**终态兜底**：`PlanningAgent#execute` 的 finally 保证任何异常（甚至 Error）都写任务终态并清取消标记（PlanningAgent.java:101-114）。业务码 `AGENT_BUDGET_EXCEEDED(20005)` 就是为此设计的。

**Q3：MCP 工具为什么返回 String 而不是结构化对象？错误为什么要转成文字？**
参考回答：MCP 是跨实现的开放协议，工具结果要被 Claude Desktop、IDE 插件、自研 Agent 等任意客户端消费，纯文本是最不会出错的表示；返回 POJO 则依赖两端 JSON Schema 生成实现一致，跨实现容易踩坑（AiHubTools 类注释 ①）。错误转文字同理：工具方法抛异常会变成 JSON-RPC error，模型的常见反应是直接放弃任务；而"鉴权未通过，请检查 API Key"是可推理的信息，模型能重试或如实告诉用户（AiHubTools 类注释 ②）。`HttpAiHubApi#exchange（HttpAiHubApi.java:148-162）` 配合把 HTTP 状态码也翻译成中文提示，两个设计共同保证"模型永远拿到可理解的反馈"。

## 6. 五条链路公共横切面

五条链路看似业务各异，底下压着同一套公共设施。这一章把它们抽出来对照讲。

### 6.1 统一响应体 R：一个格式走天下

`R<T>`（aihub-common/src/main/java/com/aihub/common/result/R.java）四个字段：`code / message / data / traceId`。
- **构造收敛**：构造器私有（R.java:58-62），只能走静态工厂 `R#ok`（74-81 行）/`R#fail`（84-96 行），统一汇入 `R#build（R.java:65-71）`——**traceId 在这里自动从 `TraceContext` 填充**，调用方想漏都漏不掉；
- `@JsonInclude(NON_NULL)`（R.java:37）：失败响应不会出现 `"data":null` 的脏字段；
- `isSuccess()`（R.java:99-101）：前端 `if (r.isSuccess())` 替代魔法数字比较。
- **业务码分段**（ResultCode.java:13-21 注释）：`0` 成功；`1xxxx` 通用（10002 未认证 / 10005 跨租户 / 10006 限流 / 10007 配额）；`2xxxx` AI 能力（20001 模型不可用 / 20005 Agent 超预算）；`5xxxx` 系统（50000 内部错误）。**HTTP 状态码始终 200，成败看 body.code**——网关手写 401 是唯一例外（AuthGlobalFilter.java:188，WebFlux 下没有 advice 可用），但 body 里同样塞了 `code:10002` 对齐。

### 6.2 全局异常：业务代码只管抛

`GlobalExceptionHandler`（aihub-common/.../exception/GlobalExceptionHandler.java）`@RestControllerAdvice` 三级兜底：
| 处理器 | 行号 | 语义 |
|---|---|---|
| `handleBiz` | 37-41 | `BizException` 原样透传 code/message，**故意不写日志**（业务分支如密码错误，记 error 会污染告警） |
| `handleValidate` | 48-57 | `@Valid` 校验失败取第一个字段错误的自定义提示 |
| `handleException` | 64-68 | 兜底 Exception：完整堆栈进日志，前端只给笼统"系统内部错误"（防泄露表名/类名/模型地址） |

配合关系：链路一的"用户名或密码错误"、链路二的"请求缺少租户上下文"、链路三的"文档解析失败"全是 `throw new BizException(...)`，Controller 零 try-catch。**网关不在覆盖范围**（WebFlux），所以有 `AuthGlobalFilter#unauthorized` 手写响应体（AuthGlobalFilter.java:183-200 注释自己说明了这一点）。

### 6.3 日志 TraceId：一次请求一个身份证

传递链（三个环境三种载体，逻辑一致）：
1. **网关（WebFlux）**：`TraceIdGlobalFilter#filter（TraceIdGlobalFilter.java:35-52）` 生成/沿用 `X-Trace-Id`，`getOrder()=Integer.MIN_VALUE` 保第一个执行，回写响应头；
2. **下游服务（Servlet）**：`TraceIdInterceptor#preHandle（TraceIdInterceptor.java:31-43）` 读头写入 `TraceContext`（ThreadLocal + SLF4J MDC 双写，TraceContext.java:65-73），afterCompletion 清理；
3. **业务代码**：零感知——logback pattern `%X{traceId:--}`（网关 application.yml:109-110）让每行日志自动带 traceId；响应体 `R.traceId` 由 `R#build` 自动填充；前端报障时只要一个 traceId 就能横跨三个服务 grep 出完整链路。
4. **跨线程**：`TraceContext#wrap（TraceContext.java:99-113）` 快照-还原模式——知识库入库线程（KnowledgeAppService.java:152）、SSE 工作线程（ChatController.java:108）都用它带链路。
5. **注册顺序讲究**：ai 服务 `WebMvcConfig#addInterceptors（config/WebMvcConfig.java:26-37）` 中 TraceId 是 order 0、TenantResolveInterceptor 是 order 1——**先有 traceId，"租户缺失"的报错日志才有 ID 可查**。

### 6.4 限流切点：Sentinel 网关流控

网关 `application.yml:47-69`：
- 规则类型 `gw-flow`（**按路由维度**限流），规则持久化在 Nacos data-id `aihub-gateway-flow-rules`（datasource 配置 53-63 行）——Dashboard 或 Nacos 控制台改规则不再"重启即丢"，单机没起 Nacos 时拉取失败仅 WARN 不阻断启动；
- 命中后兜底响应（65-69 行）：HTTP 429 + `{"code":10006,"message":"请求过于频繁，请稍后再试"}`——对应 `ResultCode.RATE_LIMITED(10006)`，前端识别 code 与其他错误走同一套处理。
- **为什么限流放网关**：流量未进业务前就挡掉，保护的是整个下游（Tomcat 线程池、数据库连接、模型 token 预算）；服务内部再按需用 `@SentinelResource` 做点级保护是第二层。

### 6.5 配额与降级：贯穿链路三/五的财务闸门

- **事前闸门**：对话前 `ChatAppService#checkQuota（ChatAppService.java:122-142）` 扣 REQUEST 次数；Agent 前扣 TASK（`consumeAgentTask`，177-191 行）；入库前扣 DOC（`KnowledgeAppService#checkDocQuota`，167-181 行）——平台明确拒绝（allowed=false）才抛 `QUOTA_EXCEEDED`；
- **事后补扣**：token 用量只有拿到模型响应才知道，`consumeTokens（ChatAppService.java:150-164）` 事后补扣，失败只记日志（钱已花掉，不能让用户看到错误）；
- **两级降级**：平台不可用时放行 + `eventOutbox.enqueue`（`ChatAppService#reportUsage`，249-261 行）落发件箱由 `EventOutboxDispatcher` 后台重投——宁可账面少扣，不能让对话失败，也不能让账永久丢。

### 6.6 横切面总结表

| 横切能力 | 网关（WebFlux） | 下游服务（Servlet） | 异步/跨线程 | 源码锚点 |
|---|---|---|---|---|
| TraceId | TraceIdGlobalFilter#filter | TraceIdInterceptor#preHandle | TraceContext#wrap | TraceContext.java:99 |
| 身份校验 | AuthGlobalFilter#filter | 信任内网（不做） | — | AuthGlobalFilter.java:83 |
| 租户注入 | AuthGlobalFilter#authenticateByJwt/ApiKey | TenantResolveInterceptor#preHandle | AiCallContext（AI 调用链） | TenantResolveInterceptor.java:42 |
| 统一响应 | 手写 JSON（unauthorized） | R + GlobalExceptionHandler | — | R.java:65 |
| 限流 | Sentinel gw-flow（Nacos 持久化） | — | — | gateway application.yml:53 |

## 7. 收尾：把五条链路串成一句话

一次用户提问的背后：
**认证链路**证明"你是谁"（JWT 签名背书 tenantId）→ **租户链路**保证"你只能看自己的"（头→ThreadLocal→SQL 条件→向量过滤四级传递）→ **RAG 链路**让模型"开卷考试"（异步入库、TopK 检索、受限 Prompt）→ **SSE 链路**把回答"一个字一个字"送回（三通道一编排、断连不惊慌）→ **工具/Agent 链路**在模型需要时给它"手脚"（审计包装、三重预算、MCP 三件套）——而**横切面**（R/异常/TraceId/限流/配额）像五条平行焊缝，把五条链路固定在同一个工程底盘上。

面试时若只能讲一分钟项目，就讲这五条链路；若能讲五分钟，把每一跳的"为什么"展开——**架构的价值不在类图，在这些设计决策之间的因果**。
