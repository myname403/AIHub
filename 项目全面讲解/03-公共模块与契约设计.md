# 03 - 公共模块与契约设计（aihub-common 与 aihub-api）

> 本文档自成一体，不依赖阅读其他文档。文中所有源码路径均以仓库根目录（`javaai/`）为基准（即 `aihub/aihub-common/...`），引用格式为 `文件相对路径#行号`，全部经过存在性校验。

AIHub 是一个多租户 AI 平台微服务项目：网关（8080）→ 平台服务（8081，认证与 RBAC/租户/配额）→ AI 服务（8082，知识库/对话/Agent）。在这两个业务服务之外，还有两个"没有业务、却处处都在"的基础模块——`aihub-common` 与 `aihub-api`。它们不对外提供接口，却决定了：前端拿到什么格式的 JSON、业务异常长什么样、一次请求在多个服务间如何保持"同一租户、同一条链路"、以及 AI 服务如何调用平台服务扣配额。

一句话概括两者的分工：

- **aihub-common 是"通用语言"**：所有服务都说的方言——统一响应体、错误码、业务异常、租户上下文、链路追踪、安全工具。
- **aihub-api 是"电话专线"**：只有需要跨服务通话的两端才接入——Feign 契约接口 + 跨服务 DTO + 配额维度常量。

## 1. 为什么要有 common 与 api 两个独立模块

### 1.1 先看依赖关系图

```text
                    ┌────────────────────────────┐
                    │  aihub-common（通用语言）    │
                    │  R / ResultCode / BizException / GlobalExceptionHandler
                    │  TenantContext / TraceContext（+ 两个拦截器）
                    │  JwtVerifier / ApiKeyCodec / AesGcmTextCipher
                    └──────────┬─────────────────┘
                               │ 被 5 个模块依赖
        ┌──────────┬───────────┼───────────────┬──────────────┐
        ▼          ▼           ▼               ▼              ▼
   aihub-gateway  platform  aihub-ai-service  aihub-api   （mcp 三件套按需）
   （WebFlux）    （8081）   （8082）            ▲
        │            │         │               │ 仅两端依赖
        │            │         ├─── Feign 调用 ──┘
        │            ◄─────────┘  （契约接口 PlatformClient 两端共享）
        │
        └─ 网关也直接引用 common 的 TenantContext/TraceContext 常量
           （aihub/aihub-gateway/src/main/java/com/aihub/gateway/filter/AuthGlobalFilter.java#L116-L118）
```

依据是两个 POM 的真实依赖声明：

- `aihub/aihub-common/pom.xml#L12-L14`：`<description>通用支撑：统一响应、错误码、异常、租户上下文</description>`，依赖仅 `spring-boot-starter-web`、`jackson-databind`、`jjwt`（JWT 校验），非常"轻"。
- `aihub/aihub-api/pom.xml#L12-L14`：`<description>跨服务 Feign 契约与 DTO（AI 服务调用平台服务）</description>`，依赖 `aihub-common` + `spring-cloud-starter-openfeign` + `spring-cloud-starter-loadbalancer`（#L17-L28）。

### 1.2 复用 vs 解耦：为什么不合并成一个模块

合并的诱惑是真实存在的："都是公共代码，塞一个模块不就完了？"但拆成两个，换来三个可验证的好处：

**① 依赖最小化。** 平台服务是"被调用方"，它的启动类 `aihub/aihub-platform-service/src/main/java/com/aihub/platform/PlatformApplication.java#L23` 的注释明确写着：

```java
// 因此无需 @EnableFeignClients —— 只有"要调用别人"的服务才需要启用 Feign 客户端。
```

如果 common 和 api 合并，平台服务（以及网关、MCP 服务）将被迫拖入 openfeign/loadbalancer 整套依赖，却一行 Feign 代码都不写。拆开后，Feign 能力被隔离在 `aihub-api` 内，`aihub-api → aihub-common` 是单向依赖，没有反向污染。

**② 变更波及面可控。** 改 common 里的东西（比如响应体加字段）影响所有服务，这是"语言变更"，本来就应该大张旗鼓；改 api 里的东西（比如契约加参数）只影响通话两端，这是"专线变更"。混在一起后，你就失去了"区分这次改动是语言级还是专线级"的能力——代码评审时无法快速圈定受影响方。

**③ 契约的"编译期握手"才成立。** `aihub/aihub-api/src/main/java/com/aihub/api/client/PlatformClient.java#L28-L31` 的注释说得直白：

```java
 * <p><b>为什么接口和 DTO 都放在独立的 aihub-api 模块？</b>
 * 调用方（ai 服务）和服务提供方（platform 服务）都要引用"一模一样"的契约。
 * 放独立模块，两边依赖同一份 jar，改接口时编译器立刻暴露两端不一致 ——
 * 这就是"契约优先"（contract-first）设计。
```

### 1.3 改契约的爆炸半径（本章核心概念）

"爆炸半径"指：改动一处代码后，**会在多少个地方、以什么方式、在什么阶段**暴露故障。对这两个模块做一次逐项分析（所有场景均为本项目真实结构推导）：

| 改动 | 波及方 | 暴露阶段 | 后果与项目内的证据 |
|---|---|---|---|
| `R` 增删字段/改字段名 | 两个业务服务全部接口 + 两个前端 + Feign 反序列化 | 运行期 | 前端拿到的是不认识的结构，页面全挂；这是最高危的"语言级"改动 |
| `ResultCode` 某个枚举的数值变更 | 所有硬编码判断该 code 的前端代码 | 运行期（静默！） | 例如前端 `if (code === 10002) 跳登录`，后端改了数值前端不报错但逻辑失效——**静默失效比崩溃更危险** |
| `ResultCode` 新增枚举 | 无 | 编译期 | 向后兼容，安全 |
| `TenantContext.HEADER_TENANT` 改名 | 网关过滤器 + 两个服务的拦截器 + Feign 透传，**共 4 处** | 编译期 | 因为各方都引用同一常量（`AuthGlobalFilter.java#L116`、`TenantResolveInterceptor.java#L45`、`FeignTenantConfig.java#L50`），编译器一次性暴露全部调用点——这正是常量收敛的价值 |
| `PlatformClient` 方法签名/路径 | AI 服务调用点 + 平台服务 `InternalController` | 编译期 | 两端编译不过，被迫同步修改——契约模块的核心收益 |
| `PlatformClient` 的 record 新增字段 | 兼容 | 运行期无感 | Spring Boot 默认关闭 `FAIL_ON_UNKNOWN_PROPERTIES`，旧端收到多余字段会忽略 |
| `PlatformClient` 的 record 删字段/改名 | 对端反序列化 | 运行期 | 对端拿到 `null`/`0`，可能出现"配额永远为 0"这类业务事故 |
| `QuotaDimensions` 字面量（如 `"token"` 改成 `"tokens"`） | 双端编译期同步改，**但历史存量数据不会改** | 运行期（静默！） | `ai_usage_record` 等表里已落库的旧维度字符串与新口径对不上，配额账目静默错乱 |
| `FeignTenantConfig` 透传逻辑删除 | 平台服务 `TenantResolveInterceptor` | 运行期（请求级） | AI 服务发起的所有 Feign 调用被平台侧 fail-fast 拒绝（`TenantResolveInterceptor.java#L49-L51` 租户头缺失即抛异常） |

从表中提炼出两条设计纪律：

1. **能编译期暴露的，绝不留给运行期**——常量收敛、契约共享 jar 都是这个目的。
2. **静默失效（对不上账、逻辑空转）是比异常更可怕的故障**——错误码数值、配额维度字面量这类"跨进程口径"一旦定下，变更必须连带数据迁移，而不是只改代码。

## 2. aihub-common 逐类讲解

common 模块共 11 个类，全部位于 `com.aihub.common` 下的 6 个包中。先给出归类总表，再逐类四段式讲解。

| 归类 | 包 | 类 | 一句话职责 |
|---|---|---|---|
| 统一响应 | result | `R<T>` | 全项目所有 HTTP 接口的返回外壳 |

### 2.1 统一响应体 `R<T>`

来源：`aihub/aihub-common/src/main/java/com/aihub/common/result/R.java`

**作用与原理。** 微服务下前端会同时调网关后的多个服务接口，若每个服务返回格式不同，前端就要写各种兼容分支。`R` 用一个四字段外壳统一了成功与失败：

```java
// 来源：aihub/aihub-common/src/main/java/com/aihub/common/result/R.java
@Data
@JsonInclude(JsonInclude.Include.NON_NULL)  // 转 JSON 时跳过 null 字段，失败响应不会出现 "data": null
public class R<T> implements Serializable {
    private int code;        // 业务码：0 成功，非 0 见 ResultCode
    private String message;  // 给人看的提示
    private T data;          // 业务数据，失败时通常为 null
    private String traceId;  // 链路追踪 ID，拿它跨服务搜日志
}
```

三个关键设计：

1. **私有构造器 + 静态工厂**（`R.java#L58`、`R.java#L74-L96`）：外部不能 `new R<>()`，只能 `R.ok(...)` / `R.fail(...)`。所有工厂方法都经过私有方法 `build`（`R.java#L65-L71`），traceId 在这一处统一从 `TraceContext.get()` 填充——把"怎么构造"收拢到一处，杜绝"有的接口忘了填 traceId"这种不一致。
2. **HTTP 状态码恒为 200，成败看 body 里的 `code`**。业务码分段规则定义在 `ResultCode` 注释里（`ResultCode.java#L13-L21`）：0 成功、1xxxx 通用错误、2xxxx AI 能力错误、5xxxx 系统错误。好处是前端拦截器只需读 body 一个地方；代价是网关层必须注意：业务错误不会体现在 HTTP 状态码上。
3. **`@JsonInclude(NON_NULL)`**（`R.java#L37`）：失败时响应体干净地只有 `code/message/traceId` 三个键。

**项目真实用例。** 登录接口是教科书式的一处：

```java
// 来源：aihub/aihub-platform-service/src/main/java/com/aihub/platform/auth/controller/AuthController.java
public R<AuthLoginRespVO> login(@Valid @RequestBody AuthLoginReqVO reqVO) {   // #L64
    return R.ok(authService.login(reqVO));                                    // #L65
}
```

AI 服务的知识库接口同样大量使用 `R.ok(knowledgeAppService.listKb(TenantContext.requireTenantId()))`（`aihub/aihub-ai-service/src/main/java/com/aihub/ai/web/KnowledgeController.java#L45`）。全局异常处理器也依赖 `R.fail` 三个重载（见 2.4）。

**常见误用。**

- 绕过工厂方法暴露构造：不可能，编译器拦着——这正是私有构造器的意义。
- 在 Controller 里手动拼 `R.fail(10003, "xxx")`：项目里真有这种写法——`aihub/aihub-platform-service/src/main/java/com/aihub/platform/internal/controller/InternalController.java#L50` 写了 `R.fail(10003, "租户不存在或已停用")`，其上方注释（#L48）也承认"直接用数字 10003 而不是 `ResultCode.FORBIDDEN.getCode()`——两种写法等价，枚举更规范"。能用，但把魔法数字重新散回了业务代码，与 `ResultCode` 的集中管理初衷相悖。
- 误以为 `R` 会自动携带 HTTP 401/403：不会。想让浏览器行为正确（如触发登录跳转），要么前端按 code 分支处理，要么网关层显式返回对应 HTTP 状态码。

**面试怎么说。** "我们用私有构造 + 静态工厂把响应体的构造收敛到唯一出口，traceId 在工厂方法里统一从 ThreadLocal 取值填充，配合 `@JsonInclude(NON_NULL)` 保证失败响应干净；业务码与 HTTP 状态码解耦、按分段枚举集中管理。这套设计本质上是用类型系统约束'接口出参只有一种形状'，前端 axios 拦截器只需写一次判码逻辑。"

### 2.2 错误码枚举 `ResultCode`

来源：`aihub/aihub-common/src/main/java/com/aihub/common/result/ResultCode.java`

**作用与原理。** 用枚举集中管理 `R.code` 的合法取值（`ResultCode.java#L28-L79`），分段如下（本项目真实取值）：

| 分段 | 枚举 | 值 | 含义 |
|---|---|---|---|
| 成功 | `SUCCESS` | 0 | 成功码是 0 而不是 200，与 HTTP 语义区分 |
| 通用 1xxxx | `PARAM_ERROR` | 10001 | `@Valid` 校验失败等 |
| | `UNAUTHORIZED` | 10002 | 未认证/令牌失效，前端应跳登录 |
| | `FORBIDDEN` | 10003 | 已认证但无权限 |
| | `NOT_FOUND` | 10004 | 资源不存在 |
| | `TENANT_MISMATCH` | 10005 | **跨租户访问被拒**——多租户核心防线 |
| | `RATE_LIMITED` | 10006 | Sentinel 限流命中 |
| | `QUOTA_EXCEEDED` | 10007 | 租户配额耗尽 |
| AI 2xxxx | `MODEL_UNAVAILABLE` | 20001 | 主备模型都失败 |
| | `MODEL_DEGRADED` | 20002 | 已降级到备用模型 |
| | `KNOWLEDGE_EMPTY` | 20003 | RAG 检索无命中 |
| | `TOOL_TIMEOUT` | 20004 | Agent 工具调用超时 |
| | `AGENT_BUDGET_EXCEEDED` | 20005 | Agent 步数/token 预算耗尽 |
| 系统 5xxxx | `SYSTEM_ERROR` | 50000 | 未捕获异常的兜底文案 |
| | `UPSTREAM_UNAVAILABLE` | 50001 | Feign 下游不可用 |

选择枚举而非常量类的理由写在注释里（`ResultCode.java#L8-L11`）：可读性（`UNAUTHORIZED` 比 `10002` 可读）、集中管理、编译期防拼错。每个枚举实例由构造器固定 `code + message` 两个 final 字段（#L81-L94），JVM 保证实例唯一。

**项目真实用例。** 登录服务的密码校验（`aihub/aihub-platform-service/src/main/java/com/aihub/platform/auth/service/AuthService.java#L100`）：

```java
// 来源：aihub/aihub-platform-service/src/main/java/com/aihub/platform/auth/service/AuthService.java
throw new BizException(ResultCode.UNAUTHORIZED, "用户名或密码错误");   // #L100（#L104 同）
```

配额超限（`aihub/aihub-ai-service/src/main/java/com/aihub/ai/application/ChatAppService.java#L135`）：`throw new BizException(ResultCode.QUOTA_EXCEEDED, result.reason())`——把平台服务返回的拒绝原因透传给用户。

**常见误用。** ① 数值变更不具向后兼容性（见 1.3 爆炸半径表）；② 把"用户可读的 message"当成"日志排障信息"——`SYSTEM_ERROR` 的文案是刻意笼统的，真实堆栈只在 `GlobalExceptionHandler` 的日志里（`GlobalExceptionHandler.java#L66`），若把内部细节拼进 message 会直接泄露给前端。

**面试怎么说。** "错误码分四个段位：0、1xxxx 通用、2xxxx AI 业务、5xxxx 系统，分段让'这类错该谁处理'一眼可判；用枚举而非常量类是因为枚举有编译期类型安全和不可变性，还避免了'常量类被继承污染常量'的老问题。"

### 2.3 业务异常 `BizException`

来源：`aihub/aihub-common/src/main/java/com/aihub/common/exception/BizException.java`

**作用与原理。** 表示"业务规则不允许"的**可预期**错误。继承 `RuntimeException`（非受检异常）的原因（#L9-L12）：受检异常会强迫每一层写 `throws`/`try-catch`，而业务异常 99% 的中间层都不需要关心——让它一路向上抛，最终由 `GlobalExceptionHandler` 统一转成响应体。类结构极简：

```java
// 来源：aihub/aihub-common/src/main/java/com/aihub/common/exception/BizException.java
@Getter
public class BizException extends RuntimeException {
    private final int code;   // 最终写入 R.code 的业务码
    public BizException(ResultCode resultCode) { ... }               // #L38 用枚举默认文案
    public BizException(ResultCode resultCode, String message) { ... } // #L45 自定义文案（最常用）
    public BizException(ResultCode resultCode, String message, Throwable cause) { ... } // #L51 保堆栈
}
```

三个构造器对应三种场景：默认文案、自定义文案、包装底层异常（保留完整堆栈便于排障）。

**项目真实用例。** 平台服务的认证链路（`AuthService.java#L91-L108`）连续三个 BizException 分支：验证码错误（`PARAM_ERROR`）、用户名或密码错误（`UNAUTHORIZED`）、账号停用（`FORBIDDEN`）。AI 服务的知识库入口也有 `TenantResolveInterceptor.java#L50` 的 `throw new BizException(ResultCode.TENANT_MISMATCH, "请求缺少租户上下文")`——用异常代替返回 `false`，让错误信息更明确地经全局处理器变成响应体。

**常见误用。** ① message 会**原样返回给前端**（`GlobalExceptionHandler.handleBiz` 不做脱敏），拼入密钥、完整 Prompt、SQL 就是事故——类注释 #L25-L27 明确警告了这点；② 在中间层 `catch` 后转抛别的新异常，业务码丢失，前端拿到 50000 而不是真实业务码；③ 把 BizException 当控制流滥用（用异常做正常分支跳转），破坏代码可读性。

**面试怎么说。** "业务异常选非受检是分层取舍：可预期错误不该污染中间层签名，统一在 `@RestControllerAdvice` 出口转换。异常对象携带业务码而非裸文本，让'错误码'这种契约信息在异常链路里不丢。"

### 2.4 全局异常处理器 `GlobalExceptionHandler`

来源：`aihub/aihub-common/src/main/java/com/aihub/common/exception/GlobalExceptionHandler.java`

**作用与原理。** `@RestControllerAdvice`（#L30）让本类成为所有 `@RestController` 的切面——任何未被业务代码捕获的异常都会进入匹配的 `@ExceptionHandler` 方法。按异常类型就近匹配，三个处理器构成兜底网：

```java
// 来源：aihub/aihub-common/src/main/java/com/aihub/common/exception/GlobalExceptionHandler.java
@ExceptionHandler(BizException.class)                    // #L37 第一层：业务异常
public R<Void> handleBiz(BizException e) {
    // 不写日志是有意的：密码错误这类"正常业务分支"记 error 会污染告警   // #L39
    return R.fail(e.getCode(), e.getMessage());
}

@ExceptionHandler({MethodArgumentNotValidException.class, BindException.class})  // #L48 第二层：参数校验
public R<Void> handleValidate(Exception e) {
    // instanceof 模式匹配（Java 16+）：判断+强转一步完成                    // #L51
    String msg = e instanceof MethodArgumentNotValidException m
            ? m.getBindingResult().getFieldError() != null
                    ? m.getBindingResult().getFieldError().getDefaultMessage()
                    : "参数校验失败"
            : "参数绑定失败";
    return R.fail(ResultCode.PARAM_ERROR, msg);
}

@ExceptionHandler(Exception.class)                       // #L64 第三层：兜底
public R<Void> handleException(Exception e) {
    log.error("未处理异常", e);                            // #L66 完整堆栈只进日志
    return R.fail(ResultCode.SYSTEM_ERROR);               // #L67 前端只拿笼统文案
}
```

两处安全细节值得咀嚼：兜底层把真实异常细节**只写日志**、给前端永远返回"系统内部错误"，防止泄露表名/类名/模型地址（#L59-L63 注释）；业务异常层**刻意不打日志**（#L39），避免把"密码错误"这种正常分支刷爆 error 告警。

**项目真实用例。** 它生效的前提藏在两个启动类里——`@SpringBootApplication(scanBasePackages = "com.aihub")`（`aihub/aihub-platform-service/src/main/java/com/aihub/platform/PlatformApplication.java#L46`、`aihub/aihub-ai-service/src/main/java/com/aihub/ai/AiServiceApplication.java#L50`），把扫描范围从默认的 `com.aihub.platform`/`com.aihub.ai` 扩大到整个 `com.aihub`，common 包里的 `@RestControllerAdvice` 才会被注册。`AiServiceApplication.java#L48-L49` 的注释点明了动机："让 common 的 GlobalExceptionHandler 接管业务异常，统一返回 `{"code":xxx}` 响应体而不是原生 500"。实际触发示例：`ApiKeyController` 的 `@Valid` 校验失败（`aihub/aihub-platform-service/src/main/java/com/aihub/platform/apikey/controller/ApiKeyController.java#L64`）由 `handleValidate` 把 `@NotBlank` 的 message 送回前端；吊销接口对不存在的密钥抛出的 `NOT_FOUND`（`aihub/aihub-platform-service/src/main/java/com/aihub/platform/apikey/controller/ApiKeyController.java#L89`）走 `handleBiz`。

**常见误用。** ① 以为它是全系统兜底——类注释 #L26-L27 明确说明：网关（WebFlux）过滤器里的异常**不走这里**，网关必须自己处理；SSE/WS 异步链路里抛的异常也要在各自通道内转换成事件（如 `ChatAppService.java#L109-L112` 的注释"执行器已发出 error 事件并关闭 sink；此处仅记录，避免向上抛断开连接"）。② 忘了扩大 `scanBasePackages`，导致 common 的处理器根本没注册，业务异常变成原生 Whitelabel 500——这是引入 common 模块后最常见的"为什么不生效"问题。

**面试怎么说。** "异常处理我做三件事：分层匹配（业务异常静默透传、校验异常取字段 message、未知异常兜底脱敏）、日志分级（业务异常不打 error 防告警污染、未知异常只进日志不进响应）、以及用组件扫描把处理器以共享 jar 的方式装配进每个服务——公共模块的 Bean 生效依赖 `scanBasePackages` 扩大，这是 Spring 多模块装配的经典坑。"

### 2.5 租户上下文 `TenantContext`

来源：`aihub/aihub-common/src/main/java/com/aihub/common/tenant/TenantContext.java`

**作用与原理。** SaaS 多租户的第一安全约束：任何查询必须限定当前租户，绝不允许 A 租户看到 B 租户数据。`TenantContext` 用两个 `ThreadLocal<Long>`（#L32-L35）保存"当前请求是谁"：

```java
// 来源：aihub/aihub-common/src/main/java/com/aihub/common/tenant/TenantContext.java
public static final String HEADER_TENANT = "X-Tenant-Id";   // #L26 服务间透传租户的请求头
public static final String HEADER_USER   = "X-User-Id";     // #L29 服务间透传用户

public static void set(Long tenantId, Long userId) { ... }  // #L42 入口一次性写入
public static Long requireTenantId() {                      // #L53 缺失即抛 TENANT_MISMATCH
    Long id = TENANT.get();
    if (id == null) {
        throw new com.aihub.common.exception.BizException(
                com.aihub.common.result.ResultCode.TENANT_MISMATCH, "租户上下文缺失");
    }
    return id;
}
public static void clear() { TENANT.remove(); USER.remove(); }  // #L82 出站必须清理
```

三个设计要点：**① 租户 ID 只允许从 JWT/API Key 解析后写入，绝不接受前端传参**（#L17-L18 标注为"最高危项"）；**② `requireTenantId` 与 `getTenantId` 的语义区分**——前者把"缺租户"升格为越权风险强制失败，后者容忍定时任务等无请求场景返回 null；**③ `clear` 防串台**——线程池复用线程，不清理则上一个请求的租户泄漏给下一个请求，这是 ThreadLocal 最经典的内存泄漏/数据串台坑（#L78-L80 注释）。

**项目真实用例。** 三个层面的消费者：Controller 层 `TenantContext.requireTenantId()`（`aihub/aihub-ai-service/src/main/java/com/aihub/ai/web/KnowledgeController.java#L39`）；MyBatis-Plus 租户插件里自动拼 SQL 条件（`aihub/aihub-platform-service/src/main/java/com/aihub/platform/config/MybatisPlusConfig.java#L106-L112`、AI 侧同类实现 `aihub/aihub-ai-service/src/main/java/com/aihub/ai/config/TenantSqlGuardConfig.java#L121-L130`）；跨服务透传由 Feign 拦截器搬运（`aihub/aihub-api/src/main/java/com/aihub/api/config/FeignTenantConfig.java#L46-L53`）。写入方是网关：`AuthGlobalFilter.java#L116-L118` 剥离客户端伪造的 `X-Tenant-Id` 后用解析出的 claims 重写（`aihub/aihub-gateway/src/main/java/com/aihub/gateway/filter/AuthGlobalFilter.java`）。

**常见误用。** ① 在异步线程里直接调 `TenantContext.getTenantId()` 拿到 null——ThreadLocal 不跨线程，需要显式快照传递（参考 `TraceContext.wrap` 的思路）；② 忘记在自定义异步出口调 `clear()`；③ 从请求参数/cookie 里读租户 ID 写入上下文——等于亲手拆掉隔离防线。

**面试怎么说。** "多租户行级隔离的上下文传递我用 ThreadLocal 做'请求级会话'，配合拦截器一进一出配对（preHandle 写入、afterCompletion 清理）。安全上坚持'租户身份只来自服务端解析的令牌'，`requireXxx` 语义把缺失上下文定义为越权风险而非空值场景；跨服务则由 Feign 拦截器统一透传，业务代码全程不接触 HTTP 头。"

### 2.6 租户解析拦截器 `TenantResolveInterceptor`

来源：`aihub/aihub-common/src/main/java/com/aihub/common/tenant/TenantResolveInterceptor.java`

**作用与原理。** 下游服务（platform/ai）的入口组件，实现 `HandlerInterceptor`：`preHandle` 把网关写入的 `X-Tenant-Id`/`X-User-Id` 头解析进 `TenantContext`（#L42-L56），`afterCompletion` 清理（#L63-L66）。两个关键决策：

1. **信任链与边界统一鉴权**（#L20-L23 注释）：租户头之所以可信，是因为网关已强制剥离客户端伪造的同名头；内网服务信任内网流量，鉴权只做一次。
2. **fail-fast**（#L49-L51）：租户头缺失直接抛 `TENANT_MISMATCH`，宁可拒绝请求，也不让"无主请求"进入业务层——否则"漏传租户"会演变成越权。

```java
// 来源：aihub/aihub-common/src/main/java/com/aihub/common/tenant/TenantResolveInterceptor.java
if (tenant == null || tenant.isBlank()) {
    throw new BizException(ResultCode.TENANT_MISMATCH, "请求缺少租户上下文");   // #L50
}
TenantContext.set(Long.valueOf(tenant), user == null || user.isBlank() ? null : Long.valueOf(user)); // #L54
```

**项目真实用例。** 注册点在两个服务的 `WebMvcConfig`：AI 侧 `aihub/aihub-ai-service/src/main/java/com/aihub/ai/config/WebMvcConfig.java#L28-L36`——先注册 `TraceIdInterceptor`（order 0）再注册本拦截器（order 1），并排除 `/actuator/**`、`/error`、`/v3/api-docs/**`、`/swagger-ui/**`；平台侧 `aihub/aihub-platform-service/src/main/java/com/aihub/platform/config/WebMvcConfig.java#L46-L49` 同构。顺序之所以讲究：**先有 traceId，租户缺失的报错日志才有 ID 可查**（`TraceIdInterceptor.java#L20` 注释同款要求）。

**常见误用。** ① 只创建拦截器实例不注册到 `WebMvcConfigurer`，组件扫描不会自动生效——它是普通类而非 `@Component`（`TenantResolveInterceptor.java#L28-L30` 注释明确要求手动注册）；② 把内部探活/文档端点也纳入拦截，导致健康检查全红；③ 在 `preHandle` 返回 `false` 代替抛异常——前端只会收到空 200，而抛 BizException 能拿到结构化错误码。

**面试怎么说。** "拦截器 vs 过滤器我选拦截器做租户解析：它运行在 Spring MVC 体系内，能拿到 handler 信息、能被 `WebMvcConfigurer` 精细控制 order 和排除路径，抛出的异常还能被同体系的 `@RestControllerAdvice` 接住转成统一响应体。租户头采用'网关剥离重写 + 下游 fail-fast'的双保险信任链。"

### 2.7 链路上下文 `TraceContext`

来源：`aihub/aihub-common/src/main/java/com/aihub/common/trace/TraceContext.java`

**作用与原理。** 微服务下一个请求穿网关、平台、AI 多个服务，没有 TraceId 排障就要翻遍所有服务日志手工拼链路。`TraceContext` 实现 **ThreadLocal + SLF4J MDC 双写**（#L15-L21 注释）：

- ThreadLocal（`HOLDER`，#L39）给业务代码和 `R.traceId` 自动填充用；
- MDC 给日志框架用——logback pattern 配 `%X{traceId}` 后每行日志自动带 ID，业务代码零改动。

`set` 同时写两边（#L65-L73），空值双清防脏数据；`newTraceId` 用 UUID 去连字符生成 32 位十六进制（#L46-L48）方便 grep；`getOrDefault` 用 `-` 占位保证日志格式整齐（#L56-L59）。

最精妙的是 `wrap`（#L99-L113）——解决"ThreadLocal 不跨线程"：

```java
// 来源：aihub/aihub-common/src/main/java/com/aihub/common/trace/TraceContext.java
public static Runnable wrap(Runnable task) {
    String traceId = HOLDER.get();          // 提交任务那一刻在主线程"拍快照"
    return () -> {
        String previous = HOLDER.get();     // 记住工作线程原有值
        set(traceId);                       // 把快照 set 进当前工作线程
        try {
            task.run();
        } finally {
            set(previous);                  // 还原，不污染线程池里复用的线程
        }
    };
}
```

**项目真实用例。** SSE 流式对话是核心消费者——模型生成在独立线程池执行，必须显式带链路：`aihub/aihub-ai-service/src/main/java/com/aihub/ai/web/ChatController.java#L108` 的 `streamExecutor.submit(TraceContext.wrap(() -> {...}))`；WebSocket Agent 同理（`aihub/aihub-ai-service/src/main/java/com/aihub/ai/web/ws/AgentWebSocketHandler.java#L85`）。Feign 透传端在 `FeignTenantConfig.java#L56` 用 `TraceContext.ensure()`——本地没有就现场生成，避免下游出现"无 traceId"的孤立日志。

**常见误用。** ① 异步任务直接 `executor.submit(() -> ...)`，工作线程里 traceId 为空，日志链断掉；② 在 wrap 里不还原 `previous`，污染线程池；③ 只写 ThreadLocal 忘写 MDC（或反之），日志和响应体里的 traceId 对不上。

**面试怎么说。** "全链路追踪我做的是轻量自研版：UUID traceId + ThreadLocal/MDC 双写，入口拦截器'优先复用上游、缺失才生成'保证全链路同一 ID；跨线程用装饰器模式包一层 Runnable 快照传递并 finally 还原。生产级方案可以平滑升级成 SkyWalking/OTel，但自研这 120 行让团队真正理解 MDC 和 ThreadLocal 传播原理。"

### 2.8 链路追踪拦截器 `TraceIdInterceptor`

来源：`aihub/aihub-common/src/main/java/com/aihub/common/trace/TraceIdInterceptor.java`

**作用与原理。** Servlet 栈入口组件：`preHandle`（#L31-L43）优先复用上游传来的 `X-Trace-Id`（网关已生成过，大多数请求直接命中），缺失才新生成；写入 ThreadLocal + MDC 后**回写响应头**（#L41）——即便 body 是流式输出，前端也能从响应头拿到本次链路 ID。`afterCompletion`（#L46-L50）清理防串台。

```java
// 来源：aihub/aihub-common/src/main/java/com/aihub/common/trace/TraceIdInterceptor.java
String incoming = request.getHeader(TraceContext.HEADER);                    // #L35
String traceId = incoming == null || incoming.isBlank()
        ? TraceContext.newTraceId() : incoming;                              // #L36-L37
TraceContext.set(traceId);                                                   // #L39
response.setHeader(TraceContext.HEADER, traceId);                            // #L41
```

**项目真实用例。** 注册于两个服务 `WebMvcConfig` 且 **order 必须小于租户拦截器**：`aihub-ai-service/.../config/WebMvcConfig.java#L28-L30`（order 0）先于 #L31-L36 的租户拦截器（order 1）——理由是 #L27 注释写的"TraceId 必须先就绪，否则租户校验失败的日志里拿不到链路 ID"。网关侧（WebFlux）不用本类，对应实现是 `aihub/aihub-gateway/src/main/java/com/aihub/gateway/filter/TraceIdGlobalFilter.java#L37-L48`，两端口径一致（同一 `TraceContext.HEADER` 常量，#L38 引用）。

**常见误用。** ① 与租户拦截器注册顺序颠倒，排障日志缺 ID；② 忘记回写响应头，前端无法自助上报链路 ID；③ 在 WebFlux 网关误用这个 Servlet 拦截器——类型都不兼容，必须用 WebFilter。

**面试怎么说。** "入口组件的 order 是语义的一部分：日志上下文先于业务上下文建立，任何'拒绝请求'类的报错才可追踪。同一个常量 `X-Trace-Id` 被网关 WebFilter 与下游 HandlerInterceptor 共同引用，保证多框架栈（WebFlux/Servlet）不出现两套 ID 体系。"

### 2.9 JWT 校验器 `JwtVerifier`

来源：`aihub/aihub-common/src/main/java/com/aihub/common/security/JwtVerifier.java`

**作用与原理。** JWT 是三段式令牌（Header.Payload.Signature），服务端不存会话、验签通过即认人。本类只做**校验**（签发在平台服务 `JwtTokenProvider`），核心 15 行：

```java
// 来源：aihub/aihub-common/src/main/java/com/aihub/common/security/JwtVerifier.java
public static Map<String, Object> verify(String secret, String token) {
    try {
        Claims claims = Jwts.parser()
                .verifyWith(Keys.hmacShaKeyFor(secret.getBytes(StandardCharsets.UTF_8)))  // #L50 绑定验签密钥
                .build()
                .parseSignedClaims(token)   // #L52 验签 + 过期检查 + 格式检查，任一失败抛异常
                .getPayload();              // #L53 Claims 继承自 Map
        return claims;
    } catch (Exception e) {
        return Map.of();                    // #L58 无效令牌返回空 Map，不抛异常
    }
}
```

两个设计取舍：**① "空结果"而非抛异常**（#L43-L44）——无效 token 在网关侧是常态不是故障，让调用方用 `isEmpty()` 判断，调用点不必包 try-catch；**② 为什么网关验过一次这里还要验**（#L27-L29）——纵深防御：WebSocket 握手（`AgentWebSocketHandler` 直连 AI 服务）等入口绕过网关过滤器，必须自己再验，"不能假设一定有人验过了"。

**项目真实用例。** WebSocket 握手鉴权（`aihub/aihub-ai-service/src/main/java/com/aihub/ai/web/ws/AgentWebSocketHandler.java#L53`）：

```java
// 来源：aihub/aihub-ai-service/src/main/java/com/aihub/ai/web/ws/AgentWebSocketHandler.java
Map<String, Object> claims = JwtVerifier.verify(jwtSecret, token);
```

**常见误用。** ① 复用本类做**签发**——它只有 verify；签发逻辑（含 claims 组装、过期时间策略）在平台服务，职责分离防"校验端"误持签发能力。② 把 `Map.of()` 空返回当成"用户存在但无 claims"，漏判导致 NPE——正确姿势是先判空再取字段。③ HS256 密钥少于 32 字节会在 `Keys.hmacShaKeyFor` 直接抛 `WeakKeyException`，配置密钥时要注意长度。

**面试怎么说。** "JWT 无状态认证里我把签发与校验拆到不同模块：平台服务签发、common 提供校验工具，网关统一校验一次后透传身份头；对 WebSocket 这类旁路入口做二次校验实现纵深防御。校验失败用空对象而不是异常表达'无效令牌'，把异常留给真正的系统故障——这是把'预期失败'与'意外失败'区分开的典型实践。"

### 2.10 API Key 编解码 `ApiKeyCodec`

来源：`aihub/aihub-common/src/main/java/com/aihub/common/security/ApiKeyCodec.java`

**作用与原理。** 除用户名密码登录外，程序间调用（脚本/第三方集成）用 API Key 鉴权。四个静态方法构成完整生命周期：

- `generate`（#L46-L51）：`SecureRandom` 产 24 字节（约 192 bit 熵）→ hex 48 字符，加 `ak_` 前缀。**明文只在签发时返回一次**。
- `hash`（#L59-L71）：HMAC-SHA256 计算存储哈希。为什么用 HMAC 而不是密码学的 bcrypt（#L21-L25 注释）：bcrypt 刻意慢是为抗弱口令暴力破解，而 Key 是 256 位随机值不存在被猜中问题，鉴权又在每个请求上发生，慢哈希会拖垮吞吐；HMAC 带服务端密钥（不落库），即使库被拖走也无法伪造可用 Key——这是对"拖库"的最后防线。
- `prefixOf`（#L77-L82）：取 `ak_9f3c` 形式的前缀用于控制台展示，短值防越界。
- `matches`（#L96-L104）：重算哈希后用 `MessageDigest.isEqual` 做**常数时间比较**——`String.equals` 发现第一个不同字符就返回，攻击者可测比较耗时逐字节猜哈希（时序侧信道攻击），`MessageDigest.isEqual` 无论差在哪耗时相同。

```java
// 来源：aihub/aihub-common/src/main/java/com/aihub/common/security/ApiKeyCodec.java
byte[] actual = hash(rawKey, secret).getBytes(StandardCharsets.UTF_8);      // #L101
byte[] expected = expectedHash.getBytes(StandardCharsets.UTF_8);
return MessageDigest.isEqual(actual, expected);                             // #L103
```

**项目真实用例。** 平台服务签发与校验（`aihub/aihub-platform-service/src/main/java/com/aihub/platform/apikey/service/ApiKeyService.java`）：签发三连 `generate`/`hash`/`prefixOf`（#L68、#L73-L74），校验重算哈希（#L97）；哈希值经契约接口回传网关做鉴权（`aihub/aihub-api/src/main/java/com/aihub/api/client/PlatformClient.java#L68-L72` 的 `verifyApiKey`）。common 自带单测覆盖熵、确定性、密钥隔离、防时序等性质（`aihub/aihub-common/src/test/java/com/aihub/common/security/ApiKeyCodecTest.java#L23-L124`）。

**常见误用。** ① 存明文 Key——签名接口明文只返回一次，丢了只能重置；② 用 `String.equals` 比哈希，埋下时序攻击面；③ HMAC 密钥与数据加密密钥混用同一配置项，违反密钥用途分离。

**面试怎么说。** "API Key 安全我按'生成-存储-校验'三段设计：SecureRandom 高熵生成、HMAC-SHA256 带服务端密钥哈希存储（库被拖走也伪造不出可用 Key）、常数时间比较防时序侧信道。选用 HMAC 而非 bcrypt 是按'威胁模型'做的性能取舍——抗暴力猜解靠熵，不靠慢。"

### 2.11 AES-GCM 文本加解密 `AesGcmTextCipher`

来源：`aihub/aihub-common/src/main/java/com/aihub/common/crypto/AesGcmTextCipher.java`

**作用与原理。** 解决"模型 API Key（如 DeepSeek 的 key）明文落库，拖库即泄露"的问题——静态数据加密（encryption at rest）。选 AES-GCM 而非 AES-CBC（#L19-L21）：GCM 是认证加密，密文被篡改一位解密直接失败（自带完整性校验），而 CBC 会返回乱码。

```java
// 来源：aihub/aihub-common/src/main/java/com/aihub/common/crypto/AesGcmTextCipher.java
public static String encrypt(String plainText, String keyPhrase) {
    byte[] iv = new byte[IV_LENGTH];                                  // #L63 12 字节随机 IV
    RANDOM.nextBytes(iv);
    Cipher cipher = Cipher.getInstance(ALGO);                         // "AES/GCM/NoPadding" #L37
    cipher.init(Cipher.ENCRYPT_MODE, deriveKey(keyPhrase), new GCMParameterSpec(TAG_BITS, iv));
    byte[] cipherText = cipher.doFinal(plainText.getBytes(StandardCharsets.UTF_8));  // #L69 doFinal 同时生成认证标签
    byte[] out = new byte[iv.length + cipherText.length];             // #L71 拼 IV||密文
    System.arraycopy(iv, 0, out, 0, iv.length);
    System.arraycopy(cipherText, 0, out, iv.length, cipherText.length);
    return Base64.getEncoder().encodeToString(out);                   // #L75 存 VARCHAR 列
}
```

三个安全约定（#L23-L28）：密钥来自环境变量/Nacos 的 `aihub.security.data-key`，不落库不打日志；每次加密随机 IV（IV 不需保密但绝不能重复），同一明文两次密文不同防彩虹表；解密失败提示直接指向最常见原因——换了 data-key 导致旧密文解不开（#L104）。`deriveKey`（#L112-L121）用 SHA-256 把任意长度口令"整形"为 AES-256 要求的恰好 32 字节。

**项目真实用例。** AI 服务调用模型前解密：`aihub/aihub-ai-service/src/main/java/com/aihub/ai/infra/ai/OpenAiCompatibleChatModelResolver.java#L35`：

```java
// 来源：aihub/aihub-ai-service/src/main/java/com/aihub/ai/infra/ai/OpenAiCompatibleChatModelResolver.java
String apiKey = AesGcmTextCipher.decrypt(endpoint.apiKeyCipher(), dataKey);
```

配套单测验证"同一明文两次加密结果不同"与"换密钥解不开"（`aihub/aihub-common/src/test/java/com/aihub/common/crypto/AesGcmTextCipherTest.java#L25-L33`）。

**常见误用。** ① 固定 IV——同一明文密文相同，GCM 在 IV 重用时甚至会被推导出认证密钥，这是密码学大忌；② 用 `new Random()` 替代 `SecureRandom`，序列可预测；③ 换了 `aihub.security.data-key` 却不迁移存量密文，所有已保存的模型 Key 集体解密失败；④ 把解密出的明文 Key 打进日志。

**面试怎么说。** "静态数据加密我选 AES-GCM：认证加密自带完整性校验，密文被篡改直接解密失败而不是返回乱码；每次加密随机 12 字节 IV 且与密文一起 base64 存储，口令经 SHA-256 派生成 256 位密钥。加密对象是用户配置的第三方模型 Key——泄露后果是别人替用户付费，所以必须 at-rest 加密 + 使用时才在内存解密。"

## 3. aihub-api 契约讲解

api 模块仅 3 个类，但"以少驭多"：一个 Feign 接口 + 内嵌 8 个 record DTO、一个维度常量类、一个 Feign 透传配置。

| 归类 | 类 | 职责 |
|---|---|---|
| Feign 契约 | `PlatformClient` | AI 服务 → 平台服务的 5 个远程方法 + 8 个内嵌 record DTO |
| 跨服务共享常量 | `QuotaDimensions` | 配额计量维度字面量（request/token/doc/task） |
| Feign 配置 | `FeignTenantConfig` | 请求拦截器：每次调用自动透传租户/用户/traceId 头 |

### 3.1 Feign 契约接口 `PlatformClient`（含 8 个 record DTO）

来源：`aihub/aihub-api/src/main/java/com/aihub/api/client/PlatformClient.java`

**作用与原理。** Feign 是声明式 HTTP 客户端：只写接口 + 注解，运行时自动生成实现，完成"服务发现 → 负载均衡 → 发 HTTP → 解析 JSON"全过程。接口级注解两行定生死（#L38-L41）：

```java
// 来源：aihub/aihub-api/src/main/java/com/aihub/api/client/PlatformClient.java
@FeignClient(
        name = "aihub-platform-service",   // 必须与平台服务在 Nacos 注册的 spring.application.name 一致
        path = "/internal"                 // 公共路径前缀：实际请求 = http://服务名/internal/xxx
)
public interface PlatformClient {
```

5 个方法对应平台侧 `InternalController` 的 5 个端点（路径一一对应）：

| 方法 | HTTP | 平台端实现 | 语义 |
|---|---|---|---|
| `checkTenant(tenantId)` | GET `/internal/tenants/check` | `InternalController.java#L43-L51` | 校验租户存在且启用 |
| `checkAndConsume(request)` | POST `/internal/quota/check` | `#L74-L78` | 单维度配额校验并扣减，`requestId` 幂等 |
| `consume(request)` | POST `/internal/quota/consume` | `#L80-L84` | 多维批量扣减（M5），任一维度超限整体拒绝 |
| `reportUsage(report)` | POST `/internal/usage/report` | `#L86-L91` | 用量与审计上报，失败走 outbox 异步补偿 |
| `verifyApiKey(request)` | POST `/internal/apikey/verify` | `#L60-L72` | 校验开放 API Key，只回传归属不含密钥材料 |

8 个 DTO 用 **Java 17 record** 内嵌在接口里（#L74-L111）：`TenantBrief`、`ApiKeyVerifyRequest`、`ApiKeyVerifyResult`、`QuotaRequest`、`QuotaItem`、`QuotaConsumeRequest`、`QuotaResult`、`UsageReport`。record 一行定义不可变数据类，自动获得构造器/getter/equals/hashCode/toString，字段 final 天然适合跨服务值对象。`ApiKeyVerifyResult` 的注释（#L86-L87）藏着一个防越权关键设计："租户由 Key 反查得到，调用方无法通过传参指定"。

**项目真实用例。** AI 服务三个消费点：

```java
// 来源：aihub/aihub-ai-service/src/main/java/com/aihub/ai/application/ChatAppService.java
private final PlatformClient platformClient;   // #L60 构造器注入（@RequiredArgsConstructor）

var quotaResp = platformClient.checkAndConsume(         // #L124 每次对话扣 1 次"request"维度
        new PlatformClient.QuotaRequest(
                UUID.randomUUID().toString(),           // #L126 requestId 保证幂等
                turn.tenantId(), String.valueOf(turn.appId()),
                QuotaDimensions.REQUEST, 1));           // #L128
```

多维扣 token（#L157-L159）、扣 Agent 任务（#L179-L181）；知识库文档入库扣 doc 维度（`aihub/aihub-ai-service/src/main/java/com/aihub/ai/application/KnowledgeAppService.java#L171`）；审计上报走 outbox 异步补偿（`aihub/aihub-ai-service/src/main/java/com/aihub/ai/infra/outbox/EventOutboxDispatcher.java#L46`）。激活点在启动类：`@EnableFeignClients(basePackages = "com.aihub.api")`（`AiServiceApplication.java#L46`）——basePackages 限定只扫契约包，避免误扫无关包。

**常见误用。** ① 平台端 `InternalController` 与契约接口路径/参数不同步——好在两端引用同一 jar，改契约立刻编译红（这正是模块存在的意义）；② 跨服务传 DTO 之外的对象（如 DO/领域对象），把数据库结构泄漏成网络契约；③ 给 `/internal/**` 配了网关路由，内部接口暴露公网——架构约束是"网关不暴露该前缀，路径无法从公网到达"（`InternalController.java#L21-L24` 注释）；④ 无视"只允许租户校验/配额扣减/审计上报三类跨服务调用，禁止跨服务 JOIN、禁止流式响应跨服务传播"的约束（`PlatformClient.java#L33-L36` 注释），随手加一个高耦合接口把两个服务焊死。

**面试怎么说。** "契约优先落地上就是把 Feign 接口和 record DTO 收进独立模块，两端依赖同一 jar，签名不一致编译期就爆；DTO 用 record 保证传输值对象不可变；服务端实现类与契约方法一一对应并写在 `/internal` 前缀下、网关不路由，内外网边界靠架构约束而不是靠自觉。"

### 3.2 配额维度常量 `QuotaDimensions`

来源：`aihub/aihub-api/src/main/java/com/aihub/api/client/QuotaDimensions.java`

**作用与原理。** 配额系统按维度计量扣减，AI 侧上报写、平台侧扣减读的是同一批字符串。若两端各写一份，一边手滑成 `"tokens"`，扣减就静默失配——不报错但账对不上（#L6-L9 注释把这个问题讲得非常清楚）。四个维度常量（#L21-L30）：

```java
// 来源：aihub/aihub-api/src/main/java/com/aihub/api/client/QuotaDimensions.java
public static final String REQUEST = "request";  // 每次对话/调用扣 1
public static final String TOKEN   = "token";    // 按 token_in + token_out 扣
public static final String DOC     = "doc";      // 每个文档入库扣 1
public static final String TASK    = "task";     // 每个 Agent 任务扣 1
```

设计上 final 类 + 私有构造器（#L14-L15 注释特意说明：接口定义常量的老写法会被类实现导致"常量污染"，final class 更规范）。放在 aihub-api 而非各自模块的理由（#L11-L12）：契约模块被两端同时依赖，天然是共享常量的家。

**项目真实用例。** AI 侧三处扣减（`ChatAppService.java#L128` REQUEST、#L159 TOKEN、#L181 TASK；`KnowledgeAppService.java#L171` DOC）；平台侧默认维度兜底（`aihub/aihub-platform-service/src/main/java/com/aihub/platform/quota/service/QuotaService.java#L72`、#L96）：

```java
// 来源：aihub/aihub-platform-service/src/main/java/com/aihub/platform/quota/service/QuotaService.java
? QuotaDimensions.REQUEST : request.dimension();   // 未指定维度默认按"次数"
```

**常见误用。** ① 在业务代码里手写 `"token"` 字符串绕过常量——编译器帮不了你，口径漂移就此开始；② 变更字面量时只改代码不迁移存量数据（见 1.3：`ai_usage_record` 历史行里的旧字符串与新口径对不上，报表静默错账）。

**面试怎么说。** "跨服务共享的字符串口径必须收敛到一个两端共同依赖的常量类——这类问题的特征是'不报错但账错'，比崩溃更难排查。我还会加一层防护：平台侧收到未知维度直接告警拒绝，而不是默认放行。"

### 3.3 Feign 透传配置 `FeignTenantConfig`

来源：`aihub/aihub-api/src/main/java/com/aihub/api/config/FeignTenantConfig.java`

**作用与原理。** 解决的问题（#L12-L15）：AI 服务调平台服务时，平台侧 `TenantResolveInterceptor` 要求 `X-Tenant-Id` 头必须存在；若每个调用点手动塞头，迟早有地方忘掉。`RequestInterceptor` 是 Feign 扩展点，每次发请求前回调一次，`RequestTemplate` 就是"即将发出的 HTTP 请求"的可编辑草稿：

```java
// 来源：aihub/aihub-api/src/main/java/com/aihub/api/config/FeignTenantConfig.java
@Bean
public RequestInterceptor tenantPropagationInterceptor() {   // #L42
    return template -> {
        Long tenantId = TenantContext.getTenantId();          // #L46 从 ThreadLocal 取上游上下文
        Long userId = TenantContext.getUserId();
        if (tenantId != null) {
            template.header(TenantContext.HEADER_TENANT, String.valueOf(tenantId));  // #L50
        }
        if (userId != null) {
            template.header(TenantContext.HEADER_USER, String.valueOf(userId));      // #L53
        }
        template.header(TraceContext.HEADER, TraceContext.ensure());  // #L56 本地没有就生成
    };
}
```

它只是"搬运工"：值来自 common 的 `TenantContext`/`TraceContext`——上游拦截器已写入 ThreadLocal，这里取出来塞进 Feign 请求头，下游服务再由自己的 `TenantResolveInterceptor` 解回 ThreadLocal。一条完整的"上下文接力"由此闭环。

**项目真实用例。** 装配方式是 `@Import`（`aihub/aihub-ai-service/src/main/java/com/aihub/ai/config/WebMvcConfig.java#L22`）：

```java
// 来源：aihub/aihub-ai-service/src/main/java/com/aihub/ai/config/WebMvcConfig.java
@Configuration
@Import(FeignTenantConfig.class)
public class WebMvcConfig implements WebMvcConfigurer {
```

类上**刻意不加 `@Configuration`**（`FeignTenantConfig.java#L22-L24` 注释）：若标注了，会被组件扫描全局拾取，影响所有 Feign 客户端；作为普通配置类由使用方显式 Import，作用域可控。

**常见误用。** ① 给它加上 `@Configuration` 又放在被扫描的包里，导致所有 Feign 客户端（未来接入的任何第三方调用）都被强塞租户头；② 在定时任务等无请求线程里调 Feign——ThreadLocal 为空，租户头缺失，平台侧 fail-fast 拒绝；正确做法是任务入口先 `TenantContext.set(...)` 或走 outbox 异步补偿；③ 以为 `template.header` 是替换语义——同名多次调用是追加，注意避免重复头。

**面试怎么说。** "服务间上下文传播我做成 Feign 的 RequestInterceptor：业务代码零感知，拦截器从 ThreadLocal 搬运租户/用户/traceId 到请求头。配置类不加 @Configuration 防止全局扩散，用 @Import 显式装配——Feign 配置的作用域控制是 Spring Cloud 的经典细节题。"

### 3.4 服务间调用的兜底与超时

契约只定义了"正常怎么调"，健壮性来自三层防护（均为项目真实代码）：

**① 超时：走默认值 + 心里有数。** 全仓库 `application*.yml` 未配置任何 feign 超时项（已检索确认），即使用 Spring Cloud OpenFeign 默认值：连接超时 10 秒、读取超时 60 秒。没有显式调优，是因为项目给所有跨服务调用配了应用层降级（见②），默认超时足够兜住。

**② 应用层降级：分维度定义失败语义。** `ChatAppService.checkQuota`（#L116-L142）的注释是教科书写法：

```java
// 来源：aihub/aihub-ai-service/src/main/java/com/aihub/ai/application/ChatAppService.java
 * <p><b>降级放行设计（重要）：</b>catch(Exception) 后放行 —— 平台服务挂了/超时，
 * 不应让所有用户对话失败。闸门只在平台"明确拒绝"（allowed=false）时生效。   // #L117-L118
```

三类调用三种语义：配额校验失败**放行**（可用性优先，#L139-L141）；token 事后补扣失败**只记日志**（成本已发生，不能让用户看到错误，#L147-L148）；Agent 任务超限**硬拒绝**（#L169-L172 注释还复盘了真实事故："早期版本忽略了返回的 allowed，导致 task 配额形同虚设，这里修正为与其他维度一致"）。

**③ 幂等与异步补偿。** 每次 `QuotaRequest` 带 UUID `requestId`（#L126），网络重试导致同一请求重复到达时平台侧只扣一次（`PlatformClient.java#L48` 注释）；审计上报失败落 outbox 表异步补偿（`EventOutboxDispatcher.java#L46`），不阻塞主链路。

**面试怎么说。** "跨服务调用的健壮性我按'语义分层'设计：同步闸门类调用降级放行保可用性，事后记账类调用失败不阻塞，Agent 这类高成本调用硬拒绝防烧钱；配合 requestId 幂等 + outbox 补偿，做到'重试安全、故障可恢复'。超时没有盲目调优，因为应用层语义已经定义了任何失败路径的行为。"

## 4. 设计取舍：VO / DO / DTO 的职责边界

### 4.1 为什么不把 DO 直接丢进 common

反例方案：把 `SysUserDO` 等 DO 全部放进 common，让所有服务共用。后果有三：

1. **数据库结构泄漏成全局契约。** DO 上是 `@TableName("sys_user")`、`passwordHash` 这类持久化细节（`aihub/aihub-platform-service/src/main/java/com/aihub/platform/user/entity/SysUserDO.java#L21-L34`）。放进 common 后，任何服务（甚至前端 Feign 反序列化）都能"顺手"引用它，`passwordHash` 这类敏感字段是否出门全靠"记得手动置空"而不是靠类型系统挡住。`AuthLoginReqVO.java#L9-L15` 的注释把规则写死："DO 绝不允许出现在 Controller 签名里——否则数据库结构变化会直接波及前端契约（passwordHash 这类敏感字段也必须靠'分层'而不是'记得手动置空'来保证不出门）。"
2. **公共模块被特定业务绑架。** common 的 POM 里若出现 MyBatis-Plus、各服务的实体，网关和 MCP 服务就被迫拖入不需要的持久化依赖；DO 的一列改动（如 Q3 事故里的 `create_time`）会从"平台服务内部事务"升级为"全仓库编译事件"。
3. **丧失服务自治。** 微服务的收益之一是每个服务独立演进数据模型。DO 收进 common 等于宣告"所有服务共享一个数据库结构"，拆库、分表、字段重构全部变成跨团队协商。

项目现状印证了这个取舍：10 个 DO 全部留在平台服务自己的 `entity` 包（`SysTenantDO`、`SysUserDO`、`SysRoleDO`、`SysMenuDO`、`SysUserRoleDO`、`SysRoleMenuDO`、`AiUsageRecordDO`、`AiQuotaUsageDO`、`AiQuotaPolicyDO`、`SysApiKeyDO`），common 里没有任何持久化依赖（`aihub-common/pom.xml#L16-L46`）。

### 4.2 三类对象的职责边界与转换链路

项目里三类数据对象的分工（文件均真实存在）：

| 角色 | 全称 | 项目里的形态 | 存放位置 | 代表文件 |
|---|---|---|---|---|
| VO | View Object | `@Data` 类，带 `@NotBlank` 等校验注解；请求 `*ReqVO` / 响应 `*RespVO` | 各服务自己的 `vo` 包（platform 18 个） | `auth/vo/AuthLoginReqVO.java`、`system/vo/SysUserCreateReqVO.java` |
| DO | Data Object | `@TableName` 实体，字段对应表列 | 各服务 `entity` 包（platform 10 个） | `user/entity/SysUserDO.java` |
| DTO | Data Transfer Object | Java record，不可变 | **只存在于 aihub-api 契约模块**（8 个内嵌 record） | `client/PlatformClient.java#L79-L111` |

职责边界：

- **VO 面向"浏览器"**：Controller 只收发 VO。入参校验注解写在 VO 上（`AuthLoginReqVO.java#L23-L30` 的三个 `@NotBlank`），由 `@Valid` 触发、`GlobalExceptionHandler.handleValidate` 接住；响应 VO 按前端需要裁剪字段（如 `AuthLoginRespVO` 绝不含 `passwordHash`）。
- **DO 面向"数据库"**：只被 Mapper 和 Service 内部使用，字段与表列一一对应，`tenantId`/`passwordHash` 等敏感列在此层流转。
- **DTO 面向"服务间网络"**：record 不可变，字段是两端公认的最小必要集（`QuotaResult(boolean allowed, long remain, String reason)`），不携带任何持久化细节。

转换链路与转换位置（一句话记忆：**转换发生在"边界变窄"的地方，且放在 Service 层**）：

```text
浏览器 ──VO──▶ Controller ──VO──▶ Service ──[VO→DO]──▶ Mapper ──▶ MySQL
浏览器 ◀──VO── Controller ◀──[DO→VO]── Service ◀──DO── Mapper ─────────┘

AI 服务 ──record DTO──▶ Feign ──HTTP──▶ InternalController ──record DTO──▶ QuotaService ──▶ DO
```

`AuthController.java#L64-L65` 是标准示范：Controller 签名里只有 VO（`AuthLoginReqVO`/`AuthLoginRespVO`），DO 从不出现在接口层。VO→DO 转换放 Service（`AuthLoginReqVO.java#L15` 注释："字段少直接手写映射，字段多用 BeanUtils 拷贝"）。

### 4.3 为什么契约 DTO 用 record 而校验 VO 用 @Data class

- record：字段 final、不可变、自动实现 equals/hashCode——跨服务传输值对象的理想形态；代价是反序列化依赖规范化构造器，**不适合放 `@NotBlank` 这类 Bean Validation 注解做复杂校验**。
- `@Data` class：可变、配合 Bean Validation 与 Jackson 宽松反序列化更顺手——Web 层入参的现实选择（本项目所有 `*ReqVO` 均为此形态）。

一句话总结第 4 章：**common 管格式（R/错误码），api 管契约（record DTO），VO/DO 留在各服务自己的边界内——每一类对象只在它的"地理边界"里活动，跨界就必须转换。**

## 5. 本章面试三问与参考回答

**Q1：为什么你们的公共代码要拆成 common 和 api 两个模块，放一个不行吗？**

参考回答：不行，核心是依赖方向和变更半径。common 是所有服务共享的"语言"（响应体、错误码、异常、上下文），依赖极轻（web + jackson + jjwt）；api 是跨服务调用的"专线"（Feign 契约 + record DTO + 共享常量），带 openfeign/loadbalancer 依赖。被调用方（platform）和网关不需要 Feign——合并会强迫它们引入无用依赖。更关键的是契约模块实现了"编译期握手"：调用方和提供方依赖同一份 jar，改接口签名两端立刻编译红，把不一致扼杀在编译期而不是运行期。我们还总结过"爆炸半径"清单：改 R 字段是全局事故，改契约是两端同步修复，改常量若历史数据不迁移则静默错账——分模块让这三类改动的评审流程可以区别对待。

**Q2：多租户的租户 ID 在一次请求里是怎么传递的？为什么不能前端传？**

参考回答：链路是"JWT claims → 网关解析 → 内部请求头 → ThreadLocal → SQL 条件"。网关的 AuthGlobalFilter 校验 JWT 后，强制剥离客户端伪造的 `X-Tenant-Id`/`X-User-Id` 再用 claims 重写（防冒充租户）；下游服务的 TenantResolveInterceptor 在 preHandle 把头写进 ThreadLocal 上下文，缺头直接抛 TENANT_MISMATCH（fail-fast，不让无主请求进业务层）；业务代码和 MyBatis-Plus 租户插件从 ThreadLocal 读取自动拼查询条件；AI 服务再调平台服务时，Feign 拦截器把 ThreadLocal 的值搬回请求头完成跨服务接力，请求结束 afterCompletion 清理防线程复用串台。前端传参绝不可信——租户身份只能来自服务端验签后的令牌，这是整个隔离体系的根。

**Q3：AI 服务调平台服务扣配额，平台服务挂了怎么办？直接拒绝用户对话吗？**

参考回答：我们按调用语义分层定义失败行为，不是一刀切。对话次数校验是"可用性优先"：catch 任何异常后降级放行，闸门只在平台明确返回 allowed=false 时生效——平台挂了不应该让所有用户不能聊天；token 扣减是"事后补扣"，失败只记日志，因为成本已发生，不能让用户看到报错，用完额度的下一次请求会在校验环节被拦；Agent 任务是"硬拒绝"，因为它是高成本调用，超限必须拦，这里还修过一个真实 bug——早期版本忽略了返回的 allowed，task 配额形同虚设。同时每次请求带 UUID requestId 保证平台侧重试幂等，审计上报失败落 outbox 表异步补偿。这套设计的关键认知是：分布式调用的容错策略取决于业务语义，而不是统一加个熔断就完事。
