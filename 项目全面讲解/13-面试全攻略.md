## 1. 电梯演讲（三个版本，各有侧重）

### 1.1 30 秒版（电话面/开场自我介绍）

> 我做了一个叫 AIHub 的多租户 AI 能力中台。整体是 Spring Cloud Alibaba 微服务架构：
> 网关 8080 统一做 JWT 鉴权和 Sentinel 限流，platform-service 8081 负责认证、RBAC 和多租户，
> ai-service 8082 提供知识库 RAG 和 SSE 流式对话，另有一套 MCP 工具服务让大模型调用外部工具。
> 前端是 Vue3 管理端加 uni-app 跨端应用（一套代码同时出 H5 和微信小程序）。
> 中间件用 docker-compose 一键拉起 MySQL、Redis、Nacos、Prometheus 全家桶，
> 数据库结构用 Flyway 做版本化迁移。我在这个项目里独立完成了从架构设计到前后端联调的全过程。

要点：**30 秒内必须出现"多租户、网关鉴权、RAG、流式"四个关键词**，这是钩子，让面试官主动往下问。

### 1.2 2 分钟版（项目介绍环节，侧重架构纵深）

> AIHub 是一个多租户的 AI 能力中台，三类角色：平台管理员运营模型与应用，企业租户自助注册使用，终端用户在 H5 或小程序上对话。
>
> 后端拆成网关、平台服务、AI 服务和 MCP 工具服务四个可独立部署的单元。我讲三个最有含金量的设计：
>
> **第一，安全边界收口在网关。** `AuthGlobalFilter` 是全系统唯一的身份关卡：它同时支持终端用户的 JWT 和第三方对接的 API Key 两种凭证；解析出的 tenantId/userId 会**强制剥离并覆盖**客户端自带的 `X-Tenant-Id` 头再透传给下游——因为下游信任这个头，不剥离的话攻击者自己带个假头就能冒充别的租户。租户身份只有一个可信来源：签名过的凭证。
>
> **第二，多租户行级隔离。** 所有业务表都以 `tenant_id` 为隔离维度且是复合索引首位；tenantId 从 JWT claims 出发，经网关透传请求头，最后落到 MyBatis 查询条件里，形成"token → 头 → SQL"的完整链路。
>
> **第三，RAG 与流式。** 知识库文档用自研的 `TextChunker` 切片（段落优先、超长滑动窗口、相邻分片保留重叠），向量化后入 Redis Stack 做相似度检索，检索结果拼进 Prompt；对话走 SSE 流式返回，同一个编排 `ChatAppService` 支撑三种通道——H5 用 SSE、微信小程序用 NDJSON 分块（小程序不支持 SSE）、调试用同步，差异被 `StreamSink` 接口隔离。
>
> 落地质量上，docker-compose 一键拉起全部中间件，Nacos 3.0.3 开了鉴权，数据库结构由 Flyway 管控，Prometheus/Grafana 监控，traceId 贯穿网关到服务的日志。

### 1.3 5 分钟版（深聊环节，加"我踩的坑"证明真实性）

前 3 分钟讲 2 分钟版的内容（可以适当展开每个设计的原因），**最后 2 分钟主动讲一个踩坑故事**，推荐讲"种子密码哈希事故"（见第 4 章故事 2）：

> ……这个项目不只是把功能跑通。举一个印象最深的例子：演示账号 admin 按注释里的密码 admin123 登录永远报错。排查发现 V1 种子脚本里硬编码的 BCrypt 哈希实际对应的是 123456——BCrypt 不可逆，没法直接"看"出哈希对应什么明文，我是另起一个 BCrypt 编码器对 `admin123` 和 `123456` 分别 encode 再 `matches` 对拍，才确认哈希贴错了。修复也不能改 V1 脚本，因为 Flyway 会校验已应用脚本的 checksum，改历史脚本启动直接失败——所以用了增量迁移 V10 去 UPDATE 这一行。这件事让我形成了两个习惯：种子数据写完必须当场登录验证一次；改表结构永远走增量迁移。

## 3. 八大高频主题问题清单与参考回答

> 每个主题 3-5 问，参考回答控制在面试口述 30-60 秒的长度。回答的套路：
> **先给结论 → 再给项目里的真实证据 → 主动补一句 Trade-off。**

### 3.1 主题一：整体架构

**Q1：介绍下你的微服务拆分，为什么这么拆？**

> 按业务能力拆：网关只做横切（鉴权/限流/路由），platform-service 承载"平台域"（认证、RBAC、租户、配额），ai-service 承载"AI 域"（知识库、对话、工具），MCP 服务承载工具协议。拆的判断标准是**变更速率和扩缩容特征不同**：认证接口要求稳定低延迟，AI 对话是长连接高耗时，混布会互相拖累——比如流式对话占满线程池时，登录请求会被波及。同时公共的响应体/异常/租户上下文沉到 aihub-common 模块复用。Trade-off：拆得细会增加运维成本，所以我用 docker-compose + Nacos 把这个成本压到最低，没有引入 K8s——数据量没到，不为技术栈而技术栈。

**Q2：为什么鉴权放网关，而不是各服务自己校验？**

> 放网关的核心收益是**租户身份只有一个可信出口**：`AuthGlobalFilter`（order = -100）统一验签，剥离客户端伪造的 `X-Tenant-Id` 头后注入可信值，下游服务无需也不允许自己信任请求头。如果各服务自查，每个服务都要保管验签密钥，密钥扩散面大，而且很容易漏掉"剥离伪造头"这一步。Trade-off：网关成了单点风险，所以网关要尽量薄——只做验签和透传，不做业务查询（API Key 校验走平台服务但有 2 秒超时和 60 秒本地缓存兜底），并且保留了各服务从 `TenantContext.requireTenantId()` 二次防御的能力。

**Q3：网关挂了怎么办？限流怎么做的？**

> 网关无状态，水平扩容即可；限流用 Sentinel 网关流控，规则类型是 gw-flow（按路由维度），规则不存内存——配置了 Nacos 数据源（data-id 为 `aihub-gateway-flow-rules`），控制台改规则持久化生效，解决"重启即丢"。命中限流返回结构化 429：`{"code":10006,"message":"请求过于频繁，请稍后再试"}`，前端能按 code 统一处理，而不是收到裸的 429 页面。

**Q4：服务间怎么调用？注册中心为什么选 Nacos？**

> 服务发现用 Nacos，网关路由用 `lb://aihub-platform-service` 这类形式做负载均衡转发。选 Nacos 的理由：一是项目用的 Spring Cloud Alibaba 生态，依赖版本兼容性最好；二是 Nacos 同时提供配置中心（`spring.config.import: optional:nacos:...`），改配置不用重启，一套组件两个用途。Trade-off：相比 Eureka 它多了配置能力，相比 ZooKeeper 它是 AP 优先，对服务发现场景更合适。

### 3.2 主题二：JVM 与 Java 基础

**Q1：项目里哪里用到了多线程？怎么控制风险的？**

> 两处典型。一是 ai-service 的流式对话：`ChatController` 里建了固定 32 线程的 `streamExecutor`（daemon 线程），SSE 任务提交进去执行，Tomcat 容器线程立刻释放——否则每个流式对话占一个容器线程，几十个并发就把 Tomcat 拖垮了。二是 `SseStreamSink` 的 `closed` 标志用了 `volatile`：流任务线程和超时回调线程都会读写它，不加 volatile 一个线程关闭后另一个线程可能一直读到缓存的旧值，往已关闭的连接写数据。跨线程还必须用 `TraceContext.wrap()` 把 traceId 带过去，因为 ThreadLocal 不跨线程，不带的话日志就断链了。

**Q2：ThreadLocal 的原理和风险，项目里怎么用的？**

> ThreadLocal 是每个 Thread 内部的 Map（ThreadLocalMap），以 ThreadLocal 实例为 key，实现线程封闭。项目里 `TenantContext` 和 `TraceContext` 都是 ThreadLocal：一次请求内随时取当前租户 ID 和 traceId。两个风险都在项目里处理过：一是**内存泄漏**——线程池的线程复用，用完必须 remove，`ChatController` 的 NDJSON 分支在 finally 里 `TraceContext.clear()`；二是**不跨线程**——提交到 `streamExecutor` 的任务要用 `TraceContext.wrap()` 预先捕获 traceId 再传递。

**Q3：BCrypt 和 MD5 区别？为什么密码用它？**

> 三点：自带随机盐（同一密码每次加密结果都不同，防彩虹表）；故意慢（可调 cost，暴力破解成本指数上升）；MD5 是为快速校验设计，GPU 每秒能算几十亿次。项目里 `AuthService#login` 用 Spring Security 的 `PasswordEncoder.matches(明文, 哈希)` 校验，盐内嵌在哈希串里不需要单独存储。我还真踩过它的一个特性坑：BCrypt **不可逆**，种子数据哈希贴错了没法直接看出来的，要用对拍验证（见第 4 章故事 2）。

**Q4：讲讲你们项目里的异常体系。**

> 业务异常统一抛 `BizException(ResultCode, message)`，由 common 模块的全局异常处理器兜底转成统一响应体 `R{code, message, traceId}`；网关是 WebFlux 环境没有这个机制，所以 `AuthGlobalFilter.unauthorized()` 手写 401 JSON（code 10002），并刻意带上 traceId——401 多发生在客户端配置错误，没有 traceId 很难排查。分层含义：错误码全局唯一（10002 未认证、10006 限流），前端只认 code 不解析 message 文案。

### 3.3 主题三：Spring 与微服务

**Q1：Spring Boot 自动装配原理，一句话+项目实例。**

> `@SpringBootApplication` 里的 `@EnableAutoConfiguration` 通过 `AutoConfiguration.imports` 文件加载候选配置类，按 `@ConditionalOnClass/@ConditionalOnMissingBean` 等条件筛选后注册 Bean。项目实例：引入 `spring-cloud-starter-gateway` 依赖后，路由过滤器和 `GlobalFilter` 收集机制自动生效，我只要把自己的过滤器标 `@Component`，Spring Cloud Gateway 就会自动收集所有 `GlobalFilter` 类型的 Bean 排序执行——这就是自动装配加 SPI 思想。

**Q2：@Transactional 什么时候失效？你项目里怎么规避的？**

> 经典失效场景：自调用（this 调用不走代理）、方法非 public、异常被 catch 吞掉、默认只回滚 RuntimeException。项目里 `AuthService#register` 是标准用法：必须 public（供 Controller 调用，无自调用），并且显式写 `@Transactional(rollbackFor = Exception.class)`——因为注册流程要写 5 张表（租户/用户/角色/角色菜单/用户角色），授权菜单失败时不能留下"有租户有管理员但没角色"的脏数据，checked 异常也要回滚。

**Q3：构造器注入为什么优于字段注入？**

> 字段可以声明为 final，依赖不可变；不依赖容器也能 new 出来做单测；依赖关系在构造器签名里一目了然，依赖过多会直接暴露设计问题。项目里所有 Service 都是 `@RequiredArgsConstructor` + final 字段，比如 `AuthService` 的 7 个依赖全在构造器上，单测里直接 new 传 mock 即可，不需要反射注入。

**Q4：Nacos 开鉴权后注册 403 怎么解决？（结合版本升级经验）**

> Nacos 3.x 默认开启鉴权，客户端没带账号密码就会被 403 拒绝注册和拉配置。解决分两步：服务端初始化管理员账号；客户端在配置里显式声明 `spring.cloud.nacos.username/password`（项目里用环境变量 `NACOS_USERNAME`/`NACOS_PASSWORD` 注入，不硬编码真实密码）。教训是**大版本升级的 breaking changes 要先读 migration 指南**：2.x 客户端直连 3.x 服务端会静默失败在鉴权上，报错信息不直接指向根因。

**Q5：@ConfigurationProperties 热更新有什么坑？**

> Nacos 改配置触发刷新事件时，Spring 会重新绑定配置属性，但有两个静默失效条件：属性类是 record/不可变对象无法重新绑定；使用方在启动时把值拷贝进了本地字段。规避方式：属性类用可变 JavaBean，使用方**调用时读值**而不是缓存值。这类问题的可怕之处是不报错，所以我的习惯是每次改配置类都手动改一次 Nacos 验证生效，而不是相信"它应该能用"。

### 3.4 主题四：数据库与多租户

**Q1：你的多租户隔离方案是什么？为什么选行级隔离？**

> 共享表 + 行级隔离：所有业务表带 `tenant_id` 列，且是复合索引首位（如 `KEY idx_tenant (tenant_id)`）。三条防线：登录查询按"租户+用户名"联合条件（`selectByTenantAndUsername`）天然防跨租户撞库；租户 ID 从 JWT claims 而非前端参数来；网关强制覆盖租户请求头。选行级而非独立库/schema 的理由：租户数量预期大但单个租户数据量小，独立库运维成本（备份/迁移/连接池）不可接受。Trade-off：行级隔离的隔离强度依赖代码纪律，一旦某条 SQL 忘了带租户条件就漏数据——所以这个方案必须配合"租户上下文统一注入"和代码评审/测试兜底，并且明确知道将来数据量大时可平滑升级为独立 schema。

**Q2：tenantId 的完整传递链路是什么？**

> 三跳：① 登录时 `JwtTokenProvider.generate(tenantId, userId, username)` 把 tenantId 写进 JWT claims；② 网关 `AuthGlobalFilter.authenticateByJwt` 验签后解析 claims，先 `remove` 再 `set` 重建 `X-Tenant-Id` 头（防伪造）；③ 下游服务通过 `TenantContext.requireTenantId()` 读取，进 MyBatis 查询条件。**任何一跳都不接受前端明文传租户 ID**，这是设计铁律——`String.valueOf` 还处理了 claims JSON 往返后 "null" 字符串的边界情况。

**Q3：Flyway 的机制？为什么不能改历史迁移？**

> Flyway 按版本号顺序执行迁移脚本，并对每个已应用脚本记录 checksum；再次启动时逐个校验，历史脚本内容变了 checksum 对不上，直接启动失败——这是防止"环境间 schema 不一致"的保护机制。所以修 bug 永远用增量迁移：项目里 V10 迁移只做了一件事，`UPDATE sys_user SET password_hash = ... WHERE id = 1 AND username = 'admin'`，注释里写清了"不动 V1"的原因。表结构和 DO 不一致的问题也一样，能改代码对齐就不动已应用的 DDL。

**Q4：种子数据密码哈希错了，你怎么发现并确认的？**

> 现象是按注释密码 admin123 登录必报"用户名或密码错误"。BCrypt 不可逆，无法"看"哈希对应什么明文，我用**对拍法**：分别对 admin123 和 123456 调用 encode，再用 `matches` 对库里哈希逐一验证，确认库里哈希匹配 123456——是生成种子脚本时贴错了哈希串。修复走 V10 增量迁移更新这一行。教训两条：种子数据写完必须当场登录验证；登录接口"用户不存在"和"密码错误"返回同一文案（防用户名枚举），所以报错信息不指向根因，排查要有自己的验证手段。

**Q5：唯一键和索引怎么设计的？举个例子。**

> 隔离维度进索引：`ai_document` 表 `KEY idx_tenant_kb (tenant_id, kb_id)`，文档列表查询先按租户再按知识库过滤，最左前缀正好覆盖；租户码是登录入口，`sys_tenant.code` 全局唯一索引，注册时先查后插防重。设计原则：**租户列永远做复合索引第一列**，否则行级隔离的查询会退化成全表扫描。

### 3.5 主题五：Agent 与 LLM 应用

**Q1：讲讲你的 RAG 链路。**

> 五步：文档上传 → `TextChunker` 切片 → Embedding 向量化 → 向量入库 Redis Stack（按知识库建索引，`vectorDim` 与嵌入模型维度强校验，`index_name` 带版本号便于重建索引）→ 用户提问时相似度检索 topK 结果拼进 Prompt 回答。切片策略是面试重点：`TextChunker.split(text, maxChars, overlap)` **优先按段落切**，超长段落用滑动窗口二次切分，相邻分片保留 overlap 重叠（上限为 size 的一半），避免关键句被切断——实践结论是"段落+重叠"的检索效果明显优于固定字数硬切。

**Q2：为什么切片要有重叠？检索用什么相似度？**

> 切片边界会把语义切断——比如一句话正好跨在两个分片上，两个分片各有一半，谁都不是完整证据。重叠让边界区域的语义在相邻分片中至少完整出现一次，代价是存储和索引量增加，所以 overlap 设上限（不超过分片大小一半）。相似度用向量余弦相似度，检索时按分数排序取 topK，配合引用溯源接口（`/api/ai/chat/references`）把每个回答引用的文档名、分片内容和分数返回给前端，让回答可回溯。

**Q3：SSE 流式对话怎么实现的？为什么选 SSE 不选 WebSocket？**

> `ChatController#chatSse` 返回 `SseEmitter(120_000L)`（120 秒超时），流任务提交到独立 32 线程池执行，容器线程立即释放；任务里通过 `SseStreamSink.emit` 逐事件推送，发送失败（客户端断开）置 volatile closed 标志，后续事件直接丢弃。选 SSE 因为对话是**单向推送**场景，SSE 基于 HTTP 无需协议升级、断线重连语义简单；WebSocket 的双向能力在这里用不上。真正的 Trade-off 在小程序端：微信 request API 不支持 SSE，所以同一个编排服务额外提供 NDJSON 分块通道（`Content-Encoding: identity` + `X-Accel-Buffering: no` 禁压缩和缓冲），差异被 `StreamSink` 接口隔离——这就是"抽象隔离平台差异"。

**Q4：前端 EventSource 不是天生支持 SSE 吗，为什么不用？**

> EventSource **不能携带自定义 Header**，而本项目的鉴权要求 `Authorization: Bearer <jwt>` 头，EventSource 传不了。所以 H5 端用 fetch + ReadableStream 手工解析 SSE 流：读增量 chunk、累积缓冲、按事件边界切分。这也是流式渲染的一个通用坑：网络分块不保证按事件边界切分（半包），必须自己做缓冲拼接。

**Q5：MCP 工具调用是怎么接进来的？一次调用的完整旅程？**

> MCP（Model Context Protocol）让 LLM 以标准协议发现和调用工具。项目拆了三件：mcp-service 实现工具逻辑，mcp-sse 走 HTTP/SSE 远程传输（端口 8090），mcp-stdio 走本地进程标准输入输出（供 Claude Desktop 这类客户端接入）。一次调用的旅程：用户提问 → 模型判断需要工具并给出工具名+参数 → 服务端执行工具 → 结果回填对话上下文 → 模型基于结果继续生成最终回答。stdio 传输有个隐蔽的坑：**stdout 就是 JSON-RPC 通道**，Spring Boot banner 和控制台日志混进去会导致客户端 JSON 解析失败，必须把日志改道 stderr 并关闭 banner。

### 3.6 主题六：前端

**Q1：管理端动态路由怎么实现的？**

> 登录成功后调后端菜单权限接口，拿到平铺树节点 `MenuNode{id, path, component, menuType, children}`（M=目录/C=菜单/F=按钮）；`routes.ts` 的 `toPureRoute` 递归转换成 pure-admin 需要的路由格式（F 型按钮过滤掉不进路由，只用于按钮权限指令），图标名转 iconify 格式，component 是字符串时由框架映射到 `src/views` 下的同名 Vue 文件注册路由。细节：过滤掉 `/welcome` 防止与静态路由重复注册；页面刷新后内存缓存丢失，`getAsyncRoutes` 会用 token 重新拉权限树，保证刷新后菜单不丢。

**Q2：刷新后菜单丢失是什么问题？怎么修的？**

> 登录时菜单树存在内存变量里，F5 之后内存清空，动态路由没人再生成，表现为"刷新后只剩首页"。修复在 `getAsyncRoutes` 里加兜底：缓存为空时用当前 token 重新请求同一个权限接口（注意这里用原始 axios 手动取 `res.data.data.routes`，绕过 http 拦截器的响应解包，避免二次解包取错层级）。类似的"一次接口结构变更引发多点故障"一共修了 5 处（动态菜单、刷新丢失、顶级叶子路由崩溃、菜单管理页、角色管理页），教训是**前后端数据结构契约要有单一事实来源**，改动接口必须全局搜索消费方。

**Q3：uni-app 一套代码出 H5 和小程序，原理和坑？**

> 原理是条件编译 + 平台适配层：写一份 Vue 代码，编译期按平台注入不同实现，`uni.request` 这类 API 由运行时适配到浏览器 fetch 或微信 request。踩过的最深的坑：项目沿用 HBuilderX 根目录结构（manifest.json 在项目根），而 uni CLI 默认从 `src/` 读源码，启动直接报 ENOENT manifest.json。官方约定是启动前设置环境变量 `UNI_INPUT_DIR`，但**写在 vite.config.js 里来不及**——CLI 初始化读取 manifest 发生在加载 vite 配置之前。所以写了 `scripts/uni.js` 启动器：先用绝对路径设置 `process.env.UNI_INPUT_DIR` 指向根目录，再 require uni CLI 入口，所有 npm 命令统一经它转发。

**Q4：Vite 7 启动报 crypto.getRandomValues is not a function 怎么回事？**

> Vite 7 要求 Node 20.19+，本机是 Node 16.20.2，老版本没有全局暴露 Web Crypto API（`crypto.getRandomValues`），依赖它的启动路径直接崩。用 nvm 切到 Node 24 解决。这个报错的迷惑性在于它看起来像代码 bug，实际是**运行时版本与工具链要求不匹配**——看到 crypto/WebStream 类报错先查 Node 版本，再怀疑代码。

**Q5：前端请求层怎么设计的？401 怎么处理？**

> 管理端 axios 封装统一注入 `Authorization: Bearer` 头，响应拦截器按 `R{code, message}` 契约解包，401（code 10002）统一跳登录；开发期 vite 代理把 `/auth`、`/api` 转发到网关 8080，规避跨域（生产可在网关开 CORS，项目里已配 `allowedOriginPatterns` 并暴露 `X-Trace-Id` 头，报障时用户贴 traceId 就能三份日志对链路）。用户端小程序网络层用 baseUrl 直连网关，真机调试要改成局域网 IP——小程序不允许 localhost。

### 3.7 主题七：系统设计与场景题

**Q1：如果让你把单租户系统改造成多租户，步骤是什么？**

> 按依赖顺序四步：① 身份——认证体系签发租户标识（JWT claims），杜绝前端传参；② 数据——所有表加 tenant_id 列并调整索引（租户列做复合索引首位），存量数据刷默认租户；③ 请求链路——统一入口解析租户并注入上下文（网关层做，配合防伪造剥离），数据访问层统一把上下文转成查询条件；④ 运营——配额、计量、审计按租户维度重建。最容易翻车的是 ③：只改数据层不改入口，攻击者换个头就能越权，所以**入口的可信性校验是第一优先级**。

**Q2：验证码接口怎么防刷的？**

> 三层：图形验证码本身过滤机器批量请求；验证码在 Redis 中存短 TTL、**校验时一次性消费**（无论成败立即作废，防重放）；校验放在登录流程最前面——验证码不对连数据库都不查，既省资源也不泄露"账号是否存在"的信息。配合登录错误文案统一（"用户名或密码错误"不区分用户不存在），堵住用户名枚举。

**Q3：API Key 校验会不会拖慢网关？**

> 会，所以做了三重防护：校验是回调平台服务的远程调用，设 2 秒超时（鉴权在主链路上，不能让平台服务拖死网关）；结果本地缓存（Caffeine 语义，TTL 60 秒，上限 10000 条），绝大部分请求不打到平台；Trade-off 是缓存期内吊销的 Key 有最长 60 秒的存活窗口——这是延迟与吊销及时性的平衡点，金融场景应改事件驱动的主动失效。

**Q4：流式对话的线程模型怎么设计？如果并发 1000 人怎么办？**

> 当前模型：每请求占用流线程池（32 线程）中的一个线程 + 一个容器线程瞬时交接，SSE 超时 120 秒兜底防泄漏。1000 并发下瓶颈在模型侧吞吐而非线程数，垂直扩线程收益有限，正确方向是：流任务改响应式/虚拟线程降低阻塞成本；模型调用排队+按租户配额限流（Sentinel 已具备接入点）；推送层换 WebFlux/SseEmitter 事件驱动。回答要点是**先识别瓶颈在下游模型而不是线程池**，不要上来就"加机器"。

**Q5：日志怎么串联一次跨服务请求？**

> 网关最先执行的 `TraceIdGlobalFilter` 生成/透传 traceId（order 最小，先于鉴权过滤器的 -100），traceId 进 `TraceContext`（ThreadLocal）+ MDC，日志 pattern 里 `%X{traceId:--}` 自动打印；跨线程用 `TraceContext.wrap()` 捕获传递；响应头暴露 `X-Trace-Id`，用户报障直接贴 traceId，网关和两个服务的日志一 grep 就还原全链路。没有上 SkyWalking 的理由：自研 traceId 零运维、够用，Trade-off 是没有自动化的调用拓扑图——服务数到两位数时再上 APM。

### 3.8 主题八：手撕代码

> 手撕题尽量往项目场景上靠，每道题先说"这个我在项目里写过类似的"，再写。

**T1：实现一个文本切分器：按 maxChars 切分、支持 overlap 重叠。**

> 就是 `TextChunker.split` 的简化版。先讲思路再写：段落优先聚合（凑不满 maxChars 就继续装下一个段落），段落超长用滑动窗口（步长 = size - overlap），边界条件三个——overlap 不得超过 size/2（`Math.min(overlap, size/2)`）、文本为空返回空列表、最后一段不足时保留尾段。核心循环是"缓冲区 + 刷出时保留尾部 overlap"：
>
> ```java
> // 来源：aihub/aihub-ai-service/src/main/java/com/aihub/ai/domain/support/TextChunker.java
> if (buffer.length() + paragraph.length() + 1 > size) {
>     String flushed = buffer.toString();
>     chunks.add(new Chunk(seq++, flushed));
>     String tail = flushed.length() > ov ? flushed.substring(flushed.length() - ov) : flushed;
>     buffer.setLength(0);
>     buffer.append(tail);          // 保留尾部 overlap 衔接上下文
> }
> ```

**T2：手写一个 ThreadLocal（或讲清原理并实现 get/set）。**

> 每个 Thread 持有一个 ThreadLocalMap，key 是 ThreadLocal 的弱引用，value 是值。实现要点：`get` 先取当前线程的 map，以 this 为 key 查；`set` 直接写。必须能答出**内存泄漏链**：key 弱引用被回收后 entry 的 value 悬空，线程池线程长期存活导致 value 永不释放——所以 map 的 key 为 null 时要清理 stale entry，且使用者必须 finally remove。结合项目：`ChatController` NDJSON 分支 finally 里 `TraceContext.clear()` 就是这个纪律。

**T3：用数组/链表实现一个带 TTL 和容量上限的缓存（LRU 语义）。**

> 对应网关 `ApiKeyCache` 的设计意图：API Key 校验结果本地缓存，TTL 60 秒、容量 10000。手撕方案：`LinkedHashMap` 重写 `removeEldestEntry` 实现 LRU（accessOrder=true），外层再存一个过期时间戳，get 时惰性判断过期。要主动说 Trade-off：TTL 是"延迟与吊销及时性"的平衡，60 秒内吊销的 Key 仍可用；更严格的方案是吊销时发失效事件。

**T4：写一个生产者-消费者（限流/削峰场景）。**

> 结合流式对话线程池讲：固定大小线程池本质就是"无界队列 + 固定消费者"（`Executors.newFixedThreadPool`），风险是任务堆积 OOM，所以要改 `new ThreadPoolExecutor(32, 32, 0, MS, new ArrayBlockingQueue<>(200), 命名工厂, CallerRunsPolicy)`——队列满时由提交线程自己执行，天然反压。能说出"为什么不用无界队列"和"拒绝策略选什么"就是满分。

**T5：判断一个字符串是否为合法 JWT（不依赖库）。**

> 考字符串处理 + 协议理解：按 `.` 切成三段，Header 和 Payload Base64URL 解码后必须是合法 JSON，Header 含 alg 字段，Payload 的 exp 若存在则与当前时间比较。注意 Base64URL 与 Base64 的差异（`-`/`_` 替换 `+`/`/`、无填充）。答完补一句：真实验签必须服务端用密钥做（项目里 `JwtTokenProvider.parse` 走 jjwt 的 `parseSignedClaims`，一步完成格式/签名/过期三重校验），前端只做格式预判。

## 4. STAR 故事库（6 个真实 Bug 全量改写）

> 使用规则：每个故事按 S（情境）→ T（任务）→ A（行动）→ R（结果）讲述；
> 口述时**先说结果再讲过程**，定位手法是最值钱的部分，结尾必须落到提炼的方法论。
> 所有细节（文件名、报错、命令）都与仓库现状对得上，可经得起第三层追问。

### 故事 1：Nacos 3.0.3 开鉴权后客户端注册 403

- **S**：项目用 docker-compose 编排中间件，为了安全把 Nacos 升到 3.0.3 并开启鉴权。升级后所有微服务启动报 403，服务注册不上，配置也拉不到，网关路由空转。
- **T**：定位 403 根因，让服务恢复注册与配置拉取，且密码不能硬编码进仓库。
- **A**：
  1. 读 Nacos 3.x 升级文档，确认 breaking change：**3.x 默认开启鉴权**，未认证的客户端请求直接 403，2.x 时代"裸连"的习惯全部失效；
  2. 在 Nacos 侧初始化管理员账号；
  3. 客户端配置显式声明凭据，并全部走环境变量注入，默认值只用于本地开发（见 `aihub/aihub-gateway/src/main/resources/application.yml` 的 `spring.cloud.nacos.username/password`，`NACOS_USERNAME`/`NACOS_PASSWORD` 占位）；
  4. 同样的账号密码同时配给 Sentinel 的 Nacos 数据源（gw-flow 规则拉取），因为规则持久化也要过鉴权。
- **R**：全部服务注册恢复，配置中心与限流规则持久化链路全部走通；从此本地一键 `docker-compose up` 后无需任何手工干预。
- **提炼**：**大版本升级先读 breaking changes，"升级后第一个 403"大概率是默认安全策略变了，而不是配置写错。**凭据一律环境变量化，默认值只服务开发环境。

### 故事 2：种子管理员密码哈希与注释不符

- **S**：演示账号 admin 的密码注释写着 admin123，但每次登录都报"用户名或密码错误"，demo 租户根本登不进去。
- **T**：在**无法反解哈希**的前提下确认库里哈希到底对应哪个明文，并安全修复。
- **A**：
  1. 先排除验证码/租户码问题（接口日志走到密码校验步）；
  2. 利用 BCrypt `matches(明文, 哈希)` 可单向验证的特性做**对拍**：分别对候选明文 admin123 和 123456 encode，再与 `sys_user` 里的哈希逐一 matches，确认库里哈希匹配 123456——V1 种子脚本生成时贴错了哈希串；
  3. 修复不能改 V1：Flyway 校验已应用脚本的 checksum，改历史脚本直接启动失败。新增增量迁移 `V10__fix_admin_seed_password.sql`，一行 `UPDATE sys_user SET password_hash = <admin123 的正确 BCrypt> WHERE id = 1 AND username = 'admin'`，注释里写明来龙去脉；
  4. 修完当场用 demo/admin123 登录验证。
- **R**：演示账号恢复登录；沉淀出"种子数据写完必须当场验证"的习惯；对拍法后来在另一个哈希问题上复用了一次。
- **提炼**：**哈希不可逆 ≠ 无法验证**——`matches` 就是验证通道；报错文案出于防枚举故意模糊（用户不存在与密码错误同文案），排查时不能依赖报错指向性，要有自己的验证手段。

### 故事 3：知识库表缺列导致接口 500（DO 与 DDL 不一致）

- **S**：知识库列表接口偶发 500，报错是 SQL 异常：`Unknown column 'create_time'`——实体映射引用了 `ai_knowledge_base` 表里不存在的列。
- **T**：让接口恢复，并决定"加列"还是"改代码"的修复方向。
- **A**：
  1. 对比 DO 字段与 `V1__init_ai.sql` 的 `ai_knowledge_base` 建表语句，确认表定义（id/tenant_id/name/embedding_model_id/vector_dim/index_name/status/deleted）里没有 create_time，而代码侧引用了它；
  2. 权衡两个方向：加列要动已应用的 V1（Flyway checksum 不允许），走增量迁移加列又会让一张刚建的表带着补丁脚本，语义冗余；**该列并非业务必需**（列表按 tenant 过滤，不依赖时间排序）；
  3. 决定以 DDL 为事实基准：去掉代码侧对 create_time 的引用，让 DO 与表结构对齐，迁移历史保持干净；
  4. 重启验证接口 200，并顺手核对了同批 DO 与各表定义的一致性。
- **R**：接口恢复；`ai_knowledge_base` 现行 DDL 与实体字段完全一致；这个案例成为团队里"DO 与 DDL 对齐"的反面教材。
- **提炼**：**先问"这列该不该存在"，再问"怎么补"**——修复方向错了，手段再规范也是负债。两个修复原则：能改代码对齐就不动已应用的迁移；修复前先全局对拍同批 DO/DDL，避免按 bug 逐个救火。

### 故事 4：后端菜单接口结构变更引发前端 5 连 Bug

- **S**：后端菜单/权限接口返回**平铺树节点**（`MenuNode{id, path, component, menuType, children}`，M=目录/C=菜单/F=按钮），而管理端脚手架期望的是自己的一套路由格式，对接时前端连环崩。
- **T**：让动态菜单、权限按钮、页面管理功能全部恢复正常，且刷新不丢。
- **A**：逐个击破 5 处（全部在 aihub-admin-ui）：
  1. **动态菜单解析**：`src/api/routes.ts` 写 `toPureRoute` 递归转换，menuType 为 F 的按钮节点过滤出路由、转投按钮权限指令；Element Plus 图标名经 `toIconify` 转 iconify 格式；
  2. **刷新后菜单丢失**：登录缓存的菜单树在内存里，F5 即丢。`getAsyncRoutes` 加兜底：缓存为空且本地有 token 时重拉权限接口（用原始 axios 手动取 `res.data.data.routes`，绕过 http 拦截器解包防止二次解包取错层级）；
  3. **顶级叶子路由崩溃**：后端把菜单节点直接挂在顶层时，脚手架路由转换对无 children 的顶级节点处理不健壮，router/index.ts 补防御；
  4. **菜单管理页、角色管理页**：两处页面按旧的 `{menu:{...}}` 包裹结构取值，全部改成直接消费平铺节点字段。
- **R**：5 处全部修复，动态菜单/按钮权限/刷新保持全链路可用；回归时把"登录→刷新→访问每个菜单"列为标准验收路径。
- **提炼**：**接口结构变更是"一个根因多点爆炸"的典型**——根因只有一个（数据结构契约不一致），爆炸点有 N 个。修完最后一处不等于结束，必须全局搜消费方逐一核对；长期解是把数据契约写成单一事实来源（类型定义 + 契约测试）。

### 故事 5：Vite 7 与 Node 16 的兼容性崩溃

- **S**：管理端升级到 Vite 7 后，本机（Node 16.20.2）执行 dev 命令直接崩，报错 `crypto.getRandomValues is not a function`，看起来像代码或依赖的 bug。
- **T**：定位真实原因并让团队任何人 clone 后都能一条命令跑起来。
- **A**：
  1. 顺着报错查栈，崩溃点在依赖 Web Crypto API 的启动路径——`crypto.getRandomValues` 是浏览器/新版 Node 的全局 API；
  2. 查 Vite 7 发布说明：**要求 Node 20.19+**，Node 16 的全局对象没有暴露该 API，不是代码 bug 而是**工具链版本不满足**；
  3. 用 nvm 安装并切换 Node 24.14.0，启动正常；
  4. 为防复发，把 Node 版本要求写进项目文档与 README 的前置条件。
- **R**：从报错到修复约半小时；此后新环境搭建零踩坑。
- **提炼**：**看到 crypto/WebStream/AbortController 类报错，第一反应查运行时版本**——报错指向的是"缺 API"，缺 API 的原因往往是"Node 太老"。工具链版本约束要写进仓库，不能靠口口相传。

### 故事 6：uni-app CLI 报 ENOENT manifest.json

- **S**：用户端 aihub-app 沿用 HBuilderX 目录结构（manifest.json、pages.json 在项目根目录），改用 CLI 工程化启动时报 ENOENT：找不到 `src/manifest.json`。
- **T**：不改目录结构（与 HBuilderX 生态兼容），让 CLI 正常构建 H5 与微信小程序。
- **A**：
  1. 读 uni CLI 的 node_modules 源码，确认它按约定从 `src/` 读源码，入口解析发生在**加载 vite 配置之前**——这意味着写在 vite.config.js 里的环境变量来不及生效，这是一个时序问题而不是配置问题；
  2. 官方逃生口是环境变量 `UNI_INPUT_DIR`，必须在进程启动前设置；
  3. 写启动器 `aihub-app/scripts/uni.js`：先用 `path.resolve(__dirname, "..")` 把 `UNI_INPUT_DIR` 设为项目根目录，再 `require("@dcloudio/vite-plugin-uni/bin/uni.js")` 转发 CLI 入口；
  4. package.json 里所有命令（dev:h5 / dev:mp-weixin / build:h5 / build:mp-weixin）统一经该脚本转发，命令行参数原样透传。
- **R**：不改一行业务代码，H5 与微信小程序两种构建全部正常；目录结构与 HBuilderX 保持兼容。
- **提炼**：**报"找不到文件"先怀疑路径约定，再怀疑时序**——"配置写了却没生效"要画出配置的加载时序图。读 node_modules 源码是定位 CLI 类问题的最后一招，也是最有效一招。

### 6.1 反问清单（按目的分类，挑 2-3 个问）

**避坑类（判断要不要去）：**

**不要问**：薪资加班（留到 HR 面）、"你们用什么技术栈"（面试前就该查）、任何官网首页能查到的问题。

### 6.2 面试策略六条

1. **每个项目点都准备"三层深度"**：一句话版本（30 秒电梯演讲）→ 机制版本（本文件第 3 章答案）→ 源码版本（类名+关键数字：`AuthGlobalFilter` order=-100、SSE 120s、流线程池 32、JWT 7200s、API Key 缓存 TTL 60s）。面试官挖到哪层你讲到哪层，**不要一次全倒出来**。
2. **先说结果再讲过程**：讲 bug 故事第一句永远是"最后发现是 XXX"。面试官的注意力窗口只有 30 秒。
3. **Trade-off 是区分度的来源**：每个选型背熟一句"为什么不选另一个"——Nacos vs Eureka（配置中心一体化、AP 优先）、SSE vs WebSocket（单向够用、小程序硬约束）、行级隔离 vs 独立库（租户多量小的成本函数）。
4. **主动降调比被问穿体面**：没做完的事（如更系统的自动化测试、独立库方案、完整 APM）被问到时，直接说"这是明确的待补项，我的改进方案是……"，并给出方案——这反而加分。
5. **说不出处的数字不要用**：本文所有数字都能对应到源文件（application.yml、ChatController、JwtTokenProvider），被问"这个 120 秒在哪配的"要能答上来。
6. **手撕题往项目靠**：拿到手撕题先说一句"这和我在项目里写的 XX 场景很像"，然后按项目场景的边界条件展开（比如切分器的 overlap 上限），既有代码又有业务理解。
