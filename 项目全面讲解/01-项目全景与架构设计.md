## 1. 项目是做什么的

### 1.1 一句话介绍

**AIHub 是一个多租户的通用 AI 能力中台（SaaS 化 AI 平台）**：用一套 Java 微服务系统，同时服务多家企业租户，把"大模型调用、AI 应用、知识库 RAG、MCP 工具、Agent、用量计费"这些 AI 基础能力统一封装，让租户像开箱用电一样使用 AI 能力，平台方则统一管控模型、配额与安全。

### 1.2 先讲"为什么"：为什么不直接写一个聊天 Demo？

写一个调用大模型的单机 Demo 只要几十行代码。但一旦想让**多家公司**都来用它，问题立刻出现：

- A 公司配置的模型 Key 不能让 B 公司看到（**隔离**问题）；
- 每家公司该用多少 token、收多少费（**计量计费**问题）；
- 某家公司上传的文档，检索结果绝不能出现在另一家公司的答案里（**数据安全**问题）；
- 模型供应商今天用 OpenAI、明天想换通义/火山（**可替换**问题）；
- 流式输出、并发限流、审计日志（**生产工程化**问题）。

AIHub 就是为了把这些问题一次性解决而设计的。所以它不是"聊天应用"，而是一个**平台**——聊天只是跑在平台上的一个应用形态。

### 1.3 三类角色

| 角色 | 谁来扮演 | 用什么入口 | 核心诉求 |
| --- | --- | --- | --- |
| **平台管理员** | 运营方自己 | 管理端 `aihub-admin-ui`（端口 8849） | 管用户/角色/菜单（RBAC）、管租户、看全局用量 |
| **企业租户（管理员+成员）** | 接入的企业 | 同一管理端，按租户隔离数据 | 配模型、建知识库、建应用、管 API Key、看本租户用量 |
| **终端用户** | 企业最终客户 | 用户端 `aihub-app`（H5 端口 5173，可发微信小程序） | 直接对话、用知识库问答，不关心后台 |

配套的真实账号体系（本地开发）：租户码 `demo`，管理员用户 `admin`，密码 `admin123`。

AIHub 把平台能力归纳为五个要素，每一项都有对应的库表和管理页面：

| 要素 | 是什么 | 在代码/库里的落点 |
| --- | --- | --- |

### 2.3 怎么读这张图

1. **所有流量只从网关 8080 进来**。两个前端都不同源（8849、5173），跨域由网关全局 CORS 解决（`aihub/aihub-gateway/src/main/resources/application.yml` 中 `spring.cloud.gateway.globalcors`），开发期前端再用 Vite 代理减少一层干扰（`aihub-admin-ui/vite.config.ts` 中 `server.proxy` 把 `/auth`、`/api` 转发到 `http://localhost:8080`）。
2. **网关按路径前缀路由**：`/auth/**`、`/api/platform/**` → platform-service；`/api/ai/**` → ai-service。`lb://` 前缀表示走 Nacos 服务名负载均衡，而不是写死 IP。
3. **两个业务服务各配一个 MySQL 库**（`aihub_platform` / `aihub_ai`），数据库"按服务拆"而不是"全项目共用一个库"，这是微服务数据边界的底线。
4. **服务无状态**：登录态在 JWT 里，验证码/缓存/向量在 Redis，会话与任务在 MySQL——所以任何一个业务服务都可以水平扩多实例（注册到 Nacos 后网关自动负载均衡）。
5. **AI 服务是"能力内聚"的单体**：模型、RAG、Agent、会话都放在 ai-service 里，而不是拆成更多微服务——原因见第 3.3 节。

## 3. 微服务拆分讲解

### 3.1 先讲"为什么"：拆分的两条铁律

微服务拆分最常见的错误是"按层拆"（一个服务专门放 Controller、一个专门放 Service），这会导致改一个功能要横跨所有服务。正确做法只有两条：

1. **按业务能力拆（Business Capability）**：每个服务对应一块能独立交付价值的业务——"认证与权限"是一个服务（platform-service），"AI 能力"是一个服务（ai-service）。
2. **契约层独立成模块**：服务之间调用的接口与 DTO 单独放在 `aihub-api` 模块，谁被调用谁实现，谁要调用谁依赖——避免"把实现类拷来拷去"的腐烂。

### 3.2 八个后端模块职责表

模块清单来自父 POM（`aihub/pom.xml` 的 `<modules>` 节点，共 8 个）：

| --- | --- | --- | --- | --- |
| `aihub-common` | 普通 jar | 无 | 通用支撑：统一响应体 `R`/`ResultCode`、异常 `BizException`/`GlobalExceptionHandler`、租户上下文 `TenantContext`/`TenantResolveInterceptor`、JWT 校验器 `JwtVerifier`、API Key 编解码 `ApiKeyCodec`、AES 加密 `AesGcmTextCipher`、链路追踪 `TraceContext`/`TraceIdInterceptor` | `aihub/aihub-common/src/main/java/com/aihub/common/`（11 个类） |

### 3.3 为什么这么拆？逐个回答

**Q：为什么网关单独一个服务？**
鉴权、限流、路由是所有请求的"公共前置逻辑"。如果不放网关，每个业务服务都要自己写一遍 JWT 解析、限流、CORS——三处代码三处 Bug。收口到网关后，业务服务只需信任网关透传的 `X-Tenant-Id`/`X-User-Id` 头（由 `aihub/aihub-common/src/main/java/com/aihub/common/tenant/TenantContext.java` 定义的 `HEADER_TENANT`/`HEADER_USER` 常量约定）。

**Q：为什么认证+RBAC+配额在 platform-service，而对话+RAG 在 ai-service？**
按"变更频率与治理要求"拆：
- 认证、用户、角色、配额属于**治理面**：变更少、安全等级高、数据强一致（BCrypt 密码、角色树、余额）；
- 模型、应用、知识库、对话属于**能力面**：迭代快、流量大、允许最终一致。
拆开后 AI 功能的频繁迭代不会碰坏登录链路；配额扣减（钱相关）也有独立的事务边界。

**Q：为什么 AI 能力不继续拆成"模型服务/知识库服务/Agent 服务"多个微服务？**
因为它们共享同一个上下文：一次 RAG 对话要同时用到模型客户端、向量检索、会话记忆。若拆成三个服务，一次对话要跨 3 次网络调用，且 SSE 流式响应被中转两次（延迟、半包问题都会放大）。父 POM 里 ai-service 的模块描述写得很直白（`aihub/aihub-ai-service/pom.xml` 第 14 行）：*"AI 服务（内聚）：模型网关、应用、知识库RAG、工具MCP、Agent、会话、产物"*。这是刻意的取舍：**先内聚保证链路简单，包内部用分层（web/application/domain/infra）防止腐化，将来真有独立伸缩需求再外拆**。

**Q：为什么 MCP 要拆成三个模块？**
见第 3.2 节引文。核心动机有两个：
1. **传输与业务解耦**：`@Tool` 工具实现只写一次，SSE 与 stdio 两种传输各自引入协议 starter（对比两个 POM 可证：`aihub/aihub-mcp-sse/pom.xml` 引 `spring-ai-starter-mcp-server-webmvc`，`aihub/aihub-mcp-stdio/pom.xml` 引 `spring-ai-starter-mcp-server`）。
2. **依赖最小化**：`aihub/aihub-mcp-service/pom.xml` 第 17~20 行注释专门解释了为什么**刻意不依赖 aihub-common**——因为它带 `spring-boot-starter-web`，会把整个 Servlet 容器拖进 stdio 进程的 classpath；stdio 版是被宿主进程拉起的 CLI，容器纯属负担。模块只保留"发 HTTP + 解 JSON"的最小依赖。

**Q：为什么 common 和 api 分成两个模块，而不是合成一个？**
`aihub-common` 是**纵向复用**（所有服务都依赖它的 R/异常/租户上下文）；`aihub-api` 是**横向契约**（只有调用方与被调方依赖）。合在一起的话，任何一个服务引 common 就被动拿到了 Feign 接口——比如网关并不调用 platform 的内部接口，却要背上 OpenFeign 依赖。契约独立后，"改契约影响谁"一目了然：只有 `aihub/aihub-api/pom.xml` 的依赖方（platform 与 ai-service）。

```
│    :8080    │      │  service   :8081    │◀─────  (common+api) :8082
└─────────────┘      └─────────────────────┘
```

阅读要点：`aihub-gateway` 只依赖 `common`（它不调用 Feign 契约，见 `aihub/aihub-gateway/pom.xml`）；`aihub-platform-service` 与 `aihub-ai-service` 同时依赖 `common` 与 `api`；MCP 三件套自成小体系。

### 3.5 补一块拼图：`lb://` 是怎么找到服务的？

架构图里网关写的是 `lb://aihub-platform-service`，它为什么能变成一个真实的 IP+端口？流程是：

```
① platform-service 启动，spring.application.name=aihub-platform-service（aihub/aihub-platform-service/src/main/resources/application.yml 第 6 行）
        │  Nacos Discovery Starter 把「服务名 + IP:8081 + 健康状态」注册进 Nacos 注册表
        ▼
② Nacos 服务端（docker 容器 aihub-nacos，8848/9848）维护服务列表，心跳断掉即摘除实例
        │  网关启动时订阅 aihub-platform-service / aihub-ai-service 两个服务名的实例列表
        ▼
③ 请求到达网关，路由断言命中 Path=/auth/** → uri lb://aihub-platform-service
        │  Spring Cloud LoadBalancer 从本地缓存的实例列表里挑一个（客户端负载均衡）
        ▼
④ 真正发出 http://192.168.x.x:8081/auth/login —— 全程没有任何人手写 IP
```

这解释了三个设计事实：
- 两个业务服务的 yml 里都配了 `spring.cloud.nacos.discovery.server-addr: ${NACOS_ADDR:127.0.0.1:8848}` 和鉴权账号（与网关同构，因为 Nacos 3.0.3 开了鉴权）；
- 网关关闭了服务名自动路由 `discovery.locator.enabled: false`（`aihub/aihub-gateway/src/main/resources/application.yml` 第 24~26 行）——**只允许显式声明的路由**，避免"随便一个服务注册进来就自动暴露给外网"的安全口子；
- 扩容时只需要再起一个 platform-service 实例（改端口），它会自己注册进 Nacos，网关无感知分流。这就是第 2.3 节"服务无状态"的实现基础。

### 4.3 核心选型逐项答辩（为什么选它、备选是什么）

#### ① 注册中心与配置中心：Nacos（3.0.3） vs Eureka

- **为什么选 Nacos**：一个组件同时干两件事——**服务发现**（服务上下线自动感知，网关 `lb://` 直接按服务名路由）+ **配置中心**（`aihub/aihub-gateway/application.yml` 里 `spring.config.import: optional:nacos:aihub-common.yaml` 实现配置热更新）。另外它是国内 Spring Cloud Alibaba 生态的一等公民，文档与社区问答多。本项目用 Docker 镜像 `nacos/nacos-server:v3.0.3`（`aihub/docker-compose.yml`），3.x 走 gRPC 长连接（端口 9848），并开启了鉴权（`NACOS_AUTH_ENABLE: "true"`）。
- **备选对比**：
  - *Eureka*：Netflix 老牌方案，但配置中心能力缺失（还得配 Spring Cloud Config + Git），且社区已进入维护模式；AP 模型下服务列表短暂不一致可接受，但功能面窄。
  - *Consul / etcd*：能力强但偏云原生 K8S 场景，Java 生态接入成本高。
  - *ZooKeeper*：CP 模型，注册中心场景"为了可用性牺牲一致性"更合适（宁可短暂拿到旧列表，不可注册服务不可用）。
- **代价**：Nacos 3.0.3 开鉴权后客户端必须显式配账号密码，否则注册 403——本项目就真实踩过这个坑（客户端统一在 yml 里配 `username/password`，见网关配置第 12~13 行，初始化 admin 的 curl 命令写在 compose 第 66~68 行注释里）。详见系列第 02 篇专题。

#### ② 服务间调用：OpenFeign + LoadBalancer vs RestTemplate / Dubbo

- **为什么选 OpenFeign**：声明式 HTTP 客户端——接口+注解即契约（`aihub/aihub-api/src/main/java/com/aihub/api/client/PlatformClient.java`），配合 LoadBalancer 从 Nacos 拉实例做客户端负载均衡。本项目只有一个跨服务调用方向（ai-service → platform-service 扣配额），Feign 的轻量恰到好处。
- **备选对比**：*RestTemplate/WebClient 手写*：URL、序列化、错误处理全要手写，契约散落各处；*Dubbo*：性能好但引入另一套 RPC 体系与注册协议，与"HTTP+JSON 足够"的规模不匹配。
- **加分设计**：`aihub/aihub-api/src/main/java/com/aihub/api/config/FeignTenantConfig.java` 用 `RequestInterceptor` 让**所有** Feign 调用自动携带 `X-Tenant-Id`/`X-User-Id`——租户透传一处配置全局生效，杜绝"某个调用忘了带租户头"的越权事故。

#### ③ 网关：Spring Cloud Gateway vs Zuul

- **为什么选 SCG**：基于 WebFlux 的响应式非阻塞模型，长连接/流式（SSE 转发）场景吞吐高；路由断言+过滤器链的编程模型清晰。本项目网关 POM 明确注释"网关基于 WebFlux，不可引入 spring-boot-starter-web"（`aihub/aihub-gateway/pom.xml` 第 21 行），并在 yml 里显式 `spring.main.web-application-type: reactive`（`aihub/aihub-gateway/src/main/resources/application.yml` 第 8 行）。
- **备选对比**：*Zuul 1*：Servlet 阻塞模型，一请求一线程，SSE 高并发下线程耗尽；*Nginx+Lua*：性能强但鉴权逻辑要写 Lua，团队栈不匹配。
- **配套**：限流选 **Sentinel**（网关流控规则 `gw-flow` 从 Nacos 拉取持久化，命中返回 429 + 统一 JSON 兜底体，同 yml 第 47~69 行）。备选 *Hystrix* 已停更；*Resilience4j* 无开箱限流看板。

#### ④ ORM：MyBatis-Plus vs Spring Data JPA

- **为什么选 MyBatis-Plus**：
  1. **SQL 透明可控**：多租户项目的每条查询都要带 `tenant_id`，SQL 写在哪、怎么写必须看得见；JPA 的派生查询和一级缓存让"这条 SQL 长什么样"变黑盒。
  2. **生产力**：`BaseMapper` 免写单表 CRUD，`@TableLogic` 声明式软删，分页插件即插即用。
  3. **团队与生态**：国内微服务项目事实标准，排错资料丰富。
- **备选对比**：*JPA/Hibernate*：对象图导航方便，但复杂 SQL 要退回 native query，缓存与脏检查的心智负担重；*纯 MyBatis*：全部手写 XML，单表 CRUD 重复劳动多。
- **项目实证**：platform-service 与 ai-service 都引 `mybatis-plus-spring-boot3-starter`（`aihub/aihub-platform-service/pom.xml` 第 50~53 行）；DO 命名统一为 `XxxDO`（如 `aihub/aihub-ai-service/src/main/java/com/aihub/ai/infra/persistence/dataobject/AiKnowledgeBaseDO.java`），且多租户 SQL 兜底有专门的 `aihub/aihub-ai-service/src/main/java/com/aihub/ai/config/TenantSqlGuardConfig.java`。

#### ⑤ 向量检索：Redis Stack（RediSearch） vs Milvus

- **为什么选 Redis Stack**：`aihub/docker-compose.yml` 第 36~50 行用的是 `redis/redis-stack-server:7.4.0-v6`，健康检查甚至专门断言 `MODULE LIST` 里存在 `search` 模块——因为普通 Redis 没有向量能力。选它的理由：
  1. **组件复用**：Redis 本来就要做缓存和验证码，一个组件三用，本地开发与部署成本低；
  2. **规模匹配**：单租户知识库文档量在万级 chunk、向量百万条以内时，RediSearch 的 HNSW 索引性能完全够用；
  3. **Spring AI 官方适配**：引 `spring-ai-starter-vector-store-redis`（`aihub/aihub-ai-service/pom.xml` 第 67~70 行）即得 `VectorStore` 抽象，索引名与前缀在 yml 配置（`aihub/aihub-ai-service/src/main/resources/application.yml`：`spring.ai.vectorstore.redis.index-name: ${AI_VS_INDEX:spring-ai-index}`）。
- **备选对比**：*Milvus*：亿级向量、多副本、GPU 检索能力强，但要独立部署（通常还带 etcd/MinIO），运维复杂度陡增——对毕设/中小项目是"用大炮打蚊子"；*pgvector*：复用 PostgreSQL，但本项目主库是 MySQL，引入第二个数据库不划算；*Elasticsearch*：全文检索强，向量能力后期才补齐且内存开销大。
- **关键约束**：知识库创建时要指定 `vectorDim`（嵌入维度），必须与所选 Embedding 模型输出维度一致（如 1536/1024），见 `aihub/aihub-ai-service/src/main/java/com/aihub/ai/web/KnowledgeController.java` 第 112~113 行注释："Embedding 维度，须与模型一致（如 1536 / 1024）"。索引建好后维度不可改，换模型要走重建索引流程。

#### ⑥ 数据库迁移：Flyway vs Liquibase

- **为什么选 Flyway**：约定优于配置——`V<版本号>__描述.sql` 放进 `db/migration/` 即生效，启动时自动执行并记录 checksum；SQL 就是原生 SQL，无 XML/YAML 中间层。本项目两个服务各自维护迁移目录，历史从 V1 演进到 V10。
- **备选对比**：*Liquibase*：支持 changelog 抽象（可跨数据库），但表达力换来的复杂度对本项目是负担。
- **纪律**：历史迁移文件**不可修改**（checksum 会校验失败），有 Bug 就新增 V(n+1) 修复迁移——项目里就有两个真实修复案例：`V10__fix_admin_seed_password.sql` 与 `V10__kb_add_create_time.sql`（详见第 02 篇）。

#### ⑦ 认证：JWT（jjwt） vs Session / OAuth2

- **为什么选 JWT 无状态认证**：网关要本地校验而不回查平台服务（`aihub/aihub-gateway/pom.xml` 第 65 行注释："JWT 自解析：网关本地校验令牌，避免每个请求都回查平台服务"）。签发在 platform-service 的 `aihub/aihub-platform-service/src/main/java/com/aihub/platform/auth/service/AuthService.java`，校验用的 `JwtVerifier` 放在 common 模块给网关共用（`aihub/aihub-common/src/main/java/com/aihub/common/security/JwtVerifier.java`）。
- **备选对比**：*Session*：有状态，多实例要粘性会话或集中存储，且小程序端 cookie 管理麻烦；*Spring Security 全家桶/OAuth2 授权服务器*：能力全但配置重，本项目只需要"签发+校验"两个动作，引完整 Security 过滤器链得不偿失——所以 platform-service 只引了 `spring-security-crypto`（`aihub/aihub-platform-service/pom.xml` 第 34~38 行注释："仅使用其密码加密能力（BCrypt），未引入完整 Security 过滤器链"）。

## 5. 关键设计决策

本章讲四个最重要的架构决策。每个都按"为什么需要 → 是什么 → 项目怎么落地的"展开。

### 5.1 多租户隔离：共享行级隔离 + 四道防线

**为什么需要隔离方案对比**：多租户有三种经典隔离粒度——

| 方案 | 做法 | 优点 | 缺点 | 何时选 |
| --- | --- | --- | --- | --- |
| 独立数据库 | 每租户一个 DB | 隔离最强、可按租户备份 | 成本高、连接池爆炸、跨租户运营难 | 金融/强合规大客户 |
| 独立 Schema | 每租户一个 schema | 折中 | 迁移脚本要跑 N 遍，MySQL 对 schema 支持弱 | 中型 SaaS |
| **共享表 + 行级 `tenant_id`** | 所有业务表带 `tenant_id` 列，查询强制过滤 | 成本最低、运营方便 | **依赖代码纪律**，漏条件即越权 | 绝大多数 SaaS（本项目选它） |

**项目落地（证据链）**：

0. **上下文载体长什么样**——`aihub/aihub-common/src/main/java/com/aihub/common/tenant/TenantContext.java` 的核心结构（节选）：

```java
// aihub/aihub-common/src/main/java/com/aihub/common/tenant/TenantContext.java
/** 服务间透传租户的请求头。网关解析 JWT 后写入，下游服务读取 */
public static final String HEADER_TENANT = "X-Tenant-Id";
/** 服务间透传用户的请求头 */
public static final String HEADER_USER = "X-User-Id";

/** 租户 ID 的线程级存储。泛型 Long 对应数据库 tenant_id 列 */
private static final ThreadLocal<Long> TENANT = new ThreadLocal<>();
private static final ThreadLocal<Long> USER = new ThreadLocal<>();

/** 必须存在的租户 ID，缺失即视为越权风险 */
public static Long requireTenantId() {
    Long id = TENANT.get();
    if (id == null) {
        throw new com.aihub.common.exception.BizException(
                com.aihub.common.result.ResultCode.TENANT_MISMATCH, "租户上下文缺失");
    }
    return id;
}
```

  三个细节值得在面试里展开：① `requireTenantId()` 在缺失时直接抛 `TENANT_MISMATCH` 业务异常——"宁可报错，不可裸奔"；② `USER` 与 `TENANT` 分开存，因为 API Key 调用有租户无用户；③ `clear()` 由拦截器在请求结束调用，否则线程池复用线程会串台。

1. **租户上下文载体**：`aihub/aihub-common/src/main/java/com/aihub/common/tenant/TenantContext.java`——基于 ThreadLocal 存"当前请求是谁"，类注释把最高危约束写死："**租户 ID 只允许从 JWT / API Key 解析后写入，绝不接受前端传参**"。同时定义了跨服务透传头 `X-Tenant-Id`（`HEADER_TENANT`）与 `X-User-Id`（`HEADER_USER`）。
2. **入口写入**：`aihub/aihub-common/src/main/java/com/aihub/common/tenant/TenantResolveInterceptor.java` 在服务入口从请求头解析并写入上下文，请求结束 `clear()` 防止线程池串台。
3. **网关来源可信**：`aihub/aihub-gateway/src/main/java/com/aihub/gateway/filter/AuthGlobalFilter.java` 校验 JWT 后把 claims 中的租户/用户写入请求头，下游服务只认这个头。
4. **跨服务透传**：`aihub/aihub-api/src/main/java/com/aihub/api/config/FeignTenantConfig.java` 保证 Feign 调用自动带租户头。
5. **SQL 兜底**：`aihub/aihub-ai-service/src/main/java/com/aihub/ai/config/TenantSqlGuardConfig.java`——MyBatis 拦截器兜底补全租户条件（当前默认关闭，需在真实库回归后按注释开启，这是项目里明确记录的演进项）。
6. **向量库的租户过滤**：检索入口 `aihub/aihub-ai-service/src/main/java/com/aihub/ai/infra/ai/RedisKnowledgeRetriever.java` 强制按 `tenant_id` + `kb_id` 过滤向量元数据，业务代码禁止直接拿 VectorStore 裸查。

**面试一句话**："我们选共享行级隔离，租户 ID 只能从 JWT/API Key 解析、经网关→Feign 全链路透传，业务查询强制带租户条件，再用拦截器兜底——四道防线，每道都有对应类。"

### 5.2 JWT 无状态认证：签发与校验分离

**为什么**：微服务下如果用 Session，要么粘性路由要么共享 Session 存储，扩容与跨端（小程序无 cookie）都麻烦。JWT 把"你是谁、你属于哪个租户、你有什么角色"签进令牌，任何持有密钥的节点都能本地验真——**认证从"每次问权威服务"变成"本地验签"**。

**项目落地**：

- **签发侧**：platform-service 的 `AuthService` 完成验证码校验、BCrypt 密码比对后签发 JWT，claims 携带 `tenantId`/`userId`/`roles`。为什么把 `tenantId` 放 claims？因为它是后续所有数据过滤的根，放进令牌后**客户端无法伪造**（签名保护），服务端也就无需每请求查库。
- **校验侧**：网关 `AuthGlobalFilter` 用 common 的 `JwtVerifier` 本地验签，白名单放行（登录、验证码等公开接口），通过后把 `X-Tenant-Id`/`X-User-Id` 写入转发头。
- **路由与密钥的真实配置**——`aihub/aihub-gateway/src/main/resources/application.yml` 节选：

```yaml
# aihub/aihub-gateway/src/main/resources/application.yml
aihub:
  security:
    # 生产环境请放入 Nacos 并开启鉴权，不要使用默认值
    jwt-secret: ${AIHUB_JWT_SECRET:aihub-default-dev-secret-please-change-me-32bytes}
  apikey:
    verify-url: ${AIHUB_PLATFORM_URL:http://aihub-platform-service}
    # 校验超时：鉴权在主链路上，不能让平台服务拖死网关
    verify-timeout-ms: 2000
    # 缓存 TTL 是「延迟」与「吊销及时性」的平衡点
    cache-ttl-seconds: 60
    cache-max-size: 10000
```

  注意 `verify-timeout-ms: 2000` 的注释——**鉴权在主链路上，不能让平台服务拖死网关**：远程校验必须设超时上限，超时宁可拒绝也不无限等，这是把"安全组件"当"可用性组件"来设计的意识。
- **签发侧的密钥来源**：platform-service 与网关共用同一个 `jwt-secret` 环境变量约定（`AIHUB_JWT_SECRET`），密钥不一致时网关验签必然失败——这是部署时"登录成功但后续请求 401"的第一排查点。
- **API Key 双轨**：面向开放 API 的调用没有登录态，用 API Key 代替 JWT：`aihub/aihub-common/src/main/java/com/aihub/common/security/ApiKeyCodec.java` 负责编解码，网关 `aihub/aihub-gateway/src/main/java/com/aihub/gateway/apikey/ApiKeyVerifier.java` 回调平台校验，`ApiKeyCache.java` 用 Caffeine 缓存校验结果（TTL 60 秒）——注释原话："校验结果缓存：省掉绝大部分远程调用；设 false 则每次实时校验"。

**取舍与代价**：JWT 无法主动作废（吊销要等过期或引入黑名单），敏感操作仍需服务端二次校验角色权限——本项目 RBAC 校验在服务层，不完全信任令牌内容。

### 5.3 流式输出：SSE 一等公民，三种 StreamSink 适配

**为什么流式是刚需**：大模型生成一篇回答需要数秒到数十秒，非流式接口用户要盯着白屏等完整结果，体验极差且容易网关超时。流式让 token 一到就推给前端，首字延迟从"整篇时间"降到"第一个 token 时间"。

**为什么主选 SSE 而不是 WebSocket**：
1. 对话场景**只需服务端单向推送**，WebSocket 的双向能力用不上，反而多了协议升级（HTTP→WS）、代理兼容（Nginx 需额外配置）、心跳维护三个负担；
2. SSE 走纯 HTTP，网关（`aihub-gateway`）无需任何特殊配置即可转发；
3. 浏览器端接收简单（`fetch + ReadableStream` 或 EventSource）。
备选 WebSocket 留给**真正双向**的场景——本项目的 Agent 长任务用了它（`aihub/aihub-ai-service/src/main/java/com/aihub/ai/web/ws/AgentWebSocketHandler.java`，因为 Agent 执行中用户要能发"停止"指令）。

**项目落地**：输出通道抽象成 SPI 接口 `aihub/aihub-ai-service/src/main/java/com/aihub/ai/domain/spi/StreamSink.java`，三个实现按客户端类型选择：

| 实现 | 通道 | 适用端 |
| --- | --- | --- |
| `SseStreamSink`（`.../web/sink/SseStreamSink.java`） | `text/event-stream` | H5 用户端（5173） |
| `NdjsonStreamSink`（`.../web/sink/NdjsonStreamSink.java`） | `application/x-ndjson` 分块 JSON | 微信小程序（`uni.request` 的 `enableChunked` + `onChunkReceived`） |
| `WsStreamSink`（`.../web/sink/WsStreamSink.java`） | WebSocket | Agent 长任务（双向、可中断） |

入口在 `aihub/aihub-ai-service/src/main/java/com/aihub/ai/web/ChatController.java`，编排逻辑在 `aihub/aihub-ai-service/src/main/java/com/aihub/ai/application/ChatAppService.java`（含 token 用量"事后补扣"，第 145 行注释）。

**统一事件帧**：三种通道共用同一套事件模型 `aihub/aihub-ai-service/src/main/java/com/aihub/ai/domain/model/StreamEvent.java`（`msg.start`/`token`/`tool.start`/`rag.sources`/`msg.end`/`error` 等），前端换端不改事件协议。事件帧形态示意（设计约定见 `docs/03-架构设计说明书.md` 第 7 节）：

```json
// 流式对话中每一帧的大致形态（示意，字段以 StreamEvent 实际定义为准）
{ "e": "msg.start", "data": { "messageId": "..." } }
{ "e": "token",     "data": { "content": "你好" } }
{ "e": "rag.sources", "data": { "sources": [ { "docId": 1, "chunkId": 42 } ] } }
{ "e": "msg.end",   "data": { "usage": { "tokens": 356 } } }
```

**为什么小程序不用 SSE 而用 NDJSON**：微信小程序的 `wx.request`/`uni.request` 不支持浏览器原生的 `text/event-stream` 解析，但提供了 `enableChunked: true` + `onChunkReceived` 的分块接收能力——于是服务端把同一份事件流序列化成"一行一个 JSON"的 NDJSON 持续分块写出，客户端按 `\n` 切分处理半包。同一套 `StreamSink` 抽象让这两种协议的差异被完全吸收在服务端，`ChatAppService` 的编排代码一行不改。

**一个常被追问的细节**：SSE 连接中断怎么办？`SseEmitter`/流式写出的回调里会收到 `onError`/`onCompletion`，服务端据此关闭 `StreamSink`、停止模型调用、落库已完成的部分内容——这正是把输出通道抽象成 `StreamSink.close()` 的原因之一：**生命周期被收敛到一个接口方法里**，三种通道的清理逻辑各自实现但调用方无感。

### 5.4 仓储模式：`domain.spi` 接口 + `infra.persistence` 实现

**为什么**：如果业务代码直接拿着 MyBatis-Plus 的 Mapper 写，会发生两件坏事：一是领域逻辑与框架焊死（换库=重写），二是无法脱离数据库做单元测试。解法是**依赖倒置**：业务定义"我需要什么"（接口），基础设施回答"我怎么做到"（实现）。

**是什么**：ai-service 包结构本身就是分层（注意与旧设计文档的演进差异——实际代码把分层做成了单服务内的包，而不是独立 Maven 模块）：

```
aihub/aihub-ai-service/src/main/java/com/aihub/ai/
├── web/                  # 表现层: Controller + 三种 StreamSink
├── application/          # 编排层: ChatAppService / KnowledgeAppService / AppAdminService ...
├── domain/
│   ├── model/            # 领域模型: App / ChatTurn / Chunk / RetrievedChunk / StreamEvent ...
│   ├── spi/              # ★ 扩展点接口: KnowledgeBaseRepository / ModelGateway /
│   │                     #   KnowledgeRetriever / KnowledgeIndexer / AppRepository /
│   │                     #   AgentTaskRepository / EventOutbox / StreamSink ...
│   └── support/          # 纯域工具: TextChunker（切片算法，无框架依赖）
└── infra/
    ├── ai/               # AI 适配: ChatClientFactory / DbModelGateway /
    │                     #   RedisKnowledgeRetriever / RedisKnowledgeIndexer /
    │                     #   OpenAiCompatibleChatModelResolver / agent/* / tools/*
    ├── persistence/      # MySQL 适配: DbKnowledgeBaseRepository / DbDocumentRepository /
    │                     #   DbAppRepository / DbModelGateway / mapper/* / dataobject/*
    ├── storage/          # 文件存储: LocalIngestFileStore / MinioIngestFileStore
    └── outbox/           # 事件外发: DbEventOutbox / EventOutboxDispatcher
```

**逐方法看一个例子**——接口 `aihub/aihub-ai-service/src/main/java/com/aihub/ai/domain/spi/KnowledgeBaseRepository.java` 声明知识库的增删查；实现 `aihub/aihub-ai-service/src/main/java/com/aihub/ai/infra/persistence/DbKnowledgeBaseRepository.java` 用 `AiKnowledgeBaseMapper`（MyBatis-Plus）落地，创建时写入 `vectorDim`/`indexName` 并设置默认 Embedding 模型（第 28 行注释："M2 使用默认 Embedding 模型，M5 支持按 KB 选型"——同时是第 6 章里程碑的证据）。

**收益实例**：
- 同一个 `ModelGateway` 接口，MySQL 配置驱动的实现是 `DbModelGateway`（`.../infra/ai/DbModelGateway.java`）——换模型供应商只改配置表，不改业务代码；
- 同一个 `KnowledgeRetriever` 接口，实现是 `RedisKnowledgeRetriever`——将来换 Milvus 只需新增 `MilvusKnowledgeRetriever` 并替换装配；
- 编排层 `KnowledgeAppService`、`ChatAppService` 的单测（`aihub/aihub-ai-service/src/test/java/com/aihub/ai/application/KnowledgeAppServiceTest.java` 等）可以 mock SPI 接口而无需真库。

**架构守护**：`aihub/aihub-ai-service/pom.xml` 第 119~124 行引入 `archunit-junit5`，把"编排层不得依赖 infra、domain 不得依赖框架"变成会失败的测试，防止分层随时间腐化（设计规则详见 `docs/03-架构设计说明书.md` 第 4 节）。

### 5.5 横切面：统一响应、统一异常、统一追踪

三个小而关键的全局约定（放 common，全服务复用）：

- **统一响应体** `aihub/aihub-common/src/main/java/com/aihub/common/result/R.java` + 错误码枚举 `ResultCode.java`：所有接口返回同构 JSON（code/message/data），前端拦截器只认 code。
- **统一异常** `BizException.java`（业务异常，带错误码）+ `GlobalExceptionHandler.java`（`@RestControllerAdvice` 兜底，防栈信息外泄）。
- **统一追踪** `TraceContext.java` / `TraceIdInterceptor.java` + 网关 `aihub/aihub-gateway/src/main/java/com/aihub/gateway/filter/TraceIdGlobalFilter.java`：入口生成/透传 traceId，写进 MDC 后日志自动携带（网关 yml 第 105~110 行日志 pattern 里的 `%X{traceId:--}`）——跨服务排错时一个 traceId 串起全链路日志。

### 6.3 演进顺序背后的三个"为什么"

1. **为什么 M1 先做模型网关**：一切 AI 功能的原子操作是"调模型"。把供应商差异（OpenAI 兼容/火山/通义）收进 `ModelGateway` + `OpenAiCompatibleChatModelResolver`（`aihub/aihub-ai-service/src/main/java/com/aihub/ai/infra/ai/OpenAiCompatibleChatModelResolver.java`）后，后面所有功能都只面向统一句柄。
2. **为什么 M2 是 RAG 而不是 Agent**：RAG 依赖链短（文件→切片→Embedding→检索→拼 Prompt），见效快且是 Agent 的前置能力（M3 的 `KnowledgeTools` 让 Agent 能调用 M2 的检索）。先易后难，同时每一步都为下一步供弹药。
3. **为什么 M5 把配额/用量/可观测放最后**：计量计费的对象（request/token/doc/task 四个维度）是前面四个里程碑创造出来的行为；没有行为就无从计量。同时 M5 的 `TraceId`、Prometheus 指标、springdoc 文档是"从能用到能用生产"的跨越。

### 6.4 把里程碑变成面试叙事

里程碑顺序本身就是一条"项目叙事线"，面试自我介绍可以按它组织：

> "项目分五个里程碑迭代：M1 我先用 Spring AI 把多供应商模型调用收敛成统一网关，解决'换模型不改代码'；M2 做 RAG，从文档上传、切片、Embedding 到 Redis 向量检索全链路打通；M3 引入工具调用，让模型能自主查知识库并接入 MCP 工具生态，所有工具调用过审计包装器落日志；M4 做 Agent，规划 Agent 拆解任务、浏览器 Agent 执行操作，WebSocket 推送步骤并支持用户中断；M5 做商业化闭环——四维配额扣减、用量看板、开放 API Key、TraceId 全链路追踪与 Prometheus 监控。"

对应到代码，每个里程碑都留有"可指认的类"（见 6.2 表格右列），面试官要证据时直接报文件路径——比空谈"我做了微服务"可信一个量级。

## 7. 本章面试三问与参考回答

### Q1：你这个项目的微服务是怎么拆分的？为什么这么拆？

**参考回答**：我们按**业务能力**拆，而不是按技术层拆。后端 8 个 Maven 模块：common（统一响应/异常/租户上下文等纵向复用件）、api（跨服务 Feign 契约与 DTO，契约独立成模块来控制"改接口的爆炸半径"）、gateway（统一入口，JWT 本地校验 + Sentinel 限流 + 路由）、platform-service（认证、RBAC、租户、配额——治理面，变更少但安全等级高）、ai-service（模型、应用、知识库 RAG、Agent——能力面，迭代快流量大）、MCP 三件套（工具业务实现与 SSE/stdio 两种传输分离，同一套 @Tool 复用两个协议）。两个业务服务各配一个独立 MySQL 库，服务无状态可水平扩展。特别说明：AI 能力**刻意内聚**在一个服务里，因为一次 RAG 对话要同时用到模型、向量检索和会话记忆，拆散会引入跨服务流式转发，得不偿失——先在服务内部用 web/application/domain.spi/infra 分层防腐化，将来有独立伸缩需求再外拆。

**可能的追问**：为什么不把 ai-service 再拆？（见上）；网关为什么用 WebFlux？（SSE 流式转发与高并发下非阻塞优势）；两个服务怎么互调？（OpenFeign 声明式调用，契约放 api 模块，租户头由 FeignTenantConfig 统一透传）。

### Q2：多租户的数据隔离是怎么保证的？A 租户能看到 B 租户的知识库内容吗？

**参考回答**：我们选共享行级隔离（对比独立库/独立 schema，成本与运维最优），并用**四道防线**防越权：第一道，租户 ID 只允许从 JWT 或 API Key 解析，绝不接受前端传参——TenantContext 类注释里写明了这是最高危约束；第二道，网关 AuthGlobalFilter 校验令牌后把 tenantId/userId 写入 `X-Tenant-Id`/`X-User-Id` 请求头，跨服务时 FeignTenantConfig 自动透传，业务服务入口由 TenantResolveInterceptor 写入 ThreadLocal 上下文；第三道，所有数据查询强制带租户条件，向量检索在 RedisKnowledgeRetriever 里对元数据做 tenant_id + kb_id 强制过滤；第四道，配置了 MyBatis 拦截器 TenantSqlGuardConfig 做条件兜底（当前默认关闭，待真实库回归后开启，这是一个诚实的演进项）。所以 A 租户检索时即使构造恶意 kbId，向量过滤层也会因为租户标签不匹配而拿不到 B 租户的 chunk。

**可能的追问**：ThreadLocal 有什么坑？（线程池复用串台，必须 afterCompletion 里 clear）；JWT 里的 tenantId 被改了怎么办？（签名校验会失败，payload 不可伪造）；为什么不用 MyBatis-Plus 官方 TenantLineInnerInterceptor 一劳永逸？（它是方案候选，项目当前用手写条件+兜底拦截器，并把它作为可开启的增强项）。

### Q3：版本矩阵是怎么管理的？如果 Spring Cloud Alibaba 版本和 Boot 版本不匹配会怎样？

**参考回答**：父 POM 用 dependencyManagement 引入三个 BOM（Spring Cloud 2025.0.0、Spring Cloud Alibaba 2025.0.0.0、Spring AI 1.1.5），子模块一律不写版本号，由 BOM 统一仲裁；父 POM 注释里明确"严禁混用"并写了对齐关系——Boot 3.5.x ↔ Cloud 2025.0.x ↔ SCA 2025.0.0.0，SCA 2025.1.x 是给 Boot 4.0 的。错配的典型症状是启动期 `NoSuchMethodError`/`ClassNotFoundException`、Nacos 注册失败、配置项不生效，而且往往在运行期才炸。另外我们把教训也沉淀进了配置：Nacos 升到 3.0.3 后默认开鉴权，客户端必须显式配 username/password，并且要先初始化管理员账号，否则服务注册直接 403——这个坑我们在 compose 和 yml 注释里都留了修复命令。

**可能的追问**：Spring AI 为什么用 1.1.5？（BOM 管理 + Milestones 仓库兜底，见父 POM repositories 配置）；为什么向量库选 Redis Stack 不选 Milvus？（百万级以内 HNSW 够用、组件三用、Spring AI 官方 starter 一接即用，vectorDim 必须与 Embedding 模型维度一致且建索引后不可改）。
