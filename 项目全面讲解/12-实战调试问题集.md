## Q1 Nacos 3.0.3 开鉴权后客户端注册 403

### 现象

中间件用 docker-compose 一键拉起后（Nacos 版本 3.0.3，`NACOS_AUTH_ENABLE: "true"` 显式开启鉴权），三个后端服务启动时疯狂刷注册失败日志，核心现象是：**服务实例始终注册不上 Nacos，客户端与 Nacos 的 HTTP 交互返回 403 Forbidden**；网关路由 `lb://aihub-platform-service` 时也因为注册表里没有实例而找不到目标。

用 curl 直接探 Nacos 控制台登录接口，同样被 403 拒绝——这说明问题不在 Java 客户端，而在 Nacos 服务端的鉴权层面。

### 排查过程

1. **确认网络可达**：`docker compose ps` 看到 `aihub-nacos` 容器 healthy（compose 里的健康检查 `curl -sf http://127.0.0.1:8848/index.html` 能通过），8848/9848 端口映射正常——排除"服务没起来/端口没通"这类低层问题。
2. **区分 401 与 403**：Nacos 客户端日志里的状态码是 403。401 是"没登录"，403 是"登录了但被拒绝"或"身份体系根本不存在"。结合 Nacos 3.x 的行为（鉴权开启后必须存在可登录的用户），怀疑是**鉴权开了但没有任何可用账号**。
3. **直接对 Nacos OpenAPI 求证**：绕开 Java 客户端，用 curl 打 Nacos 的用户管理接口验证假设。项目最终把这条初始化命令固化进了 compose 配置注释（来源：`aihub/docker-compose.yml` 第 66-68 行真实注释）：

```yaml
# 注意：开启鉴权后必须先初始化管理员用户，否则客户端登录 403：
#   docker exec aihub-nacos curl -s -X POST 'http://127.0.0.1:8848/nacos/v3/auth/user/admin' -d 'password=Nacos@aihub123'
# （仅管理员不存在时可调用一次；凭据需与 aihub-common.yml 的 spring.cloud.nacos 账号一致）
```

4. **查客户端配置**：翻各服务 `application.yml`，发现最初只配了 `server-addr`，没配 `username/password`——就算 Nacos 侧账号建好了，客户端也是"匿名"去注册的。

### 根因

两个根因叠加：

1. **Nacos 3.x 与 2.x 相比，鉴权体系是 breaking change 级别的差异**：3.x 显式开启 `NACOS_AUTH_ENABLE=true` 后，必须先初始化管理员用户（`/nacos/v3/auth/user/admin` 接口，仅允许在管理员不存在时调用一次），否则任何登录/注册请求都会被拒绝。这是**中间件大版本升级必须读 breaking changes 的典型教训**——compose 里 Nacos 相关变量也注明了"Nacos 3.x 必须显式配置鉴权相关变量"（`NACOS_AUTH_TOKEN`、`NACOS_AUTH_IDENTITY_KEY/VALUE`）。
2. **客户端侧没有配置账密**：Spring Cloud Alibaba 客户端在 Nacos 开鉴权后，需要显式提供 `spring.cloud.nacos.username/password`，否则以匿名身份访问被鉴权拦截。

### 修复

两步，两处代码现场都已在仓库中固化：

**第一步：初始化 Nacos 管理员**（命令已写入 `aihub/docker-compose.yml` 注释，随环境一键留痕）：

```bash
docker exec aihub-nacos curl -s -X POST \
  'http://127.0.0.1:8848/nacos/v3/auth/user/admin' \
  -d 'password=Nacos@aihub123'
```

**第二步：客户端配置账号密码**（来源：`aihub/aihub-gateway/src/main/resources/application.yml` 第 10-17 行，其余两个服务同款）：

```yaml
spring:
  cloud:
    nacos:
      # 本地开发默认账号（Nacos 3.x 开启了鉴权）。生产环境用环境变量覆盖，不要提交真实密码
      username: ${NACOS_USERNAME:nacos}
      password: ${NACOS_PASSWORD:Nacos@aihub123}
      discovery:
        server-addr: ${NACOS_ADDR:127.0.0.1:8848}
        namespace: ${NACOS_NAMESPACE:public}
        group: ${NACOS_GROUP:DEFAULT_GROUP}
```

细节讲究：Sentinel 规则持久化的 Nacos 数据源也要各自带账密（来源：`aihub/aihub-gateway/src/main/resources/application.yml` 第 55-59 行的 `spring.cloud.sentinel.datasource.gw-flow.nacos` 下同样配了 `username/password`）——因为 Sentinel 的 `NacosDataSourceProperties` 是独立拉配置的连接，不会自动复用 discovery 的凭据。

修复后重启三个服务，注册成功，`http://127.0.0.1:8848` 控制台"服务列表"里出现 `aihub-gateway` / `aihub-platform-service` / `aihub-ai-service` 三个健康实例。

### 预防

1. **升级中间件大版本前，把 Migration/Breaking Changes 文档过一遍**，把"新增必配项"直接写进 docker-compose 注释或 README 启动手册（本项目就是这么做的），让下一个人不用重新踩。
2. **鉴权类凭据统一走环境变量占位**：`${NACOS_USERNAME:nacos}` 的写法保证本地有默认值、生产可覆盖，且密码不进版本库历史。
3. **健康检查覆盖"功能级"而不是"进程级"**：compose 里 Nacos 的健康检查只探测了页面可达，探不出鉴权配置错误；更稳的做法是加一个用账密登录一次的探活脚本。
4. **面试表达**：这个案例的加分点在于能说清 401 与 403 的语义差异、以及"先 curl 直连排除客户端嫌疑，再回头改客户端配置"的隔离思路。

## Q2 种子管理员密码哈希与注释不符（BCrypt 无法反解 → 对拍验证法）

### 现象

按文档说明使用 `租户码 demo / 用户 admin / 密码 admin123` 登录管理端，**必然失败**。接口返回的文案就是登录接口设计的统一提示（来源：`aihub/aihub-platform-service/src/main/java/com/aihub/platform/auth/service/AuthService.java` 第 104 行）：

```
用户名或密码错误
```

诡异之处在于：换 `123456` 试试，居然登录成功了——但代码库里根本搜不到任何写 123456 的地方。

### 排查过程

1. **先排除低层问题**：验证码能通过、租户 `demo` 能查到、`sys_user` 表里确实有 `id=1, username=admin` 的记录——用户存在、账号状态启用，问题聚焦在密码校验这一步。
2. **意识到 BCrypt 不能反解**：`password_hash` 是 BCrypt 哈希（单向慢哈希，带随机盐），**没有任何工具能从哈希反推出明文**。所以"看看哈希里存的是什么密码"这条路是死路。
3. **改用对拍验证（当时写的临时验证代码）**：既然哈希无法反解，那就反过来——**用明文去撞哈希**。写一段一次性的对拍代码，把两个候选明文分别和库里那条哈希做 `matches` 验证：

```java
// 临时对拍代码（验证完即弃，不入库）：验证 V1 种子哈希到底对应哪个明文
// 依赖：spring-security-crypto 的 BCryptPasswordEncoder（与 AuthService 校验逻辑同一实现）
import org.springframework.security.crypto.bcrypt.BCryptPasswordEncoder;

public class HashProbe {
    public static void main(String[] args) {
        String seedHash = "$2a$10$N.zmdr9k7uOCQb376NoUnuTJ8iAt6Z5EHsM8lE9lBOsl7iKTVKIUi";
        BCryptPasswordEncoder encoder = new BCryptPasswordEncoder();
        System.out.println("admin123 -> " + encoder.matches("admin123", seedHash)); // false
        System.out.println("123456  -> " + encoder.matches("123456",  seedHash)); // true
    }
}
```

对拍结果：`admin123` 不匹配、`123456` 匹配——铁证：**V1 种子脚本里硬编码的那条哈希，实际对应 123456**。

4. **溯源找到事故点**：检查建库脚本（来源：`aihub/aihub-platform-service/src/main/resources/db/migration/V1__init_platform.sql` 第 118-124 行）：

```sql
-- 初始化演示租户与用户（密码： admin123）
INSERT INTO sys_tenant (id, name, code, status) VALUES (1001, '演示租户', 'demo', 1)
    ON DUPLICATE KEY UPDATE name = VALUES(name);

INSERT INTO sys_user (id, tenant_id, username, password_hash, nickname, status)
VALUES (1, 1001, 'admin', '$2a$10$N.zmdr9k7uOCQb376NoUnuTJ8iAt6Z5EHsM8lE9lBOsl7iKTVKIUi', '管理员', 1)
    ON DUPLICATE KEY UPDATE nickname = VALUES(nickname);
```

真相：注释写的是 admin123，但当时生成哈希的脚本**贴错了哈希串**（贴成了 123456 对应的哈希），于是"注释与哈希"从此南辕北辙。

### 根因

1. **直接根因**：生成种子数据的脚本把"注释里的目标密码"和"贴进 SQL 的哈希"错配了——哈希生成和 SQL 编写是两步人工操作，没有程序化闭环。
2. **放大根因**：BCrypt 单向不可逆，导致问题不能靠"看一眼数据"发现，而密码错误在登录页的表现（统一文案防用户名枚举）与"用户真输错密码"完全一样，极强的迷惑性。

### 修复

**不能改 V1**：Flyway 会校验已应用脚本的 checksum，改动历史迁移文件会让下次启动校验失败（详见 Q3 的预防小节对 Flyway 机制的展开）。正确做法是**新增一份增量迁移把哈希更新为 admin123 的正确值**（来源：`aihub/aihub-platform-service/src/main/resources/db/migration/V10__fix_admin_seed_password.sql` 全文）：

```sql
-- 修复种子管理员密码哈希与注释不一致的问题。
-- 背景：V1__init_platform.sql 注释声称密码为 admin123，但其中硬编码的 BCrypt 哈希
--       实际对应的是 123456（生成脚本贴错哈希），导致按文档登录必然报
--       "用户名或密码错误"。
-- 处理：不动 V1（Flyway 校验已应用脚本的 checksum，改历史脚本会导致启动失败），
--       用本增量迁移把 admin 的哈希更新为 admin123 的正确 BCrypt 值。
-- 安全提示：演示环境的默认口令仅限本地开发，部署前务必修改。
UPDATE sys_user
SET password_hash = '$2a$10$4a6Yl4qwbtuOs8vD5j0yZ.lgnSSeh1jKyROA116dG366EUc7Bf5gG'
WHERE id = 1 AND username = 'admin';
```

注意 UPDATE 语句带了 `id = 1 AND username = 'admin'` 双条件——种子数据的修复也要遵循幂等与精确匹配原则，避免误伤其他租户下的同名用户（该表唯一键是 `uk_tenant_username`，同名用户在别的租户完全合法）。

修复后，`demo/admin/admin123` 一次登录成功。

### 预防

1. **种子密码必须"程序生成、程序注入"**：让脚本先生成哈希、再把哈希和明文注释一起写入 SQL，禁止手工复制粘贴哈希串。生成与写入必须是同一个原子动作。
2. **种子数据要幂等**：`ON DUPLICATE KEY UPDATE` / `WHERE id=1 AND username='admin'` 这类写法保证迁移可重复执行不炸、不产生脏数据——这也是所有 `INSERT/UPDATE` 型种子迁移的通用写法。
3. **对拍验证法的推广**：凡是"不可逆哈希、加密数据、序列化产物"这类无法直接读出内容的存储，验证手段一律是**用已知输入去撞**（matches / 解密 / 反序列化后比对），而不是试图反解。
4. **登录失败统一文案是对的，但要配可观测性**：防枚举值得保留，代价是排障变难；补一个"最近登录失败原因（密码错/用户不存在/停用）"的管理端审计视图，既不暴露给普通用户，又给运维留排查入口。
5. **面试表达**：先主动说清 BCrypt 不可逆这个前提，再讲"对拍验证"这个解法，能同时展示密码学常识与实验思维——比背"BCrypt 有盐慢哈希"高一个层次。

## Q3 ai_knowledge_base 表缺 create_time 列 → 知识库接口 500

### 现象

管理端/用户端访问知识库相关接口全部 500：

- `GET /api/ai/kb`（知识库列表）500；
- `POST` 新建知识库也 500。

服务端日志的数据库异常核心报错原文（该原文已被固化进修复迁移的注释中，来源：`aihub/aihub-ai-service/src/main/resources/db/migration/V10__kb_add_create_time.sql` 头注释，git HEAD 可见）：

```
Unknown column 'create_time' in 'field list'
```

### 排查过程

1. **读异常栈，先看 SQL 再看代码**：日志栈里能看到 MyBatis 抛出的 SQL 异常，往上翻到由哪条 SQL 触发——是 MyBatis-Plus 为 `ai_knowledge_base` 生成的 `SELECT id,tenant_id,...,create_time FROM ai_knowledge_base ...`。`Unknown column 'create_time' in 'field list'` 是 MySQL 在说：**SQL 里引用了表里不存在的列**。
2. **比对 DO 与 DDL**：
   - 查代码侧 DO（来源：`aihub/aihub-ai-service/src/main/java/com/aihub/ai/infra/persistence/dataobject/AiKnowledgeBaseDO.java` 第 29-32 行）：

   ```java
   @TableLogic
   private Integer deleted;

   private LocalDateTime createTime;
   ```

   - 再查建表迁移（来源：`aihub/aihub-ai-service/src/main/resources/db/migration/V1__init_ai.sql` 第 58-69 行）：

   ```sql
   CREATE TABLE IF NOT EXISTS ai_knowledge_base (
       id                 BIGINT       NOT NULL,
       tenant_id          BIGINT       NOT NULL,
       name               VARCHAR(128) NOT NULL,
       embedding_model_id BIGINT       NOT NULL,
       vector_dim         INT          NOT NULL,
       index_name         VARCHAR(128) NOT NULL COMMENT 'Redis 索引名(带 v{n} 版本)',
       status             TINYINT      NOT NULL DEFAULT 1,
       deleted            TINYINT      NOT NULL DEFAULT 0,
       PRIMARY KEY (id),
       KEY idx_tenant (tenant_id)
   ) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='知识库';
   ```

   **DO 有 `createTime`，DDL 没有 `create_time`——两边不一致，根因实锤。**

3. **确认写入路径为何必炸**：新建知识库的仓储实现还会显式写入创建时间（来源：`aihub/aihub-ai-service/src/main/java/com/aihub/ai/infra/persistence/DbKnowledgeBaseRepository.java` 第 32-33 行）：

   ```java
   ddo.setCreateTime(LocalDateTime.now());
   kbMapper.insert(ddo);
   ```

   `INSERT` 的字段列表里带 `create_time`，列不存在 → 同样报 `Unknown column`。这解释了"新建也 500"。

### 根因

**V1 建表时遗漏了 `create_time` 列，而 Java 侧 DO 模型含有该字段**——典型的"代码模型与 DDL 漂移"。任何一张 MyBatis-Plus 全字段映射的表，DO 多一个字段而表少一列，查询（`SELECT *` 展开后的字段列表）与写入（`INSERT` 字段清单）两侧都会命中同一类错误。

### 修复

用**增量迁移补列**，而不是去改 V1（原因见预防小节）。修复迁移内容如下（git HEAD 提交 `43a7333 fix: 修复数据库字段缺失和管理员密码哈希不一致问题` 中通过 `git show HEAD:aihub/aihub-ai-service/src/main/resources/db/migration/V10__kb_add_create_time.sql` 可读得全文）：

```sql
-- 修复 ai_knowledge_base 表缺失 create_time 列的问题。
-- 背景：V1 建表时遗漏 create_time，而 AiKnowledgeBaseDO 含 createTime 字段
--       （DbKnowledgeBaseRepository.create() 还会显式写入），导致知识库列表
--       （GET /api/ai/kb）与新建知识库接口全部因
--       "Unknown column 'create_time' in 'field list'" 报 500。
ALTER TABLE ai_knowledge_base
    ADD COLUMN create_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP AFTER deleted;
```

三个设计细节：

1. `NOT NULL DEFAULT CURRENT_TIMESTAMP`：存量行自动回填当前时间，不会因 NOT NULL 约束失败；
2. `AFTER deleted`：列顺序与 DO 字段声明顺序对齐，方便人肉比对；
3. 放进新的 `V10` 迁移而不是改 V1：已建库的环境执行 `ALTER` 补列，全新环境 V1→V10 顺序执行，两条路都通。

**关于当前工作区状态的如实说明**：编写本文档时，`ai-service` 的这份 `V10__kb_add_create_time.sql` 已从工作区删除（`git status` 显示为已暂存的删除 `D`），但其内容仍完整保留在 git HEAD 历史中（提交 `43a7333`），用 `git show HEAD:aihub/aihub-ai-service/src/main/resources/db/migration/V10__kb_add_create_time.sql` 即可读得。需要特别提醒：**当前工作区里的 `V1__init_ai.sql` 建表语句仍未包含 `create_time` 列**——如果用全新数据库环境从头执行迁移，缺少这份 V10 迁移该 500 问题仍会复现；已应用过 V10 的存量库不受影响（Flyway 历史表 `flyway_schema_history` 已有该版本记录）。

### 预防

1. **理解 Flyway 机制，永远不改历史迁移**：
   - Flyway 把每个已执行脚本的 checksum 记录在 `flyway_schema_history` 表里；
   - 启动时逐脚本校验 checksum，**改动已应用的 V1 文件 → checksum 不匹配 → 启动直接失败**；
   - 所以任何"补列/改数据/修约束"都走新的 `V(n+1)` 增量迁移。历史迁移文件应当被当作"已发布的不可变账本"。
2. **DO 与 DDL 联动检查**：新增/修改 DO 字段时必须同步编写迁移；团队协作中可以把"DO 字段清单 vs 迁移后表结构"的比对做成单测或 CI 脚本（例如启动期用 `INFORMATION_SCHEMA.COLUMNS` 断言关键字段存在）。
3. **本地环境常用 `CREATE TABLE IF NOT EXISTS` / 幂等迁移**：重复执行不报错，但也**静默跳过**——这既是优点（可重跑）也是陷阱（表已存在但缺列时，V1 不会帮你补）。这正是本案例里 `IF NOT EXISTS` 掩盖遗漏的原因。
4. **面试表达**：先讲清报错→栈→SQL→DO/DDL 比对这条定位链，再主动引申 Flyway 的 checksum 机制说明"为什么不改历史迁移"，一处案例同时覆盖数据库与工程规范两个考察面。

**修复 1+2：`api/routes.ts` 按平铺结构解析 + 刷新后重新拉取**（来源：`aihub-admin-ui/src/api/routes.ts`）：

```ts
/**
 * 后端 MenuNode → pure-admin 路由对象（递归）。
 * 后端节点为平铺结构：{ id, name, path, component, icon, menuType, sort, visible, children }，
 * 其中 menuType："M" 目录 / "C" 菜单 / "F" 按钮。
 */
const toPureRoute = (node: any): any => {
  const menu = node ?? {};
  const route: any = {
    path: menu.path ?? `/${menu.id}`,
    // component 为字符串，addAsyncRoutes 会映射到 src/views/<component>.vue；
    // 目录节点（M 型）无组件，交给 addAsyncRoutes 置空（仅作菜单层级）
    component: menu.component ?? undefined,
    meta: {
      title: menu.name,
      icon: toIconify(menu.icon),
      rank: menu.sort ?? 99,
      showLink: menu.visible !== 0
    }
  };
  const children = (menu.children ?? [])
    .filter((c: any) => c?.menuType !== "F") // 按钮不进路由
    .map(toPureRoute);
  if (children.length > 0) {
    route.children = children;
  }
  return route;
};
```

```ts
/**
 * 获取动态路由。
 * 优先用登录流程（api/user.ts）缓存的菜单树；页面刷新后内存缓存清空，
 * 此时用当前 token 重新拉取权限树（与登录时同一个接口），保证刷新后菜单不丢。
 */
export const getAsyncRoutes = async (): Promise<Result> => {
  if (!cachedMenuTree.length) {
    const { getToken } = await import("@/utils/auth");
    const token = getToken()?.accessToken;
    if (token) {
      // 走原始 axios（不经 http 拦截器解包），手动取 R.data.routes

        headers: { Authorization: `Bearer ${token}` },
        timeout: 10000
      });
      cacheRoutes(res.data?.data?.routes ?? []);
    }
  }
  // 过滤 /welcome：静态路由里已有首页，避免重复注册
  const routes = cachedMenuTree
    .filter(node => node?.path !== "/welcome")
    .map(toPureRoute);
  return { success: true, data: routes };
};
```

## Q5 Vite 7 + Node 16 启动报 crypto.getRandomValues（engines 语义、nvm）

### 现象

管理端 `aihub-admin-ui` 在本机执行 `pnpm dev`，**启动即崩**：报错信息的关键片段指向 `crypto.getRandomValues`——这是 Node 16.20.2（本机当时默认 Node 版本）没有的全局 Web Crypto API，而 Vite 7 的依赖链在启动早期就要用它。项目声明要求的 Node 版本远高于此（来源：`aihub-admin-ui/package.json`）：

```json
"engines": {
  "node": "^20.19.0 || >=22.13.0",
  "pnpm": ">=9"
},
```

依赖里 Vite 版本为 `"vite": "^7.1.12"`。也就是说：Node 16.20.2 距离最低要求 20.19 差了整整一个大版本区间。

### 排查过程

1. **看报错关键词**：`crypto.getRandomValues` 是浏览器/新版 Node 的全局 Web Crypto API；Node 17 之前没有全局 `crypto` 对象。报它"不存在/不是函数"，第一反应就是 **Node 版本过低**，而不是代码 bug——业务代码一行没改就突然崩，且崩在启动最早期，符合"运行时环境不满足"的特征。
2. **核对版本矩阵**：查 `package.json` 的 `engines` 字段（`^20.19.0 || >=22.13.0`）和 Vite 7 的官方要求（Node 20.19+ / 22.12+），与本机版本对表。
3. **确认本机实际版本**：

```powershell
node -v    # v16.20.2 —— 低于要求
```

4. **反思为什么之前没被拦住**：`engines` 字段在 npm 下默认只是**警告**，pnpm 也需要配合 `engine-strict` 才会硬失败——所以装依赖、起服务都能一路走到崩，直到撞上缺失的 API 才爆。`engines` 表达的是"意图约束"，不等于运行时强制。

### 根因

**Vite 7 要求 Node 20.19+（或 22.12+），本机默认 Node 是 16.20.2**。Node 16 没有全局 `crypto.getRandomValues`（Web Crypto 成为全局对象是很新的 Node 才有的能力），Vite 7 的启动链路一调用就崩。`engines` 字段只是声明约束、多数包管理器默认不强校验，导致问题直到运行期才暴露。

### 修复

用 **nvm（Node Version Manager for Windows）切换 Node 版本**。本机执行 `nvm list` 的真实输出（也是这个案例的现场证据）：

```
  * 24.14.0 (Currently using 64-bit executable)
    16.20.2
```

即：本机通过 nvm 同时装有 16.20.2 与 24.14.0，当前生效 24.14.0。当时的修复操作就是：

```powershell
nvm install 24.14.0   # 安装满足要求的 LTS 新版本
nvm use 24.14.0       # 切换全局默认
node -v               # v24.14.0
pnpm install          # 切大版本后重装依赖（native 模块按 Node ABI 重编）
pnpm dev              # 正常启动
```

注意最后一步的配套动作：**切 Node 大版本后必须重装依赖**——`esbuild`、`@parcel/watcher` 这类带 native 二进制/平台包的依赖是按 Node ABI 解析的，旧 `node_modules` 可能不可用。

### 预防

1. **把 `engines` 从"声明"升级为"强制"**：pnpm 下在 `.npmrc`/`pnpm-workspace.yaml` 配 `engine-strict=true`（本项目管理端还配了 `preinstall: npx only-allow pnpm` 强制包管理器），让版本不符在**安装期**就失败，而不是运行期才崩。
2. **Node 版本交给 nvm 管理，并在仓库里声明版本**：README 写清"需要 Node ≥ 20.19（用 nvm 安装 24.x 即可）"，新人按文档 `nvm install` + `nvm use`，避免"我这里好好的"式环境漂移。多前端项目并存时（本项目 `aihub-app` 用 Vite 5、`aihub-admin-ui` 用 Vite 7），nvm 允许不同项目锁定不同 Node 大版本，这正是它的价值。
3. **认识 `engines` 的语义**：它是包作者向使用者声明的兼容范围，npm 默认仅警告、pnpm 默认警告（strict 才硬失败）——**不要把声明当成护栏**。
4. **面试表达**：能说清"报错 API 在哪个 Node 版本引入 → 对照 engines/官方矩阵 → nvm 切换 → 重装依赖"的完整链条，并主动指出 engines 默认不强制这个多数人忽略的细节，是这题的加分点。

## Q6 uni-app CLI 启动报 ENOENT src/manifest.json（读 node_modules 源码定位加载时机）

### 现象

用户端 `aihub-app` 是 uni-app + Vue3 项目，沿用 **HBuilderX 目录结构**：`manifest.json`、`pages.json` 等都在**项目根目录**（不是官方 CLI 约定的 `src/` 目录）。执行 `npm run dev:h5` 启动 H5 开发服务时，CLI 直接崩掉，报错原文：

```
Error: ENOENT: no such file or directory, open 'e:\微服务\javaAI\javaai\aihub-app\src\manifest.json'
```

（ENOENT = 文件不存在；它去找的是 `src\manifest.json`，而这个文件实际在 `aihub-app\manifest.json`。）

### 排查过程

1. **第一反应改 vite.config.js 兜底**：在 `vite.config.js` 顶部加 `process.env.UNI_INPUT_DIR = process.cwd()`，指望 vite 配置加载阶段把输入目录指回项目根。结果**不生效，照样报 ENOENT**。这个"为什么兜底了还崩"就是本题的题眼。
2. **读 node_modules 源码，定位加载时机**（这是本案的关键动作）：顺着报错去找"谁在读 manifest.json"：

   - 读 `manifest.json` 的实现（来源：`aihub-app/node_modules/@dcloudio/uni-cli-shared/dist/json/manifest.js` 第 163-168 行）：

   ```js
   function getPlatformManifestJsonOnce() {
       const manifestJson = !process.env.UNI_INPUT_DIR
           ? {}
           : (0, exports.parseManifestJsonOnce)(process.env.UNI_INPUT_DIR);
       return getPlatformManifestJson(manifestJson);
   }
   ```

   ——它从环境变量 `UNI_INPUT_DIR` 指向的目录里解析 manifest.json。
   - `UNI_INPUT_DIR` 的默认值在哪里设置？搜依赖源码，找到 CLI 初始化函数 `initEnv`（来源：`aihub-app/node_modules/@dcloudio/vite-plugin-uni/dist/cli/utils.js` 第 126-127 行）：

   ```js
   process.env.UNI_INPUT_DIR =
       process.env.UNI_INPUT_DIR || path_1.default.resolve(process.cwd(), 'src');
   ```

   ——**CLI 启动阶段就把 `UNI_INPUT_DIR` 默认成了 `process.cwd()/src`**。
   - 再看调用链：`bin/uni.js`（来源：`aihub-app/node_modules/@dcloudio/vite-plugin-uni/bin/uni.js` 第 109 行）在文件末尾 `require('../dist/cli/index.js')` 进入 CLI，CLI 先执行 `initEnv`，**然后才加载 vite 配置文件**。也就是说：

   ```text
   node bin/uni.js → dist/cli/index.js → initEnv()（默认 UNI_INPUT_DIR=<cwd>/src，读 manifest.json）
                  → 之后才轮到 vite 加载 vite.config.js（此时 manifest 早已按 <cwd>/src 读过了）
   ```

   这就解释了"vite.config.js 里兜底不生效"——**CLI 初始化（读 manifest）发生在 vite 配置加载之前**，兜底代码执行时已经晚了。
3. **顺带确认官方约定的两条出路**：源码里能看到 HBuilderX 环境（`isInHBuilderX()`）会走 `UNI_HBUILDERX_PLUGINS` 下的独立上下文——CLI 版本没有这个豁免，所以只能自己把 `UNI_INPUT_DIR` 提前喂对。

### 根因

**项目目录结构（根目录）与 uni CLI 的默认约定（`src/`）不匹配**。CLI 在初始化阶段用 `process.env.UNI_INPUT_DIR || <cwd>/src` 确定源码目录并立即解析 `manifest.json`；根目录结构下 `<cwd>/src/manifest.json` 不存在，于是 ENOENT。而 `vite.config.js` 的兜底执行得太晚（vite 配置加载晚于 CLI 初始化），救不了场。

### 修复

**新增启动器脚本，在 require uni CLI 之前就把环境变量设好**（来源：`aihub-app/scripts/uni.js` 全文，18 行）：

```js

 * uni CLI 启动器（scripts/uni.js）。
 *
 * 背景：本项目沿用 HBuilderX 目录结构（manifest.json / pages.json 在项目根目录），
 * 而 uni CLI 默认从 src/ 读取源码。官方约定是在进程启动前设置环境变量
 * UNI_INPUT_DIR 指向源码目录 —— 写在 vite.config.js 里来不及生效，
 * 因为 CLI 初始化（读取 manifest.json）发生在加载 vite 配置之前。
 *
 * 本脚本必须在启动 uni CLI 前用绝对路径设置好该变量，所有 npm 命令
 * （dev:h5 / dev:mp-weixin / build:h5 / build:mp-weixin）统一经由这里转发，
 * 命令行参数原样透传（CAC 解析 process.argv.slice(2)）。
 */
const path = require("path");

// 项目根目录（scripts/ 的上一级）；HBuilderX 运行时也使用根目录结构，保持一致
process.env.UNI_INPUT_DIR = path.resolve(__dirname, "..");

require("@dcloudio/vite-plugin-uni/bin/uni.js");
```

npm scripts 全部改为经由启动器（来源：`aihub-app/package.json` 第 6-11 行）：

```json
"scripts": {
  "dev:h5": "node scripts/uni.js",
  "dev:mp-weixin": "node scripts/uni.js build -p mp-weixin -w",
  "build:h5": "node scripts/uni.js build",
  "build:mp-weixin": "node scripts/uni.js build -p mp-weixin"
},
```

同时 `vite.config.js` 里保留一层兜底（防绕过启动器直接调 vite 的场景），并注释说明主次关系（来源：`aihub-app/vite.config.js` 全文）：

```js
import { defineConfig } from 'vite'
import uni from '@dcloudio/vite-plugin-uni'

// 本项目沿用 HBuilderX 目录结构（pages.json 在项目根目录），而 uni CLI 默认从 src/ 读源码。
// npm 命令由 scripts/uni.js 启动器在 CLI 初始化前设置 UNI_INPUT_DIR 指向项目根；
// 这里再兜底设置一次（Vite 配置阶段，保证 vite 自身阶段变量已生效）。
process.env.UNI_INPUT_DIR = process.env.UNI_INPUT_DIR || process.cwd()

export default defineConfig({
  plugins: [uni()]
})
```

启动器设计的两个要点：`path.resolve(__dirname, "..")` 用**绝对路径**，不依赖执行时的工作目录；`require(...)` 放在设置环境变量**之后**，利用 CommonJS 的顺序执行语义保证时机正确。修复后 `npm run dev:h5` 与小程序构建均正常。

### 预防

1. **把"读第三方库源码"当成本能**：本案的定位路径是"报错文件路径 → 在 node_modules 里 grep 读 manifest 的代码 → 找到默认值设置点 → 理清执行时序"。npm 生态里脚手架/CLI 类问题九成出在**时序与约定**上，源码是唯一权威答案。同类手段还有 `javap` 反编译 jar 验证框架契约（本项目 MCP 章节用过：验证 `NacosDataSourceProperties` 是否支持 username/password）。
2. **新项目尽量顺应脚手架默认目录约定**（`src/`），除非有强理由；若沿用 HBuilderX 结构，就把启动器这类"环境适配层"集中到一个文件并在 package.json scripts 全量收口，不让任何人绕过它。
3. **环境变量问题用"打印时序"验证**：怀疑时序类 bug 时，在两个可疑位置各打印一次变量值（如 CLI 阶段 vs vite 配置阶段），一眼看清谁先谁后。
4. **面试表达**：这题的差异化价值极高——大多数人会卡在"改了 vite 配置怎么没用"，而你可以说"我读了 vite-plugin-uni 的 CLI 源码，确认 initEnv 在 vite 配置加载前就把 UNI_INPUT_DIR 默认成 src，所以把设置提前到 require CLI 之前"。一句话就证明你会读源码、懂执行时序。

## 7. 排障方法论总结

6 个案例做完，方法论可以收敛成四把"手术刀"。它们的共同哲学是：**先把问题空间砍小，再用便宜的实验去验证，最后才动手改代码**。

### 7.1 二分定位：把不确定空间砍半再砍半

- **是什么**：在链路的中间点做一次观测，判断问题在前半段还是后半段，循环此过程直到锁定单点。
- **本项目实例**：
  - Q1 里"curl 直连 Nacos OpenAPI"就是一次二分：403 出现即证明问题在 Nacos 服务端鉴权侧，Java 客户端配置是后半段的事，排除了一大半嫌疑；
  - Q3 里读异常栈定位到具体 SQL，等于把"整个知识库模块 500"砍成"一条 SQL 的一列不存在"；
  - Q6 里"改 vite.config.js 无效"本身也是一次二分——它证明崩点在 vite 配置加载**之前**的 CLI 阶段。
- **要点**：中间观测点要选**信息量最大的位置**（状态码、异常栈、环境变量打印），一次观测最好能排除一半假设。

### 7.2 最小复现：把"偶发的大系统故障"变成"必现的小实验"

- **是什么**：剥离与问题无关的一切（框架、配置、网络），造一个最小环境让问题必现。必现才可研究，可研究才可修复。
- **本项目实例**：
  - Q2 的对拍代码就是一个最小复现：不启动 Spring、不连数据库，用一个 main 方法对一条哈希跑 `matches`，30 秒出结论；
  - Q1 用 curl 复现 403，把"三个服务起不来"收敛成"一条 HTTP 请求被拒"；
  - Q5 的最小复现就是 `node -v`——一行命令证明运行时环境不满足。
- **要点**：复现成本越低，验证修复的回合越快；修完后最小用例顺手就能留下当回归测试。

### 7.3 读源码：依赖与脚手架问题的唯一权威答案

- **是什么**：当文档缺失、报错无指向性时，直接读依赖包源码（node_modules），或用 `javap` 反编译 jar 验证框架契约。npm 生态的 CLI/脚手架问题尤其如此——问题多出在**执行时序**和**隐式约定**上。
- **本项目实例**：
  - Q6 是教科书案例：grep `UNI_INPUT_DIR` 定位到 `vite-plugin-uni/dist/cli/utils.js` 的 `initEnv`，确认默认值 `<cwd>/src` 与执行时机早于 vite 配置加载；
  - 项目里同类实践还包括用 `javap` 确认 Sentinel 的 `NacosDataSourceProperties` 支持 username/password（Q1 修复时才敢在数据源配置里加账密）、确认 `@Tool` 注解在 `spring-ai-model` 包里。
- **要点**：读源码不是通读，是**带着假设去 grep**——先有关键词（报错里的 API 名、配置项名），再找赋值点/调用点，最后理清时序。

### 7.4 对拍验证：不可逆数据的唯一观测手段

- **是什么**：对哈希、加密、序列化等**不可逆**的存储内容，无法"读出来看"，只能"用已知输入去撞"——正向计算后与目标比对。
- **本项目实例**：
  - Q2 用 `BCryptPasswordEncoder.matches("admin123", seedHash)` / `matches("123456", seedHash)` 双向对拍，一次锁定"注释与哈希不符"；
  - 引申：验证加密配置的正确性（解密后与明文比对）、验证序列化兼容性（老数据反序列化后断言字段）都是同一思想。
- **要点**：对拍要**覆盖全部候选答案**（两个候选明文都测了才能下结论），且实验代码用完即弃，不进版本库。

### 7.5 方法论速查与面试表达模板

| 方法 | 适用信号 | 6 题中的对应 |
| --- | --- | --- |
| 二分定位 | 链路长、嫌疑面广 | Q1 curl 探服务端 / Q3 读栈定 SQL / Q6 兜底无效反推时序 |
| 最小复现 | 偶发、环境相关、链路长 | Q2 对拍脚本 / Q1 curl / Q5 `node -v` |
| 读源码 | 第三方库/脚手架报错无指向性 | Q6 grep UNI_INPUT_DIR / javap 验证框架契约 |
| 对拍验证 | 不可逆数据（哈希/加密/序列化） | Q2 matches 验证种子哈希 |

**面试表达模板（把任意一题讲成 90 秒故事）**：

1. **现象一句话 + 关键报错**（证明你真的遇过：报错原文、状态码脱口而出）；
2. **两步定位**（先二分排除了什么，再用什么实验锁定的根因）；
3. **根因一句话**（用"机制"而不是"表象"回答，例如"CLI 读 manifest 早于 vite 配置加载"，而不是"路径配错了"）;
4. **修复 + 一个设计细节**（例如 Flyway 为什么不改历史迁移、启动器为什么用 `require` 顺序语义）；
5. **预防一句**（契约测试 / 程序化种子 / engine-strict / 目录约定），展示你把个案变成了机制。

最后提醒一句：排障故事的含金量不在"修好了"，而在**每一步都有证据**——报错原文、命令输出、源码行号，本文档里所有引用都可在标注的路径下核对，这也是这份文档本身就是"证据链"的原因。
