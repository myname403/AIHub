## 1. 服务职责与端口

aihub-ai-service 监听 **8082** 端口（`src/main/resources/application.yml` 第 1-2 行 `server.port: 8082`），是整个平台里"AI 能力"的承载者。它对外提供四块能力：

| 能力 | 入口类 | 典型接口 | 一句话说明 |
|---|---|---|---|
| 知识库管理 | `web.KnowledgeController` | `POST/GET /api/ai/kb` | 建库、列库、绑应用 |
| 文档入库 | `web.KnowledgeController` | `POST /api/ai/kb/{kbId}/documents` | 上传 → 解析 → 切片 → 向量化（异步） |
| 对话 | `web.ChatController` | `POST /api/ai/chat`、`/chat/sse`、`/chat/ndjson` | 同步 / SSE / NDJSON 三通道 |
| 模型与应用管理 | `web.ModelController`、`web.AppController` | `/api/ai/model/**`、`/api/ai/app/**` | 供应商、路由、助手的增删改查 |

此外它还承担**用量上报**（通过 Feign 契约 `PlatformClient` 把每次对话的 token 消耗报给平台服务）与 **RAG 检索调试**（`POST /api/ai/kb/search`，直接返回命中分片与相似度分数）。

依赖的中间件有两个关键点（均在 `application.yml` 中）：

- **MySQL**（`aihub_ai` 库，第 13-17 行）：存知识库、文档、分片、会话记忆、模型路由等结构化数据；
- **Redis Stack**（第 19-22 行 + 第 77-81 行 `spring.ai.vectorstore.redis`）：必须是含 Redis Query Engine 的 redis-stack 镜像，普通 Redis 没有向量索引能力，这一点在 `config/VectorStoreConfig` 的类注释里被明确标注为第一个要点。

一个值得先记住的全局约束：**web 层只依赖 application 与 domain，禁止触碰 Spring AI 与 infra**。`ChatController` 类注释（第 46-48 行）写明这条规则由 ArchUnit 测试强制检查。这是理解本章所有分层的钥匙。

## 2. 仓储模式讲解：domain.spi 接口 + infra.persistence 实现

### 2.1 先讲"为什么"：如果不分层会怎样

最朴素的写法是 Controller 里直接 `kbMapper.selectList(...)`。这样写三个月内没问题，但它带来三个慢性病：

1. **业务代码与 MyBatis-Plus 的 Wrapper 语法焊死**——换 ORM、换存储（比如把知识库元数据迁到 MongoDB）要改遍所有 Service；
2. **测试必须连数据库**——Service 的单测跑不起来，只能靠手工点页面；
3. **租户隔离条件散落各处**——每个查询都要记得手写 `tenant_id = ?`，漏一处就是数据泄漏事故。

仓储模式（Repository Pattern）的解法：在**领域层定义接口**（domain.spi 包，SPI = Service Provider Interface），在**基础设施层提供实现**（infra.persistence 包）。业务编排层（application）只 import 接口，永远不知道背后是 MyBatis 还是 Redis。

### 2.2 domain.spi 接口清单（本项目真实存在）

| SPI 接口（domain/spi/ 下） | 实现（infra/ 下） | 职责 |
|---|---|---|
| `KnowledgeBaseRepository` | `persistence.DbKnowledgeBaseRepository` | ai_knowledge_base 表读写 |
| `DocumentRepository` | `persistence.DbDocumentRepository` | ai_document / ai_document_chunk 读写 |
| `IngestTaskRepository` | `persistence.DbIngestTaskRepository` | 入库任务进度 |
| `KnowledgeIndexer` | `ai.RedisKnowledgeIndexer` | 分片向量化写入向量库 |
| `KnowledgeRetriever` | `ai.RedisKnowledgeRetriever` | 向量检索（租户隔离唯一入口） |
| `ChatExecutor` | `ai.SpringAiChatExecutor` | 对话执行（Spring AI 封装） |
| `ModelGateway` | `ai.DbModelGateway` | 场景 → 模型路由解析 |
| `StreamSink` | `web.sink.SseStreamSink` 等 3 个 | 流式事件输出通道 |
| `ConversationMemoryStore` | `persistence.DbConversationMemoryStore` | 会话记忆存储 |

注意这张表的规律：**接口全在 domain，实现分居 infra.persistence（数据库类）与 infra.ai（AI 框架类）、web.sink（传输类）**。也就是说"抽象"只有一份，实现可以有 N 份——这就是仓储模式加上依赖倒置的完整形态。

### 2.3 以 DbKnowledgeBaseRepository 逐方法讲解

先看接口定义（`domain/spi/KnowledgeBaseRepository.java` 全文，第 10-17 行）：

```java
// 来源：aihub/aihub-ai-service/src/main/java/com/aihub/ai/domain/spi/KnowledgeBaseRepository.java#L10-L17
public interface KnowledgeBaseRepository {

    Long create(Long tenantId, String name, String embeddingModelCode, int vectorDim, String indexName);

    List<DocumentInfo> list(Long tenantId);

    boolean exists(Long tenantId, Long kbId);
}
```

三个方法，全部以 `tenantId` 作为**第一个参数**——这不是巧合，而是把"租户隔离"写进接口签名，让实现类想绕都绕不开。

实现类 `infra/persistence/DbKnowledgeBaseRepository.java` 全文只有 52 行，逐方法拆解：

**方法一：create（第 24-35 行）——新建一个知识库记录**

```java
// 来源：aihub/aihub-ai-service/src/main/java/com/aihub/ai/infra/persistence/DbKnowledgeBaseRepository.java#L23-L35
@Override
public Long create(Long tenantId, String name, String embeddingModelCode, int vectorDim, String indexName) {
    AiKnowledgeBaseDO ddo = new AiKnowledgeBaseDO();
    ddo.setTenantId(tenantId);
    ddo.setName(name);
    ddo.setEmbeddingModelId(0L); // M2 使用默认 Embedding 模型，M5 支持按 KB 选型
    ddo.setVectorDim(vectorDim);
    ddo.setIndexName(indexName);
    ddo.setStatus(1);
    ddo.setCreateTime(LocalDateTime.now());
    kbMapper.insert(ddo);
    return ddo.getId();
}
```

四个看点：
1. **领域对象与数据对象分离**：方法收的是接口参数，落库用的是 `AiKnowledgeBaseDO`（infra.persistence.dataobject 包），返回的是 `Long` 主键。领域层（application/service）看不到任何 DO 类型。
2. **`vectorDim` 与 `indexName` 被持久化**：这两个字段是后续向量检索的"契约"，第 4 节会展开为什么 vectorDim 不能改。
3. **`embeddingModelId` 暂写 0L**：里程碑注释写明 M2 用默认 Embedding 模型、M5 支持按 KB 选型——从代码注释反推演进路线，这正是讲解文档要抓的细节。
4. **主键回填**：`kbMapper.insert(ddo)` 后直接 `ddo.getId()`，依赖 MyBatis-Plus 的 ID 回填（`AiKnowledgeBaseDO` 上是 `@TableId(type = IdType.ASSIGN_ID)`，雪花 ID）。

**方法二：list（第 38-44 行）——列出本租户全部知识库**

```java
// 来源：aihub/aihub-ai-service/src/main/java/com/aihub/ai/infra/persistence/DbKnowledgeBaseRepository.java#L37-L44
@Override
public List<DocumentInfo> list(Long tenantId) {
    return kbMapper.selectList(Wrappers.<AiKnowledgeBaseDO>lambdaQuery()
                    .eq(AiKnowledgeBaseDO::getTenantId, tenantId))
            .stream()
            .map(d -> new DocumentInfo(d.getId(), null, d.getName(), "kb", d.getStatus(), null))
            .toList();
}
```

关键点：`Wrappers.lambdaQuery().eq(...::getTenantId, tenantId)` 是**无条件必带**的租户过滤；返回类型是领域层的 `DocumentInfo`（record），DO 到领域对象的转换被封闭在实现类里。

**方法三：exists（第 47-51 行）——归属校验的基石**

```java
// 来源：aihub/aihub-ai-service/src/main/java/com/aihub/ai/infra/persistence/DbKnowledgeBaseRepository.java#L46-L51
@Override
public boolean exists(Long tenantId, Long kbId) {
    return kbMapper.selectCount(Wrappers.<AiKnowledgeBaseDO>lambdaQuery()
            .eq(AiKnowledgeBaseDO::getTenantId, tenantId)
            .eq(AiKnowledgeBaseDO::getId, kbId)) > 0;
}
```

它是水平越权防护的守门员：`KnowledgeAppService` 里所有按 kbId 的操作（列文档、传文档、绑定、检索调试）第一步都调 `requireKb(tenantId, kbId)`，而 `requireKb` 的实现就是转发到 `exists`（`application/KnowledgeAppService.java#L332-L336`）。租户 A 传租户 B 的 kbId？`exists` 直接 false，抛"知识库不存在"。

**DO 侧的配合**（`infra/persistence/dataobject/AiKnowledgeBaseDO.java#L15-L33`）：

```java
// 来源：aihub/aihub-ai-service/src/main/java/com/aihub/ai/infra/persistence/dataobject/AiKnowledgeBaseDO.java#L15-L17,L29-L30
@Data
@TableName("ai_knowledge_base")
public class AiKnowledgeBaseDO {
    @TableId(type = IdType.ASSIGN_ID)
    private Long id;
    // ... vectorDim / indexName / status ...
    @TableLogic
    private Integer deleted;
```

`@TableName` 绑表名、`@TableLogic` 开启逻辑删除（配合 `application.yml` 第 127-130 行的 `logic-delete-field: deleted` 配置，MyBatis-Plus 会把 delete 自动改写为 update deleted=1）。类注释同时埋了一句强约束："vector_dim 必须与所选 Embedding 模型维度一致（强校验，建索引后不可改）"——第 4.4 节解释原因。

### 2.4 四段式小结（面试可以直接背）

- **作用与原理**：领域层定义"我能做什么"（SPI 接口），基础设施层定义"我怎么做"（Db 实现）。依赖方向永远是 infra → domain，倒置了传统的"业务依赖数据库细节"。
- **项目真实用例**：`domain/spi/KnowledgeBaseRepository.java` 三方法接口 + `infra/persistence/DbKnowledgeBaseRepository.java#L24-L51` 三方法实现；编排层 `application/KnowledgeAppService.java#L49-L56` 注入的 7 个依赖全部是接口。
- **常见误用**：①把 DO 泄漏到 application 层（一个 import 就破功）；②接口方法不带 tenantId，让实现"自己想办法拿"——隔离条件从签名上就消失了；③在一个实现类里偷偷 import 另一个实现类的工具类，形成实现间横向耦合。
- **面试怎么说**："我们用 DDD 的仓储模式做读写分离抽象，domain.spi 定义接口、infra.persistence 用 MyBatis-Plus 实现，ArchUnit 强制 web 层不碰 infra。最大的收益是租户隔离条件固化在接口签名里、单测可以 Mock 仓储不连库，以及向量库实现可替换——把 RedisKnowledgeRetriever 换成 Milvus 实现，application 层一行不改。"

### 3.2 文档上传：为什么必须异步

接口 `web/KnowledgeController.java#L59-L75`（upload 方法）：接收 `MultipartFile`，读出字节数组就调 `submitIngest`，**立即返回 taskId**，注释写明前端轮询 `GET /api/ai/kb/ingest/{taskId}` 拿进度。

为什么不能同步做完再返回？看编排层注释（`KnowledgeAppService.java#L130-L134`）："原实现是同步阻塞——大文件解析加向量化会占满请求线程，现在改为提交即返回，前端凭 taskId 轮询进度。" 一个 50 页 PDF 的解析加几百个分片的 Embedding 调用是分钟级操作，Tomcat 线程被占满后整个服务就不可用了。

`submitIngest` 的四个动作（`KnowledgeAppService.java#L137-L156`）：

```java
// 来源：aihub/aihub-ai-service/src/main/java/com/aihub/ai/application/KnowledgeAppService.java#L140-L155（节选）
String fileType = fileTypeOf(filename);
```

三个细节值得讲：**入库线程池固定 4 线程**（第 77-81 行），注释解释"解析与向量化都是 IO 密集，并发不宜过高以免压垮向量库"；**原始文件必须落盘**（`ingestFileStore.save`），注释坦白早先用进程内 Map、重启即丢——所以有 `IngestFileStore` SPI 与 local/minio 两个实现（`application.yml` 第 156-162 行 `aihub.storage.type`）；**TraceContext.wrap** 把 HTTP 请求线程的链路 ID 带到工作线程，否则入库日志在 ELK 里是孤立的（ThreadLocal 不跨线程）。

### 3.3 切片策略：TextChunker 的段落优先 + 滑动窗口

切片是 RAG 效果的第一决定因素。本项目没有引第三方 splitter，而是自己写了个 87 行的纯 Java 切分器（`domain/support/TextChunker.java`），策略写在类注释里："优先按段落（空行）切分；超长段落按固定字数二次切分；相邻分片保留 overlap 字符重叠，避免关键信息被切断。（课程实践结论：按段落 + 重叠的检索效果明显优于固定字数硬切）"

核心方法 `split`（第 20-61 行）逐段讲解：

```java
// 来源：aihub/aihub-ai-service/src/main/java/com/aihub/ai/domain/support/TextChunker.java#L25-L61（节选）
int size = Math.max(maxChars, 100);            // 最小分片 100 字符，防止碎片化
int ov  = Math.max(0, Math.min(overlap, size / 2)); // 重叠最多半片，防止"全是重叠"
List<String> paragraphs = splitParagraphs(text);     // 按行切出非空段落
StringBuilder buffer = new StringBuilder();
for (String paragraph : paragraphs) {
    if (paragraph.length() > size) {           // 分支一：单段超长 → 滑动窗口硬切
        if (!buffer.isEmpty()) { chunks.add(new Chunk(seq++, buffer.toString())); buffer.setLength(0); }
        for (String piece : slidingWindow(paragraph, size, ov)) {
            chunks.add(new Chunk(seq++, piece));
        }
        continue;
    }
    if (buffer.length() + paragraph.length() + 1 > size) {  // 分支二：装不下 → 先刷出缓冲
        String flushed = buffer.toString();
        chunks.add(new Chunk(seq++, flushed));
        String tail = flushed.length() > ov ? flushed.substring(flushed.length() - ov) : flushed;
        buffer.setLength(0);
        buffer.append(tail);                   // ★ 保留尾部 overlap，衔接上下文
    }
    if (!buffer.isEmpty()) { buffer.append('\n'); }
    buffer.append(paragraph);
}
```

三段逻辑对应三种情况：**普通段落**尽量多段合并成一个分片（语义完整）；**单段超长**（比如没有空行的纯文本）用 `slidingWindow`（第 74-85 行，步长 `size - overlap`）切出重叠窗口；**缓冲区装不下**时刷出，但把尾部 overlap 字符留下当下一片的"开头记忆"。`Chunk` 本身是个极简 record（`domain/model/Chunk.java#L6`：`record Chunk(int seq, String content)`），seq 供还原顺序与引用编号用。

切片参数从配置注入（`KnowledgeAppService.java#L66-L70`）：`aihub.rag.chunk-size:500`、`aihub.rag.chunk-overlap:100`（`application.yml` 第 147-148 行）。为什么这两个用 `@Value` 而不是像检索参数那样走 `@ConfigurationProperties` 热更新？`KnowledgeAppService` 第 63-65 行注释给出架构理由："架构规则禁止 application 层依赖 infra（RagProperties 定义在 infra.ai.config 包），@Value 字段在启动时绑定一次，这些低频参数改后需重启生效。"

### 3.4 Embedding 调用与向量入库

真正的入库执行体 `execute`（`KnowledgeAppService.java#L256-L287`）把四阶段串起来，每阶段都回写进度并计时：

```java
// 来源：aihub/aihub-ai-service/src/main/java/com/aihub/ai/application/KnowledgeAppService.java#L256-L287（节选）
ingestTaskRepository.updateProgress(tenantId, taskId, IngestTask.STATUS_RUNNING, IngestTask.STAGE_PARSE, 10);
String text = timed(IngestTask.STAGE_PARSE, () -> parseText(filename, bytes)); // pdf→PDFBox / docx→POI / 其余按 UTF-8
...
List<Chunk> chunks = timed(IngestTask.STAGE_SPLIT, () -> TextChunker.split(text, chunkSize, chunkOverlap));
...
timed(IngestTask.STAGE_SAVE, () -> { documentRepository.saveChunks(tenantId, kbId, docId, chunks, 0); return null; });
...
int indexed = timed(IngestTask.STAGE_VECTOR, () -> knowledgeIndexer.index(tenantId, kbId, docId, chunks));
documentRepository.updateChunkStatus(tenantId, docId, 1);
```

进度阶梯 10 → 30 → 50 → 70 →（成功后 markDone）100，对应 `IngestTask` record 里的阶段常量（`domain/model/IngestTask.java#L33-L36`：parse/split/save/vector）。失败时 `ingest` 方法（第 223-242 行）统一写失败终态并**保留暂存文件**以便重试；自动重试 `runWithRetry`（第 290-308 行）做指数退避（`backoff` 第 310-316 行：200ms 翻倍封顶 2 秒，重试上限 `aihub.rag.ingest-max-retry:2`）。

向量化本体在 `infra/ai/RedisKnowledgeIndexer.java`：

```java
// 来源：aihub/aihub-ai-service/src/main/java/com/aihub/ai/infra/ai/RedisKnowledgeIndexer.java#L28-L43
@Override
public int index(Long tenantId, Long kbId, Long docId, List<Chunk> chunks) {
    if (chunks == null || chunks.isEmpty()) {
        return 0;
    }
    List<Document> documents = chunks.stream()
            .map(chunk -> new Document(
                    chunk.content(),
                    Map.of(
                            "tenant_id", String.valueOf(tenantId),
                            "kb_id", String.valueOf(kbId),
                            "doc_id", String.valueOf(docId))))
            .toList();
    vectorStore.add(documents);
    log.info("知识入库完成 tenant={} kb={} doc={} chunks={}", tenantId, kbId, docId, documents.size());
    return documents.size();
}
```

这里发生了两件事：

1. **Embedding 是 `vectorStore.add()` 内部隐式完成的**——`VectorStore` 持有 `EmbeddingModel`（见第 4.1 节装配），Spring AI 会把每条文本先调嵌入模型转成 768/1536 维浮点向量，再连同元数据写进 Redis；
2. **每个分片强制写入三元组元数据** `tenant_id / kb_id / doc_id`——类注释（第 17-19 行）称之为"租户隔离的数据源头，缺失该元数据的向量在检索侧会被 TenantGuard 丢弃"。

## 4. 向量检索原理：余弦相似度、HNSW 与 vectorDim

### 4.1 向量与 Embedding 是什么

文本对机器本是离散符号，Embedding 模型把一段文本映射成固定长度的浮点数组（本项目用 Ollama 本地模型 `embeddinggemma`，**768 维**——见 `VectorStoreConfig` 第 29 行注释）。语义相近的文本在向量空间中方向相近，"搜索"就变成了"找方向最接近的向量"。装配代码：

```java
// 来源：aihub/aihub-ai-service/src/main/java/com/aihub/ai/config/VectorStoreConfig.java#L38-L56
@Bean
public EmbeddingModel embeddingModel(...) {
    OpenAiApi api = OpenAiApi.builder().baseUrl(baseUrl).apiKey(apiKey).build();
    return new OpenAiEmbeddingModel(
            api,
            org.springframework.ai.document.MetadataMode.EMBED,
            OpenAiEmbeddingOptions.builder().model(model).build(),
            org.springframework.retry.support.RetryTemplate.builder()
                    .maxAttempts(2).fixedBackoff(500).build());
}
```

指向 Ollama 的 OpenAI 兼容 `/v1/embeddings` 接口，离线可用；类注释（第 25-29 行）写明这个显式 Bean 正是 3.5 节那次"对话卡死"事故的修复——定义本 Bean 后 Spring AI 的默认 OpenAI 嵌入自动装配退位（`@ConditionalOnMissingBean`）。

### 4.2 余弦相似度

两向量 a、b 的余弦相似度 = `a·b / (|a| × |b|)`，取值 [-1, 1]，衡量的是**方向**而非长度。文本向量场景普遍选它而不是欧氏距离，因为嵌入向量的模长往往反映词频/文本长度等"响度"因素，归一化掉模长后比较纯语义方向更稳。Spring AI 的 RedisVectorStore 默认距离度量即 COSINE，检索返回的 `score` 已经归一化为 [0,1] 的相似度——所以 `RedisKnowledgeRetriever` 里 `similarityThreshold` 可以直接用 0~1 的业务阈值过滤。

### 4.3 HNSW 索引：为什么检索不用全库扫描

朴素做法是拿查询向量与库里每条向量算一遍余弦——10 万条 768 维就是 10 万次 768 维点积，毫秒级都保不住。Redis Stack（RediSearch）为向量字段建 **HNSW**（Hierarchical Navigable Small World，分层可导航小世界图）索引：把向量组织成多层跳表式近邻图，上层稀疏长边快速"跳到"目标区域，下层稠密短边精确逼近，查询时从顶层入口贪心下行，只访问 O(log N) 量级的节点，用"近似"换百倍千倍的速度（召回率通常 95%+）。本项目装配处（`VectorStoreConfig.java#L59-L84`）没有显式指定算法，Spring AI `RedisVectorStore` 建的默认即 HNSW；`metadataFields` 把三个租户字段建成 TAG 类型（第 78-81 行），让"相似度排序"与"标签精确过滤"在同一次查询里完成。

### 4.4 vectorDim 为什么必须与模型维度一致

`vectorDim`（建库时默认 1536，存入 `ai_knowledge_base.vector_dim`）声明的是"这个知识库里的向量有多长"。它必须与实际 Embedding 模型输出维度严格相等，原因有三层：

1. **索引结构是按维度建死的**：RediSearch 建 HNSW 索引时指定 VECTOR TYPE/DIM，写入维度不符的向量直接报错——DO 注释"强校验，建索引后不可改"说的就是它；
2. **不同模型的空间互不相通**：embeddinggemma 的 768 维空间与 OpenAI text-embedding-3-small 的 1536 维空间是两套完全不同的坐标系，即使维度凑巧相同，同一文本的两套向量也没有可比性；
3. **查询与入库必须同源**：检索时问题文本会先过同一个 EmbeddingModel 向量化（`vectorStore.similaritySearch` 内部完成），若换模型则历史向量全部作废——所以本项目把嵌入模型统一固定在一处装配（`VectorStoreConfig#embeddingModel`），换供应商只改 `aihub.embedding.*` 三个配置项并重建索引。

值得注意的是一个现实的"配置即契约"细节：`application.yml` 第 81 行 `initialize-schema: false`，而 `VectorStoreConfig#vectorStore`（第 66-69 行）的 `@Value` 注释专门记录了一个静默失效 bug："早期版本此处硬编码 true，配置里写 initialize-schema: false 完全不生效……属于'配置项存在但形同虚设'的静默失效，排查时极易被误导。" 修复方式就是把配置真的读出来用——面试讲"配置可靠性"时这是极好的小故事。

### 4.5 租户隔离的三道防线（检索侧）

## 5. SSE 流式对话源码讲解

### 5.1 为什么要流式

大模型逐 token 生成，一次回答 5~60 秒。同步接口意味着用户盯着白屏等完整答案；流式把每个 token 到达就推给前端，首字延迟从"整段生成时间"降到"第一个 token 时间"，体验差距是质变的。

### 5.2 SseEmitter 是什么、生命周期五步

`SseEmitter` 是 Spring MVC 的 SSE 推送器：Controller 返回它 = 告诉容器"这个响应我稍后慢慢写"，容器随即把请求线程释放为异步模式。完整生命周期五步：

1. **创建**：`new SseEmitter(120_000L)` 设超时 2 分钟（`ChatController#chatSse` 第 105 行）；
2. **返回**：Controller 方法 return，容器发出响应头（`Content-Type: text/event-stream`），进入异步上下文；
3. **写事件**：任意线程持有 emitter 调 `emitter.send(...)` 推帧；
4. **完成**：`emitter.complete()` 正常关闭；
5. **终止**：超时 / 客户端断开 / send 抛异常——此后再 send 会抛 `IllegalStateException`。

**生命周期最大的坑在跨线程**：模型生成耗时几十秒，绝不能占着 Tomcat 请求线程干等。`ChatController` 的解法（第 81-85 行 + 103-118 行）：

```java
// 来源：aihub/aihub-ai-service/src/main/java/com/aihub/ai/web/ChatController.java#L81-L118（节选）
/** 流式任务执行线程池（阻塞式写回，与容器线程隔离） */
private final ExecutorService streamExecutor = Executors.newFixedThreadPool(32, r -> {
    Thread t = new Thread(r, "aihub-stream-" + UUID.randomUUID().toString().substring(0, 8));
    t.setDaemon(true);
    return t;
});

@PostMapping(value = "/chat/sse", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
public SseEmitter chatSse(@Valid @RequestBody ChatRequest request) {
    SseEmitter emitter = new SseEmitter(120_000L);
    ChatTurn turn = turn(request);
    // 流式任务在独立线程执行：必须把链路 ID 带过去，否则日志断链
    streamExecutor.submit(TraceContext.wrap(() -> {
        StreamSink sink = new SseStreamSink(emitter);
        try {
            chatAppService.chatStream(turn, sink);
        } catch (Exception e) {
            sink.emit(StreamEvent.error(9999, "50000", "服务异常"));
            sink.close();
        }
    }));
    return emitter;
}
```

`produces = TEXT_EVENT_STREAM_VALUE` 声明响应是 SSE 流；任务提交给自建 32 线程池后 **return emitter 立即执行**，容器线程回去接客；真正调模型的活儿在 `aihub-stream-*` 线程上干。`TraceContext.wrap` 是跨线程送链路 ID 的关键（ThreadLocal 不跨线程）。

### 5.3 异常与断连处理：volatile closed 标记

`web/sink/SseStreamSink.java` 是 SSE 通道的统一封装，类注释点明本类正确性关键（第 18-21 行）："closed 标记会被多个线程读写（流任务线程 emit/close，可能还有超时线程），volatile 保证一个线程的写入立即对其他线程可见（否则可能一直读到缓存的旧值 false，往已关闭的连接写数据）。"

```java
// 来源：aihub/aihub-ai-service/src/main/java/com/aihub/ai/web/sink/SseStreamSink.java#L37-L64
@Override
public void emit(StreamEvent event) {
    if (closed) {
        return;
    }
    try {
        emitter.send(SseEmitter.event()
                .name(event.event())
                .data(mapper.writeValueAsString(event)));
    } catch (IOException | IllegalStateException e) {
        // 客户端断开等情况：标记关闭，后续事件直接丢弃
        closed = true;
        log.debug("SSE 发送失败（客户端可能已断开）: {}", e.getMessage());
    }
}

@Override
public void close() {
    if (closed) {
        return;
    }
    closed = true;
    try {
        emitter.complete();
    } catch (Exception e) {
        log.debug("SSE complete 异常: {}", e.getMessage());
    }
}
```

设计要点：断连**不算错误**（debug 级日志），因为用户关页面天经地义；emit 失败后置 `closed = true` 让后续几百个 token 事件静默丢弃，避免每个 token 都抛一次异常刷屏；`close()` 幂等（双重 if + 先置位再 complete）。执行器侧还有一层兜底：`SpringAiChatExecutor#stream` 的 finally 块（第 171-174 行）保证 `AiCallContext.clear()` 与 `sink.close()` 恒被执行；而 `ChatAppService#chatStream`（第 93-113 行）的 catch 只记日志不向上抛——注释解释"流式通道上抛异常前端收不到（连接已建立、响应头已发出），所以失败必须转成 StreamEvent.error 事件"。

另一个真实踩坑记录在 `application.yml` 第 8-12 行：Tomcat 异步请求默认 30 秒超时，大模型生成超 30 秒被容器掐断，"前端表现为回答中途报'模型调用失败'"，解法是 `spring.mvc.async.request-timeout: 300000` 放宽到 5 分钟——SSE 超时排查必背案例。

### 5.4 事件帧协议：StreamEvent 统一信封

三种通道共用一套事件信封（`domain/model/StreamEvent.java#L6-L8`）：

```text
{ "i":12, "e":"token", "ts":1757400000000, "data":{...} }
```

事件时间线（第 14-20 行注释）：`msg.start → [rag.sources] → token×N → [tool.start→tool.end]×N → [agent.step]×N → [artifact] → msg.end`（任何时刻可发 error；空闲心跳 ping）。`index` 字段从 0 递增，前端用于排序/去重/判断丢帧。类本身是 Java 17 record——注释顺带讲了 record 语义：final 字段 + 访问器 + equals/hashCode/toString，不可变对象天然线程安全。

### 5.5 为什么选 SSE 不选 WebSocket（以及为什么还有 WebSocket）

结论先行：**H5 对话场景选 SSE，因为它是"够用的最简方案"；Agent 长任务场景保留 WebSocket，因为需要双向通道。** 逐条对比：

| 维度 | SSE | WebSocket |
|---|---|---|
| 协议 | 纯 HTTP（可过普通网关/代理/CDN） | 独立协议，需 Upgrade 握手 |
| 方向 | 单向（服务端→客户端），对话推流刚好够用 | 全双工 |
| 断线重连 | 浏览器/框架内置语义，简单 | 需自己实现心跳+重连 |
| 携带鉴权头 | 需 fetch + ReadableStream（`SseStreamSink` 注释：EventSource 不能带自定义 Header，而本项目鉴权要 Authorization 头） | 握手时可带 Header |
| 服务器实现成本 | SseEmitter 一个类 | WebSocketConfig + Handler 会话管理 |

`ChatController` 类注释（第 49-56 行）补充了第三个通道存在的理由："NDJSON（每行一个 JSON 的 Chunked 传输）：微信小程序 request API 不支持 SSE，只能用 enableChunked 分块接收"。所以同一套编排 `ChatAppService.chatStream`，三个实现各配一个 `StreamSink` 实现：

- `SseStreamSink`：H5，`emitter.send()`；
- `NdjsonStreamSink`（`web/sink/NdjsonStreamSink.java#L31-L42`）：小程序，直接 `out.write(json + "\n")` + flush；Controller 侧（第 141-147 行）为小程序设了四个硬性响应头：`Content-Encoding: identity`（禁 gzip——gzip 会让分块变整块）、`X-Accel-Buffering: no`（禁 Nginx 缓冲）、`Cache-Control: no-cache, no-transform`（禁中间层转换）；
- `WsStreamSink`（`web/sink/WsStreamSink.java#L27-L37`）：Agent 长任务，`session.sendMessage(...)`，emit 前先查 `session.isOpen()`。

这正是 2.2 节 `StreamSink` SPI 的价值落地：`domain/spi/StreamSink.java#L11-L17` 只有两个方法（emit/close），`ChatAppService` 注释第 89 行写明"本方法不关心 sink 背后是 SSE / NDJSON / WebSocket——这就是抽象的好处"。

```java
            .defaultOptions(OpenAiChatOptions.builder().model(endpoint.modelCode()).temperature(0.7).build())

}
```

三个安全/健壮性细节：密钥在库里是**密文**（`ModelEndpoint` 注释："解密动作由 infra 层完成，密文永不外泄、永不进日志"）；解密后的明文密钥只活在本次构建栈帧里；`openAiCompatible()`（`ModelEndpoint.java#L28-L30`，白名单 `openai/volcengine/dashscope/deepseek/ollama`）做**快速失败**——注释说得很形象："而不是带着错误的 baseUrl 去发请求（那会得到难以定位的连接/404 错误）"。

3. **`domain/spi/ChatExecutor`**（第 11-29 行）：对话执行接口，`call`（同步）与 `stream（流式）` 两方法 + `StreamResult` record（content/modelCode/costMs/tokenIn/tokenOut）。`SpringAiChatExecutor` 类注释（第 29-31 行）点明防腐层思想："Spring AI 的所有类型被限制在本包内——业务层只依赖 domain 的 ChatExecutor 接口，将来升级 Spring AI 2.0 时只需改这里。"

### 6.2 ChatClientFactory：最核心的"装配车间"

`infra/ai/ChatClientFactory.java`（约 270 行）类注释用"电话线/电话机"比喻讲清 Spring AI 两个核心对象：ChatModel 是"电话线"（指向哪家 API、什么密钥），ChatClient 是"装好了通讯录和助理的电话机"（可挂系统提示词、记忆 Advisor、工具）。每个 `(租户, 应用, 场景)` 组合的配置都可能不同，ChatClient 不能全局共享一个；但每次对话都重新装配又太贵，所以**按 key 缓存 + TTL 过期**：

```java
// 来源：aihub/aihub-ai-service/src/main/java/com/aihub/ai/infra/ai/ChatClientFactory.java#L134-L150
public ChatClient create(Long tenantId, Long appId, String scene, String modelCode) {
    String key = cacheKey(tenantId, appId, scene, modelCode);
    CacheEntry entry = cache.get(key);
    long now = System.currentTimeMillis();
    long ttlMillis = chatClientProperties.getCacheSeconds() * 1000;
    if (entry == null || now - entry.createdAt() > ttlMillis) {   // 无锁快路径
        synchronized (cache) {                                     // 双重检查锁
            entry = cache.get(key);
            if (entry == null || now - entry.createdAt() > ttlMillis) {
                entry = build(tenantId, appId, scene, modelCode);
                cache.put(key, entry);
            }
        }
    }
    return entry.client();
}
```

缓存 key 是四元组（第 163-165 行：`tenant:app:scene:modelCode`），TTL 来自 `aihub.chat-client.cache-seconds: 60`（application.yml 第 141-142 行）——注释写明这是"支持 Nacos / DB 配置变更后的自动刷新（无需重启）"：管理员改了模型路由，最多 60 秒后新装配生效。

`build` 方法（第 167-203 行）依次做四件事：**选模型**（优先级：前端指定 modelCode > 场景路由主模型 > 备用模型 > Spring Boot 自动装配默认模型，`resolveModel` 第 244-266 行含逐级降级 try-catch）、**取系统提示词**（应用配置的 systemPrompt，缺省 `DEFAULT_SYSTEM_PROMPT` 第 79-84 行）、**Ollama 特判**（第 188-190 行：给 Qwen3 系列追加 ` /no_think` 软开关，注释解释这些推理模型"默认把回答输出到 reasoning 字段、content 恒为空"）、**挂 Advisor 与工具**：

```java
// 来源：aihub/aihub-ai-service/src/main/java/com/aihub/ai/infra/ai/ChatClientFactory.java#L192-L200
ChatClient client = ChatClient.builder(resolved.chatModel())
        .defaultSystem(systemPrompt)
        .defaultAdvisors(
                MessageChatMemoryAdvisor.builder(chatMemory).build(),  // 历史对话自动注入
                new AuditAdvisor())                                     // 审计留痕
        .defaultToolCallbacks(buildToolCallbacks())                     // 内置 + MCP 外部工具
        .build();
```

Advisor 是 Spring AI 的"请求/响应拦截器链"（类注释第 41-44 行的 AOP 比喻）。工具装配 `buildToolCallbacks`（第 211-234 行）把内置 `@Tool` 方法（时间、知识库、可选浏览器）与 MCP 外部工具统一包上 `AuditedToolCallback` 审计——MCP 未接入时 `orderedStream()` 为空，"功能自然降级为「仅内置工具」"。

### 6.3 流式与非流式的实现差异

`SpringAiChatExecutor` 的两个方法对着看最清楚。同步 `call`（第 66-100 行）：`client.prompt().user(...).advisors(...).call().chatResponse()` 一把拿全量响应，再取 token 用量、落引用、上报指标；流式 `stream`（第 114-175 行）：

```java
// 来源：aihub/aihub-ai-service/src/main/java/com/aihub/ai/infra/ai/SpringAiChatExecutor.java#L131-L150（节选）
client.prompt()
      .user(augmented.prompt())
      .advisors(a -> a.param(ChatMemory.CONVERSATION_ID, memoryKey)
              .param(AuditAdvisor.CTX_TENANT, turn.tenantId())
              .param(AuditAdvisor.CTX_APP, turn.appId())
              .param(AuditAdvisor.CTX_SCENE, turn.scene()))
      .stream()
      .chatResponse()
      .doOnNext(response -> {
          last[0] = response;
          if (response != null && response.getResult() != null
                  && response.getResult().getOutput() != null) {
              String token = response.getResult().getOutput().getText();
              if (token != null) {
                  content.append(token);
                  sink.emit(StreamEvent.token(index[0]++, token));   // 每个 token 到达即推给前端
              }
          }
      })
      .blockLast();
```

类注释（第 35-39 行）把这种写法定性为"响应式数据源 + 阻塞消费的混合用法——因为本服务是 MVC（Servlet 线程模型），在自建线程池里阻塞是安全的"：模型侧是 Reactor Flux（逐 token 事件流），消费侧 `doOnNext` 转发 + `blockLast()` 等流结束。两条路径都会在结束时把 `usage` 的 token 数记入 `AiMetrics`（注释强调"失败也要计数与计时，否则成功率与耗时分位数都是失真的"），并 `referenceStore.save(...)` 把 RAG 引用挂到会话上供 `/chat/references` 溯源。

### 6.4 会话记忆：DbChatMemory

多轮对话靠记忆。`infra/ai/DbChatMemory` 实现 Spring AI 的 `ChatMemory` 接口，存储走 SPI `ConversationMemoryStore`（MySQL）。两个要点：

1. **会话键自带租户**（第 37-39 行）：`"t" + tenantId + ":" + conversationId`——"租户隔离由键本身保证"；
2. **窗口策略**（`get` 方法第 59-73 行）：每次取最近 `aihub.memory.window-size: 20` 条（application.yml 第 164-165 行），按角色还原成 `UserMessage`/`AssistantMessage`。

类注释还留了一个真实 bug 复盘（第 23-25 行）："会话 ID 是字符串（前端生成，形如 a3f2c1e09b8d4a7f），原实现把非数字 ID 一律退化成 0L 写入 BIGINT 列，导致同一租户下所有会话的历史被混写在同一份记忆里"——后来以 `conv_key` 字符串列承载（迁移 `db/migration/V9__fix_conversation_id.sql`）。对应的编排侧动作在 `SpringAiChatExecutor#stream` 第 133 行：`.param(ChatMemory.CONVERSATION_ID, memoryKey)` 把键传给记忆 Advisor，无需业务代码手工拼历史。

## 7. 本章面试三问与参考回答

**Q1：为什么你们的仓储层要"domain.spi 接口 + infra.persistence 实现"，而不是 Service 直接用 Mapper？直接用不是更快吗？**

参考回答：三层理由。第一，**依赖方向**：业务只依赖抽象，MyBatis-Plus 被封闭在 infra 包内，换 ORM/换存储（例如向量库从 Redis Stack 换 Milvus）只改实现类，ArchUnit 还强制 web 层不碰 infra。第二，**租户隔离固化在签名里**：所有仓储方法第一个参数都是 tenantId（如 `KnowledgeBaseRepository#exists`），配合 `requireKb` 前置校验与 MyBatis-Plus SQL 兜底拦截器（application.yml 第 181-185 行 tenant.sql-guard），形成多道防线。第三，**可测试性**：Service 单测 Mock 接口即可，不连库。成本只是多一层薄薄的转换代码，DbKnowledgeBaseRepository 全类 52 行——这个代价远小于收益。

**Q2：讲讲 RAG 全链路，一个 PDF 从上传到被引用经历了什么？**

参考回答：六步。①上传接口落文档记录 + 入库任务、原始文件存暂存区，立即返回 taskId（异步化，防止占满请求线程）；②后台线程池解析为纯文本（PDFBox/POI）；③TextChunker 切片：段落优先合并、超长段滑动窗口、相邻分片保留 100 字符重叠（语义完整性优于固定字数硬切）；④RedisKnowledgeIndexer 调 Embedding 模型（本地 Ollama 的 768 维 embeddinggemma，OpenAI 兼容协议）把每片转成向量，连同 tenant_id/kb_id/doc_id 元数据写入 Redis Stack 的 HNSW 索引；⑤对话时应用绑定的知识库被检索：问题先向量化，RediSearch 做余弦相似度 + TAG 过滤下推 + TenantGuard 出口校验，取 topK=4、阈值 0.6 的片段；⑥命中片段编号拼进提示词并附防幻觉约束（"仅依据知识库内容回答，不足时明说，禁止编造"），同时发 rag.sources 事件让前端渲染引用角标。两个工程保险：检索 3 秒超时降级为普通对话（曾有嵌入模型连外网无限阻塞卡死对话的真实事故）；入库四阶段（parse/split/save/vector）回写进度供前端轮询，失败指数退避自动重试 + 手动重试兜底。

**Q3：SSE 和 WebSocket 怎么选？你们流式对话的线程模型是什么？**

参考回答：选型上，H5 对话是"服务端单向推流"场景，SSE 用纯 HTTP 就够——过网关/代理无障碍、断线重连语义简单、服务端只需 SseEmitter，没必要为单向场景引入全双工 WebSocket 的握手与会话管理；但 Agent 长任务需要双向中断控制所以保留 WebSocket；微信小程序 request API 不支持 SSE，加了第三个 NDJSON Chunked 通道（每行一个 JSON，禁 gzip + X-Accel-Buffering: no）。三通道共享同一 ChatAppService 编排与 StreamEvent 统一信封（index 序号防丢帧），差异全部被 StreamSink SPI 吸收——这是依赖倒置的直接收益。线程模型上，模型生成几十秒不能占容器线程：Controller 把流式任务提交给自建 32 线程池后立即 return SseEmitter（Tomcat 异步模式释放请求线程），跨线程用 TraceContext.wrap 带链路 ID；SseStreamSink 用 volatile closed 标记保证断连后事件静默丢弃，Tomcat 异步超时放宽到 5 分钟（默认 30 秒会掐断长回答）。流式路径的异常必须转成 error 事件帧而非向上抛——响应头已发出，抛异常前端什么都收不到。
