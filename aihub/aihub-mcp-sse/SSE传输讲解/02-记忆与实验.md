# 02｜记忆卡片与动手实验

## 1. 总口诀

**"一参两端口，开关三件套"**

| 口诀 | 含义 |
|---|---|
| 一参 | `scanBasePackages="com.aihub.mcp"`（往上扫一层捞后厨） |
| 两端点 | `/sse` 建连收、`/mcp/message` 回传（SSE 双通道） |
| 开关三件套 | ConditionalOnProperty 装配 + fail-fast 构造器 + Filter 门禁（order 0） |

## 2. 六张卡片

**卡 1｜SSE 为什么是"两个端点"？** SSE 通道单向（服务器→浏览器），客户端发请求得另开 POST——
所以建连 `/sse` 收到 `event: endpoint`（内含 sessionId），之后所有 JSON-RPC 都 POST 到 `/mcp/message?sessionId=xxx`。
**一条只出不进的流 + 一条普通 POST = 双向会话**。
**卡 2｜instructions vs description**：前者是"整套工具的使用策略"（initialize 时下发给客户端模型），
后者是"单个工具说明书"（tools/list 时下发）——两级提示词，管的事不同。
**卡 3｜超时咬合**：`request-timeout(70s) > aihub.mcp.timeout(60s)`，反了会怎样？——上游慢查询被 MCP 层先掐，
日志只有"MCP 请求超时"，排查指不到 HTTP 层。
**卡 4｜Filter vs Interceptor**：拦**框架注册的端点**（不走自己 Controller 的 URL）必须用 Filter；
Interceptor 只在 DispatcherServlet 派发 Controller 的前后生效。
**卡 5｜时序攻击一句话**：`equals` 提前返回→耗时泄露"前几个字节对了"→用 `MessageDigest.isEqual` 全比完。
**卡 6｜fail-fast 三连**：enabled=true 没 token 拒启动；token 比较不区分 scheme 直接拒；capabilities 按实报。
共同哲学：**配置错误/能力缺失要在启动和握手期暴露，不要留到运行期神秘失败**。

## 3. 动手实验

**实验 1｜亲眼看 SSE 双通道握手**
```powershell
# 终端 A：建连（-N 不缓冲，-F 后台跑不了就新开一个终端）
curl.exe -N http://127.0.0.1:8090/sse
```
预期：立刻吐一行 `event: endpoint` + `data: /mcp/message?sessionId=xxxx`，然后**挂住不退出**（流保持打开）。
终端 B 按它给的地址发消息：
```powershell
curl.exe -X POST "http://127.0.0.1:8090/mcp/message?sessionId=刚才的id" -H "Content-Type: application/json" -d '{\"jsonrpc\":\"2.0\",\"id\":1,\"method\":\"initialize\",\"params\":{\"protocolVersion\":\"2024-11-05\",\"capabilities\":{},\"clientInfo\":{\"name\":\"cli\",\"version\":\"1\"}}}'
```
预期：POST 秒回 202 空响应，而**真正的 JSON-RPC 响应出现在终端 A 的流里**——
"请求走 POST、响应走 SSE"这一 MCP/SSE 规范的核心形态，一次看穿。

**实验 2｜门禁开与关（10 分钟走完三件套）**
```powershell
# 只改配置不编译：门禁开、token 配上
java -jar target\aihub-mcp-sse-1.0.0-SNAPSHOT.jar --aihub.mcp.auth.enabled=true --aihub.mcp.auth.token=t123
curl.exe -i http://127.0.0.1:8090/sse                     # → 401 + 那句清晰的 JSON
curl.exe -i -H "Authorization: Bearer t123" http://127.0.0.1:8090/sse   # → 挂住收 endpoint（放行）
curl.exe -i http://127.0.0.1:8090/actuator/health         # → 200（非保护路径不受影响）
# 再验证 fail-fast：
java -jar target\aihub-mcp-sse-1.0.0-SNAPSHOT.jar --aihub.mcp.auth.enabled=true
# → 启动直接失败："通道门禁没有令牌可校验，拒绝启动"
```

**实验 3｜协议热切换（体现 protocol 键的价值）**
```powershell
java -jar target\aihub-mcp-sse-1.0.0-SNAPSHOT.jar --spring.ai.mcp.server.protocol=streamable
```
不重新编译、不加依赖——端点从 `/sse` 变 `/mcp`（streamable-http 模式）。
用 MCP Inspector（`npx @modelcontextprotocol/inspector`）分别连两种协议，客户端配置里选 SSE 或 Streamable 都能通。

**实验 4｜跑门禁单测**
```powershell
cd aihub\aihub-mcp-sse ; mvnd test -Dtest=McpChannelAuthFilterTest
```
7 个用例全绿；改坏一处（比如把 matchesToken 的 isEqual 换成 equals 再故意传错长度）看哪个用例红——体会"用例钉行为"。

## 4. 自测五问

1. 客户端报"连接成功但工具列表为空"，第一查什么？（capabilities.tool 是否 true + AiHubMcpConfiguration 的 ToolCallbackProvider 是否装配——scanBasePackages 有没有指对）
2. 为什么 `/mcp/message` 带 sessionId 查询串也能被门禁拦下？（isProtected 走 `path + "/"` 前缀匹配 + urlPatterns 注册了 `/*`；测试 messageEndpointWithSubPathIsProtected 钉的就是它）
3. 把 server.address 改 0.0.0.0 而不开门禁的后果？（同网段任何人都能调你的工具——工具能读写业务数据，等于裸奔）
4. keep-alive 30s 和 request-timeout 70s 谁管谁？（keep-alive 管**空闲连接**保活；request-timeout 管**单次工具调用**上限，互不相干但都在 SSE 长连接语境下）
5. 想在门禁里加"按 token 区分租户"可行吗？（当前形态一个实例一个租户：token 只解决"谁能连"，租户由 aihub.mcp.api-key 定；要一会话一租户得把 Key 按会话传递——Properties 注释里标了这条演进路径）
