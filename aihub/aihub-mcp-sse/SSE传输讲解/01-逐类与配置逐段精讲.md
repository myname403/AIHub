# 01｜逐类与配置逐段精讲

## 1. pom.xml —— 传输=换一个 starter（4 个依赖讲透）

```xml
<dependency> com.aihub:aihub-mcp-service        <!-- 后厨：@Tool 工具+HTTP 客户端+装配 -->
<dependency> spring-ai-starter-mcp-server-webmvc <!-- ★本模块存在的意义：带 Web 的 MCP 传输 -->
<dependency> spring-boot-starter-actuator        <!-- 健康检查 -->
<dependency> micrometer-registry-prometheus      <!-- 指标暴露给 Prometheus -->
```

三个讲解点：
1. **webmvc starter 自带 spring-boot-starter-web**（注释特意标了）——所以这个进程有 Tomcat、有端口；
   对照 stdio 版引的是不带 web 的 `spring-ai-starter-mcp-server`。**"传输与业务解耦"在 pom 层的体现
   就是这一行依赖之差**；
2. actuator+prometheus 只有 SSE 版配了——因为它是"在线服务"，要被抓指标、要被探活；stdio 是短命 CLI，不需要；
3. `spring-boot-maven-plugin` 指定 `mainClass` 并 `repackage`——打成可执行 fat jar。

## 2. AiHubMcpSseApplication —— 一个参数的学问

```java
@SpringBootApplication(scanBasePackages = "com.aihub.mcp")   // ★不是默认的 com.aihub.mcp.sse！
```

组件扫描默认只扫**启动类所在包及子包**。而工具装配 `AiHubMcpConfiguration` 住在 `com.aihub.mcp.config`
（mcp-service 模块）——不在 `...mcp.sse` 下面。**往上指一层，后厨的 Bean 才能进本进程容器**。
stdio 版的启动类同一写法——两个传输模块"共用后厨"就靠这一行。

## 3. application.yml 逐段精讲（105 行，全键覆盖）

### 3.1 server 段

```yaml
server:
  port: ${MCP_SSE_PORT:8090}          # 8090：避开网关8080/平台8081/AI8082/管理端8849
  address: ${MCP_SSE_ADDRESS:127.0.0.1}  # ★默认只绑回环=只有本机能连
```
`address` 是安全默认值：本机开发零暴露；要跨机给同事/客户端用，改 `0.0.0.0` 之前**必须先开下面的 auth 门禁**
（注释写明了这个顺序：通道有 Bearer 门禁 → 数据边界仍由背后的 X-API-Key 保证，两层各管各的）。

### 3.2 spring.main / 与 stdio 的第一处对照

```yaml
main:
  banner-mode: console   # 保留 banner（这是 Web 服务，stdout 不是协议通道）
```
stdio 版这里是 `"off"`——**同一行配置在两个模块里的相反取值**，正好说明各自 stdout 的身份差异。

### 3.3 spring.ai.mcp.server 段（协议核心，逐键）

| 键 | 值 | 为什么 |
|---|---|---|
| `enabled` | true | 总开关 |
| `annotation-scanner.enabled` | **false** | 我们走 Spring AI 原生 `@Tool`+`ToolCallbackProvider` 路线；不关的话 mcp-annotations 库启动时全类路径找 `@McpTool`，找不到打一条**误导性 WARN**（让人以为工具没注册上）——关掉既省一次扫描又让日志干净 |
| `protocol` | `${MCP_PROTOCOL:sse}` | 三选一：sse(默认) / streamable / stateless。切 streamable-http **零新依赖**（WebMvc 自动配置类就在同一个 starter 里），端点变 `/mcp` |
| `name/version` | aihub/1.0.0 | initialize 握手时上报的服务器身份 |
| `instructions` | 一段中文说明书 | ★这是给**客户端模型**看的系统级提示："用户问有哪些应用/知识库时直接用对应工具，不要凭猜测回答；要基于企业文档回答时先检索再作答"——工具描述管"单个工具怎么用"，instructions 管"这套工具的整体使用策略" |
| `type` | sync | 工具同步执行（对照还有 async 形态） |
| `request-timeout` | 70s | ★必须**大于** `aihub.mcp.timeout`(60s)：否则上游 HTTP 慢查询会先被 MCP 层掐断，日志只剩"MCP 请求超时"指不到真凶——**超时链外层>内层** |
| `keep-alive-interval` | 30s | SSE 是长连接，空闲连接会被中间设备(路由器/NAT)掐；定期 ping 保活 |
| `sse-endpoint` | /sse | 建连端点（GET，返回 event: endpoint） |
| `sse-message-endpoint` | /mcp/message | 消息回传端点（POST，带 sessionId） |
| `capabilities` | tool:true，prompt/resource/completion:false | **按真实能力上报**——写 true 但没实现，客户端就会去调不存在的东西 |
| `*-change-notification` | 三个 false | 我们没有运行时会变的列表，关掉免去无意义的推送通道 |

还有一行重要注释：**本模块不接数据库/注册中心**——它只是"协议适配器"，业务能力全部 HTTP 调 AIHub。

### 3.4 aihub.mcp 段（回调 AIHub 的参数）

```yaml
base-url: http://127.0.0.1:8080   # ★走网关而不是直连 ai-service：鉴权/限流/TraceId 统一在网关生效
api-key: ${AIHUB_API_KEY:}        # 必配！没有它所有工具调用被网关 401
timeout: 60s                      # 上游 HTTP 超时（< request-timeout 70s）
default-app-id / default-top-k: 5 / chunk-max-chars: 800   # 工具层兜底参数（见 mcp-service 讲解）
auth:
  enabled: false                  # 通道门禁开关（默认关=本地零行为变化）
  token: ${AIHUB_MCP_AUTH_TOKEN:}
  # protected-paths: ["/sse", "/mcp/message", "/mcp"]
```

### 3.5 management / logging 段

暴露 health+prometheus（MCP 网关侧工具调用指标可被 Prometheus 抓取、Grafana 展示）；
`com.aihub.mcp: INFO`，注释提醒**别常开 DEBUG**（会把请求体刷进日志）。

## 4. 通道门禁三件套（本模块唯一的"自有代码"）

### 4.1 开关装配 McpChannelAuthConfiguration

```java
@Configuration
@ConditionalOnProperty(prefix="aihub.mcp.auth", name="enabled", havingValue="true")
```
- **enabled=false 时这三个类根本不存在于容器**（不是"存在但放行"）——默认形态零开销；
- **构造器 fail-fast**：`enabled=true` 但 token 没配 → **直接拒绝启动**。注释给了理由：这是部署错误，
  要么"默默全员 401"要么"更糟的全员放行"，都不如炸在启动期；
- `FilterRegistrationBean`：`order=0` 挂最前（赶在 MCP transport 处理前完成门禁）；
  urlPatterns 由 protected-paths 生成 `path/*`——和过滤器内部的判断用**同一份配置**（双保险，改配置只改一处）。

### 4.2 过滤器 McpChannelAuthFilter（三个精妙点）

**① 为什么是 Servlet Filter 而不是拦截器？**
`/sse`、`/mcp/message` 是 **Spring AI MCP 框架注册的端点，不走我们自己的 Controller**——
HandlerInterceptor 挂在 DispatcherServlet→Controller 的链上，根本管不到它们；
Filter 在 DispatcherServlet **之前**，什么端点都能拦。（一段话记住 Servlet 请求链的顺序！）

**② 常量时间比较防时序攻击**
```java
return MessageDigest.isEqual(provided, expected);
```
普通 `String.equals` 逐字节比较、遇不同立即返回——攻击者统计响应耗时能**逐字节试出**正确 token。
`MessageDigest.isEqual` 把两个数组全比完才给结果，耗时与"对了几个字节"无关。

**③ 拒绝要"响而清晰"**
401 + JSON `{"error":"unauthorized","message":"MCP 通道需要鉴权：Authorization: Bearer <...>"}`——
注释点破：让客户端**建连时立刻看到明确原因**，而不是连接挂着、等到工具调用才神秘失败。
（错误设计原则：错误信息是给排障的人写的，不是给协议看的。）

继承 `OncePerRequestFilter`：Servlet 转发/包含场景原生 Filter 可能被触发多次，这个基类保证一次请求只过滤一次。

### 4.3 配置类 McpChannelAuthProperties
`enabled / token / protectedPaths` 三个字段，`@ConfigurationProperties` 绑定（默认 protectedPaths 含三个 MCP 端点）。

## 5. 测试 McpChannelAuthFilterTest（7 用例钉行为）

纯 `MockHttpServletRequest/Response/Chain`，不碰网络。7 个用例就是一张行为合同表：

| 用例 | 钉住的行为 |
|---|---|
| disabledFilterAllowsAllRequests | 开关关=全放行（零行为变化） |
| missingTokenRejectedWith401 / wrongTokenRejectedWith401 | 缺/错 token → 401 |
| nonBearerSchemeRejectedWith401 | `Basic xxx`  scheme 不对也拒（不认非 Bearer） |
| correctTokenPassesThrough | 对的 Bearer → 放行 |
| messageEndpointWithSubPathIsProtected | `/mcp/message?sessionId=` 这类也要拦 |
| unprotectedPathNotAffected | `/actuator/health` 不受影响（门禁只圈 MCP 端点） |

学两点：① 过滤器可以这样脱离容器单测（Mock 三件套）；② 用例命名 `场景+期望` 的格式值得抄。
