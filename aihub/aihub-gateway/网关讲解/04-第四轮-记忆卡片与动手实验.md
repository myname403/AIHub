# 第四轮：记忆卡片与动手实验（拒绝纸上谈兵）

> 目标：① 用口诀+卡片把前三轮钉进长期记忆；② 用 6 个实验在你本机跑着的网关（8080）上**亲手复现**每一个概念。
> 前提：网关、platform 服务在跑（当前你的环境：8080/8081 均 UP，直接用）。
> PowerShell 里请用 `curl.exe`（不是 curl，那是 PowerShell 别名 Invoke-WebRequest，参数不一样）。

## 4.1 六张记忆卡片（正面问题，背面答案，隔天自问自答）

**卡 1｜网关四件事**
正面：网关对每个请求做的四件事，按顺序？
背面：盖邮戳(TraceId) → 查证件(Auth) → 发工牌(注入可信头) → 指路(路由转发)。口诀：**"戳、证、牌、路"**。

**卡 2｜链的三约定**
正面：想往过滤器链上加一站，需要满足什么？
背面：实现 `GlobalFilter` + 注册 `@Component` + 实现 `Ordered` 定顺序（越小越先）。没有任何"总装文件"，链是框架收集排序 Bean 自动攒的。

**卡 3｜放行与掐断**
正面：`chain.filter(exchange)` 不调用会怎样？项目里谁在什么时候不调？
背面：请求不再往下走。AuthGlobalFilter 鉴权失败时不调，而是 `response.writeWith` 直接写 401——"扣下不挥手"。

**卡 4｜先撕再贴**
正面：为什么注入 X-Tenant-Id 前要先 remove？
背面：下游无条件信任该头；先撕掉客户端伪造值再写可信值，把"只有网关能写身份头"变成结构性保证，不依赖后人记得写代码。

**卡 5｜fail-closed**
正面：平台服务挂了，API Key 请求和 JWT 请求命运有何不同？为什么？
背面：Key 全 401（远程核实失败按拒绝处理= fail-closed）；JWT 无影响（本地验签，自包含）。这也是 JWT 的核心优势之一。

**卡 6｜缓存的三件套**
正面：ApiKeyCache 为什么是 60s TTL + 派生键 + AsyncCache？
背面：60s=吊销延迟与远程调用成本的平衡；派生键=明文别在堆里过夜（jmap 一 dump 全泄）；AsyncCache=并发未命中只打一次电话（防击穿）。

## 4.2 一张总图（默写用）

```
                       aihub-gateway :8080（WebFlux/Netty，无数据库）
客户端请求 ──────────▶ ┌────────────────────────────────────────────┐
                      │ CORS预检(框架内置)                          │
                      │ ① TraceIdGlobalFilter   order=MIN_VALUE    │
                      │    有X-Trace-Id沿用，无则新生成              │
                      │    写【请求头+响应头】                      │
                      │ ② AuthGlobalFilter      order=-100         │
                      │    A白名单 /auth/** /actuator/health → 放行 │
                      │    B X-API-Key → Cache→(未命中)Verifier     │
                      │       └─POST /internal/apikey/verify→平台   │
                      │    C 无凭证 → 401"缺少认证令牌"              │
                      │    D Bearer JWT → 本地验签(共享密钥)         │
                      │    通过：remove伪造头 + set可信头            │
                      │    失败：writeWith 401{code,traceId} 链终止  │
                      │ ③ 路由匹配(Path predicates)                 │
                      │ ④ NettyRoutingFilter  lb://服务名→Nacos→转发 │
                      └────────────────────────────────────────────┘
                              │                    │
                    /auth/**,/api/platform/**   /api/ai/**
                              ▼                    ▼
                     platform :8081          ai-service :8082
                （TenantResolveInterceptor 接工牌 → TenantContext）
```

## 4.3 六个动手实验（每个 1~3 分钟，按顺序做）

### 实验 1｜看见邮戳
```powershell
curl.exe -i http://127.0.0.1:8080/actuator/health | Select-String -Pattern "X-Trace-Id","HTTP"
```
**预期**：响应头里出现 `X-Trace-Id: xxxx`。
**证明**：TraceIdGlobalFilter 连白名单路径都会盖戳（它排在一切判断之前）。

### 实验 2｜自定义邮戳被沿用
```powershell
curl.exe -i -H "X-Trace-Id: my-test-123" http://127.0.0.1:8080/actuator/health | Select-String "X-Trace-Id"
```
**预期**：返回的就是 `my-test-123`。
**证明**："有则沿用"逻辑——跨系统链路就是这样串起来的。

### 实验 3｜裸奔请求吃 401
```powershell
curl.exe -i http://127.0.0.1:8080/api/platform/system/user/page
```
**预期**：`HTTP/1.1 401` + 响应体 `{"code":10002,"message":"缺少认证令牌","traceId":"..."}`。
**证明**：① Auth 在白名单判断后拦截；② 401 是网关手写的（格式和 R 一致、带 traceId——实验 1 的戳在这里用上）；③ 请求根本没到 8081。

### 实验 4｜伪造工牌混不进租户
```powershell
curl.exe -i -H "X-Tenant-Id: 1001" -H "X-User-Id: 1" http://127.0.0.1:8080/api/platform/system/user/page
```
**预期**：照样 401"缺少认证令牌"。
**证明**：**光有工牌没用，先要看证件**——身份头只在凭证校验通过后由网关重写，你手动带的同名头连被"信任"的资格都没有（对照卡 4）。

### 实验 5｜假 API Key 的死亡路径
```powershell
curl.exe -i -H "X-API-Key: ak_fake_test" http://127.0.0.1:8080/api/platform/system/user/page
```
**预期**：401，message 是 `API Key 无效、已停用或已过期`。
**证明**：请求走了分支 B → ApiKeyCache 未命中 → ApiKeyVerifier 真的打电话给了平台 → 平台说无效 → Mono.empty → switchIfEmpty 写 401。
**加餐**：连发 10 次，看 platform 服务日志里 `/internal/apikey/verify` 只出现 1 次左右——**第 2 次起命中 60 秒缓存**（"失败也进缓存"的 trade-off 你亲眼见过）。

### 实验 6｜真 JWT 走全程（终极大招）
1. 浏览器打开管理端 `http://localhost:8849`，用 `demo / admin / admin123` 登录；
2. F12 → Network 找任意 `/api/platform/` 请求 → 复制 `Authorization: Bearer eyJ...` 整串；
3. 用真令牌重放实验 3/4：
```powershell
curl.exe -i -H "Authorization: Bearer 把刚才复制的eyJ...贴这里" http://127.0.0.1:8080/api/platform/system/user/page
```
**预期**：`200` + 用户列表 JSON。
4. 再叠加一个伪造头：
```powershell
curl.exe -i -H "Authorization: Bearer eyJ..." -H "X-Tenant-Id: 9999" http://127.0.0.1:8080/api/platform/system/user/page
```
**预期**：依然 200，且返回的还是 **demo 租户（1001）** 的数据，不是 9999 的。
**证明**：令牌的 tenantId 赢了伪造头——remove+set 在真实系统里就是这道闸门（卡 4 的实证）。

## 4.4 费曼检验法（终极验收，讲不出的就是没懂的）

合上所有文档，对着下面 5 个问题各讲 1 分钟（讲给同事/ Rubber duck / 录音回听）：

1. 为什么下游服务不需要再做 JWT 校验？它们靠什么知道"你是谁"？这个信任是怎么建立起来的？
2. 过滤器链的"顺序"写在项目的哪个文件里？（陷阱题：答案是"哪个文件都没写全"，分散在各 Bean 的 getOrder()，由框架汇总）
3. API Key 校验为什么要拆成 Verifier + Cache 两个类？各自去掉会怎样？
4. 网关挂了和平台服务挂了，症状上怎么区分？（网关挂：8080 全拒连；平台挂：/auth 登录也挂、Key 通道 401，但已签发 JWT 的 /api/ai/** 还能跑）
5. 如果产品说"吊销 Key 要立刻生效"，你改哪两个地方？（吊销接口里调 `ApiKeyCache.invalidate`——但注意缓存在网关进程内，平台调不到；正解：网关暴露内部清缓存接口 或 把本地缓存换 Redis 广播失效。能想到"跨进程缓存一致性"这层，说明你真懂了）
