# 第二轮：过滤器链到底怎么串起来的

> 目标：解决你最大的困惑——"链是如何定义的"。
> 核心结论先砸这里：**这个项目里没有任何一行代码"组装"过链。链是框架按"约定"自动攒出来的。**

---

## 2.1 先补三个基础概念（新面孔类速认）

看过滤器代码前，先认识三个会反复出现的类型，不然后面每行都卡：

### ① ServerWebExchange —— "档案袋"

一次 HTTP 交互的上下文，里面装着：**请求 + 响应 + 一个随便放的属性袋**。
链上每一站传的都是同一个 exchange（像接力赛里那个棒子，也是那个"选手档案袋"）。

关键脾气：**它和里面的 request 都是不可变的**——你不能"修改"请求头，只能"基于它造一个改过的副本"：

```java
ServerHttpRequest mutated = exchange.getRequest().mutate()   // mutate=复印
        .headers(h -> h.set("X-Tenant-Id", "1001"))          // 在复印件上改
        .build();
chain.filter(exchange.mutate().request(mutated).build());    // 用新档案袋继续跑
```

记法：**mutate() = 复印机。想改？复印一份改，原件不动。**

### ② GatewayFilterChain —— "剩余的链"

`chain.filter(exchange)` 这个调用的含义是：**"我这站干完了，把档案袋交给下一站"**。

- 调了 = 放行；
- 不调 = 链到此掐断（比如鉴权失败时直接往响应里写 401 然后 return，后面的路由转发根本不会发生）。

记法：**chain.filter() = 交警挥手放行；不挥手 = 扣下。**

### ③ Mono&lt;Void&gt; —— "办完的信号"

filter 方法返回的不是"直接执行"，而是一个"未来会完成"的承诺。
- `chain.filter(exchange)` 返回的 Mono：代表"后面所有站跑完"这件事；
- `response.writeWith(...)` 返回的 Mono：代表"我直接把响应写回客户端，完事"。

第一轮说过 WebFlux 是"一个服务员盯二十桌"，Mono 就是服务员手里的**取餐号**——先给你个号，饭好了再叫你。这一轮你只要会读：`return X` 里的 X 永远是"号"（Mono），不是"饭"（结果本身）。

## 2.2 链是怎么"自动攒出来"的（本文件的灵魂）

三条约定，凑齐就上牌桌：

| 约定 | 谁满足 | 结果 |
|---|---|---|
| 1. 实现 `GlobalFilter` 接口 | 两个 Filter 类都实现了 | 框架承认你是"链上的一站" |
| 2. 注册成 Spring Bean（`@Component`） | 两个类都标了 | 框架启动时**扫描容器，把所有 GlobalFilter 类型的 Bean 全收集** |
| 3. 实现 `Ordered`，`getOrder()` 给个数字 | TraceId 给 `Integer.MIN_VALUE`，Auth 给 `-100` | **数字越小越先执行**，框架照此排序 |

所以"链的定义"分散在三个地方，没有总装图：

```
链 = 按 getOrder() 排序( 容器里所有 GlobalFilter Bean ) + 框架内置的那几站
```

框架内置的站你看不见源码，但要知道两个关键的：

- 链的**最前面**还有一堆框架自己的活（跨域处理、路由匹配等）；
- 链的**最后**是 `NettyRoutingFilter`（order 极大，垫底），它才是真正把请求 HTTP 转发给下游服务的那一站。

### order 数字为什么这么选？（数字是"语义"不是"随便填"）

```
Integer.MIN_VALUE (-2147483648)   TraceIdGlobalFilter   "我必须绝对第一"
-100                              AuthGlobalFilter      "业务过滤器里我要靠前，但让邮戳先盖"
（框架内置，几千几万）              路由匹配、转发          "最后干活"
```

- TraceId 必须绝对第一：不然鉴权失败的 401 响应里就没有 traceId 了，而 401 恰恰最需要 traceId 排查；
- Auth 要 -100：在**所有**要转发的逻辑之前——任何请求没查完证件，都不许靠近路由器。

记法：**"先盖邮戳再查证，查完才许上路"**。

## 2.3 "前段/后段"：一条链其实跑了两趟

进阶但重要：`chain.filter(exchange)` 这一行是**分界线**——

```java
public Mono<Void> filter(ServerWebExchange exchange, GatewayFilterChain chain) {
    // ===== 请求下行段（去程：客户端 → 下游）=====
    // 在这里改请求头，下游收到的就是改过的
    return chain.filter(exchange)
        .then(Mono.fromRunnable(() -> {
            // ===== 响应上行段（回程：下游 → 客户端）=====
            // 在这里改响应头、打耗时日志
        }));
}
```

类比高速收费站：**去程**查你证件（下行段），放行后你跑完全程，**回程**（响应回来时）还能再收一次费/盖个出站章（上行段）。

本项目两个过滤器都只用了"去程"（外加 TraceId 顺手把响应头也写了）。但**路由转发的本质**要理解：真正把请求发给 8081、等响应回来，发生在 `chain.filter()` 执行**期间**——它不是"交给下一站就完事"，而是"下一站连同它后面的整条链+真实网络调用"都在这一个调用里异步完成。

## 2.4 完整链路图（把第一轮 5 站升级成 8 站）

以 `GET /api/platform/system/user/page`（带 JWT）为例：

```
①  Netty 收到 TCP 请求，WebFlux 组装出 ServerWebExchange
②  框架内置站：CORS 预检处理（跨域 OPTIONS 在这里就被拦下回复，不进业务链）
③  TraceIdGlobalFilter（order=MIN_VALUE）
     生成/沿用 traceId → 写请求头 X-Trace-Id + 写响应头 X-Trace-Id
     chain.filter() ────────────────┐ 放行
④  AuthGlobalFilter（order=-100）   │
     白名单？否 → 有 X-API-Key？无 → 有 Bearer JWT？有
     验签成功 → 撕掉伪造的 X-Tenant-Id/X-User-Id → 写入 tenantId=1001, userId=1
     chain.filter() ────────────────┐ 放行
     （任何一步失败 → writeWith 写 401，链终止，⑤⑥⑦ 全部不发生）
⑤  框架内置站：路由匹配
     Path=/api/platform/** 命中 aihub-platform 这条 Route
⑥  NettyRoutingFilter（链尾）
     lb://aihub-platform-service → 问 Nacos 要实例列表 → 挑一个 → 真实 HTTP 转发到 :8081
⑦  下游响应原路回来（回程段）
⑧  Netty 写回客户端（响应头里带 ② ③ 期间写入的 X-Trace-Id）
```

**默写测试**：合上文档，从 ① 复述到 ⑧，哪一步卡住回到 2.2 重看。

## 2.5 GlobalFilter 和"路由级 Filter"的区别（知道有这回事就行）

SCG 有两种过滤器：

| | GlobalFilter（本项目用的） | 路由级 GatewayFilter |
|---|---|---|
| 作用范围 | 所有路由都执行 | 只挂在某一条 route 的 `filters:` 配置下 |
| 定义方式 | Java 类 + @Component | yml 里配置，如 `- AddRequestHeader=X-From, gw` |
| 本项目 | 2 个全局的 | 没配（routes 里 filters 是空的） |

所以你在 application.yml 的 routes 下看不到 filters 配置是正常的——本项目所有"自定义关卡"都走 Java 全局过滤器。

1. 想往链上加第三个过滤器"请求耗时统计"，且要在鉴权**之后**（只给通过鉴权的请求计时），你需要写哪三样东西？（新类 implements GlobalFilter, Ordered + @Component + getOrder() 返回比 -100 大的数，如 -50）
2. `chain.filter(exchange)` 不调用会发生什么？（请求不再往下走；如果也没写响应，客户端拿到空响应/挂起——所以拒绝场景必须像 AuthGlobalFilter 那样自己 writeWith）
3. 为什么 exchange 里的 request 要 mutate 而不能直接 set？（不可变设计——响应式下多个操作可能并发持有同一对象，改了会互相踩；副本模式让"改造请求"变成显式、可追溯的动作）
