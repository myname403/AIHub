## 1.1 为什么需要网关？（没有它会怎样）

想象没有网关的世界，前端要直面三个服务：

```
前端 → 127.0.0.1:8081（平台服务）
前端 → 127.0.0.1:8082（AI 服务）
前端 → 还有一堆以后拆出来的服务...
```

会疼的地方：

| 痛点 | 具体表现 |
|---|---|
| 前端要背地址 | 每个服务的 IP:端口都写死在前端，服务一挪全站崩 |
| 鉴权各写各的 | 8081 写一套 JWT 校验，8082 再写一套，漏一个就是一个洞 |
| 没有统一闸口 | 限流、熔断、跨域、日志追踪……每个服务都要重复建设 |

网关的解法：**所有流量只进一个门（8080），门内统一办完"公共手续"，再按 URL 分流**。

```
                 ┌── /auth/**、/api/platform/** ──→ 平台服务 :8081
前端/第三方 ──→ 网关 :8080 ──┤
   （唯一入口）  │  盖邮戳→查证件→发工牌→指路
                 └── /api/ai/** ────────────────→ AI 服务 :8082
```

一句话记忆：**网关是"流量海关"——所有进出口货物统一在这里报关、贴标签、放行，内部的仓库不重复安检。**

## 1.2 模块文件地图：5 个类 + 2 个配置

打开 `aihub-gateway/src/main/`，全部家当就这些：

```
java/com/aihub/gateway/
├── GatewayApplication.java          ①启动类——保安亭开门营业
├── filter/
│   ├── TraceIdGlobalFilter.java     ②盖邮戳——发全链路追踪 ID
│   └── AuthGlobalFilter.java        ③查证件+发工牌——★全模块最核心的类
└── apikey/
    ├── ApiKeyVerifier.java          ④打电话核实——远程问平台"这把 Key 有效吗"
    └── ApiKeyCache.java             ⑤小本本——核实结果记 60 秒，别老打电话

resources/
├── application.yml                  ⑥指路牌——路由表/CORS/限流（Nacos 模式）
└── application-standalone.yml       ⑦备用指路牌——没有 Nacos 时直连 IP
```

每个用一句大白话定位（先背这 7 句，后面两轮都挂在这上面）：

1. **GatewayApplication**：没什么逻辑，就是"开机"。特殊之处是它跑的是**响应式世界**（WebFlux），不是下游那种传统 MVC。
2. **TraceIdGlobalFilter**：每个请求进来第一件事就是给它盖个"邮戳"（`X-Trace-Id`），请求头、响应头各盖一个——这样前端 F12 能看到、下游日志里也能搜到，一次客诉可以串起全链路日志。
3. **AuthGlobalFilter**：保安本安。看你的证件（JWT 或 API Key），证件有效就把"租户编号"写进工牌（`X-Tenant-Id` 请求头）放行；证件有问题直接拒（401）；同时**撕掉你自己乱贴的工牌**（防止冒充别的租户）。
4. **ApiKeyVerifier**：API Key 这种证件上没写租户是谁，得"打电话回平台问"——调平台的 `/internal/apikey/verify` 接口反查。
5. **ApiKeyCache**：电话费太贵（每次请求都远程问一遍太慢），拿个小本本把问过的结果记 60 秒。
6. **application.yml**：写着"什么 URL 去哪个服务"（路由表），以及跨域放行、Sentinel 限流规则从哪拉。
7. **application-standalone.yml**：单机降级版路由表——不用 Nacos 时，服务地址写死成 `127.0.0.1:8081/8082`。

## 1.3 一个请求的"极简旅程"（先记 5 站，第二轮再展开）

以"前端带着登录拿到的 JWT，去查用户列表 `GET /api/platform/system/user/page`"为例：

```
① 进 8080 大门
② 盖邮戳      （TraceIdGlobalFilter：生成/沿用 X-Trace-Id）
③ 查证件      （AuthGlobalFilter：验 JWT 签名，解析出 tenantId=1001, userId=1）
④ 发工牌      （撕掉伪造的 X-Tenant-Id，写入从证件解析出的真值）
⑤ 指路转发    （路由匹配 /api/platform/** → 发给平台服务 8081）
```

反例路径也要记：**③ 查证件失败 → 当场 401 打发走，④⑤ 根本不会发生**。
链是"随时可以掐断"的，这就是过滤器链的威力（第二轮细讲）。

## 1.4 为什么网关里全是 Mono、Flux，跟下游服务写法完全不一样？

第一轮只需要建立这个认知，细节第三轮讲：

- 下游 platform/ai 服务是 **MVC 模型**：一个请求占一个线程，请求没处理完线程就干等；
- 网关是 **WebFlux 响应式模型**：网关要同时挂住成千上万条连接（尤其 SSE 长连接），如果一条连接占一个线程，几千人就把线程池耗死了。响应式用**少量线程 + 回调**：你的请求在等下游时，线程去服务别人，你的结果回来了再叫你。

类比：**MVC 餐厅 = 一个服务员盯一桌，客人慢慢点菜他也只能站着等；WebFlux 餐厅 = 一个服务员同时盯二十桌，谁举手他去哪桌**。

代价就是你看到的：代码里全是 `Mono`/`Flux`，而且**绝对不能在网关里写阻塞代码**（同步 JDBC、Thread.sleep），一阻塞等于把服务员钉死在一桌，其他二十桌全没人管。

## 1.5 第一轮自测（能秒答就进第二轮）

1. 网关自己有没有数据库连接？它需要吗？（没有/不需要，它是"海关"不是"仓库"）
2. 五个类里，哪两个是"一对搭档"，只在 API Key 通道才会被用到？（ApiKeyVerifier + ApiKeyCache）
3. 前端 F12 里看到的 `X-Trace-Id` 响应头是谁写进去的？（TraceIdGlobalFilter）
4. 为什么下游服务敢无条件相信 `X-Tenant-Id` 请求头？（因为这个头只有网关写得进来，客户端带进来的同名头会被网关撕掉——第三轮细讲这个动作）
