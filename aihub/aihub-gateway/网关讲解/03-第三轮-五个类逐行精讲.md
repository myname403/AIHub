# 第三轮：五个类逐行精讲（每行代码"为什么"）

> 阅读方式：左手开源码，右手开本文档，对照着走。每个类按

## 3.1 GatewayApplication —— 启动类

### 职责一句话
开机。顺便通过两个注解宣告"我是网关、我注册到 Nacos"。

### 走查
```java
@EnableDiscoveryClient     // 注册到 Nacos + 能按服务名发现别人
@SpringBootApplication     // 配置类 + 自动装配 + 组件扫描（三合一）
public class GatewayApplication {
    public static void main(String[] args) {
        SpringApplication.run(GatewayApplication.class, args);
    }
}
```

### 为什么这么写
- `@SpringBootApplication` 里的**组件扫描以"启动类所在包"为根**。它在 `com.aihub.gateway`，所以子包 `filter`、`apikey` 里所有 `@Component` 都能被扫到；
- 自动装配探测到 classpath 有 webflux + spring-cloud-gateway，就自动配好 Netty 服务器、路由、过滤器机制——**你从没写过一行"new 一个过滤器链"的代码，全是它装的**（呼应第二轮 2.2）。

### 不这么写会怎样
把启动类挪到 `com.aihub`（比包根还高）没事，但挪到 `com.aihub.gateway.filter`（低了）——`apikey` 包扫不到，启动直接报 `ApiKeyCache` 这个 Bean 找不到注入。

## 3.2 TraceIdGlobalFilter —— 盖邮戳（60 行的类，5 分钟吃透）

### 职责一句话
给每个请求确定一个全链路唯一的 `traceId`，写进**下游请求头**和**浏览器响应头**。

### 走查（核心 15 行）
```java
public Mono<Void> filter(ServerWebExchange exchange, GatewayFilterChain chain) {
    ServerHttpRequest request = exchange.getRequest();
    // ① 有则沿用，无则新生成 —— 保证"一次业务一个 ID"
    String incoming = request.getHeaders().getFirst(TraceContext.HEADER);
    String traceId = incoming == null || incoming.isBlank()
            ? TraceContext.newTraceId() : incoming;

    // ② 写进转发给下游的请求头（复印机改造，第二轮学的）
    ServerHttpRequest mutated = request.mutate()
            .header(TraceContext.HEADER, traceId)
            .build();
    // ③ 写进返回给浏览器的响应头（response 可直接 set）
    exchange.getResponse().getHeaders().set(TraceContext.HEADER, traceId);

    // ④ 放行，交给下一站（Auth）
    return chain.filter(exchange.mutate().request(mutated).build());
}
public int getOrder() { return Ordered.HIGHEST_PRECEDENCE; }  // ⑤ 绝对第一
```

### 为什么这么写（三个点）
1. **"有则沿用"**：如果调用方（比如另一个系统的网关）已经带了 `X-Trace-Id`，说明这是一条跨系统大链路的延续，换新 ID 就断链了；
2. **写响应头**是给"人"用的：产品反馈"我点了按钮没反应"，让他 F12 把 `X-Trace-Id` 抄过来，你全链路日志一搜一个准；
3. **order = MIN_VALUE**：它必须比 Auth 早。Auth 拒绝请求时，响应头里得已经有 traceId（`unauthorized()` 方法里真的去读了响应头的 traceId 拼进 401 的 JSON——两个类的呼应）。

### 不这么写会怎样
- 把它删了：下游拿不到 X-Trace-Id，日志 pattern 里的 `[%X{traceId:--}]` 永远是 `--`，排障两眼一抹黑；
- order 改成比 -100 大：401 响应没有 traceId 也没有关系？——有关系，`unauthorized()` 里 `tracePart` 会拼成空串，前端报错时你查不到任何日志线索。

### 接力棒交接（面试高频）
网关（WebFlux 世界）用 `GlobalFilter` 盖戳；下游（Servlet 世界）由 common 模块的 `TraceIdInterceptor` 接戳、塞进 **MDC**（日志线程上下文），于是下游每一行日志自动带 `[traceId]`。**同一个逻辑，两种载体**——因为 WebFlux 根本没有 Servlet 拦截器那套东西。

## 3.3 AuthGlobalFilter —— ★全模块灵魂（值得花 40 分钟）

### 职责一句话
唯一鉴权关卡：验 JWT / API Key，把可信身份写进请求头；撕掉一切客户端自己伪造的身份头。

### 3.3.1 主方法的决策树（filter()，20 行）

```java
String path = request.getURI().getPath();
if (isPublicPath(path)) return chain.filter(exchange);        // 分支A：白名单
                                                                       // /auth/**（登录注册）
                                                                       // /actuator/health（探活）
String apiKey = request.getHeaders().getFirst("X-API-Key");
if (apiKey != null && !apiKey.isBlank())
    return authenticateByApiKey(exchange, chain, apiKey);     // 分支B：机器通道
String token = resolveToken(request);                          // 读 Authorization: Bearer xxx
if (token == null) return unauthorized(exchange, "缺少认证令牌"); // 分支C：裸奔→401
return authenticateByJwt(exchange, chain, token);              // 分支D：人用通道
```

背下这个 **A白名单 → B密钥 → C裸奔 → D令牌** 四分支，整个类就一张图。

为什么 API Key 优先判断？两条通道都有各自的固定请求头，先查哪个都行，但**先查 API Key 是"高频机器流量快速通道"**的常见写法，且 Key 校验是异步的（flatMap 链），放前面不影响 TraceId 的同步逻辑。

### 3.3.2 分支 D：JWT 通道（authenticateByJwt）

```java
Claims claims = Jwts.parser()
        .verifyWith(Keys.hmacShaKeyFor(secretKey))   // 用共享密钥验签
        .build().parseSignedClaims(token).getPayload();
tenantId = claims.get("tenantId", ...);              // 身份从"令牌里"取
userId   = claims.get("userId", ...);                // 绝不从"参数里"取！
```

- **验签原理一句话**：平台签发 JWT 时用密钥 `aihub.security.jwt-secret` 对内容做了 HMAC 签名；网关用**同一个密钥**重算签名，对不上就是伪造/篡改。所以 JWT 内容虽然 Base64 肉眼可读，但改一个字符签名就废——**防篡改不防偷看，别在 payload 放敏感数据**；
- `String.valueOf(null)` 会产生字符串 `"null"` 的坑，代码里专门挡了一枪（`"null".equals(tenantId)` 也拒绝）——读这种小防御最能学严谨；
- **全程零远程调用**：JWT 是自包含证件，验签纯本地算术。这就是"用 JWT 的系统网关不需要问登录服务你是谁"的原因。

然后是**本类最核心的 4 行**（两条通道殊途同归都要执行）：

```java
headers.remove(TenantContext.HEADER_TENANT);  // ① 撕掉客户端自己带的 X-Tenant-Id
headers.remove(TenantContext.HEADER_USER);    // ② 撕掉 X-User-Id
headers.set(TenantContext.HEADER_TENANT, tenantId); // ③ 写入从证件解析的可信值
headers.set(TenantContext.HEADER_USER, userId);     // ④
```

**为什么必须先 remove 再 set？**（第三轮最重要的面试题）
下游服务的 `TenantResolveInterceptor` **无条件信任**这两个头（它不知道也不该知道外面发生过什么）。如果攻击者在请求里自己塞一个 `X-Tenant-Id: 1002`，而网关只 set 不 remove——某些"set 没执行到"的路径（或未来有人改了逻辑加了提前放行分支）就会让假头漏下去，**别人的租户数据就裸奔了**。先撕再贴，把"下游信任的头只有网关能写"变成一条**不依赖任何人记得写代码**的结构性保证。

（还记得吗——第一轮自测题 4 埋的就是这个伏笔。）

### 3.3.3 分支 B：API Key 通道（authenticateByApiKey）

```java
return apiKeyCache.verify(apiKey)                       // 异步问"这 Key 是谁的"
    .flatMap(principal -> {                             // 查到了 → 发工牌
        ServerHttpRequest mutated = exchange.getRequest().mutate()
            .headers(headers -> {
                headers.remove(...); headers.remove(...);
                headers.set(HEADER_TENANT, principal.tenantId());
                // 注意：没有 set USER！
            }).build();
        return chain.filter(exchange.mutate().request(mutated).build());
    })
    .switchIfEmpty(Mono.defer(() -> unauthorized(exchange, "API Key 无效、已停用或已过期")));
```

三个细节：
1. **API Key 不注入 userId**——Key 代表"某个系统"，不代表"某个人"。下游若要求"必须是登录用户"的操作，拿 Key 通道就是做不了（能力边界由身份类型天然决定）；
2. `verify()` 的返回约定：**有值=有效，Mono.empty()=无效**。所以拒绝逻辑挂在 `switchIfEmpty` 上——读响应式代码先找"空值语义"；
3. `Mono.defer(...)`：不包 defer 的话，`unauthorized(exchange,...)` 会在**组装链**时就执行（写响应头的动作提前了），包 defer 让"真正空了才去写 401"。这是响应式新手最容易踩的"立即执行 vs 延迟执行"坑。

### 3.3.4 拒绝出口（unauthorized）——为什么手写 JSON 字符串

```java
String body = String.format("{\"code\":10002,\"message\":\"%s\"%s}", message, tracePart);
return exchange.getResponse().writeWith(Mono.just(
        exchange.getResponse().bufferFactory().wrap(body.getBytes(UTF_8))));
```

- 网关是 WebFlux，common 模块那套 `@RestControllerAdvice + GlobalExceptionHandler` 是 **Servlet/MVC 体系**的，这里根本加载不了——想返回统一格式只能自己 `writeWith` 写字节；
- 但**格式仍与 R 对齐**（code/message/traceId），这样前端一套拦截器就能同时处理"网关拒绝"和"业务异常"（对应你们"前端统一处理登录过期"的实践——401 就是从网关这里发出的）；
- `writeWith` 返回后**不再调 chain.filter()**——第二轮说的"扣下不挥手"，请求到此为止。

### 3.3.5 构造器里的密钥从哪来

```java
public AuthGlobalFilter(@Value("${aihub.security.jwt-secret}") String jwtSecret, ...)
```

配置在 application.yml：`jwt-secret: ${AIHUB_JWT_SECRET:aihub-default-dev-secret...}`。
**和平台服务的 `aihub.security.jwt-secret` 必须一字不差**（都默认从 Nacos 的 aihub-common.yaml 共享）——两个服务各配各的、配歪了，症状是"登录成功但所有接口 401"，新人杀手。

## 3.4 ApiKeyVerifier —— 打电话核实（95 行）

### 职责一句话
把 Key 明文 POST 给平台服务的 `/internal/apikey/verify`，换回"这把 Key 属于哪个租户"。

### 为什么网关不自己连库查？
微服务边界铁律：**网关没有也不该有平台库的密码**。跨服务拿数据只有两条路——对方给的接口（本项目选了这条），或者消息。`/internal/**` 前缀的接口只在内网暴露（网关白名单也不放行 /internal，外部进不来）。

### 为什么传明文而不是传哈希？
算哈希需要 HMAC 密钥 → 密钥就得配到网关一份 → **多一个服务持密 = 多一个泄露面**。明文只走内网，让"持密者"（平台）自己算自己比。安全设计里这叫"密钥收敛"。

### 走查 WebClient 链（每段都标了序号，背这个结构）

```java
webClient.post()                          // ① 发 POST
    .uri("/internal/apikey/verify")       // ② baseUrl+uri
    .bodyValue(new VerifyRequest(plainKey)) // ③ record 自动序列化 JSON
    .retrieve()                           // ④ 准备收响应
    .bodyToMono(VerifyResponse.class)     // ⑤ JSON→对象（异步，结果是 Mono）
    .timeout(timeout)                     // ⑥ 2 秒不回来 → TimeoutException
    .flatMap(resp -> {...})               // ⑦ 业务码非 0 / data 为 null → empty
    .onErrorResume(e -> Mono.empty());    // ⑧ 任何异常 → empty（并打 WARN）
```

**空值语义再次出现**：`Mono.empty()` = "校验不通过"。调用方 AuthGlobalFilter 的 switchIfEmpty 就是接这里的。

### 最重要的设计决定：fail-closed（⑧）

平台服务挂了、超时了，怎么办？两个选择：
- fail-open（出错就放行）：平台一抖，鉴权裸奔——灾难；
- **fail-closed（出错就拒绝）**：平台一抖，API Key 流量全 401——故障，但不安全事故。

代码选了后者，且注释写明了理由。**"不确定时宁可拒绝"是所有鉴权组件的默认姿势**。

### baseUrl 里的 `http://aihub-platform-service` 是什么鬼地址？
不是 URL 是**服务名**。WebClient 配合 loadbalancer 会去 Nacos 查 `aihub-platform-service` 的实例列表再替换成真实 IP。这也解释了为什么 `application-standalone.yml`（无 Nacos）模式下这个 Key 校验会失败——服务名解析不了。单机模式没 Key 流量，所以可接受。

## 3.5 ApiKeyCache —— 小本本（110 行）

### 职责一句话
给"打电话核实"套一层 60 秒本地缓存，把每个请求一次远程调用摊薄成每分钟一次。

### 三个设计点，每个都有"为什么"

**① TTL = 60 秒：延迟与吊销的平衡**
- 缓存久了：Key 在平台被吊销，网关还继续放行——每个 Key 的"死亡延迟"最多 60 秒；
- 缓存短了：省不了几次远程调用。
- 60s 是拍出来的合理值，且给了后悔药：`invalidate(plainKey)` 吊销时定点清除、`invalidateAll()` 全清应急。

**② 缓存键不用 Key 明文**
```java
private String cacheKeyOf(String plainKey) {
    return Integer.toHexString(plainKey.hashCode()) + ":" + plainKey.length();
}
```
缓存里可能同时躺着几百把活跃 Key。若键=明文，一次 `jmap` 堆转储（运维排查内存时随手就干的事）就把它们**全部**泄了。派生键（hash+长度）只用于本地 Map 寻址、不做安全判定，所以 JDK hashCode 就够——注释里特意强调"这不是密码学用途"，防止读者把它和平台侧真正的 `ApiKeyCodec.hash`（HMAC 存储哈希）搞混。**同一个项目里两种'哈希'，用途完全不同，这是很容易面倒的细节。**

**③ AsyncCache 防击穿**
1 万个并发同时缓存未命中，`AsyncCache` 保证只有**一个**线程真去打电话，其余 9999 个共享同一个 `CompletableFuture`。如果用普通 Map+判断，1 万个线程全会拨出去——平台服务瞬间被自家网关打挂（缓存击穿的教科书案例）。

### 一个诚实的 trade-off（注释自己承认）
"校验失败"的结果也会进缓存 60 秒。副作用：**平台服务抖动期间的失败，可能被误缓存成"这把 Key 无效"60 秒**。作者的取舍写在注释里：接受，应急用 invalidateAll()。读源码读到这种"自曝其短"的注释，值得学——**好的工程注释不是证明一切完美，而是标Known Issue 和逃生门**。

（对：第三轮 3.3.3 里 `defaultIfEmpty(Optional.empty())` 那行就是"失败也进缓存"的实现处，两处注释互相印证。）

## 3.6 配置双文件对照（10 分钟收尾）

| | application.yml（Nacos 模式） | application-standalone.yml（单机模式） |
|---|---|---|
| 路由 uri | `lb://aihub-platform-service`（服务名+负载均衡） | `http://127.0.0.1:8081`（写死 IP） |
| Nacos 注册/配置 | 开（还从 Nacos 拉热更配置和流控规则） | 全关 |
| 用法 | 正常开发 | 没装 Docker/Nacos 的同学自救 |

**对比读这两个文件，你才算真懂 `lb://` 替你干了什么**：它把"地址"变成了"名字"，地址由注册中心在每次调用时动态给出——服务扩容、重启换 IP，路由表一个字都不用改。

## 3.7 第三轮自测（追问链，能全答上就毕业）

1. 攻击者带着自己签的 JWT 来（内容随便编，反正 tenantId 我写 1002）——哪一行代码挡住的？（`verifyWith(...)` 验签：没有你的密钥签不出合法签名，parseSignedClaims 抛异常 → 401）
2. 攻击者不带 JWT，直接带 `X-Tenant-Id: 1002` 呢？（filter 主方法：无凭证 → "缺少认证令牌" 401；就算走白名单路径，remove 也保证该头不会被下游当可信值用）
3. 平台服务重启的 10 秒里，API Key 请求会怎样？JWT 请求会怎样？（Key 全 401（fail-closed + 超时 2s）；JWT 毫无影响（本地验签不依赖平台活着）——这就是"自包含令牌"的含金量）
4. 为什么吊销 Key 后最多还有 60 秒窗口？哪行代码能立刻关掉窗口？（TTL；`ApiKeyCache.invalidate(plainKey)`，或平台侧吊销接口联动调网关清缓存——本项目目前靠 TTL + 手动 invalidate 的口子）
