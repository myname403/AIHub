# 02｜记忆卡片与动手实验

## 1. 总口诀

**"一圣两杂三关：stdout 是圣殿，stderr/文件是杂物，banner、web、级别三把关"**

| 口诀 | 含义 |
|---|---|
| 一圣 | stdout 只准走 JSON-RPC |
| 两杂 | stderr（实时诊断）+ 临时目录文件（事后排查） |
| 三关 | banner-mode off / WebApplicationType.NONE / root=WARN |

## 2. 六张卡片

**卡 1｜stdio 版和宿主谁说了算？** 宿主。fork 进程、喂 stdin、关管道终止——stdio 进程是"被动打工"的短命 CLI；所以 `registerShutdownHook` 不主动 close。
**卡 2｜stdio 总开关是哪个键？** `spring.ai.mcp.server.stdio: true`。缺了它框架按"有 HTTP 端点"那套装配——**没有这个 true 就没有 stdio 传输**（McpServerStdioDisabledCondition 判定）。
**卡 3｜凭据怎么进来？** 只有环境变量一条路（宿主配置里的 `env` 块注入 AIHUB_API_KEY/AIHUB_BASE_URL）——没命令行、没 HTTP 头、没配置中心。
**卡 4｜为什么 jar 名要 finalName 固定？** 宿主配置写死路径 `java -jar .../aihub-mcp-stdio.jar`，带版本号=每次升级改一遍客户端配置。
**卡 5｜classpath 没 Tomcat 为什么还写 NONE？** 防的不是现在，是**将来某个同事加依赖**——Spring Boot 探测到 servlet 会"安静地"起 Web 模式，stdin 永远没人理，症状诡异。显式 NONE 把架构决定钉成代码。
**卡 6｜stderr 就绝对安全吗？** 不是——宿主给的 stderr 缓冲小，INFO 刷太猛会**写满管道阻塞进程**，所以 root 降到 WARN，只留自己包 INFO + 文件全量。

## 3. 动手实验（三个都由浅入深）

**实验 1｜手工当一回"Claude Desktop"**
```powershell
# 先打包（在 aihub 根目录）
mvnd -pl aihub-mcp-stdio -am package -DskipTests
# 一行 initialize 喂进去（PowerShell 版）
'{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2024-11-05","capabilities":{},"clientInfo":{"name":"cli","version":"1"}}}' | java -jar aihub-mcp-stdio\target\aihub-mcp-stdio.jar
```
预期：stdout 吐出**恰好一行**合法 JSON-RPC（capabilities 响应），此外**零杂质**——
banner 没出现、INFO 日志没出现（去 `%TEMP%\aihub-mcp-stdio\aihub-mcp-stdio.log` 能看到它们改道了）。
进阶：把 `tools/list` 请求再喂进去（要先发 initialized notification），能看到四个工具+完整说明书。

**实验 2｜亲手复现"一连上就崩"（本模块最值钱的实验）**
```powershell
java -jar aihub-mcp-stdio\target\aihub-mcp-stdio.jar --spring.main.banner-mode=console 2>$null
```
（同一条 initialize 管道命令再加这个参数再跑）
预期：stdout 第一坨变成 Spring 的 ASCII banner 图 → 把管道另一端换成能观察解析错误的客户端（或肉眼比对），
**第一帧不再是合法 JSON**——这就是注释里"一连上就崩，报错毫无指向性"的成因现场。玩完记住：banner-mode off 不是洁癖，是生存条件。

**实验 3｜验证"NONE 防手滑"**
```powershell
# 临时把 stdio 模块的 core starter 换成 webmvc 版（或随便加个 spring-boot-starter-web 依赖）
# 不启动类不加 NONE 会怎样？——本地跑：
'{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2024-11-05","capabilities":{},"clientInfo":{"name":"c","version":"1"}}}' | java -jar ...（带 web 依赖的构建）
```
预期（演示性推演，做完可回退）：加了 web 依赖后**当前代码依然正常**——因为启动类里那句
`setWebApplicationType(NONE)` 在兜底；把那句注释掉再跑，进程会去起 Tomcat 等 HTTP，stdin 石沉大海。
**这个 A/B 就是卡 5 的实验证明。**

**实验 4｜接上真宿主（可选，装了 Claude Desktop/任意 MCP 客户端）**
```json
"aihub": {
  "command": "java",
  "args": ["-jar", "E:/微服务/javaAI/javaai/aihub/aihub-mcp-stdio/target/aihub-mcp-stdio.jar"],
  "env": { "AIHUB_API_KEY": "ak_你的key", "AIHUB_BASE_URL": "http://127.0.0.1:8080" }
}
```
对宿主说"列出 AIHub 的应用"→ 应看到它调 `aihub_list_applications` 并复述结果。
前提：网关 8080 在跑、Key 有效（网关讲解里 API Key 通道全链路会一起工作）。

## 4. 自测五问

1. stdio 进程里 System.out.println("debug") 为什么是"投毒"？（直接混进 JSON-RPC 流，客户端解析失败）
2. 出问题去哪看日志？（`%TEMP%\aihub-mcp-stdio\aihub-mcp-stdio.log`——stderr 可能被宿主吞，文件才是排查主力）
3. 两个传输模块的 yml 哪些部分一模一样、哪些不同？为什么？（server 语义段相同=后厨共用；传输段不同=sse 有端点/keep-alive/门禁，stdio 有 stdio:true/banner off/无 web）
4. 宿主把 stdio 进程杀了，AIHub 侧有感知吗？（管道关闭→MCP 框架结束会话；进行中的上游 HTTP 调用由其自身超时收尾）
5. 为什么 stdio 版不做通道门禁？（本机进程对进程管道，不存在网络暴露面；安全边界=宿主自身的进程权限）
