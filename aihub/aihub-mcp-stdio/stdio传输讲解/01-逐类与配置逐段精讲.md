# 01｜逐类与配置逐段精讲

> 主线：抓住"**stdout = JSON-RPC 协议通道**"这一条，其余全是一环扣一环的推论。

## 1. pom.xml —— 依赖最小化的样板

```xml
<dependency> com.aihub:aihub-mcp-service          <!-- 后厨（传递引入其最小依赖） -->
<dependency> spring-ai-starter-mcp-server          <!-- ★core 版：无 web 的 stdio 传输 -->
<dependency> spring-boot-starter-test (test)
```
对比 sse 版：这里引的是 **不带 `-webmvc` 后缀** 的 core starter——**它不会传递 spring-boot-starter-web**，
所以本进程 classpath 上压根没有 Servlet 容器。这是"依赖最小化"的落地：
> 引错 starter（手滑加了 -webmvc）→ 凭空多出整个 Tomcat → 见第 2 节的"防御"。

`build` 段还有个细节：`<finalName>aihub-mcp-stdio</finalName>`——把 jar 名固定成不带版本号，
因为宿主进程配置里写的是**死路径** `java -jar .../aihub-mcp-stdio.jar`，
带 SNAPSHOT 版本号的话每次升版本都得改客户端配置。这是个容易被忽略的对接友好度设计。

## 2. AiHubMcpStdioApplication —— 29 行，两处关键

```java
@SpringBootApplication(scanBasePackages = "com.aihub.mcp")   // ① 往上扫一层捞后厨（同 sse 版）
public class AiHubMcpStdioApplication {
    public static void main(String[] args) {
        SpringApplication application = new SpringApplication(AiHubMcpStdioApplication.class);
        application.setWebApplicationType(WebApplicationType.NONE);   // ② 显式声明无 web
        ConfigurableApplicationContext context = application.run(args);
        context.registerShutdownHook();   // ③ 不主动 close，交给宿主
    }
}
```

**② 为什么 classpath 已经没有 servlet 了，还要显式写 NONE？**（注释的高光段落）
防御性编程：现在确实没有 web 容器，但**万一将来有人往依赖里加了个 web 模块**，
Spring Boot 会自动探测到 servlet 并"安静地启动一个 Tomcat 等 HTTP 请求"——
而 stdio 客户端只会往 stdin 喂 JSON，**永远等不到响应**，表现为"配好了但完全没反应"，极难排查。
显式 `NONE` 把"这个进程绝不该是 Web 应用"钉死成代码约束，**不给未来的手滑留机会**。

**③ 为什么只 `registerShutdownHook` 而不 `close()`？**
stdio 会话的生命周期**由宿主进程决定**：宿主关掉管道，MCP 框架自行结束。
如果启动类 run 完就 close，进程立刻退出，宿主还没发消息就"秒退"。
`registerShutdownHook` 只是保证 JVM 收到退出信号时能优雅释放资源——**平时挂着等宿主调度**。

## 3. application.yml —— 逐段（文件头注释就是本模块的"总纲"）

### 3.1 顶部大注释（先读它，全模块的设计动机都在这）
> "这个进程的 stdout 就是 MCP 的 JSON-RPC 通道，任何非 JSON 输出都会让客户端解析失败
> （现象是**一连上就崩，且报错毫无指向性**）。因此本文件有两处专门为此服务的配置：banner-mode 和日志。"

### 3.2 spring.main 段（两处"为 stdout 服务"）
```yaml
main:
  banner-mode: "off"            # ★ Spring Boot 默认往 System.out 打一串 ASCII 图，足以让第一条响应解析失败
  web-application-type: none    # 双保险：yml 也声明一次（和启动类代码呼应）
```
对照 sse 版这里是 `console`——**同一个键、两个模块、相反取值**，差异全部回到"stdout 是不是协议通道"。

### 3.3 无 nacos/db 的说明注释
"本进程不需要注册中心/配置中心/数据库，是个被宿主按需拉起的**短生命周期 CLI**；
本模块 classpath 上确实没有 Nacos/JDBC 依赖，所以连 `enabled:false` 都不用写。"
——**依赖里没有，就不用配置去关**：又一次"依赖最小化"的红利（对照 platform/ai 服务要写一堆开关）。

### 3.4 spring.ai.mcp.server 段（★stdio 独有的总开关）
```yaml
ai.mcp.server:
  stdio: true        # ★★ 这是 stdio 传输的开关
  annotation-scanner.enabled: false   # 同 sse 版：走原生 @Tool，关误导扫描
  request-timeout: 70s                # 同 sse 版；宿主(Claude Desktop)通常给 60s，70s 在其下
  capabilities: { tool: true, 其余 false }   # 按实上报
  name/version/instructions/type      # 同 sse 版
```
**`stdio: true` 为什么是关键开关**（注释点破了机制）：
`McpServerStdioDisabledCondition` 判定 `spring.ai.mcp.server.stdio` 缺失或 false 时，
走的是"有 HTTP 端点"那套装配；**stdio 模式必须显式置 true**，框架才走 stdin/stdout 通道。
（对照 sse 版没有这个键——它靠 webmvc starter 默认就是 HTTP/SSE。）
其余 capabilities/instructions/type 与 sse 版**逐字相同**——因为工具集是后厨共用的，
**两个模块的 yml 里"MCP server 语义"部分一致、只有"传输"部分分道**，这正是解耦的证据。

### 3.5 aihub.mcp 段（凭据怎么进来）
```yaml
aihub.mcp:
  base-url: ${AIHUB_BASE_URL:http://127.0.0.1:8080}   # stdio 版通常与网关同机，默认本机
  api-key: ${AIHUB_API_KEY:}    # ★宿主进程通过 env 注入
  timeout: 60s
  default-top-k / chunk-max-chars ...
```
关键差异：**没有 auth 门禁那一段**（stdio 是本机管道，不存在"网络暴露"，无需通道 Bearer）。
`api-key` 从哪来？——**宿主进程的配置里注入环境变量**：
```json
"env": { "AIHUB_API_KEY": "ak_xxx", "AIHUB_BASE_URL": "http://127.0.0.1:8080" }
```
stdio 版没有命令行参数、没有 HTTP 头，环境变量是它接收外部配置的**唯一通道**。

## 4. logback-spring.xml —— 本模块最该细读的 53 行

**为什么不能用 Spring Boot 默认日志配置？**（文件头注释）
默认 `ConsoleAppender` 往 `System.out` 写——启动时几条 INFO 就会**插进 JSON-RPC 流里**，
客户端解析直接失败，症状又是那句"一连上就崩、错误毫无指向性"。

三处针对性设计（对照文件逐条）：
```xml
<appender name="STDERR">
    <target>System.err</target>   <!-- ① 诊断信息改道 stderr：仍然可见，但走另一条管道，不污染 stdout -->
</appender>
<appender name="FILE"> ...RollingFileAppender... </appender>   <!-- ② 同时落文件，事后排查（stdout/stderr 都可能被宿主吞掉） -->
<root level="WARN">               <!-- ③ root 降到 WARN -->
    <appender-ref ref="STDERR"/><appender-ref ref="FILE"/>
</root>
<logger name="com.aihub.mcp" level="INFO"/>   <!-- 本项目的包保留 INFO 方便看工具调用 -->
```
- **② 为什么还要额外落文件**：宿主进程常常把子进程的 stderr 也吞了/没地方看，
  没有文件日志你将无从排查；文件放 `${java.io.tmpdir}/aihub-mcp-stdio/`（跨平台临时目录，不污染工程）。
- **③ root=WARN 的深层原因**（注释原话）：宿主给 stderr 的缓冲很小，
  一堆 INFO 刷出去可能**把管道写满而阻塞进程**——stderr 也不是绝对安全的垃圾场，
  写太猛一样会反压。所以"降噪到 WARN + 自己的包单独 INFO"是精确权衡。

## 5. 一图看尽 stdio 的"输出纪律"

```
                 ┌── stdout ──▶ 只允许 JSON-RPC！(banner 关、日志不进、无杂质)
stdio 进程的输出 ─┼── stderr ──▶ 诊断日志(root=WARN)，但缓冲小、可能被宿主吞
                 └── 文件    ──▶ 落 ${tmp}/aihub-mcp-stdio/*.log，事后排查主力
```
**记忆锚点**：一个进程三条输出，只有 stdout 是"圣殿"，其余两条都是"杂物通道"——
所有配置（banner off / logback / root WARN / NONE web）都是在保护 stdout 的纯净。
