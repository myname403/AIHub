# 第二轮：四条核心链路逐帧精讲

> 目标：类都认识了，现在顺着"一条请求"看它们怎么协作。
> 四条链路：登录、注册（建租户）、RBAC 权限、配额扣减。背链路比背类有效十倍。

---

## 链路 1｜登录（AuthService.login，六步）

```
⓪ 验证码 verify(captchaId, code)     ← 放最前：错了不必查库，省资源+不泄露账号存在性
① 租户码 → tenantId                  ← resolveTenantId：查 sys_tenant，校验 status=1
② (tenantId, username) 查用户        ← 样板 SQL：where tenant_id=? and username=? and deleted=0
③ BCrypt matches(明文, 库里哈希)
④ 用户 status=1 校验（null 也当停用，fail-safe）
⑤ 签发 JWT（tenantId/userId 写进 payload）→ 返回 {token, tenantId, userId, username}
```

**三个必背细节**：
- ②③ 失败**返回同一句**"用户名或密码错误"——分开提示=送攻击者账号枚举器；
- BCrypt 没有"解密"一说：`matches` 是把明文按哈希里自带的盐重算再比——**库里连盐都不用单独存**；
- 验证码答案存 Caffeine 本地缓存 2 分钟、一次性消费（答对/答错都作废）——防暴力靠"过期+一次性"。

## 链路 2｜注册 = 开租户（AuthService.register，八步，一个事务）

```
① 验证码 → 格式校验（租户码 2-32 位 [a-zA-Z0-9_-]；用户名宽松规则；密码 6-64）
② "demo" 保留码拒绝（防抢注搅乱演示环境）
③ 租户码全局唯一检查
④ insert sys_tenant（status=1，雪花 ID）
⑤ insert sys_user（管理员，BCrypt 加密）
⑥ insert sys_role（本租户专属 ROLE_ADMIN）
⑦ insert sys_role_menu × N（授权全部菜单）+ insert sys_user_role（人绑角色）
⑧ 返回"请用 租户码+用户名 登录"
```

**为什么必须 `@Transactional(rollbackFor=Exception.class)`**：写了 5 张表——中途失败若没事务，
会留下"有租户没角色"的残废数据（登录能过、菜单全空、接口全 403）。
**"注册即建租户"也解释了你曾经的困惑：管理端没有'创建租户'按钮不是 bug**——租户由注册产生，
管理端登录后的世界已经被网关圈在本租户内。

## 链路 3｜RBAC："你能干啥"是怎么算出来的（PermissionService）

### 3.1 权限解析四级跳（核心必背）

```
userId →sys_user_role→ 角色ids →过滤 status=1 且本租户→ sys_role_menu → 菜单ids
      → sys_menu.permission 非空集合 → {system:user:query, system:user:create, ...}
```

多角色取**并集**。菜单三种类型：**M 目录 / C 菜单 / F 按钮**——
F（按钮）**不进路由树只进权限集合**（所以前端能精确到"这个按钮该不该渲染"）。

### 3.2 两条消费路径

- **接口鉴权**：Controller 方法标 `@RequirePermission("system:user:create")`
  → PermissionInterceptor 进门前调 `hasPermission(tenantId, userId, perm)` → 不过 403；
  （自研轻量版，对齐 Sa-Token/@PreAuthorize 思想；注解只是"声明"，生效全靠拦截器读取）
- **动态菜单**：前端登录后拉"我的菜单" → 后端 `getUserMenus` 过滤 M/C+启用、按 sort 排序 → 前端据此生成路由（菜单没授权 = 看不到页面 = 接口也没权限，前后端一套数据源）。

### 3.3 缓存与失效（学"缓存三问"）

权限每次请求都要用，四级跳每请求查 4 张表太亏 → Caffeine 缓存 10 分钟。
**缓存三问，答错哪个都是事故**：
1. 存什么？key=`perm:{tenantId}:{userId}`（**租户在 key 里**，跨租户天然隔离）；
2. 何时失效？用户角色变→`invalidateUser`；角色授权变→`invalidateRole`；菜单变→`invalidateAllMenus`；
3. 失效不了怎么办？TTL 10 分钟兜底。**已知妥协**：本地缓存反查不了"哪些用户绑了这个角色"，
   invalidateRole 直接全清——单机低频可接受，多实例要换 Redis+反向索引（注释自己写明）。

> 呼应 SysUserService：每次 assignRoles/update 状态/delete 都记得调 `permissionService.invalidateUser`——
> "改权限的地方必须同时敲失效"是纪律，漏一次就是"改了没生效"的幽灵 bug。

## 链路 4｜配额扣减（QuotaService.consume，两阶段）

AI 服务每处理一次对话，Feign 调 `/internal/quota/consume`，带着**多个维度**（次数+token）：

```
第一阶段·试算：对每个维度
   取策略（day 优先于 month——更细的先扣）
   没配策略 → 该维度放行
   used + amount > limit → 立刻返回 allowed=false（一个都没扣！）
第二阶段·累加：全部维度都过关，才逐条 upsertConsume 原子累加
```

**为什么两阶段**：先扣次数再扣 token 发现超限 → 留下"次数被扣了但请求没执行"的脏账。
先全试算、后全扣减 = "要么全扣、要么全不扣"（注释诚实标注：不是严格事务隔离，极端并发有超扣窗口，够用且简单——**又一个自曝 trade-off 的好注释**）。

**三个小而美的实现点**：
- 原子累加靠 MySQL `INSERT ... ON DUPLICATE KEY UPDATE`（依赖 uk_usage 唯一键）——"不存在则插入，存在则累加"一条 SQL 完成，无"先查再改"竞态；
- 排序用 `Comparator.comparing(p -> !"day".equals(period))` 而不是手写三元——注释指出手写比较**不满足传递性**，策略 ≥3 条时 TimSort 会抛 "Comparison method violates its general contract"（JDK 真实陷阱）；且必须拷贝新列表再 sort（Mapper 可能返回不可变列表）；
- 金额字段 BigDecimal——**钱永远不用浮点**。

## 链路 5（快闪版）｜API Key 签发与消费闭环

```
签发：管理端 POST /api/platform/apikey → ApiKeyService.issue
      本租户有效 Key 数 ≥20 拒 → 生成 ak_ 随机串 → 只存 HMAC 哈希+前缀 → 明文这一次返回
消费：第三方带 X-API-Key → 网关 ApiKeyCache/Verifier → POST /internal/apikey/verify
      → ApiKeyService 按哈希反查 → 返回 {keyId, tenantId, appId} → 网关注入 X-Tenant-Id
吊销：DELETE 校验 (tenantId, keyId) 归属（防拿别人 ID 越权吊销）→ status=0
```

至此你见过了**同一个租户上下文的三次接力**：签发时从 ThreadLocal 拿、验证时从库里反查、网关再把它写回头里。
