# 第二轮：三条核心链路精讲

> 目标：AI 服务 90% 的类都挂在这三条链上——对话（含流式）、知识库（RAG）、Agent。
> 每条链先给"一图流"，再讲链上每个类的为什么。

---

## 链路 1｜对话（chat / chatStream，ChatAppService 编排）

```
ChatController(:8082 /api/ai/chat[/stream])
  → ChatAppService.chat / chatStream
     ①配额闸门 checkQuota ──Feign──▶ platform /internal/quota（request 维度扣 1）
     ② scene=agent？ 是→ consumeAgentTask(task维度先扣) + runAgent
                       否→ chatExecutor.call/stream ──┐（见下方装配）
     ③reportUsage 流水上报（失败→发件箱兜底）          │
     ④consumeTokens token 事后补扣                     │
                                                      ▼
     SpringAiChatExecutor → ChatClientFactory.get(租户,应用,场景) 的 ChatClient
        ChatClient 里装着：模型(DbModelGateway 路由→Resolver 构建)
                          + 记忆(DbChatMemory 窗口20) + 工具(内置@Tool+MCP，外套审计)
                          + Advisor(AuditAdvisor)
        → 调真实大模型（OpenAI 兼容协议）→ 流式逐 token 回传
```

### 必懂的六个设计点

1. **配额"前置扣次数、事后补 token"**：次数在请求进来时就扣（拦住白嫖）；
   token 用多少**只有模型响应后才知道**，只能事后 `consumeTokens` 补扣——
   补扣失败只记日志不报错（成本已真实发生，不能因统计失败让用户看到错误；
   下次请求会在前置闸门被拦，账最终平）。**"先拦大头、后补细账"是计费系统的通用形态**。

2. **降级放行 vs 明确拒绝，方向相反的两条路**：
   - 平台服务**挂了/超时** → catch 后**放行**（AI 能力不因依赖故障而瘫痪）；
   - 平台**明确说** allowed=false → 抛 QUOTA_EXCEEDED（闸门只在明确拒绝时落闸）。
   注释里还有一段血泪史：task 维度早期版本没检查返回值，"只记账不阻拦"，配额形同虚设——**修的是语义一致性**。

3. **流式路径的"异常→事件"翻译**：SSE 连接建立后响应头已发出，**此时抛异常前端根本看不到**。
   所以流式版把 BizException 转成 `StreamEvent.error` 事件再 close sink
   （`checkQuotaOrEmit` 复用同步版逻辑，只加一层翻译——超限判定永远只有一份代码）。

4. **requestId=UUID 保幂等**：Feign 网络重试会重发同一个扣减请求，平台按 requestId 去重——
   重试不会重复扣钱（对照 platform 讲解链路 4 的 upsert）。

5. **用量上报的"两级降级 + 发件箱"**：
   上报失败 → 第一级：打日志放行；同时第二级：`eventOutbox.enqueue` 落 `ai_event_outbox` 表，
   `EventOutboxDispatcher` 后台每 30s 扫 status=0 的重投（最多 3 次，超限标死信）。
   **把"尽力而为"升级成"最终一致"**——这就是 Outbox 模式，注释连"兜底再抛异常会盖掉原始错误"都想到了（发件箱落库失败也只记日志）。

6. **StreamSink 三实现 = 依赖倒置的教科书**：
   编排层只说"往 sink 里发事件"，背后换谁不知道：
   | 实现 | 场景 | 关键点 |
   |---|---|---|
   | SseStreamSink | H5 浏览器 | 包 SseEmitter；`volatile closed` 防并发重复写 |
   | NdjsonStreamSink | **微信小程序**（不支持 SSE） | 每行一个 JSON，`uni.request enableChunked` 收，按 \n 切半包 |
   | WsStreamSink | Agent 长任务 | 双向可中断（前端能发"停止"指令） |
   流式三件套硬要求（Controller 统一设头）：**禁 gzip（identity）、`X-Accel-Buffering: no`、`Cache-Control: no-transform`**——
   任何一个中间件敢缓冲我的流，逐 token 输出就变成"憋一大坨"。

### ChatClientFactory（装配车间，值得单独画一张小图）

```
get(tenantId, appId, scene)：
  ① 查缓存（按 租户+应用+场景，TTL 60s——改了路由/提示词最多等一分钟生效）
  ② DbModelGateway：scene → ai_model_route 表挑模型；没配路由退回 yml 默认（开发友好）
  ③ OpenAiCompatibleChatModelResolver：一把梭覆盖所有 OpenAI 协议族
     （OpenAI/DeepSeek/火山方舟/DashScope兼容模式/本地 Ollama）
     —— 供应商 Key 从库里 AES-GCM 解密拿到；base_url 拼带有无 /v1 的历史坑都在这层处理
  ④ 挂 DbChatMemory（窗口 20 条）+ MessageChatMemoryAdvisor
  ⑤ 挂工具：内置 @Tool（TimeTools/KnowledgeTools/BrowserTools*）+ MCP 外部工具，
     每个都套一层 AuditedToolCallback（记 ai_tool_call_log + Micrometer 计数）
  ⑥ 挂 AuditAdvisor（Call 与 Stream 双路径审计）
```
- **AiCallContext 为什么存在**：ChatClient 按三元组缓存复用，但被模型自主调用的 @Tool
  方法签名里拿不到租户/会话参数 → ThreadLocal 入口写出口清，工具和审计从这取
  （浏览器工具"按会话复用同一个页面"就靠它的 conversationId）；
- **KnowledgeTools = Agentic RAG**：不止"先检索再拼上下文"，还让模型**自己决定何时查、查什么**
  （多轮追问场景明显更聪明）；
- **BrowserTools 默认关**（`aihub.browser.enabled=false`）：会真拉起 Chrome 进程 + 模型可被诱导访问内网
  （SSRF 面），**危险能力必须显式开启**——关着时相关 Bean 压根不存在，装配自然跳过。

## 链路 2｜知识库：入库与检索（KnowledgeAppService + Redis 向量对）

```
入库：上传文件 → IngestFileStore 落盘(Local/Minio 可切)
   → TextChunker 切片(chunk-size/overlap)
   → RedisKnowledgeIndexer：逐片 embedding → 写 Redis Stack 向量库
      ★ 每片强制带 tenant_id 元数据 —— 隔离的"数据源头"
检索：RedisKnowledgeRetriever：query 向量化 → 相似度 topK
      → 过滤：TenantGuard 丢弃无本租户标记的向量 + similarity-threshold 阈值
      → 命中分片回填原文（DocumentRepository）→ 注入对话上下文 / 返回给工具
```

三个为什么：
1. **为什么必须 Redis Stack 不是普通 Redis**：向量检索要 RediSearch 模块（docker-compose 里 healthcheck 专门 `MODULE LIST | grep search` 断言，缺模块=向量能力不可用）；
2. **为什么入库是异步任务（IngestTask）**：大文件 embedding 慢，同步接口会超时——
   上传立即返回任务 ID，后台推进度、失败可重试（ingest-max-retry），前端轮询任务状态；
3. **为什么检索侧还要 TenantGuard**：入库带租户是"源头自律"，检索过滤是"出口把关"——
   **纵深防御**，万一有历史脏数据没带租户标记，宁可丢弃不可泄露。

## 链路 3｜Agent：拆解-派发-预算-产物（对齐课程 MyManus）

```
runAgent → AgentRegistry.lookup("planning") → PlanningAgent.execute
   ① 填三重预算 AgentBudget(最大子任务数/最大token/最大耗时, AtomicLong 计数)
   ② LLM 拆解目标 → 子任务列表(JSON) → 逐个派给执行 Agent（按名派发）
        TableAgent / ChartAgent / HtmlDocAgent（都继承 GenerationAgent：
        LLM 生成完整 HTML → ArtifactStore 落盘 → 广播 artifact 事件 → 返回摘要）
        BrowserAgent（CDP 驱动真 Chrome：导航/标注页面/点击/输入）
   ③ 每步 checkBudget + 广播 step 事件；耗尽抛 AgentBudgetExceededException
      → 归一成 AgentResult(BUDGET_EXCEEDED)（不裸抛穿协议层）
   ④ 用户可中断：AgentCancelRegistry 登记取消位，子任务边界检查 → CANCELED
```

四个必背点：
1. **BaseAgent = 模板方法模式**：骨架（llm 调用/预算校验/步骤广播/失败兜底）在基类，
   子类只填"提示词和专属动作"——规范与复用；
2. **预算实例整条子任务链共享同一引用**（AgentTask.subTask 传递）——子 Agent 花的 token
   也计入总额，防"拆小任务绕过预算"；AtomicLong 因为多个子 Agent 可能不同线程同时加；
3. **Agent 名字常量放 domain（AgentNames）**——第一轮讲过的 ArchUnit 卡口实例再现；
4. **产物（Artifact）不落对话文本**：Agent 生成的是 HTML 表格/图表页，
   `ArtifactStore` 存起来 → 广播 artifact 事件带 previewUrl → ArtifactController 在线预览。
   对话流里只留摘要——**大内容走引用，不走内联**（省上下文）。
