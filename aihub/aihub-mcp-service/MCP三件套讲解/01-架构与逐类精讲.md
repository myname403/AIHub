# 第一轮：架构与逐类精讲

> 目标：搞清楚三件套"为什么是三个模块"，16 个类各自站哪个岗，以及四个值得背下来的设计决策。

---

## 1. 先懂 MCP 是什么（30 秒）

MCP（Model Context Protocol）= **AI 客户端调用外部工具的"USB 接口标准"**。
Claude Desktop / IDE 插件这些"宿主"是主机，MCP Server 是外设；插上就能用，不用管外设里面是什么语言写的。
协议本体是一套 **JSON-RPC**（`initialize` → `tools/list` → `tools/call`），Spring AI 把它做成了 starter，我们只管写 `@Tool` 方法。

本项目要解决的实际问题：**外部 AI 客户端如何用上 AIHub 里配置好的应用和知识库？**
答案：做一个 MCP Server，把"列应用、列知识库、检索、提问"四个动作包装成工具，
底层再去调 AIHub 网关的开放 API（带 X-API-Key）。

## 2. 为什么切成三个 Maven 模块？

```
aihub-mcp-service   后厨：@Tool 工具实现 + HTTP 客户端 + 配置装配（纯 jar，不是应用）
aihub-mcp-sse       堂食窗口：引 spring-ai-starter-mcp-server-webmvc → HTTP+SSE 传输
aihub-mcp-stdio     外卖窗口：引 spring-ai-starter-mcp-server → stdin/stdout 传输
```

两个传输模块的 pom 只差一个 starter，其余全是薄壳（启动类 + mainClass）。
**对比读这两个 pom 是理解"传输与业务解耦"的最快路径。**

### 关键取舍：mcp-service 刻意不依赖 aihub-common！

common 虽好，但它传递依赖 `spring-boot-starter-web`（整个 Servlet 容器）。
stdio 进程是被宿主拉起的 CLI——**里面住一个 Tomcat 纯属负担**（启动慢、占内存、日志还可能污染 stdout）。
代价是 mcp 模块不能复用 `R`，于是自带一份客户端镜像 `ApiEnvelope`——
注释里说得很清楚：**消费公开 HTTP 契约时，像 SDK 一样自带类型才是对的，服务端重构内部 DTO 打不到我**。

### 两种传输的调用方式对照（必背）

| | SSE 版 | stdio 版 |
|---|---|---|
| 谁启动 | 自己常驻跑（8090，避开 8080/8081/8082） | 宿主进程 `java -jar` 拉起 |
| 通信 | HTTP + SSE 长连接（`/sse` 建连 + `/mcp/message` 回传） | stdin/stdout 管道 |
| stdout 身份 | 普通日志出口 | **★ 协议通道**——banner 要关（`banner-mode: off`）、日志走 stderr+文件（专属 logback-spring.xml）、root 降 WARN 防管道写满 |
| 启动类细节 | 普通 run | 显式 `WebApplicationType.NONE`（防将来有人加 web 依赖把它变成"安静启动 Tomcat 等 HTTP、stdin 永远没人理"的半吊子） |
| 客户端配置 | `{"type":"sse","url":"http://host:8090/sse"}` | `{"command":"java","args":["-jar","...jar"],"env":{...}}` |
| 通道门禁 | `aihub.mcp.auth.enabled=true` 后要求 `Authorization: Bearer <token>`（跨机暴露前必开） | 本机管道，无需 |

## 3. 逐类精讲（按包走）

### 包 tools —— ★AiHubTools（全模块灵魂，只有一个类）

四个 `@Tool`：`aihub_list_applications` / `aihub_list_knowledge_bases` / `aihub_search_knowledge` / `aihub_ask`。

**四个刻意的设计选择（注释原文编号，面试直接背）：**

① **全部返回 String，不返回对象**——工具结果要被任意客户端消费，纯文本最不会出错；返回 POJO 依赖两端 JSON Schema 生成实现一致，跨实现易踩坑；

② **错误吃掉转人话，不抛异常**——`AiHubCallException` 在这里被 catch 成"鉴权未通过，请检查 API Key"这类文字。抛出去会变成 JSON-RPC error，模型通常直接放弃；**给文字它才能继续推理或如实汇报**。这是"面向模型编程"和"面向前端编程"的本质区别；

③ **description 写成给人看的说明书**——描述是模型选工具的唯一依据。写得极讲究：什么时候用（"不确定该用哪个应用时先调这个"）、什么时候别用（"只是查资料用 search 更直接"）、结果怎么解读（"相似度低于 60% 应如实说没找到，不要强行作答"）、甚至行为引导（"多个知识库拿不准就把列表交给用户确认，不要瞎猜"）；

④ **`aihub_` 前缀防重名** + `@ToolParam(required=false)` 的参数用默认值兜底。

还有两个细节：`truncate()` 把超长分片截断并标注（一次工具塞几万字会撑爆上下文预算）；`aihub_ask` 返回尾部带**会话 ID**，供追问复用记忆。

### 包 api —— 出口三件套

| 类 | 干什么 | 关键设计 |
|---|---|---|
| `AiHubApi` | 能力端口（接口） | 抽象成接口让 AiHubTools **脱离网络可单测**——工具的价值在参数校验+结果组织 |
| `HttpAiHubApi` | 经网关调 AIHub 的实现（RestClient） | ① 默认头 `X-API-Key`（MCP 不代表终端用户，一个 Key=一个租户）；② `exchange()` 统一处理"传输异常+业务码非0"两类失败；③ `describe()` 把 401/404/429 翻译成**模型能行动的中文**（"请确认网关已启动"）；④ `maskApiKey()` 日志只回显前 7 位；⑤ `ParameterizedTypeReference` 常量解决泛型擦除下的 `ApiEnvelope<List<X>>` 反序列化 |
| `ApiEnvelope` | 服务端 R 的**客户端镜像** | 不复用 R 的两个理由（R 私有构造器反序列化不了 + common 带 servlet）；`@JsonIgnoreProperties(ignoreUnknown=true)` 服务端加字段打不挂我 |
| `AiHubCallException` | 调用失败信号 | 非受检；**它的终点是被 AiHubTools 吃掉转文字** |

### 包 config —— 装配两件套

- `AiHubMcpProperties`：`@ConfigurationProperties(prefix="aihub.mcp")` 绑 baseUrl/apiKey/timeout/defaultTopK/chunkMaxChars...（最关键两项：baseUrl + apiKey，**换 Key 即换租户**）；
- `AiHubMcpConfiguration`：把上面接线成 Bean，核心一行——
  `MethodToolCallbackProvider.toolObjects(aiHubTools)`：扫 `@Tool` 注解方法 → 转成 MCP 工具清单。
  两个传输模块**共用这套装配**（这就是为什么它们的启动类都 `scanBasePackages="com.aihub.mcp"` 往上扫一层）。

### 包 model —— 四个"只取所需"的 DTO

`AppBrief/KbBrief/ChunkHit/ChatAnswer`：全部 `@JsonIgnoreProperties(ignoreUnknown=true)`。
KbBrief 注释还披露了历史包袱：服务端 kb 列表复用 `DocumentInfo`（fileType 固定 "kb"），MCP 侧显式建独立类型，**不必继承那个别扭**。

### sse 模块的 auth 包（3 个类）

`McpChannelAuthConfiguration`（`@ConditionalOnProperty` 开关装配）+ `McpChannelAuthFilter`（OncePerRequestFilter，拦 protected-paths 校验 Bearer token，`MessageDigest.isEqual` 常量时间比较防时序攻击）+ `McpChannelAuthProperties`。
设计语境：这条通道历史上不鉴权（默认只绑 127.0.0.1，鉴权在背后的开放 API 上）；**跨机暴露前先加通道门禁，避免"端口暴露即工具裸奔"**。注意分层：通道门禁解决"谁能连"，数据边界仍由 X-API-Key 的租户归属解决——两道门管的事不同。

## 4. 配置里的两个"超时咬合"（排障高频）

```
aihub.mcp.timeout(60s, HTTP 调上游)   <   spring.ai.mcp.server.request-timeout(70s, MCP 层)
```
MCP 层必须**大于** HTTP 层，否则上游慢查询先被 MCP 掐断，日志只有"MCP 请求超时"，
指不到真正卡住的 HTTP 那一层（两个 yml 的注释都专门警告过）。
同理 stdio 版注释：宿主进程（Claude Desktop）一般给 60s 工具调用上限，70s 在它之下。
**三层超时链：宿主 > MCP 层 > HTTP 层，谁小谁先暴露，排障从最小的那个查。**

## 5. 一图总览调用链

```
Claude Desktop(模型决定调 aihub_search_knowledge)
   │ JSON-RPC(tools/call) 经 SSE 或 stdin
   ▼
AiHubTools.searchKnowledge(kbId, query, topK)
   │ 参数兜底 → api.searchKnowledge(...)
   ▼
HttpAiHubApi ── RestClient + X-API-Key ──▶ AIHub 网关 :8080 /api/ai/kb/search
                                              │ ApiKeyCache→平台反查租户（网关讲解 3.4/3.5）
                                              ▼
                                          ai-service 向量检索
   ◀── ApiEnvelope{code,data} ──────────────────┘
   │ 失败→AiHubCallException→(被吃掉)转人话
   ▼
拼 Markdown 文本（来源+相似度%+截断标注）→ 回给模型
```
